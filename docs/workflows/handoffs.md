# Протокол handoff-ов

Handoff — JSON-файл, через который ORCH даёт задание одному агенту и в который агент
пишет свой отчёт. По handoff-ам видно, кто, что, когда и на каком основании сделал: без
них нет ни независимой проверки (quality-bar Q2), ни учёта (Q14). Этот файл обязателен
для ORCH и для каждого агента, который получает handoff, — кроме ролей с разделом
«Reading scope» в файле роли: что им читать, решает только этот раздел (подробно — «Как
работает получатель»).

## Где лежат и как называются

- **Папка прогона:** `handoffs/<RUN-ID>/`. Прогон — одна работа по одному процессу:
  выбор идеи, бизнес-план, требование с разработкой, исправление дефекта, аудит.
- **RUN-ID:** `<МЕТКА>-<ГГГГММДД>-<NN>`. Метка называет работу: `WF06` — выбор идеи,
  `BP` — бизнес-план, `PO` — Pixel Office, `ISS-0002` — дефект с этим номером, `AUD-001` —
  аудит с этим номером, `SA` — самостоятельность Sai (итерация 2). Дата — день начала
  прогона; `NN` — номер прогона с этой меткой в этот день, начиная с `01`.
- **Файл:** `step-<ШАГ>-<роль>[-<уточнение>][-<суффикс>].json`:
  - `<ШАГ>` — номер шага процесса: `00`, `00a`, `01b`, `02` …;
  - `<роль>` — имя роли строчными буквами через дефис: `code-designer`, `req-validator`;
  - `<уточнение>` — если на шаге работают несколько агентов одной роли: точка зрения, тема
    или требование (`-market`, `-session-review-tools`, `-req001`);
  - `<суффикс>` — доработка `-rN`, повторный запуск после обрыва `-runN`, версия вердикта
    в WF-06 `-vN` (раздел «Доработки и повторные запуски»).
- **handoff_id:** `step<ШАГ>`, затем уточнение и суффикс, затем RUN-ID — например,
  `step06-r2-ISS-0002-20260930-01`. Во всём `handoffs/` он не повторяется.
- Handoff-ы не удаляются и не переименовываются: на их имена ссылаются другие файлы.

## Поля

Пример (значения вымышленные):

```json
{
  "handoff_id": "step02-DEMO-20990101-01",
  "run_id": "DEMO-20990101-01",
  "workflow_id": "WF-02",
  "step": "02",
  "from_agent": "ORCH",
  "to_agent": "BACKEND-DEV",
  "file": "handoffs/DEMO-20990101-01/step-02-backend-dev.json",
  "status": "PENDING",
  "priority": "NORMAL",
  "context": {
    "requirement_ids": ["REQ-999"],
    "agent_run_id": null,
    "artifacts_in": ["docs/design/REQ-999-demo.md"],
    "route": "CODE-DESIGNER -> CODE-DESIGN-VALIDATOR -> BACKEND-DEV (this) -> SECURITY-REVIEWER -> REVIEWER",
    "write_set": "tools/src/demo.js only"
  },
  "task": {
    "description": "Что сделать — полностью, простыми словами.",
    "acceptance_criteria": ["Проверяемый пункт 1", "Проверяемый пункт 2"]
  },
  "created_at": "2099-01-01T10:00:00Z",
  "started_at": "2099-01-01T10:00:00Z",
  "completed_at": null,
  "result": null
}
```

| Поле | Что это | Кто пишет |
|---|---|---|
| `handoff_id` | уникальное имя handoff-а | ORCH |
| `run_id` | RUN-ID, оно же имя папки прогона | ORCH |
| `workflow_id` | процесс: `WF-01` … `WF-07`; работа вне процессов — метка итерации (`ITER-2`). В старых прогонах встречается `ISSUE` — так назывался дефект до WF-03 | ORCH |
| `step` | номер шага процесса, как в имени файла | ORCH |
| `from_agent` | всегда `ORCH`: handoff-ы создаёт только он | ORCH |
| `to_agent` | роль получателя, например `CODE-DESIGNER` | ORCH |
| `file` | путь этого файла от корня Sai | ORCH |
| `status` | `PENDING` → `IN_PROGRESS` → `COMPLETED` или `FAILED`; `CANCELLED` — отменён | ORCH ставит `PENDING` и `CANCELLED`; получатель — `IN_PROGRESS`, `COMPLETED`, `FAILED` |
| `priority` | `HIGH`, `NORMAL` или `LOW` | ORCH |
| `context` | всё, что нужно знать о прогоне (ниже) | ORCH |
| `task` | `description` — что сделать; `acceptance_criteria` — по каким пунктам работу проверят | ORCH; получатель никогда не меняет |
| `created_at`, `started_at` | время создания и отправки | ORCH, одно чтение часов (раздел «Время») |
| `completed_at` | время сдачи | получатель |
| `result` | отчёт агента (ниже) | получатель — и только он |

Необязательные поля верхнего уровня:

- `round` — то же `N`, что в суффиксе `-rN` у доработки;
- `not_agent_attested` — пометка, что часть полей написал ORCH, а не агент (раздел
  «Перерывы и обрывы»);
- `orch_note`, `orch_correction`, `orch_cancellation` — поправки ORCH: отдельными полями,
  со временем и причиной; отчёт агента (`result`) ими не переписывается.

### context

Обязательные поля:

- `requirement_ids` — требования, ради которых шаг (пустой список, если их нет);
- `agent_run_id` — идентификатор запуска агента. ORCH пишет его сразу после запуска, до
  запуска — `null`. Продолжение того же агента (раунды WF-06, доработка тем же агентом)
  идёт с тем же идентификатором;
- `artifacts_in` — файлы, которые агент обязан прочитать.

Частые необязательные поля (их пишет ORCH, когда они нужны):

- `route` — маршрут прогона: кто был до этого шага и кто будет после;
- `write_set` — какие файлы агенту можно менять; всё остальное — нельзя;
- `edit_scope` — какую часть файла можно менять (например, один блок требования) и как
  показать, что остальное не изменилось (хеш до и после);
- `protected` — что должно остаться байт в байт;
- `parallel_work_now` — кто ещё работает сейчас и с какими файлами;
- `file_lock` — файл сейчас пишет другой агент: подготовить правку и ждать сообщения ORCH;
- `rework_of` — путь handoff-а, который дорабатывается;
- `orch_rulings` — решения ORCH по вопросам агентов;
- `before_copy`, `pre_fix_copy` — копия «до» вне проекта: с ней сравнивают изменения, на
  ней проверяют, что новый тест падал до исправления;
- `interruptions` — перерывы в работе агента (раздел «Перерывы и обрывы»);
- `task_check`, `orch_check` — собственная проверка ORCH: когда, какими командами, что
  вышло, вердикт;
- поля процесса: `lens`, `run_seal` (WF-06), `issue_id` (WF-03) и другие — их называет
  документ процесса.

### result

Пишет получатель:

- `status` — `COMPLETED`, `FAILED` или `IN_PROGRESS` (работа не закончена, и агент прямо
  об этом говорит — например, когда нечем проверить, quality-bar Q3);
- `verdict` — у проверяющих ролей: `PASS` или `FAIL` (в WF-07 на шаге 2b ещё
  `SOURCE_UNAVAILABLE`);
- `findings` — у проверяющих ролей: замечания, у каждого — место, важность и исправление;
  шкала важности общая: Critical, High и Medium блокируют (FAIL), Low не блокирует и идёт
  в следующий шаг или в отчёт; свой порог процесс задаёт только явно — исключение: в
  WF-04, шаг 4 (сравнение с образцом), блокируют только Critical и High; исключение WF-05:
  находки аудиторов лежат в их файле отчёта (`docs/audits/AUD-NNN/<часть>/<измерение>.json`),
  а `result.findings` держит путь к нему, а не копию находок;
- `summary` — что сделано и чем кончилось, простыми словами;
- `changes` — каждая правка: файл и место, что изменено; у доработки — к какому замечанию
  она относится;
- `self_check` — команды своей проверки и их настоящий вывод;
- `issues` — вопросы, сомнения, находки вне задачи, предложения поднять планку; у каждого
  пункта `id` (`I1`, `I2` …), вид или важность и текст;
- `artifacts_out` — все созданные и изменённые файлы, поимённо; сам handoff сюда не
  входит;
- другие поля, если их требует процесс (например, `urls_opened` у проверяющего
  исследований).

Агент, который остановился, оставляет `status` и `result.status` в `IN_PROGRESS`, а
`completed_at` — `null`; первая запись `result.issues` у него — вида (`kind`) «BLOCKED»,
со временем остановки в поле `at` (с часов): что мешает, чем подтверждено, что нужно,
чтобы продолжить.

## Кто что пишет

- **Только ORCH создаёт handoff-ы.** Агент, которому нужна работа другой роли, пишет об
  этом в `result.issues`, а не создаёт файл сам.
- **Получатель меняет только `status`, `completed_at` и `result`.** Ни `task`, ни
  `context`, ни время создания и отправки. Если задание кажется неверным, невыполнимым или
  устаревшим, агент пишет об этом в `result.issues` и задание не трогает: другое задание
  может дать только ORCH, новым handoff-ом.
- **Создание и закрытие — командой.** ORCH создаёт handoff командой
  `cd tools && npm run handoff -- new …` (ключи и правила — `tools/README.md`, раздел
  «Команда handoff»). Получатель после заполнения `result` закрывает свой handoff командой
  `cd tools && npm run handoff -- close <путь> --status COMPLETED|FAILED`: она меняет
  только `status` и `completed_at` и до записи проверяет файл правилами `handoffs-check`.
  Остановку по правилу роли (`IN_PROGRESS` и «BLOCKED») `close` не делает. Команда `new`
  записывает `context.write_set` списком; строка допустима в старых файлах.
- **ORCH не переписывает `result` агента.** Поправка — отдельным полем (`orch_note`,
  `orch_correction`) со временем и причиной. Исключение одно — агент не смог отчитаться
  (раздел «Перерывы и обрывы»), и это помечено `not_agent_attested`.

## Время

- Только с часов: `date -u +%Y-%m-%dT%H:%M:%SZ`. Не по памяти и не «примерно».
- `created_at` и `started_at` ORCH пишет из **одного** чтения часов, когда создаёт
  handoff и запускает агента: handoff создаётся командой
  `cd tools && npm run handoff -- new …` в момент запуска агента, время берётся с часов
  один раз; заранее (`PENDING` без запуска) handoff не создаётся. Если handoff создан заранее (`PENDING`), а агент
  запускается позже, при запуске ORCH читает часы заново и переписывает только
  `started_at` (так у шагов 11 и 12 прогона `WF06-20260925-01`). Получатель `started_at`
  не ставит.
- `completed_at` — при сдаче, с часов; не раньше `started_at`; ставится командой
  `cd tools && npm run handoff -- close <путь> --status COMPLETED|FAILED`.
- Если время неизвестно (например, агента остановил лимит), пишется «неизвестно» и то, что
  известно (например, последнее изменение файла агента), — а не придуманное время.
- Все времена в `at_note` проверяются как `at`: время в тексте не позже часов и не позже
  коммита, в котором появилась эта запись; в кавычках тоже. Прежнее значение времени
  цитируется только в полях `was` и `previous` той же поправки — их команда не проверяет.

## Как ORCH пишет задание

- Задание полное: агент не должен угадывать, что сделать, что можно менять и как сдать
  работу. Всё нужное — в handoff-е и в файлах Sai из `artifacts_in`. Целые файлы в
  задание не переписываются — они перечисляются.
- В задании — только факты из файлов проекта, со ссылкой на файл; остальное — как вопрос
  или допущение (AP-012).
- Каждому агенту — свои выходные файлы (`write_set`); два агента не пишут в один файл
  одновременно. Если без общего файла не обойтись — по очереди (`file_lock`) или по
  блокам (`edit_scope`) с хешами остальных блоков до и после.
- Доработка — только по перечню замечаний (AP-019).
- Независимое отправляется одновременно, в пределах числа агентов, которое разрешает
  `PLAN.md`; PASS проверки — зависимость: следующий шаг ждёт его (AP-010).

## Как работает получатель

**Исключение — роли с разделом «Reading scope» в файле роли** (сейчас IDEA-ANALYST и
IDEA-JUDGE, WF-06). Что читать, для них решает только этот раздел; шаги 1 и 2 ниже к ним
не относятся. `docs/anti-patterns.md`, `docs/requirements.yaml` и другие файлы, которых нет
в их списке, они не читают, даже если в handoff-е есть `requirement_ids`: иначе выбор идеи
становится круговым. Правила полей, нужные им для отчёта, повторены в
`docs/workflows/WF-06-idea-selection.md` (раздел «Handoff-ы»).

1. Читает свой handoff, файлы из `artifacts_in`, файл своей роли в `.claude/agents/`,
   `docs/quality-bar.md`, документ процесса в `docs/workflows/` и `docs/anti-patterns.md`.
2. Требование читает своим блоком по id, а не весь `docs/requirements.yaml` — файл
   большой:
   `awk '/^  - id: REQ-007$/{f=1} f&&/^  - id: /&&!/REQ-007$/{exit} f' docs/requirements.yaml`.
3. Проверяет факты задания, на которых строит работу (quality-bar §6, п. 2).
4. Ставит `status: "IN_PROGRESS"`.
5. Меняет только разрешённое (`write_set`, `edit_scope`). Найденное сверх задания — в
   `result.issues`, а не правкой.
6. Долгие команды (полная проверка, тесты, мутанты) запускает и дожидается в своём ходе.
   Запускать их в фоне и заканчивать ход «до уведомления» нельзя: после конца хода агента
   его никто не разбудит, и handoff повиснет.
7. Временные файлы держит вне проекта (в рабочей папке сессии); в документах такое место
   называется `<вне проекта>`. В папке Sai после работы не остаётся лишних файлов.
8. Перед сдачей выполняет свою проверку: команды и их вывод — в `self_check`.
9. Заполняет `result`, `completed_at` и `status` (`COMPLETED` или `FAILED`; при
   остановке — как сказано в разделе «result»); больше ничего в handoff-е не меняет.

Проверяющая роль выводит вердикт сама — из артефакта и своих запусков, а не из `summary`
автора (quality-bar Q2).

## Перерывы и обрывы

Правило одно: **отчёт пишет тот, кто работал, а когда он не смог — за него говорят файлы,
а не догадки.** Обрыв — это любой конец работы агента без заполненного `result`: лимит API,
ошибка сервиса, перезапуск сессии, ход агента закончился, а handoff всё ещё
`IN_PROGRESS`. Так было, например, с VERDICT-EXECUTOR в прогоне WF06-20260925-01 (AP-006).

**Сначала — опись.** До любого решения ORCH сам смотрит, что агент успел сделать: сравнивает
файлы из `write_set` с копией «до», смотрит время их изменения и есть ли выходные файлы
шага. Каждый обрыв — отдельная запись в `context.interruptions`:

```json
{
  "at": "<время по часам или «неизвестно» и что известно>",
  "cause": "<причина: лимит API с кодом и временем сброса, ошибка>",
  "checked_by_orch_at": "<когда ORCH проверил файлы>",
  "resumed_at": "<когда работа продолжена>",
  "how": "same agent run resumed via SendMessage"
}
```

**Потом — один из трёх исходов.** Выбирается первый подходящий сверху:

| Что видно | Что делает ORCH | Лимит доработок |
|---|---|---|
| Тот же запуск можно продолжить (лимит сброшен, `agent_run_id` известен), и после этого обрыва его ещё не продолжали | Продолжает его в том же handoff-е; агент отчитывается сам | не тратится |
| Продолжить нельзя или продолжение тоже оборвалось, и по файлам **не доказано**, что работа сделана вся | Закрывает handoff `FAILED` с пометкой `not_agent_attested` и запускает ту же роль заново с чистого листа — новый файл с суффиксом `-runN`; новый агент отчитывается за свою работу сам, пометки у него нет | не тратится |
| Продолжить нельзя, а по файлам **доказано**, что работа сделана вся, — не хватает только отчёта | Пишет отчёт сам, только из того, что видно в файлах, с пометкой `not_agent_attested` | не тратится |

Сомнение между второй и третьей строкой решается в пользу второй: отчёт за агента с
ошибочным PASS потом никто не перепроверит, а новый запуск стоит только времени.

**Пометка `not_agent_attested`.** Тот, кто позже откроет такой handoff, — проверяющий,
RELEASE-VALIDATOR, аудитор документации — должен без расспросов понять, где кончаются
слова агента и начинаются слова ORCH. Поэтому пометка — поле верхнего уровня handoff-а, и
каждое её поле отвечает на один его вопрос:

```json
{
  "written_by": "ORCH",
  "at": "<время с часов, когда ORCH это записал>",
  "reason": "<что случилось с агентом и почему он не отчитался>",
  "fields_written": ["status", "completed_at", "result"],
  "evidence": ["<команда> -> <что она показала>"],
  "unverifiable": ["<что по файлам не установить>"]
}
```

| Вопрос читателя | Поле | Как отвечать |
|---|---|---|
| Что здесь не от агента? | `fields_written` | каждое поле handoff-а, которое записал ORCH; чего нет в списке — писал агент |
| Кто и когда это записал? | `written_by`, `at` | всегда ORCH; время — с часов. `completed_at` такого handoff-а равно этому же времени: когда закончил бы агент, никто не знает |
| Почему агент молчит? | `reason` | что с ним случилось: лимит, ошибка, конец хода |
| Откуда ORCH это знает? | `evidence` | команды и их вывод — по одной на каждое утверждение отчёта |
| Чего ORCH не знает? | `unverifiable` | что по файлам не установить (например, проверял ли агент свою работу перед обрывом) |

Ответ «ничего» на последний вопрос надо заработать: пустой `unverifiable` допустим, только
если в `evidence` есть команда на каждое поле из `fields_written`. Иначе пустой список —
ошибка учёта.

Пометки, записанные до этой редакции, держат только первые четыре поля; их не дополняют.

## Доработки и повторные запуски

- **Доработка** — правка после вердикта проверяющей роли. Новый handoff той же
  производящей роли с суффиксом `-rN`, где `N` — номер доработки, считая с 1: первая
  доработка — `-r1`. В `context.rework_of` — путь handoff-а, который дорабатывается; в
  задании — только перечень замечаний; в `result.changes` у каждой правки — номер
  замечания. Повторная проверка получает тот же суффикс:
  `step-01b-code-design-validator-r1.json`. Правка файла, который уже прошёл проверку,
  тоже идёт отдельным handoff-ом и снова проверяется: без новой проверки такой файл не
  правят.
- **Повторный запуск после обрыва** — суффикс `-runN`, где `N` — номер запуска: второй
  запуск — `-run2`. Это не доработка.
- **Версия вердикта в WF-06** — суффикс `-vN` (`docs/workflows/WF-06-idea-selection.md`).
- **Старые прогоны.** В handoff-ах, записанных до этого документа, счёт разный: у части
  шагов `N` в `-rN` — номер раунда (первая доработка — `-r2`), а один повторный запуск
  после обрыва назван `-r2`
  (`handoffs/WF06-20260925-01/step-05-verdict-executor-r2.json`). Номер раунда стоит в
  поле `round`, источник доработки — в `context.rework_of`. Читая суффикс старого файла,
  сначала посмотрите эти поля. Старые файлы не переименовываются. Шаг прогона, начатого
  со счётом по раундам, доводится тем же счётом: иначе имя новой доработки совпадёт с уже
  записанным файлом.
- Сколько доработок можно и что делать, когда лимит исчерпан, говорит документ процесса.

## Проверка учёта

- Перед следующим шагом ORCH сверяет отчёт с файлами: то, что агент назвал сделанным,
  действительно есть (quality-bar Q2, Q14). Работу учётчика (DOC-UPDATER) ORCH проверяет
  своими командами по каждому названному файлу и полю и пишет вывод в
  `context.orch_check`: `at`, `by`, `verdict` и что проверено.
- Отменённый handoff не удаляется: у него `status: "CANCELLED"` и `orch_cancellation` —
  когда и почему.
- Учётные файлы только дописываются (quality-bar §6, п. 8).
- Проверку учёта выполняет команда: перед сдачей handoff-а автор шага запускает
  `cd tools && npm run handoffs-check` и сдаёт шаг при коде 0 (то же входит в
  `cd tools && npm run check`). Команда не читает смысл `task` и `result`.
- В коммите лежат только законченные handoff-ы: `COMPLETED`, `FAILED`, `CANCELLED` (с
  `orch_cancellation`) и остановка `IN_PROGRESS` с первой записью `issues` вида «BLOCKED».
  `PENDING` и `IN_PROGRESS` допустимы, пока файла нет в коммите или он изменён.
- Поправка ORCH (`orch_correction`, `orch_note`) — объект или список объектов с `by`
  (непустая строка) и `at` (время с часов) либо `at: null` с непустым `at_note`.
- Пути временной папки машины в handoff-е не пишутся: вместо них `<scratch>/…` или
  `<вне проекта>/…`.
