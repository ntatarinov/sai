# ISS-0002 — apply-verdict может оставить наполовину применённое состояние

Серьёзность: HIGH (было MEDIUM; пересмотрел ORCH 2026-09-30T17:33:01Z по диагнозу ISSUE-FIXER, `handoffs/ISS-0002-20260930-01/step-01-issue-fixer.json`: запись на месте может оставить STATE.md обрезанным или пустым — механизм M2, — а копии для восстановления нет; сюда же включён тот же пробел в `prepare-run`). Статус: open. Найдено: BACKEND-DEV при исправлении ISS-0001,
2026-09-30; подтвердил и расширил REVIEWER (решение I1). Пункт планки: Q10; дизайн §5.

## Что не так

`apply-verdict` пишет файлы по очереди: STATE.md, затем `proposed-actions.json`, затем
`apply-report.json` (`tools/src/apply.js:100-107`). Цели перед записью не проверяются,
атомарности нет. Если на втором или третьем файле случается сбой — при чтении цели для
сравнения (`apply.js:103`) или при записи (`apply.js:105`), — команда падает с
трассировкой стека Node (код 1), а уже записанное остаётся: STATE.md ссылается на
`proposed-actions.json`, которого нет.

Это нарушает дизайн §5 («Сначала вся проверка, потом все записи»: при ошибке — ни одной
записи) и то условие, по которому ISS-0001 была LOW: «команда падает до записи». В §6
нет кода для неудавшейся записи.

## Доказательство

Воспроизвёл REVIEWER (`handoffs/ISS-0001-20260930-01/step-02-reviewer.json`, решение
I1): исправленный CLI, свежая копия `sai/`. Чтобы STATE.md требовал перезаписи, в блок
WF-06 копии вставлена одна устаревшая строка; маркеры и раздел владельца не тронуты.
Контроль без поломки: код 0, STATE.md перезаписан.

- `runs/<RUN-ID>/proposed-actions.json` — папка: STATE.md уже перезаписан (15345 → 15334
  байт), затем `Error: EISDIR: illegal operation on a directory, read`, 8 строк
  трассировки, код 1.
- `apply-report.json` — папка (выходные файлы удалены заранее): STATE.md перезаписан и
  `proposed-actions.json` создан, затем EISDIR, код 1.
- Папка прогона с правами 555 (выходных файлов нет): STATE.md перезаписан, затем
  `EACCES: permission denied, open`, код 1.
- `apply-report.json` с правами 444: STATE.md перезаписан, затем EACCES, код 1.

Первые два случая нашёл BACKEND-DEV (`handoffs/ISS-0001-20260930-01/step-01-backend-dev.json`,
`result.issues`), REVIEWER их повторил; два последних нашёл REVIEWER. Повторный запуск
после устранения препятствия сходится: `applied recommend`, затем `unchanged`; байты
совпадают с настоящими выходными файлами прогона.

## Почему MEDIUM

Не LOW: нарушено правило дизайна §5, и остаётся наполовину применённое состояние — до
повторного запуска STATE.md ссылается на несуществующий `proposed-actions.json`. Не
HIGH: нужна намеренно созданная папка или смена прав, а повторный запуск после
устранения препятствия даёт верный результат.

## Как исправить

Проверка «цель отсутствует или это обычный файл» перед записью закрыла бы только случаи
с папкой, но не права доступа и не нехватку места. Поэтому (REVIEWER, I1):

1. CODE-DESIGNER проектирует фазу записи так, чтобы неудачная запись не могла оставить
   наполовину применённое состояние. Например, каждый файл пишется во временный файл
   рядом и затем переименовывается, STATE.md — последним, как точка фиксации. И
   добавляет в §6 код для неудавшейся записи.
2. Тест на каждую цель (STATE.md, `proposed-actions.json`, `apply-report.json`) и на
   каждый вид сбоя (папка, файл только для чтения, папка только для чтения): код выхода,
   строка ошибки, нет трассировки, список файлов не изменился. Список должен включать и
   папки: `tree()` (`tools/test/helpers.js:350`) видит только обычные файлы (замечание
   REVIEWER O2).

Код §6 для неудавшейся записи нужен и ISS-0003 (ошибки записи a, b, e, g1), в том числе
для того же цикла записи (`apply.js:103`, `:105`). В какой issue их делать и в каком
порядке — решает ORCH.

## Маршрут

CODE-DESIGNER → CODE-DESIGN-VALIDATOR → BACKEND-DEV → REVIEWER → TEST-RUNNER →
DOC-UPDATER (назначил ORCH, `handoffs/ISS-0001-20260930-01/step-04-doc-updater.json`).

Сверка с документами: порядок шагов разработки Sai (`docs/workflows/WF-02-development.md`,
«Маршрут», шаги 5 и 5b) и процесс дефекта Sai (`docs/workflows/WF-03-defect.md`, шаги
6–7) ставят между REVIEWER и TEST-RUNNER ещё пару TEST-DESIGNER → TEST-DESIGN-VALIDATOR:
регрессионный тест пишет не автор кода, и он
падает на коде до исправления, а после — проходит. В маршруте выше этой пары нет; ORCH
подтверждает маршрут при запуске.
