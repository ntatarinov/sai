## Что не так

The words of the review (an external security review, relayed to ORCH on 2026-11-18; the reviewer used only artificial values and localhost, nothing real leaked): `tools/src/pixel-office/mask.js` and the second masking function — the review says «both functions» — miss `password = "..."` (spaces around `=`) and `redis://:secret@host`, while `password="..."` is caught.

**Which two functions.** The review does not name the second one. By reading, the file has two independent sets of rules, both exported: `maskSecrets` (line 283; the rules M1–M10 that replace a secret with the label `[скрыто]` in the stored text of the Pixel Office journal and of the Sai Team events) and `findSecrets` (line 1031; the check of the content of a Sai Team result file, REQ-102: it finds a secret and the file is refused, nothing is replaced). The other functions that mask only call `maskSecrets`: `prepareText` (`mask.js`, line 294), `maskField` (`tools/src/pixel-office/protocol.js`, line 74) and `maskedArgs` (`tools/src/team/engine/channel.js`, line 320). So this defect reads «both functions» as `maskSecrets` and `findSecrets`; the reviewer is asked to confirm.

What this step saw, reading `mask.js` as text (unchanged against the tag `base/SECREG-20261118-01`). Nothing was run.

- `maskSecrets`, rule M9 `maskNamedValues` (lines 219–240): after the name segment one optional quote, then the next character must be `=` or `:` (line 229, `if (text[i] !== "=" && text[i] !== ":") continue;`); spaces and tabs are skipped only after the sign (line 231). A space before the sign drops the pair, so `password = "..."` is not masked by M9, and `password="..."` is. The rule of long strings (M10) takes only runs of at least 32 token characters (line 248). **Matches.**
- `maskSecrets`, rule M3 `maskUrlCredentials` (lines 61–85): the user before `:` must be non-empty (line 74, `if (i === sep + 3 || text[i] !== ":") continue;`), so `redis://:secret@host` is not masked. **Matches.**
- `findSecrets`, form F9 `findNamedValue` (lines 996–1027): the sign must stand right after the name or after one quote (line 1013, `if (sign !== 58 && sign !== 61) continue;`), so the spaced pair is not found. Form F3 `findUrlPassword` (lines 805–835): the comment on line 804 says «With no user the form does not apply», and line 819 skips an empty user. **Matches.**
- **The two shapes are already written down as a named residual risk**, so the review reopens a known hole: `docs/requirements.yaml`, block REQ-102 — the rule Ф3 («Если пользователь пуст (`redis://:${PASSWORD}@host`), форма не применяется — как в старом коде»: with an empty user the form does not apply, as in the old code), the rule Ф9 («пробел перед знаком отменяет пару, как в старом коде»: a space before the sign cancels the pair) and the residual risk (5) («Не сужение, а прежняя дыра»: not a narrowing but an old hole; the spaced assignment and the address with no user, which the old code did not find either); `decisions/0105`, item 6 («an assignment with a space before the sign and an address with no user (5)»); `tools/README.md`, line 253, the same at the tag and today («three holes of the old code stay: an assignment with a space before the sign (`password = "..."`), an address with no user (`redis://:<value>@host`), and a white-space character other than a space or a tab …»). The status note of REQ-102 says «(4)–(6) приняты владельцем 2026-10-28» ((4)–(6) accepted by the owner on 2026-10-28). The third old hole of (5), a no-break space after the sign, is not in the review; the diagnosis decides whether it goes with this fix.

Where a miss lands: a password written with spaces around `=` (a common style in code and configuration) or a connection address with no user stays as plain text in the Pixel Office journal and on its page (`maskSecrets`), in the events of a Sai Team project (`tools/src/team/store.js`, line 232), and is accepted byte-exact in a result file (`findSecrets`; callers `tools/src/team/runner.js` and `tools/src/team/store.js`). ISS-0122 is about who can read the journal.

Why MEDIUM (as proposed): masking is the only protection of text that is stored and shown; the text comes from the owner's own sessions and stays on his computer. The diagnosis may change the severity.

## Как исправить

The acceptance that the review proposes (to be measured by the diagnosis; not a ready fix, AP-161): both functions mask (or find) `key = value` with any spaces around `=` and `:`, and any `scheme://user:pass@host` and `scheme://:pass@host`; the old cases stay masked; benign twins (text without a secret) are not changed.

Before the design: the two shapes are a named residual risk of a done requirement, so ORCH decides with the owner, and a WF-01 micro-amendment of REQ-102 (rules Ф3, Ф9 and residual risk (5)) comes before the code, with the words of `tools/README.md` (line 253) and `decisions/0105`. For `findSecrets` a wider rule adds false refusals of result files (the price of the rule in REQ-102; ISS-0098): measure them on the project's own text files and name them (the way ISS-0097 item 1 asks). Every new position of a rule gets a sweep and a benign twin (AP-110, AP-161). The same file is touched by ISS-0097, ISS-0058 and ISS-0045; ISSUE-FIXER says whether they are one design or ordered fixes, so that two runs do not change `mask.js` at once. A weaker check or a skipped test is not a fix (Q6).
