# ISS-0083 — Тесты по времени и нагрузке краснеют при 3–5 параллельных полных прогонах: PG-08, EN-60, HC-7a, TM-67, HK-26, HK-27

Серьёзность: LOW (повысить до MEDIUM, если такое красное повторится в воротах работы или на GitHub: пункт Q4 «проходит одной командой» тогда нарушен). Статус: open. Найдено: ISSUE-FIXER (прогон `ISS-0075-20261021-01`, шаг 1, `handoffs/ISS-0075-20261021-01/step-01-issue-fixer.json`, I11), заведено DOC-UPDATER (шаг 10), 2026-10-21. Пункты планки: Q4, Q5 (тесты не зависят от нагрузки), Q3. Родственные: ISS-0004 (прежние тесты по времени под нагрузкой, open) и ISS-0017 (TM-67, open) — тот же класс; новый дефект не заменяет их, а собирает свежие измерения и показывает, что класс шире.

## Что не так

Под тремя–пятью одновременными полными прогонами `cd tools && npm run check` (так идут ворота, когда несколько агентов проверяют сразу) и под высокой нагрузкой на компьютер (load 40–55) краснеют тесты, которые в одиночном полном прогоне зелёные:

| Тест | Файл | Что видели |
|---|---|---|
| PG-08 | `tools/test/pixel-office-page.test.js` (около 194) | порог 1000 мс по стенным часам: «rule + tasks took 1128 ms»; красный в 10 из 27 параллельных прогонов |
| EN-60 (race) | `tools/test/team-channel.test.js` (около 873) | красный в 5 из 5 при 5 параллельных прогонах |
| HC-7a | `tools/test/handoffs-real.test.js` (около 55) | порог 20 с на команду: «the command took 20973 ms»; красный в 2 из 5 при 5 параллельных |
| TM-67 | `tools/test/team-recovery.test.js` (см. ISS-0017) | красный в 6 из 27 параллельных прогонов |
| HK-26, HK-27 | `tools/test/pixel-office-hook.test.js` (строки 1092 и 1141; пределы 2 с и 200 мс) | при высокой нагрузке: «input 2 took 2032 ms» |

В одиночном полном прогоне и при двух параллельных они зелёные (кроме PG-08 и TM-67 в первых кругах). Три подряд полных `npm run check` RELEASE-VALIDATOR прогона `ISS-0075-20261021-01` — без единого такого красного (`step-05-release-validator.json`); TEST-DESIGN-VALIDATOR (`step-03`, I1) под нагрузкой полный `check` не гонял, по этим тестам сведений у него нет.

Причины **не исследованы**. Предположение (не доказано): пороги по стенным часам и таймауты без запаса на загруженный компьютер; EN-60 — возможно, гонка, а не порог. Отдельные тесты могут и не быть однородными: как с ISS-0075, где три «нестабильных» теста оказались тремя разными причинами.

## Доказательство

`handoffs/ISS-0075-20261021-01/step-01-issue-fixer.json` (I11: числа по PG-08, EN-60, HC-7a, TM-67; способ — серия параллельных полных прогонов на копии метки `base/ISS-0075-20261021-01` вне проекта), `step-05-release-validator.json` (I3), `STATE.md` (раздел 2026-10-21 «Дефекты»: HK-26, HK-27, PG-08, EN-62 краснели при load 40–55). Вывод красных HK-26/HK-27 («input 2 took 2032 ms») — по записи в учёте; полного вывода в handoff-ах этого прогона нет (см. AP-121).

## Как исправить

Отдельный прогон WF-03 с шага 1. ISSUE-FIXER воспроизводит каждый тест **отдельно** серией параллельных полных запусков (способ диагноза ISS-0075: 3–5 параллельных `npm test` и/или 10–16 фоновых циклов `nice yes`), **сохраняет полный вывод каждого красного** (AP-121) и по каждому тесту определяет причину: порог по стенным часам, гонка, нехватка ожидания. Правка — в тесте или в его условиях ожидания (ждать состояния по условию, а не по часам), без ослабления проверок (Q6); лишнего перезапуска «до зелёного» нет. TM-67 вести вместе с ISS-0017, общий порог — вместе с ISS-0004.
