# ISS-0069 — Pixel Office: описание из одних пробелов хук отбрасывает, а сервер при записи в обход хука сохраняет как есть

Серьёзность: LOW. Статус: open. Найдено: SECURITY-REVIEWER (прогон `REQ044-20261014-01`, шаг 3, повтор, I1) и REVIEWER (шаг 4, повтор, N1); заведено DOC-UPDATER (шаг 10), 2026-10-14. Пункт планки: Q10 (одно правило записи на обоих путях). Требования: REQ-001, REQ-036 (критерий 6).

## Что не так

В `tools/src/pixel-office/protocol.js` хук (`buildWriteBody`) пропускает описание через `prepareText`: пустое или пробельное описание не попадает в тело. Сервер (`validateWriteBody`, `MASKED_FIELDS`, `maskField`) такой проверки не делает: подписанный запрос в обход хука с описанием «     » сохраняется как есть. На странице это пустое описание. Две линии записи расходятся только в этом случае (REVIEWER: «правила записи двух линий разные — род AP-014»).

На безопасность не влияет: секрета нет, писать в обход хука может только держатель секрета записи. До шага 5c хук такое описание хранил, расхождение появилось вместе с маскированием (SECURITY-REVIEWER: «Так было и до 5c» — про сервер).

## Доказательство

`handoffs/REQ044-20261014-01/step-03-security-reviewer-r1.json` (I1), `step-04-reviewer-r1.json` (N1, I1; проверено пробой), `step-09-release-validator.json` (F3). Воспроизвести: подписанный POST `/api/events` с `description: "     "` — строка в журнале с пробельным описанием; то же событие через `hook.sh` — без поля описания.

## Как исправить

WF-03: сервер отбрасывает пустое и пробельное описание тем же правилом, что хук (или проект явно записывает, что так допустимо); тест на путь в обход хука. Проверку не ослаблять.
