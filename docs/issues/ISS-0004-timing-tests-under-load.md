# ISS-0004 — Прежние тесты падают по времени при сильной нагрузке

Серьёзность: LOW. Статус: open. Найдено: TEST-DESIGNER прогона `PO-20261002-01`,
2026-10-03 (`handoffs/PO-20261002-01/step-05-test-designer.json`, `result.issues`, I5);
дефект заведён по поручению ORCH 2026-10-05. Пункт планки: Q5 (тесты не зависят от
внешнего), Q3.

## Что не так

Тесты, которые запускают процессы через `spawnSync` с пределом времени
(`CLI_TIMEOUT_MS = 10_000`, `tools/test/helpers.js:581`), на перегруженной машине получают
`ETIMEDOUT` и краснеют, хотя код исправен. Замечены прежние тесты W01, W13, W31, W34, W50
(`tools/test/apply.write.test.js`) и P12 (`tools/test/prepare.write.test.js`) — по одному-два
в прогоне. Тот же род у новых тестов с пределом времени: HK-11* хука Pixel Office
(`tools/test/pixel-office-hook.test.js`; сейчас предел 3500 мс, в момент находки — 2000 мс)
и PG-08 (`tools/test/pixel-office-page.test.js:163`, предел 1000 мс).

Красный прогон без дефекта в коде заставляет каждый раз разбирать, чьё падение
(quality-bar §6, п. 4), и приучает считать красное «шумом».

## Доказательство

- TEST-DESIGNER (I5): пока параллельно шли его отладочные циклы, один прогон
  `npm run check` шёл 973 с и дал 4 падения (W34, HK-01, HK-11c, SV-51), другой — 64 с и
  6 падений; три чистых прогона подряд — 423 из 423 за ~11,5 с. Чинить не пытался.
- TEST-DESIGN-VALIDATOR (`handoffs/PO-20261002-01/step-05b-test-design-validator-run3.json`,
  раздел «(6) НАГРУЗКА»): при трёх параллельных `npm run check` и 8 процессах с занятым
  процессором два прогона из трёх — код 1, по одному падению нового PG-08 («rule + tasks
  took 1059.892 ms» при пределе 1000 мс; обычно 356 мс). Прежние тесты W01, W13 и другие в
  его нагрузке не падали — их падение он оставил как сообщение автора, сам не воспроизвёл.
- CODE-FIXER (`handoffs/PO-20261002-01/step-07a-code-fixer.json`, I3): под сильной
  нагрузкой время хука превышает 2000 мс и без дефекта (65 из 200 запусков, максимум 2241 мс).

Как воспроизвести: на копии Sai вне проекта запустить `cd tools && npm run check`
параллельно с двумя-тремя такими же прогонами и процессами, занимающими процессор;
смотреть падения с `ETIMEDOUT` или «took … ms».

## Почему LOW

Падают только тесты, код не ломается; на спокойной машине проверка зелёная (423 из 423,
позже 428 из 428 — `handoffs/PO-20261002-01/step-09-release-validator-r1.json`). Но
красный прогон под нагрузкой останавливает ворота шага 6 и итоговую проверку, поэтому
откладывать надолго нельзя.

## Как исправить

Решает CODE-DESIGNER вместе с TEST-DESIGNER, не трогая смысла проверок (Q6):

1. Отделить предел, который проверяет свойство (например, жёсткий выход хука 1500 мс),
   от предела, который только защищает прогон от зависания; второй не должен краснеть на
   занятой машине.
2. Для проверок скорости (PG-08) — запас, рассчитанный по измерению под нагрузкой, или
   отдельная проверка скорости вне общей команды — только решением владельца
   (quality-bar §5).
3. Регрессионный тест — тот же набор под заданной нагрузкой зелёный.

## Маршрут

По `docs/workflows/WF-03-defect.md`: ISSUE-FIXER (диагноз: какие пределы и почему) →
CODE-DESIGNER → CODE-DESIGN-VALIDATOR → правка → проверки → DOC-UPDATER. Итерация 5
(`PLAN.md`). ORCH подтверждает маршрут при запуске.
