# ISS-0054 — Git, убитый сигналом, даёт из gitFailure не понятную ошибку, а необработанный Error или вводящее в заблуждение «git не запустился (EPIPE)»

Серьёзность: LOW. Статус: open. Найдено: CODE-DESIGNER (вопрос О1 проекта и находка I6), прогон `ISS-0053-20261013-01`, 2026-10-13; подтверждено SECURITY-REVIEWER (I2), REVIEWER (I2) и TEST-DESIGN-VALIDATOR (I2, мутант M7). Пункт планки: Q10. Требования: REQ-038 (критерий «Вывод, коды и сбои»).

## Что не так

Если процесс git убит сигналом, `execFileSync` кладёт в ошибку статус `null`, а не число. Функция `gitFailure` (`tools/src/handoffs/git-history.js`) знает ветки `ENOENT`, `ETIMEDOUT`, `ENOBUFS`, статус 128, статус 0 (решение `0047`) и «любое число»; статус `null` в них не попадает. Затронуты все шесть функций модуля. Исход зависит от того, был ли записан ввод:

- ввод 10 байт (запись удалась) — из `gitFailure` выходит не `TraceError`, а необработанный `Error` «Command failed: git … cat-file --batch»; команда падает со стеком (нарушение Q10: кривой сбой не должен ронять с трассировкой);
- ввод 4 МиБ (запись оборвана вместе с убитым процессом) — вводящее в заблуждение «git не запустился (EPIPE)»: git запустился, его убили;
- первый вызов git в CLI (`tools/src/traces/git-files.js`) при том же сбое даёт стек с путём компьютера и код выхода 1.

Мутант «ветка статуса 0 ловит ещё и `null`» выживает: тесты `GH-7` и `GH-7b` границу «статус `null`» не задают, потому что решение `0047` её не касается (граница вынесена сюда).

Поведение «до» и «после» исправления ISS-0053 одинаково; от этой работы дефект не зависит.

## Доказательство

`handoffs/ISS-0053-20261013-01/step-03-code-designer.json` (I6, воспроизведено на уровне функций), `step-05-security-reviewer-security.json` (I2: ввод 10 байт и 4 МиБ, первый вызов CLI), `step-05-reviewer.json` (I2), `step-07-test-design-validator.json` (I2, мутант M7). Воспроизвести: подставной git, убивающий себя сигналом (`kill -9 $$`), и вызов `readBlobs` с вводом 10 байт и 4 МиБ; на уровне CLI (`traces`) — отдельно.

## Как исправить

WF-03 с шага 1. Сделать для статуса `null` с сигналом понятный `TraceError` (`E_TRACE_GIT`, «git прерван сигналом …», код 2, без стека) в `git-history.js` и, отдельным решением, в `traces/git-files.js` (менять его запрещало решение `0038` — нужно новое решение ORCH); тест на каждый вариант ввода и контроль «статус 0 и число» не меняется. Не ослаблять `GH-6`, `GH-7`, `GH-7b`.
