# ISS-0003 — Необработанные вызовы файловой системы в `tools/src`: трассировка стека вместо кода ошибки

Серьёзность: LOW. Статус: open. Найдено: BACKEND-DEV при исправлении ISS-0001,
2026-09-30 (шесть случаев); подтвердил REVIEWER и нашёл ещё два (решение I2). Пункт
планки: Q10; дизайн §6.

## Что не так

Тот же класс, что ISS-0001: вызов `fs` без обработки ошибки. При сбое файловой системы
команда печатает трассировку стека Node (код 1) вместо кода ошибки и понятного
сообщения. Во всех случаях ниже команда падает до записи — ничего не записывается.

Четыре случая — ошибки чтения (c, d, f, g2). Дизайн §6 уже обещает: «Ошибки чтения и
разбора никогда не выводят трассировку стека», — эти случаи ему противоречат. Четыре —
ошибки записи (a, b, e, g1): для них в §6 кода нет, нужно решение дизайна.

## Доказательство

Каждый случай воспроизвёл REVIEWER (`handoffs/ISS-0001-20260930-01/step-02-reviewer.json`,
решение I2) исправленным CLI на свежей копии `sai/`: код 1, трассировка Node (у a–f —
7–10 строк `    at `), ничего не записано — строгий список файлов не изменился. Случаи
a–f нашёл BACKEND-DEV (`handoffs/ISS-0001-20260930-01/step-01-backend-dev.json`,
`result.issues`), g1 и g2 — REVIEWER.

Сначала реалистичные — опечатка в пути (Q10, «кривой ввод»):

- d) `snapshot`, папки `--root` нет: `ENOENT` scandir (`tools/src/util.js:71`,
  `listFiles`).
- g1) `snapshot`, нет родительской папки у `<out-file>` — например, опечатка в папке
  `<вне проекта>/` на шагах 0 и 6 WF-06: `ENOENT` open (`tools/src/cli.js:145`).

Остальные — только при намеренно созданной папке или файле или при смене прав:

- g2) `snapshot`, `--root` — файл: `ENOTDIR` scandir (`util.js:71`).
- b) `snapshot`, `<out-file>` — папка: `EISDIR` open (`cli.js:145`).
- c) `snapshot`, файл под `--root` не читается (`ideas/README.md` с правами 000):
  `EACCES` open (`snapshot.js:11`).
- a) `apply-verdict`, STATE.md с правами 444, и его нужно изменить: `EACCES` open при
  первой записи (`apply.js:105`). Если STATE.md менять не нужно, команда работает
  нормально.
- e) `prepare-run`, `runs` — файл: `ENOTDIR` mkdir (`prepare.js:135`). Контроль на
  обычной копии: код 0, `prepared`.
- f) `validate`, папка прогона с правами 300: `EACCES` scandir (`validate.js:144`,
  `checkUnknownLensFiles`).

## Почему LOW

Ничего не записывается: команда падает до записи. Правдоподобны d и g1 — опечатка в
пути (REVIEWER); остальные требуют намеренно созданных папок, файлов или смены прав.

## Как исправить

Один обход всех необработанных вызовов `fs` в `tools/src`, не только перечисленных
(REVIEWER, I2; AP-014). Начать с d и g1.

1. Коды §6 для каждого места решает CODE-DESIGNER (REVIEWER, I2). Для ошибок записи в §6
   кода пока нет; он нужен и ISS-0002.
2. По тесту на каждое место вызова: код выхода, строка ошибки, нет трассировки, список
   файлов не изменился — вместе с папками: `tree()` (`tools/test/helpers.js:350`) видит
   только обычные файлы (замечание REVIEWER O2; важно для `mkdirSync`, `prepare.js:135`).

Места вызова, которые назвал REVIEWER: `apply.js:103`, `:105`; `cli.js:145`;
`prepare.js:135`, `:136`, `:138`; `snapshot.js:11`; `util.js:71`; `validate.js:144`,
`:606`. `apply.js:103` и `:105` — тот же цикл записи, что в ISS-0002; в какой из двух
issue их исправлять, решает ORCH.

Остальные вызовы `fs` в `tools/src` — для сверки при обходе; REVIEWER их не оценивал:
`cli.js:51` (`existsSync`, затем `statSync`); `prepare.js:36`, `:55` и `validate.js:182`
(`existsSync`); `util.js:41` (в `try`, даёт `E_JSON`); `util.js:57`–`58`
(`readTextFile`, в `try`); `validate.js:289` (`readFileSync` при `--seal`). Список
получен поиском `grep` по `fs.` 2026-09-30: во всех модулях `fs` импортируется одинаково
(`import fs from "node:fs"`), так что вместе с местами выше это все 18 строк с вызовами
`fs` на эту дату.

## Маршрут

CODE-DESIGNER → CODE-DESIGN-VALIDATOR → BACKEND-DEV → REVIEWER → TEST-RUNNER →
DOC-UPDATER — как у ISS-0002 (маршрут ORCH). CODE-DESIGNER идёт первым, потому что коды
решает он (REVIEWER, I2). Отдельного маршрута для ISS-0003 ORCH не называл; он
подтверждает маршрут при запуске.

Сверка с документами — та же, что у ISS-0002: порядок шагов разработки Sai
(`docs/workflows/WF-02-development.md`, «Маршрут», шаги 5 и 5b) и процесс дефекта Sai
(`docs/workflows/WF-03-defect.md`, шаги 6–7) ставят между
REVIEWER и TEST-RUNNER ещё пару TEST-DESIGNER → TEST-DESIGN-VALIDATOR; в маршруте выше
её нет.
