## Диагноз

Источник — `handoffs/ISS-0053-20261013-01/step-01-issue-fixer.json`.

- **Где:** `tools/src/handoffs/git-history.js`, `readBlobs` — единственный вызов git с вводом: запросы пишутся на стандартный ввод `git cat-file --batch`.
- **Что происходит:** подставной git в GH-6 (случаи с `echo` и с `printf`) отвечает и выходит с кодом 0, не читая ввод. Если он вышел раньше, чем Node записал запросы, `execFileSync` бросает ошибку записи (`EPIPE`) со статусом 0 (git-то завершился успешно). `gitFailure` проверял `ENOENT`, `ETIMEDOUT`, `ENOBUFS`, статус 128 и затем «любое число»; 0 — число, и выходило «git не смог выполнить команду (код 0)». Текст ложен: git не вернул ошибочный код, не удалась запись ему. Если Node успевает записать (запрос уходит в буфер канала), git отвечает и разбор даёт ожидаемое «вывод git не разобран». Какая из двух веток сработает, решает гонка: на macOS всегда нужная тесту, на Linux-раннере в запуске 38331440082 её проиграл случай 2 (случай 1 выиграл).
- **Различия оболочек нет:** `printf '\377\376'` и `printf '\001nothash 2025\0'` дают одинаковые байты под `/bin/sh`, `dash` и `bash`.
- **Почему тесты не поймали:** подставной git не моделирует настоящий, который читает запросы до ответа; на macOS условие «git закрыл ввод, не прочитав» не создаётся; все замеры шли на macOS, на Linux тесты не запускались ни разу (остаточный риск 6 проекта REQ-030 сбылся). Ни критерий REQ-038, ни тест не называли текст при сбое записи.
- **Влияния на настоящий git нет:** он читает ввод; ошибка — в тексте сообщения и в тесте.

## Как исправить

Исправление не должно ослаблять проверку (Q6): тест не удаляется, не пропускается и ожидание «вывод git не разобран» не заменяется на «код 0». Регрессионный тест на Linux — запуск `check.yml` на GitHub.
