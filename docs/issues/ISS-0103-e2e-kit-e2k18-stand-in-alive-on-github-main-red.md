## Что не так

The check on GitHub for the commit on `main` is red. The test `E2K-18 a test process that ends by a signal, process.exit or a throw leaves no browser and no folder` (`tools/test/e2e-kit.test.js`, starts at line 1034) failed on its assertion at line 1070: `pidGone(pid) && groupGone(pid)` gave `false` with the message `SIGTERM: the stand-in is gone`. The step `npm run e2e` of the command `check` never ran after the failed `npm run test`, so the whole check stayed red and the push of the run is not confirmed by a green check.

The same files passed on the temporary branch and several times on the developer machine, so the result depends on the machine and the timing, not on the code of the run: a flaky test. The flaky test is a defect (`decisions/0079`, п. 2), and the red check is not repeated or hidden (Q6).

## Как исправить

A hypothesis only, not a diagnosis; ISSUE-FIXER finds the cause. The test starts a child that launches the stand-in browser, sends it a signal (`SIGTERM` among them) or lets it exit, awaits `run.done` (the exit of the child) and checks at once, without waiting, that the pid and the process group are gone (`pidGone`, `groupGone`). If the stand-in or its group is ended by the cleanup a moment after the child itself ends (or the pid is a zombie that is not yet reaped on a slower Linux runner), the immediate check is a race with the cleanup. The same pattern — a check right after the exit of the child, with no wait — may stand in many other tests of this file and of `tools/test/`; ISSUE-FIXER lists every place, and the fix must be the same in all of them (one mechanism in all neighbouring places). Possible directions to look at: a wait with a limit until the stand-in is gone, as the file already does with `until`, instead of a single check; whether the cleanup of the kit really finishes before the child exits (then the cause is in the code, not in the test). A weaker assertion, a longer timeout alone, a `skip` or a repeat of the run are not a fix (Q6). The fix needs a regression test that fails before the fix, if the cause can be reproduced (for example, a stand-in that ends late).

## Закрыто

Закрыто 2026-11-03T19:35:10Z (время с часов), прогон `ISS-0103-20261103-01` (WF-03, шаг 10, DOC-UPDATER после PASS RELEASE-VALIDATOR, `handoffs/ISS-0103-20261103-01/step-09-release-validator.json`). Итог: причина устранена в трёх местах теста, регрессионные тесты есть; код набора не менялся.

- **What was done.** The cause: the tests E2K-18 and E2K-38 ended a process with `SIGKILL` and then, right after the end of the child that watched it, checked once that the pid and the process group were gone (`pidGone(pid) && groupGone(pid)`). A killed process that its parent has not yet reaped (a zombie) still answers `kill(pid, 0)`, so the single check is a race with the reaping. Now the three exposed places (the assertion of E2K-18; the signal loop and the preflight loop of E2K-38) wait with the helper `waitGone(pid, what, ms = 5000)` until both the pid and its group answer `ESRCH`, with a limit of 5000 ms; a live process still fails the wait in time with a message that names what was waited for. Only `tools/test/e2e-kit.test.js` changed (and the ORCH progress file); `tools/src/` and the kit code under `tools/test/e2e/` did not change. The convention is recorded in `decisions/0108`, Addendum 2026-11-03 (ISS-0103).
- **Regression tests.** `tools/test/e2e-kit.test.js`: **E2K-62** pins the helper with a deterministic hold (a killed victim kept unreaped by its parent, ps state Z, once as a group kill and once as a pid kill): the old single check is false on the base tag, the new wait goes through the hold and ends true after the parent reaps; a live process fails the wait in time and is left alone. **E2K-63** pins the use: a source guard that reads the text of E2K-18 and E2K-38 and fails, with the test and the line, when a call site goes back to a single check, loses its assertion or gets a tiny limit. The known limits of E2K-63 and two surviving mutants of E2K-62 are in `docs/issues/ISS-0104-e2e-kit-e2k63-guard-limits-and-e2k62-survivors.md`.
- **How it was checked.** RELEASE-VALIDATOR reproduced the original error in a deterministic form (a killed, unreaped victim makes the old check false on the base tag; the current tree waits through the hold and ends true after the release); E2K-18 and E2K-38 30 of 30 green each under 8 busy loops on the current tree, against one natural red in the series on the base tag; E2K-63 goes red when E2K-18 is put back to the single check. The full `npm run check` on this computer: 2187 of 2187, e2e 13 of 13, exit 0, 257 s. The full check on GitHub on a temporary branch with a snapshot equal to the working files: run 41701454358, success, 2187 of 2187, 17 min 00 s of the 30-minute limit, `ok` for E2K-18, E2K-38, E2K-62 and E2K-63; the branch was deleted. The tests went from 2185 to 2187 (E2K-62, E2K-63).
- **What is NOT done or not proved (do not read the closing as more).** (1) The Linux fact «zombie, or just slow» was **not measured on the runner** (docker is absent here): the cause is confirmed in kind on macOS under load (3 of 160 runs in the diagnosis) and by one natural red in the series on the base tag, and the fix is «wait for the death with a limit», which is right for either reading. (2) The green GitHub run is **one sample**, not a proof that the flake cannot return. (3) The fix is not yet on `main`: the check on `main` after the push of this fix is read by RELEASE-FINALIZER (step 11), and this closing precedes it; a red `main` at that point reopens this defect. (4) The reading of the other call sites (every other `pidGone`/`groupGone` is after an awaited close inside the kit, inside `until(...)` or after `waitGone`; other test files check a child run with `spawnSync`, which has reaped it) is a reading, not a measurement of each one. (5) The guard E2K-63 is a source guard with known limits (ISS-0104); accidental regressions are caught, a hostile edit is not.
