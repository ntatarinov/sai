## 2. Команда

Запуск из `tools/`: `npm run traces [-- <подкоманда> [ключи]]`. Справка — `--help` (код 0).

| Подкоманда | Ключи | Что делает | Пишет |
|---|---|---|---|
| `check` (по умолчанию) | `--root <папка>` (по умолчанию — текущая) | проверяет репозиторий (п. 3–6) | ничего |
| `add` | `--root <папка>` | читает названия со стандартного ввода, добавляет их хеши в файл хешей | только `tools/traces/forbidden-names.sha256` (п. 8) |
| `hash-line` | `--root <папка>`, `--file <путь от корня>`, `--line <n>` | печатает заготовку строки файла исключений для строки `n` файла | ничего |

`--root` — любая папка внутри репозитория; корнем проверки становится корень репозитория (`git rev-parse --show-toplevel`,
п. 4). Неизвестная подкоманда или ключ, отсутствующее значение, `--line` не целое ≥ 1 — `E_TRACE_USAGE`, код 2.
**Разбор подкоманд и ключей (r3, ревью F1):** таблица подкоманд — `Map` (или объект с проверкой `Object.hasOwn`), никогда
оператор `in` или обращение к свойству обычного объекта: имена, унаследованные от `Object.prototype` (`toString`,
`constructor`, `__proto__`, `hasOwnProperty`, `valueOf` и любые другие), — неизвестная подкоманда, `E_TRACE_USAGE`, код 2,
одна строка без стека. То же для имён ключей.

### 2.1. `check`: вывод и коды выхода

stdout, по строке на находку, отсортировано по пути, затем по номеру строки, затем по виду:

```
<путь от корня>:<номер строки>: путь домашнего каталога
<путь от корня>:<номер строки>: название из списка
<путь от корня>:<номер строки>: ссылка за корень репозитория
<путь от корня>:<номер строки>: ссылка не разобрана (негодный %XX) — не след, код не меняет
<путь от корня>:<номер строки>: ссылки не разобраны (строка длиннее 100000 знаков) — не след, код не меняет
<путь от корня>: пропущен: двоичный файл | не читается | удалён в рабочей копии | не обычный файл | больше 16 МиБ | вне корня репозитория
<файл №k, sha256 пути <12 hex>>: название из списка в имени файла
traces: исключение не использовано: tools/traces/exceptions.tsv:<номер строки>
traces: файлов проверено <N>, следов <M>, пропущено <K>
traces: открытый список: sha256 <64 hex>, названий <L>, совпадений названий <C>     (только при SAI_TRACE_LIST)
```

Номер строки — с 1. Одна строка с двумя видами следа даёт две строки вывода. **Файл, в пути которого найдено название
(п. 3.5), во всех строках вывода (находки, пропуски) показывается не путём, а меткой `<файл №k, sha256 пути <12 hex>>`**:
`k` — номер файла (с 1) в списке путей, отсортированном по байтам UTF-8 (как `LC_ALL=C sort`), 12 hex — начало sha256 байтов
UTF-8 пути. Найти файл: `git ls-files -z --cached --others --exclude-standard | LC_ALL=C sort -z | tr '\0' '\n' | sed -n '<k>p'`
(команда — в `tools/README.md`). **Вывод никогда не содержит найденного
текста:** ни пути домашнего каталога, ни названия, ни адреса ссылки, ни значения `SAI_TRACE_LIST`, ни абсолютного пути
корня, ни имени папки или файла, где найдено название, ни текста ошибок git (он содержит абсолютные пути) — только путь файла от корня, номер строки и вид.

| Код | Когда |
|---|---|
| 0 | следов нет (ни в тексте, ни в именах файлов) и ни один файл не пропущен как «не читается» (двоичные, удалённые, не обычные, больше 16 МиБ, вне корня — не мешают, как двоичные) |
| 1 | найден хотя бы один след (даже если есть пропуски) |
| 2 | ошибка окружения или ввода (таблица п. 7) — проверка не выполнялась; или следов нет, но хоть один файл «не читается» — проверка неполная, зелёной она быть не может (Q6) |

Ошибки — в stderr одной строкой `traces: <КОД>: <текст по-русски>`, без трассировки стека. Ошибка программы (не ОС,
не ввода) не перехватывается и падает со стеком (как в `decisions/0004`).

### 2.2. `add`

1. Ввод: весь stdin, не больше 64 КиБ, UTF-8 (строгое декодирование). Если stdin — терминал, в stderr печатается
   подсказка «Введите названия, по одному в строке, затем Ctrl-D». **Предел ожидания (r3, ревью F5):** если чтение
   возвращает `EAGAIN` (неблокирующий ввод), повтор каждые 20 мс; 30 с подряд без новых байтов — `E_TRACE_NAME` «ввод не
   закончился за 30 с», код 2, ничего не пишется. Блокирующий ввод (терминал, канал) ждёт конца ввода без предела.
2. Каждая непустая строка (после обрезки пробелов по краям) — одно название; строки, начинающиеся с `#`, пропускаются.
3. Название → хеши по `nameToHashes` (п. 3.1). Любая негодная строка — `E_TRACE_NAME` с номером строки и причиной, без
   текста строки; **ничего не пишется**.
3а. **Папка записи (r3, безопасность F3):** до замка и до любой записи — `lstat` каждого звена `tools`, `tools/traces` (и
   файла хешей, если он есть) от корня: любое звено — символическая ссылка, или `realpath` папки `tools/traces` не внутри
   `realpath` корня — `E_WRITE` «папка записи — ссылка или вне репозитория; запись отказана», код 2; ни замок, ни папки, ни
   файлы не создаются (как отказ `writeAllOrNothing` по `decisions/0004`).
4. **Замок (N5).** `add` создаёт `tools/traces/.forbidden-names.sha256.lock` эксклюзивно (`openSync(…, "wx")`, права 0600,
   содержимое — pid и время UTC). Файл уже есть: если записанный pid жив (`process.kill(pid, 0)` не бросает `ESRCH`) или
   содержимое не разбирается — `E_TRACE_BUSY` «идёт другое пополнение; если нет — удалите tools/traces/.forbidden-names.sha256.lock»,
   код 2, ничего не пишется; pid мёртв — замок удаляется и создаётся заново один раз. Замок удаляется в `finally` на всех
   путях, включая ошибку программы.
5. Под замком: прочитать файл хешей (если он есть и годен, п. 5.1; негодный — `E_TRACE_HASHES`, ничего не пишется) и
   запомнить sha256 его байтов (или «файла нет»); объединить с новыми хешами, отсортировать, убрать повторы.
6. Нет новых хешей — файл не трогается (байты и время изменения те же), код 0.
7. **Повторное чтение перед записью (N5):** непосредственно перед записью прочитать файл снова; sha256 (или «файла нет»)
   отличается от запомненного — `E_TRACE_BUSY` «файл хешей изменился во время пополнения; повторите», код 2, ничего не
   пишется (запись в обход замка не теряет чужих хешей).
8. Иначе запись `writeAllOrNothing(root, [{ rel: "tools/traces/forbidden-names.sha256", content }], issues)`. Если папок
   `tools/` или `tools/traces/` нет, они создаются перед записью; при отказе записи созданные этим вызовом пустые папки
   удаляются. Отказ ОС — строки `E_WRITE` (как у `writeAllOrNothing`), код 2, прежний файл байт-в-байт тот же.
9. stdout: `traces: добавлено хешей <a>, уже были <b>` — без названий и без хешей. Код 0.

Замок — служебный файл рядом с целью; если он остался после убитого процесса с живым чужим pid, его удаляет человек (текст
ошибки говорит как). `check` замок не читает; как неотслеживаемый файл он проверяется как обычный текст (pid и время).

### 2.3. `hash-line`

Печатает **только** sha256 строки `n` файла — 64 hex и перевод строки (N4); ни путь, ни текст строки не печатаются. Запись
файла исключений (`<путь>\t<хеш>\t<причина>`) человек собирает сам: путь он ввёл сам. Файл, который `check` пропустил бы как «вне корня
репозитория», «не обычный файл» или «больше 16 МиБ» (п. 6, шаг 3), — `E_TRACE_USAGE`, код 2, файл не читается (r3,
безопасность F3). Если в пути файла есть название из
списка (п. 3.5) — отказ `E_TRACE_USAGE` «в пути файла название из списка: такой файл переименовывают, исключение не
поможет», код 2 (исключения на названия не действуют). Нет файла, строки с таким номером или файл не текст —
`E_TRACE_USAGE`, код 2.

## 3. Правила

### 3.1. Деление на слова (`words.js`) — одно для `add`, `check` и открытого списка

0. **Нормализация (замечание 5).** По порядку: (а) NFKC (`String.prototype.normalize("NFKC")`) — составные буквы
   (NFD «й» → «й»), полноширинные и совместимые формы (`Ｚ` → `Z`) приводятся к одной записи; (б) приведение к нижнему
   регистру (`String.prototype.toLowerCase`, без учёта локали); (в) удаление невидимых знаков U+200B, U+200C, U+200D,
   U+2060, U+00AD, U+FEFF — без замены на разделитель, так что `Zqx`+U+200B+`wvorg` даёт одно слово. Нормализация
   выполняется построчно (строки не склеиваются и не делятся, номера строк сохраняются), одинаково для текста файлов,
   путей файлов (п. 3.5), ввода `add` и открытого списка. Правила п. 3.2 и 3.4 работают по исходному тексту, не по
   нормализованному.
1. (Нижний регистр — шаг 0 (б).)
2. Слово — непрерывная последовательность символов категорий Юникода «буква» (`L`) и «цифра» (`N`); всё остальное —
   разделитель (пробел, дефис, точка, `/`, `_`, перевод строки, знаки, комбинирующие символы и прочее).
3. Слова короче 3 символов (считаются кодовые точки после шага 0) отбрасываются. Комбинирующие знаки (категория `M`),
   оставшиеся после NFKC, — разделители (п. 16).
4. Пара — два соседних слова **после** отбрасывания, в том числе через перевод строки; строка пары — первое слово, один
   пробел, второе.
5. Хеш слова — sha256 (hex, строчные) байтов UTF-8 слова; хеш пары — sha256 строки пары. Слово и пара не совпадают по
   хешу (в паре есть пробел).

Примеры: «a/Zqxwvorg/b» → слова `zqxwvorg`; «zqxwvorg-api» → `zqxwvorg`, `api`, пара `zqxwvorg api`.

Сигнатуры:

| Функция | Вход | Выход |
|---|---|---|
| `tokenize(text)` | строка | `Array<{ word: string, line: number }>` — слова после шагов 1–3, `line` — строка первого символа слова (с 1) |
| `wordHash(word)` / `pairHash(a, b)` | строки | hex sha256 |
| `nameToHashes(name)` | одно название | `{ ok: true, hashes: string[] }` или `{ ok: false, reason: "EMPTY" \| "SHORT_PART" \| "TOO_MANY_WORDS" }` |

`nameToHashes`: нормализация по шагу 0, деление по шагу 2; если хоть одна непустая последовательность букв и цифр короче 3 — `SHORT_PART`
(иначе «AB Zqxwvorg» молча стал бы одним словом и совпадал бы шире задуманного); 0 слов — `EMPTY`; 1 слово — `[wordHash]`;
2 слова — `[pairHash]`; 3 и больше — `TOO_MANY_WORDS` (правило знает только слова и пары; I3).

Совпадение названия: для каждого слова файла — `wordHash ∈ множество`, для каждой пары — `pairHash ∈ множество`; находка
пары — на строке её первого слова. Хеш одного и того же слова считается один раз (кэш на время запуска), чтобы 18 МБ
проверялись за секунды.

### 3.2. Путь домашнего каталога (`rules.js`)

След — место в строке, где: (1) стоит `/Users/` или `/home/` (регистр точный); (2) символ перед первой `/` отсутствует
(начало строки) или не из набора `[A-Za-z0-9._-]` (так `data/home/x` — не след, а `file://` + `⟨дом⟩/anna` — след);
(3) сразу после второй `/` — один или больше символов набора `[A-Za-z0-9._-]` (имя). Не след: на месте имени `<` (пометка
«<имя>»), `$`, `*`, `{`, пробел, кавычка, конец строки. Примеры: `⟨дом⟩/anna/notes.md` — след; `⟨дом⟩/<имя>/notes.md` —
нет; `⟨дом⟩/` в конце строки — нет.

**(а2) Закодированная форма (решение ORCH, замечание 1).** След — место в строке, где: (1) стоит `-Users-` или `-home-`
(регистр точный); (2) символ перед первым `-` отсутствует (начало строки) или не из набора `[A-Za-z0-9]` (так `x-home-page-`
— не след); (3) сразу после второго `-` — один или больше символов набора `[A-Za-z0-9._]` (имя), и за именем стоит `-`. Не
след: на месте имени `<` (пометка: `⟨кдом⟩<имя>-…`), имя без завершающего `-` (`⟨кдом⟩anna` в конце строки или перед `/`).
Примеры: `.claude/projects/⟨кдом⟩anna-work/x.jsonl` — след; `⟨кдом⟩<имя>-work` — нет. Вид находки — тот же «путь
домашнего каталога»; исключения на неё действуют (п. 5.2). Само имя пользователя вне таких записей (например, внутри
шаблона поиска) правило (а) не ловит — для этого владелец вносит имя в список названий (п. 13, шаг В).

### 3.3. Название из списка

По п. 3.1 с множеством «файл хешей ∪ открытый список» (п. 5). Исключения на названия **не действуют** (п. 5.2).

### 3.4. Ссылка Markdown за корень (полный разбор, замечание 7)

**Файлы.** Путь оканчивается на `.md` (без учёта регистра). Разбор построчный по исходному тексту; ссылка не переходит
через перевод строки.

**Сложность и предел (r3, безопасность F2).** Разбор строки линейный по её длине: пары `[`/`]` (с учётом вложенности и
`\`-экранирования) находятся одним проходом со стеком до поиска ссылок, и для каждого `[` парная `]` берётся из этой
таблицы (нет пары — не ссылка); повторного просмотра остатка строки для каждого `[` нет; то же для скобок адреса и
последовательностей обратных кавычек. Строка длиннее `MAX_LINE_CHARS = 100 000` знаков (кодовых единиц строки) для
ссылок не разбирается: строка вывода «ссылки не разобраны (строка длиннее 100000 знаков)», код не меняет; правила п. 3.2,
3.3 к этой строке применяются как обычно. Строка ровно в 100 000 знаков разбирается.

**Что не разбирается.**
1. *Огороженный блок кода:* строка, где после 0–3 пробелов стоит 3 или больше одинаковых знаков `` ` `` или `~` (длина
   ограды `L`; у ограды из `` ` `` в остатке строки нет `` ` ``), открывает блок; закрывает его первая следующая строка, где
   после 0–3 пробелов стоит не меньше `L` того же знака и дальше только пробелы. Строки блока, открывающая и закрывающая —
   не разбираются. Незакрытый блок длится до конца файла.
2. *Код в строке:* последовательность из `n ≥ 1` обратных кавычек открывает код, закрывает его ближайшая дальше в той же
   строке последовательность ровно из `n` кавычек; всё между ними не разбирается. Без пары — кавычки обычный текст.
3. Отступ в 4 пробела, HTML-комментарии, сырой HTML (`<a href>`, `<img src>`) не распознаются и не проверяются (п. 16).
4. Знак, перед которым `\`, — обычный знак (`\[` не открывает ссылку).

**Виды ссылок (проверяется адрес).**
1. *Встроенная:* `[текст](адрес)` и `![текст](адрес)`, в том числе с заголовком `[текст](адрес "заголовок")`,
   `(адрес 'заголовок')`, `(адрес (заголовок))`. `текст` — от `[` до парной `]` с учётом вложенных `[ ]`. Сразу после `]`
   — `(`; затем 0+ пробелов; адрес — либо `<…>` (до первой `>`, без `<` и перевода строки внутри), либо подряд идущие
   знаки без пробелов, где `(` и `)` парны (на непарной `)` адрес кончается); затем 0+ пробелов, необязательный заголовок,
   0+ пробелов и `)`. Если строка не укладывается в эту форму — это не ссылка (обычный текст), ничего не проверяется.
2. *Определение ссылки:* строка, где после 0–3 пробелов стоит `[метка]:`, затем 1+ пробел и адрес (форма как в п. 1),
   затем необязательный заголовок. Проверяется каждое определение, используется оно или нет; ссылки-ссылки `[t][r]`,
   `[r][]`, `[r]` сами не проверяются — их адрес и есть адрес определения.
3. *Автоссылки* `<схема:…>` — у них всегда есть схема, они не проверяются.

**Адрес.** Убираются `\`-экранирования. Не проверяется: пустой; начинается со схемы (`[A-Za-z][A-Za-z0-9+.-]*:` —
`http:`, `https:`, `mailto:` и любые другие); начинается с `#`. Отрезаются `#…` и `?…`. Раскодирование `%XX`: каждая `%`
должна стоять перед двумя шестнадцатеричными цифрами, а раскодированные байты — быть верным UTF-8 (строгое
декодирование); иначе адрес **неразрешим**: строка вывода `<путь>:<строка>: ссылка не разобрана (негодный %XX)`, это не
след и код выхода не меняет (по такому адресу не откроется ничего); исключение, стек и падение недопустимы — ошибка
раскодирования ловится в разборе адреса.

**След,** если адрес начинается с `/` или `~` (вне клона это корень диска или домашний каталог), или
`posix.normalize(posix.join(posix.dirname(файл), адрес))` равен `..` или начинается с `../`. Разрешение лексическое, без
`realpath`.

### 3.5. Название в пути файла (решение ORCH, I9)

Путь файла от корня (все сегменты вместе, `/` — разделитель по п. 3.1) делится на слова и пары по п. 3.1 и сравнивается с
тем же множеством, что и текст (п. 3.3). Пары образуются и через `/` (`zqxwvorg/api` → пара `zqxwvorg api`), как в тексте.
Находка вида `path-name` — одна на файл, без номера строки; проверяется у каждого файла из списка, в том числе пропущенного
(двоичного, нечитаемого, удалённого). Исключения на неё не действуют. Вид в выводе — «название из списка в имени файла»;
сам путь такого файла не печатается (п. 2.1). Путь нормализуется по п. 3.1, шаг 0. Правила п. 3.2 и 3.4 к путям не
применяются. Пример (критерий 1): файл `docs/zqxwvorg-api.md` после пополнения «Zqxwvorg» — строка
`<файл №k, sha256 пути <12 hex>>: название из списка в имени файла`; ни путь, ни `zqxwvorg` в выводе нет.

`-c core.fsmonitor=false` (r3, безопасность F4) — в обоих вызовах: иначе `core.fsmonitor` из `.git/config` или глобальной

REQ-ANALYST по WF-01; запись — `decisions/0021-traces-check.md`. Исходная постановка вопроса (r0): Критерий 4 требует «child_process — только в исполнителе claude-cli REQ-010», а

## 5. Файлы данных

### 5.2. Файл исключений `tools/traces/exceptions.tsv`

  подавляются никогда**: строка, которую надо оставить с названием, сама и есть след в Sai; общее слово, совпавшее с

## 6. Проверка (`check.js`)

`checkRepo({ root, env }) → Report` — синхронно, ничего не пишет.

Порядок: (1) прочитать файл хешей, исключения, открытый список — любая ошибка до просмотра файлов; (2) `listRepoFiles`;
(3) по каждому пути: `lstat` (через объект `fs`, не деструктурированную копию — для инъекции сбоев в тестах): `ENOENT` —
«удалён в рабочей копии»; не обычный файл (ссылка, папка подмодуля) — «не обычный файл», не читается и не следует по
ссылке; **(r3, безопасность F3)** `realpath` файла не внутри `realpath` корня (так бывает, когда отслеживаемая папка в
рабочей копии заменена символической ссылкой наружу) — «вне корня репозитория», не читается; **(r3, безопасность F1)**
`stat.size` (из того же `lstat`, до чтения) больше `MAX_FILE_BYTES = 16 МиБ` (16 777 216 байт) — «больше 16 МиБ», не
читается; файл читается не больше чем `MAX_FILE_BYTES + 1` байтом (вырос между `lstat` и чтением — тот же пропуск); ошибки
чтения — только ошибки ОС («не читается»), исключение без кода ОС не возникает; чтение `EACCES`/`EPERM`/другая ошибка ОС — «не читается»; байт `0` в первых 8000 байтах или строгое
декодирование UTF-8 не прошло — «двоичный файл»; (4) текст делится на строки по `\n`, у строки срезается `\r`; правила
п. 3.2 и 3.4 — по строкам, п. 3.3 — по всему тексту; (5) исключения (п. 5.2); (6) путь каждого файла из списка — по п. 3.5
(независимо от того, читается ли файл).

## 9. Вхождение в `npm run check` и что это меняет

`check` = `npm run format:check && npm run lint && npm run traces && npm run test` — остановка на первой ошибке.

Последствия (перечень мест, где это действует):
- **Чистая машина** (критерий 3): клон содержит `.git` — проверка работает.
- **Копии для повторов и мутантов** (quality-bar §6 п. 4, WF-02 шаг 5b; решение ORCH, I5): на копии без `.git`
  `npm run check` даёт `E_TRACE_NOT_GIT`, код 2 — так и задумано. **Требование к тестам и шагам с копиями:** каждый тест
  или шаг, который копирует папку Sai и запускает в копии `npm run check` (EN-77 — команда отчёта шага, названная в
  `tools/test/team-engine-docs.test.js`, — и подобные), копирует её **вместе с `.git`** (`cp -R` всей папки или `git clone`
  с локального пути); TEST-DESIGNER и TEST-DESIGN-VALIDATOR проверяют это у каждого такого теста и шага.
- **Новые файлы прогона** (handoff-ы, отчёты) проверяются до коммита — след в handoff-е прогона краснит `check` сразу.
- `README.md` «или взять копию папки» перестаёт быть верным для `check` (п. 10).

`SAI_TRACE_LIST`. Общее английское слово из F9 вносить парой с тем словом, что делает его названием, иначе 161 ложная
находка (I2, принято ORCH).

Шаг Г — `npm run traces` без переменной и с `SAI_TRACE_LIST` — код 0, вывод в отчёт: только хеш файла списка и числа.

Учёт: замены в `handoffs/` и `runs/` — правка истории по прямому требованию (как 0019); ни одна запись не удаляется,
файл не теряет записей (quality-bar §6 п. 8).

## 16. Ограничения (приняты ORCH, `decisions/0021-traces-check.md`)

- **Общие слова (I2).** Исключения на названия не действуют. Название, совпадающее с обычным словом (F9: 161 место в Sai),
  владелец вносит парой слов; одно слово дало бы ложные находки. Это же — одним предложением в README (п. 10, строка 7).
- **Длина названия (I3).** `add` и открытый список принимают название из одного или двух слов, каждая часть не короче 3
  знаков; иначе — отказ `E_TRACE_NAME`/`E_TRACE_LIST`; такое название вносится его отличительной парой.
- **Хеши обратимы перебором (I8).** sha256 отдельного слова подбирается по словарю; файл хешей защищает от случайного
  прочтения и поиска по тексту, а не хранит тайну.
- **Обходы правила деления — защита от случайности, не от умысла (замечание 6).** Не ловятся: склейка слов и camelCase
  («ZqxwvorgApi», «zqxwvorgapi» — одно другое слово); цифра вплотную («zqxwvorg2» — слово с цифрой); похожие буквы другого
  алфавита (гомоглифы: кириллическая «х» вместо латинской); комбинирующие знаки без составной формы после NFKC (разделитель).
  Известные владельцу склеенные формы он вносит отдельным словом.
- **Markdown:** не проверяются ссылки в сыром HTML (`<a href>`, `<img src>`), в блоках с отступом 4 пробела трактуются как
  текст (проверяются — это только строже), HTML-комментарии не распознаются; ссылка не переходит через перевод строки.
- **Имя пользователя** вне путей ловится только после того, как владелец внесёт его в список (п. 13, шаг В).
- **Замок `add`:** оставленный процессом с чужим живым pid замок снимает человек (текст ошибки говорит как).
- **Двоичные файлы** по содержимому не проверяются (только путь, п. 3.5).
- **Файлы больше 16 МиБ и строки `.md` длиннее 100 000 знаков (r3):** первые по содержимому не проверяются (только путь),
  во вторых не разбираются ссылки (названия и пути проверяются); оба случая отмечены в выводе и, как двоичные, код не
  меняют. В Sai таких файлов нет (F11: всего ≈ 18 МБ текста).
- **История git** не проверяется и не переписывается (`decisions/0019`, «Граница»).
