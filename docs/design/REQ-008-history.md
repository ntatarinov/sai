## 2. Формы данных

### 2.1 Строка журнала — два вида (`schema.js`)

Постоянные (новые, экспортируются):

| Имя | Значение | Смысл |
|---|---|---|
| `SOURCE_ORCH` | `"ORCH"` | источник записи оркестратора |
| `PROMPT_KINDS` | `["owner", "service"]` | вид сообщения |
| `PROMPT_MAX` | `4000` | предел `prompt_text`, кодовых точек |
| `NOTE_MAX` | `2000` | предел `note_text`, кодовых точек |
| `NOTE_SESSION_MAX` | `200` | предел `session_id` у записи ORCH (критерий 6) |
| `REQ_ID_PATTERN` | `^REQ-[0-9]{3,6}$` | номер требования; «REQ-8», «../x» не проходят |
| `MASK_LABEL` | `"[скрыто]"` | метка маскирования |
| `SERVICE_MARKERS` | `["<system-reminder>", "[SYSTEM NOTIFICATION", "<task-notification", "Another Claude session", "This session is being continued"]` | метки служебного сообщения |

`LINE_KEYS` дополняется в конце, в этом порядке: `prompt_kind`, `prompt_text`, `prompt_truncated`, `note_text`, `req_id`,
`request_time`, `request_time_auto`. Порядок ключей записываемой строки — порядок `LINE_KEYS`.

**Вид A — событие хука** (`source` = `"REAL"` в файле; всё прежнее по D1 п. 3.2) плюс три поля, только у `UserPromptSubmit`:

| Поле | Тип и ограничения | Когда есть |
|---|---|---|
| `prompt_kind` | `"owner"` или `"service"` | у `UserPromptSubmit`, если во входе хука `prompt` — строка |
| `prompt_text` | строка, 1…`PROMPT_MAX` кодовых точек, уже замаскирована | только при `prompt_kind = "owner"` и включённом хранении |
| `prompt_truncated` | ровно `true` | только вместе с `prompt_text`, если текст обрезан (64 КБ на входе, 4 000 после маскирования, предел тела) |

Правила, которые выполняются всегда: у событий кроме `UserPromptSubmit` нет ни одного из трёх полей; `prompt_text`
без `prompt_kind = "owner"` не бывает; `prompt_truncated` без `prompt_text` не бывает; полей записи ORCH (`note_text`,
`req_id`, `request_time`, `request_time_auto`) у вида A нет.

**Вид B — запись оркестратора** (нет `hook_event_name`):

| Поле | Тип и ограничения | Обязательно |
|---|---|---|
| `time` | канонное ISO UTC с мс (`isCanonicalTime`); ставит **сервер** с часов в момент записи | да |
| `source` | ровно `"ORCH"`; ставит сервер | да |
| `session_id` | строка, 1…`NOTE_SESSION_MAX` кодовых точек; **не маскируется** (N5: идентификатор сессии, не секрет и не текст — критерий 7 маскирует `prompt_text` и `note_text`; так же `--session` команды) | нет |
| `note_text` | строка, 1…`NOTE_MAX` кодовых точек, замаскирована, не из одних пробельных знаков | да |
| `req_id` | по `REQ_ID_PATTERN` | нет |
| `request_time` | канонное ISO; время сообщения владельца, к которому относится запись | нет (нет — запись ни к чему не привязана) |
| `request_time_auto` | ровно `true` | только вместе с `request_time`, когда его поставил сервер |

Других ключей у вида B нет (`hook_event_name`, `agent_id`, `prompt_*` и прочие — отказ).

Функции `schema.js` (сигнатуры):

- `checkLine(value, withSource) -> {ok, line} | {ok:false, reason}` — вид A, как сейчас плюс правила полей выше. При
  `withSource = true` строка с `source = "ORCH"` видом A не считается (`reason: "bad_value:source"`): событие хука с
  источником ORCH невозможно.
- `checkNoteLine(value) -> {ok, line} | {ok:false, reason}` — вид B из файла (с `time` и `source = "ORCH"`).
- `parseLine(value) -> line | null` — если у объекта нет `hook_event_name` и `source === "ORCH"` — `checkNoteLine`,
  иначе `checkLine(value, true)`. Строка вида B с `source` не `"ORCH"` и строка вида A с `source = "ORCH"` — `null`.

  **Строка с `hook_event_name` и `source = "ORCH"` (F6, r2).** Сейчас (REQ-001 до этой работы: `source` — любая
  короткая непустая строка) такая строка читается видом A и показывается с пометкой «не из хуков». После работы она
  **испорченная**: `checkLine(value, true)` → `bad_value:source`, `parseLine` → `null`; сервер при чтении пропускает её
  с предупреждением только с номером строки (как любую испорченную, D1 п. 4), страница её не показывает. Почему так, а
  не пометка «не из хуков»: правило чтения REQ-001 критерий 4 в редакции r1 (по `decisions/0011`) говорит (а) «строка
  с source не REAL и не ORCH — "не из хуков"», а строку `source ORCH` называет записью оркестратора, которая «не
  помечается "не из хуков"» и «не используется для задач и состояний». Строка с `hook_event_name` и ORCH не может быть
  ни тем, ни другим: под пометку «не из хуков» она по букве (а) не подпадает, а записью оркестратора (вид B) не является
  — её не пишет ни один путь (путь хука `source` не принимает вовсе, путь `/api/note` не принимает `hook_event_name`,
  критерий 6). Показать её событием без пометки — выдать за событие хука (R2); показать с пометкой — нарушить букву (а).
  Остаётся «испорченная строка» — она не попадает ни в задачи, ни в офис, ни в журнал страницы, ни в окна, правило (а)
  для остальных значений (`SIMULATION`, `""` и пр.) не меняется. Это изменение поведения REQ-001 (было: показ с
  пометкой), оно названо в п. 12 и проверяется **PG-22** (расширение, п. 12.1) и **SV-55** (такую строку записать
  нельзя).
- `isNoteLine(line) -> boolean` — истина ровно тогда, когда у строки источник равен `SOURCE_ORCH` **и** ключа
  `hook_event_name` у строки нет вовсе (ключ со значением любого вида, в том числе пустым, — уже не запись ORCH):

  | Вход (уже прочитанная строка) | Результат |
  |---|---|
  | источник `ORCH`, ключа `hook_event_name` нет | истина |
  | источник `ORCH`, ключ `hook_event_name` есть (любое значение) | ложь |
  | источник `REAL` (или другой), ключа `hook_event_name` нет | ложь |
  | источник `REAL`, ключ `hook_event_name` есть | ложь |
- `firstLine(text, max) -> string` — первая непустая строка (после `trim`), не длиннее `max` кодовых точек; длиннее —
  `max` точек и «…».

Причины отказа (`reason`) новые: `bad_value:prompt_kind`, `bad_value:prompt_text`, `bad_value:prompt_truncated`,
`not_allowed:<поле>` (поле вида A у другого события или поле вида B в виде A), `bad_value:note_text`,
`empty_note`, `bad_value:req_id`, `bad_value:request_time`, `bad_value:session_id`, `has_time` (у тела `/api/note`).

### 2.2 Тела запросов записи

- `POST /api/events` (хук): прежнее тело D1 п. 3.3 плюс `prompt_kind`, `prompt_text`, `prompt_truncated` по правилам
  вида A. `source` — по-прежнему `400 has_source`.
- `POST /api/note` (команда): JSON-объект, ключи только из `note_text` (обязательно), `req_id`, `request_time`,
  `session_id`. `time` и `source` в теле — `400` (`has_time`, `has_source`).

Размер: тело ≤ `BODY_MAX` (16 384 байт) на обоих путях — прежний предел, `413`. Запись ORCH укладывается всегда:
2 000 точек × 6 байт (худший случай `\uXXXX`) = 12 000 + ключи и `session_id` ≤ 200 × 6 = 1 200 → меньше 14 000.
Сообщение владельца может не уложиться — его подгоняет хук (п. 4, шаг 6).

### 2.3 Ответы сервера

| Путь | Успех | Тело успеха |
|---|---|---|
| `POST /api/events` | `204` (прежнее, D1 п. 5.2; критерий 4 r4) | нет |
| `POST /api/note` | `200 application/json` | `{"request_time": "<ISO>" \| null, "request_time_auto": true \| false}` — без текста записи |
| `GET /api/events` | `200`, прежняя форма D1 п. 3.4 | в `events` теперь есть строки вида B и поля `prompt_*` у вида A |

Отказы — `{"error":"<reason>"}`, тело запроса не повторяется (D1 п. 5.3). Новые `error`: `text_storage_off`,
`too_long_after_mask`, причины п. 2.1.

### 2.4 Окружение и постоянные (`config.js`)

## 3. Маскирование (`mask.js`, критерии 7 и 18)

Чистый модуль без Node API (импортируют хук, сервер, команда; страница — нет).

- `maskSecrets(text: string) -> string` — заменяет каждое совпадение правила меткой `MASK_LABEL`.
- `prepareText(raw: string, scanMax: number, limit: number) -> {text: string, truncated: boolean}` — порядок:
  1. взять первые `scanMax` единиц UTF-16 (не разрезая суррогатную пару: при разрезе последняя половина
     отбрасывается); если вход длиннее — `truncated = true` и **отбросить хвостовой отрезок без пробелов**, на котором
     пришёлся разрез (часть секрета на границе не остаётся);
  2. `maskSecrets`;
  3. обрезать до `limit` кодовых точек (после маскирования — значит, секрет на границе 4 000 уже заменён целиком);
     если обрезано — `truncated = true`;
  4. результат из одних пробельных знаков — `text = ""` (поле не пишется).

### 3.1 Правила (в этом порядке)

«Знак токена» — `[A-Za-z0-9_+=-]` (только для M10). «Буква или цифра» — `[A-Za-z0-9]`. «Отрезок-идентификатор» —
максимальный отрезок знаков `[A-Za-z0-9_-]`. «Кавычка» — один из знаков `'`, `"`, `` ` `` (типографские « » ‘ ’ “ ” —
не кавычки). «Конец строки» — знак `\n` или `\r`. Имена — без учёта регистра.

| # | Правило | Что заменяется |
|---|---|---|
| M1 | PEM: `-----BEGIN` … `-----END …-----`; без `-----END` — до конца текста | весь блок |
| M2 | заголовок `Authorization` + `:` или `=` + значение до конца строки | значение |
| M3 | `схема://пользователь:пароль@хост` (схема `[A-Za-z][A-Za-z0-9+.-]*`, пользователь и пароль без `/ @ пробела`) | `пользователь:пароль` |
| M4 | `sk-` + ≥ 16 знаков `[A-Za-z0-9_-]` (покрывает `sk-ant-`, `sk-proj-`); слева — начало текста или знак, который **не буква и не цифра** (`=`, `_`, `-`, `+`, `:`, кавычка, пробел — граница; r4, F2) | весь ключ |
| M5 | `ghp_`, `gho_`, `ghs_` + ≥ 20 `[A-Za-z0-9]`; `github_pat_` + ≥ 20 `[A-Za-z0-9_]`; слева — как у M4 | весь ключ |

M7 следует букве критерия 7 (решение ORCH по F4: не сужать, лишнее маскирование безопасно). Следствие, названное
прямо: маскируются и не-секреты из трёх частей через точку — имена файлов с двумя точками (`a.test.js`,
`pixel-office-page.test.js`, в том числе внутри пути), номера версий `22.21.1`, имена вида `www.example.org`. Четыре и
больше частей (`127.0.0.1`) и две части (`panels.js`, `REQ-008-history.md`) M7 не берёт, поэтому примеры критерия 7
(`docs/design/samples/history-view-sample-2026-10-05`, `tools/src/pixel-office/public/panels.js`, «REQ-008») не
портятся. Расхождение с общей фразой критерия «пути не портятся» для имён с двумя точками — вопрос ORCH (п. 13, I11).

**Значение в кавычках (M8, M9; r4, F1).**

- **В1. Открывает** — кавычка, которая стоит первым знаком значения: у M9 — после `=`/`:` и пробелов, у M8 — после
  пробелов за `Bearer`. Кавычка в любом другом месте значение не открывает.
- **В2. Закрывает** — первая **такая же** кавычка дальше в той же строке, не экранированная: знак `\` экранирует
  следующий знак, если тот не конец строки (`"a\"b"` — одно значение). Кавычка другого вида внутри — часть значения.
  Заменяется весь отрезок от открывающей кавычки до закрывающей включительно: `password="x y"` → `password=[скрыто]`.
- **В3. Нет закрывающей** в строке — заменяется отрезок от открывающей кавычки до конца строки (сам знак конца строки
  остаётся) или до конца текста. Следующая строка не затрагивается.
- **В4. Пустое значение** (закрывающая кавычка сразу за открывающей, `password=""`) — не заменяется: секрета нет.
  Непустое значение в кавычках заменяется всегда, даже если внутри уже метка (`password: "[скрыто]"` → `password: [скрыто]`):
  результат — метка без кавычек, его второе маскирование не меняет (п. 3.2).
- **В5. Граница слева** (M4–M6, M8; у M9 — край отрезка-идентификатора) проверяется по знаку **исходного текста**
  непосредственно перед совпадением; этот знак в заменяемое не входит и может быть последним знаком предыдущей
  замены (закрывающей кавычкой). Без этого `` Bearer `a`Bearer b `` маскируется за два прохода, а не за один, и
  повторяемость нарушается (проверено прототипом, п. 21).
- Значение **без кавычек** — как прежде: до пробела или кавычки; если оно пусто или начинается с метки — не заменяется.

**Почему это не противоречит критерию 7** («значение — до пробела или кавычки»). Эти слова задают, где **кончается**
значение без кавычек: кавычка после первого знака значения его завершает. Кавычка, стоящая **первым** знаком значения,
его не завершает — по букве значение было бы пустым и правило ничего бы не скрывало, а критерий требует скрывать
значение пары. Здесь она открывает значение, конец которого — такая же кавычка (В2) или конец строки (В3); внутри
кавычек допустимы пробелы. Ключ JSON в кавычках (`"password": "…"`) — та же пара `имя: значение` с кавычками вокруг
имени. Имя на конце идентификатора (`DB_PASSWORD=`) — пара для имени `password`. Лишнее маскирование — безопасная
сторона (принцип решения ORCH по F4, п. 3.1, M7). Блок REQ-008 в `docs/requirements.yaml` не меняется.

### 3.2 Правила, которые выполняются всегда

- **Повторяемость:** `maskSecrets(maskSecrets(x)) === maskSecrets(x)`. Значение, которое начинается с `[скрыто]`, ни
  одно правило не берёт (M2, M8, M9 проверяют это явно; в метке нет знаков токена, поэтому M4–M7, M10 её не задевают).
  Поэтому второе маскирование на сервере ничего не меняет в уже замаскированном хуком тексте и не удлиняет его.
  Для правил r4: значение в кавычках заменяется меткой **без кавычек** (В2, В3), поэтому после первого прохода у пары
  остаётся значение, начинающееся с метки, и второй проход его не берёт; метка начинается с `[` и кончается `]` — оба
  знака не буквы и не цифры, не знаки отрезка-идентификатора и не кавычки, поэтому замена не создаёт и не убирает
  границ для M4–M6, M8, M9 (а граница по В5 проверяется по исходному знаку, который вместе с меткой даёт тот же
  ответ). Проверка прототипом: 300 000 случайных входов из частей `password`, `DB_`, `Bearer `, `sk-`, `ghp_`,
  `AKIA`, кавычек, `\`, `=`, `:`, `_`, `-`, `/`, `.`, переносов строки и метки — 0 нарушений (п. 21).
- **Не портятся:** обычный текст, числа, пути (`docs/design/REQ-008-history.md`), номера требований («REQ-008»), хеши и
  строки короче 32 знаков, 40 строчных букв подряд, шестнадцатеричная строка из прописных букв и цифр. После правил
  r4 примеры критерия 7 «НЕ маскируются» проверены заново — строки N-1…N-5 таблицы п. 3.1 (результат равен входу);
  новые границы проверяют N-6, N-7 (буква перед `sk-` и `AKIA` по-прежнему не граница).
- **Линейность:** реализация — проходы по тексту без регулярных выражений с вложенными или соседними неограниченными
  повторами по одному и тому же классу знаков; M10 — один проход по отрезкам знаков токена (без поиска с возвратом). Для
  M1 без `-----END` — замена до конца и остановка (повторные `-----BEGIN` не перебираются). Время маскирования 64 КБ
  патологического текста ≤ 200 мс (HK-27).
  Правила r4: M9 — **один проход по отрезкам-идентификаторам** (у каждого отрезка — сравнение конца с семью именами
  постоянной длины, затем не более двух знаков `"`/`=`/`:` и пробелы за ним, затем значение); пробелы и значение
  поглощаются совпадением, следующий поиск идёт за ним, поэтому каждый знак просматривается ограниченное число раз.
  **Запрещено** выражать «конец идентификатора» регулярным выражением с повтором перед именем (вида «граница, затем
  повтор `[A-Za-z0-9_-]*`, затем `_`/`-`, затем имя»): каждый `_` — возможное начало, и на строке из `_` время
  квадратичное (проверено: 4 096 знаков — 23 мс, 16 384 — 354 мс, ×4 входа → ×15 времени; на 64 КБ — порядка
  секунд). Значение в кавычках — один просмотр до закрывающей кавычки или конца строки (В2, В3), просмотренное
  поглощается. M4–M6 — прежние выражения с другой левой границей: неудачная попытка просматривает не больше 15/19/16
  знаков, удачная поглощает просмотренное. Прототип: 14 враждебных входов по 64 КБ (`_`×, `a_`×, `_password`×,
  `password="`×, `"password"`×, `Bearer "`×, `\`×, `-sk-`×, короткие `-sk-`/`=ghp_`/`=AKIA`, `=`×, кавычка без
  закрытия) — худший 1,4 мс; ×16 входа → ≤ ×21 времени (п. 21).
- **Не бросает исключений** с текстом в сообщении; на не строку возвращает `""`.

### 3.3 Остаточный риск (называется в README и отчёте владельцу)

Не распознаются: секрет в произвольной форме с пробелами; секрет словами («пароль — имя кота и год»); секрет base64 со
знаком `/` или `.` (M10 их не берёт — только M1–M9); секрет из одних прописных букв и цифр; секрет короче 32 знаков без
имени из M9 и без префикса M4–M6. После r4 значение в кавычках после имени из M9 и после `Bearer` **маскируется**
(В1–В4) и в этот перечень больше не входит. Остаются (r4, названы прямо):

- имя из M9 слитно с другим словом, без `_` или `-` перед ним (`mypassword=…`), и имена вне перечня M9
  (`SECRET_ACCESS_KEY=…`, `PRIVATE_KEY=…`, `pwd=…`, `api-key: …`) — их значение берёт только M10 (≥ 32 знаков, без
  `/` и `.`);
- пробел **перед** `=` или `:` (`password = …`) и значение через пробел без знака (`--password …`);
- в значении без кавычек — часть после кавычки внутри (`password=ab"cd`: `cd` остаётся);
- значение в кавычках, продолженное на следующей строке, — скрывается только до конца первой строки (В3);
- типографские кавычки (« », “ ”) — не кавычки по В1.

HK-24 фиксирует эти случаи как известные непокрытые (тест утверждает, что они **не** маскируются, — чтобы изменение
правил было видно): прежние пять и новые `mypassword=primer42`, `password = primer42`, `SECRET_ACCESS_KEY=abcd/EFGH+ijkl`.

## 4. Хук (`hook.js`, `protocol.buildWriteBody`; критерии 1–3, 7, 8, 18)

`buildWriteBody(hookInput, nowIso, options = {storeText: boolean}) -> body | null` — прежние шаги D1 п. 6.3, затем у
`UserPromptSubmit`:

1. `prompt` не строка — новых полей нет (как сейчас).
2. Вид: если `prompt.trimStart()` начинается с одной из `SERVICE_MARKERS` — `"service"`, иначе `"owner"`.
   «сделай &lt;system-reminder&gt;» — `owner`.
3. `service` — только `prompt_kind`; из `prompt` ничего не копируется.
4. `owner`, хранение выключено — только `prompt_kind`.
5. `owner`, хранение включено — `prepareText(prompt, PROMPT_SCAN_MAX, PROMPT_MAX)`; непустой текст — `prompt_text`,
   при `truncated` — `prompt_truncated: true`.
6. **Предел тела.** Мера — длина тела в байтах UTF-8 после записи тела в JSON (той же записью, что уходит в запрос,
   с экранированием `\uXXXX`). Правило: тело длиннее `BODY_MAX` — `prompt_text` укорачивается с конца по кодовым точкам
   до **наибольшей** длины, при которой тело укладывается в `BODY_MAX` (способ поиска длины — на выбор разработчика,
   не дольше логарифма от длины текста шагов записи в JSON), и ставится `prompt_truncated: true`; тело уже в пределе —
   ничего не меняется. Текст уже замаскирован — укорачивание секрета не открывает.

   | Вход (после шагов 1–5) | Результат |
   |---|---|
   | тело ≤ `BODY_MAX` байт | без изменений; `prompt_truncated` — как после шага 5 |
   | тело > `BODY_MAX` (например, 4 000 эмодзи по 4 байта) | `prompt_text` — самый длинный начальный отрезок, при котором тело ≤ `BODY_MAX`; `prompt_truncated: true` |
   | тело > `BODY_MAX` из-за знаков, которые в JSON занимают 6 байт (`\uXXXX`) | то же: мерой служит записанное тело, а не число знаков |
   | укороченный текст состоит из одних пробельных знаков или пуст | `prompt_text` и `prompt_truncated` не пишутся (как шаг 4 `prepareText`), `prompt_kind` остаётся |
7. Итог проходит `checkLine(body, false)` (как сейчас): хук не шлёт того, что отверг бы сервер.

`hook.js`: читает `storeTextEnabled(process.env)`; запрос `post(...)` идёт со **своим** `new http.Agent({keepAlive:
false})` (F6) — переменные прокси не уводят тело с `127.0.0.1`. Остальное без изменений: тихий выход с кодом 0,
`HOOK_HTTP_MS`, `HOOK_HARD_EXIT_MS`, текст сообщения нигде, кроме тела запроса, не появляется (ни stdout, ни stderr, ни
файлы). Вход больше `HOOK_INPUT_MAX` (8 MiB) — как сейчас, событие теряется (HK-11j).

Тело, годное для `/api/note`, здесь даёт `400` (`unknown_key:note_text` / `missing:hook_event_name`).

`POST /api/note`, каждая проверка — отказ без записи:

1. Host → `403` (до чтения тела, D1 п. 5.1).
2. Метод не `POST` → `405 Allow: POST`.
3. Размер > `BODY_MAX` → `413` (тот же механизм `answerTooLarge`).
4. Подпись (`verifySignature`, тот же секрет, тот же заголовок) → `401`.
5. Не JSON-объект → `400 not_json`.
6. `validateNoteBody(value, nowMs) -> {ok, fields} | {ok:false, reason}`: `source` → `has_source`; `time` → `has_time`;
   ключ вне четырёх → `unknown_key:<имя>` (имя по прежнему правилу `safeKeyName`); `note_text` не строка или длиннее
   `NOTE_MAX` → `bad_value:note_text`; `""` или только пробелы → `empty_note`; `req_id` не по `REQ_ID_PATTERN` →
   `bad_value:req_id`; `request_time` не канонное время или позже часов больше чем на `WRITE_SKEW_MS` (60 с) →
   `bad_value:request_time`; `session_id` не строка, пустой или длиннее `NOTE_SESSION_MAX` → `bad_value:session_id`.
7. Хранение выключено → `400 text_storage_off`.
8. `maskSecrets(note_text)`; длиннее `NOTE_MAX` → `400 too_long_after_mask` (без обрезки: у записи ORCH нет поля
   «обрезано»; команда этот случай не допускает сама, п. 6).
9. **Привязка и запись — одна синхронная последовательность без `await`** (защита в той же операции, что действие):
   если `request_time` дан — он и пишется, `request_time_auto` нет; иначе `journal.lastOwnerPrompt(session_id ?? null)`
   и, если найдено, `request_time = найденное.time`, `request_time_auto = true`; не найдено — ни того, ни другого.
   **Основной путь — без `session_id`** (так вызывает ORCH, критерий 16): поиск по всему журналу, любая сессия;
   `session_id` в теле — необязательное сужение поиска (для ручного вызова), его отсутствие не ошибка и привязку не
   отключает. Строка
   `{time: new Date(now()).toISOString(), source: "ORCH", session_id?, note_text, req_id?, request_time?,
   request_time_auto?}` → `journal.append`. Все записи журнала делает один процесс сервера синхронно, поэтому между
   поиском и дописыванием другая строка вклиниться не может.
10. `200` с телом п. 2.3. `JournalReadError` при поиске → `500 read_failed`, ничего не записано; `JournalWriteError` →
    `500 write_failed` (как D1 п. 5.3, шаг 6).

### 5.3 `journal.lastOwnerPrompt(sessionId: string | null) -> {time, session_id} | null`

Последняя по порядку в файле (не по `time`) строка вида A: `hook_event_name = "UserPromptSubmit"`, `source = "REAL"`,
`prompt_kind = "owner"`, и только при `sessionId !== null` — тот же `session_id` (при `null` сессия не сравнивается).
Риск без сессии, принятый требованием (критерий 15): при двух параллельных сессиях запись может привязаться к
сообщению другой сессии; README называет его (п. 9). Читает с конца пачками по 512 строк через прежний
индекс смещений (`read(from, limit)`), останавливается на первой подходящей; испорченные строки пропускаются (как
`read`). Строки без `prompt_kind` (журнал до этой работы) не подходят. Сложность — O(строк после найденной).

### 5.4 Что сервер не делает

Не повторяет тело и текст ни в ответе, ни в stderr (предупреждения журнала — только номер строки, как сейчас); не
делает исходящих запросов; не создаёт новых файлов (`STATE_FILES` прежние); не выводит `request_time` из текста.

## 7. Модель страницы и окно (часть (б); критерии 9–13)

### 7.1 Где страница берёт данные

Тот же `GET /api/events?after=<n>` (D1 п. 4.6): строки вида B и поля `prompt_*` приходят в `events`; `parseLine`
(п. 2.1) пропускает их в массив `entries`. Нового пути, нового запроса и внешних адресов нет. Пределов сверх прежних
нет (окно строится из уже загруженных строк).

`model.js` (расширение, без изменения прежних правил): `isLine` по-прежнему требует `hook_event_name`, поэтому вид B
не входит ни в правило чтения, ни в задачи, ни в офис (F3). Добавляются поля: строка журнала (`journalRow`) —
`prompt_kind: "owner" | "service" | null`; строка основной сессии (`mainRows`) — то же `prompt_kind`. Ни одно прежнее
поле и правило (D1 п. 4.1–4.3) не меняется.

### 7.2 `history.js`

`buildHistory(model) -> {requests: Request[], byKey: Map<string, Request>, windowOfTask: Map<taskKey, requestKey>,
windowOfMainRow: Map<mainKey, requestKey>}` — чистая функция, без DOM.

`Request`:

| Поле | Значение |
|---|---|
| `key` | `"req:<индекс строки сообщения>"` |
| `index`, `session_id`, `time` | строка сообщения |
| `text` | `prompt_text` или `null` (хранение выключено) |
| `truncated` | `prompt_truncated === true` |
| `title` | п. 7.3 |
| `state` | `"in_progress" \| "completed" \| "unrecorded"` |
| `started_at` | `time` сообщения |
| `finished_at` | время последнего `Stop` основной сессии в окне или `null` |
| `note` | последняя запись ORCH запроса или `null`: `{time, text, req_id \| null, auto: boolean, index}` |
| `notes` | все записи ORCH запроса, по порядку |
| `tasks` | `[{ordinal, key, role, description \| null, state, started_at, ended_at, session_last_event_at}]` |
| `timeline` | `[{time, index, who, what, detail \| null, kind: "event" \| "note", auto?}]` |

### 7.3 Правила сопоставления

1. **Сообщение владельца** — доверенная (`marks[i] === null`) строка `UserPromptSubmit` с `prompt_kind = "owner"`.
   Строки `service` и строки без `prompt_kind` (журнал до этой работы) окон не открывают и границ не ставят.
2. **Окно** сообщения `i` сессии `S` — индексы `(i, j)`, где `j` — индекс следующего сообщения владельца сессии `S`
   (или конец журнала). Сообщения других сессий границ не ставят. Строки до первого сообщения сессии — ни в каком окне.
3. **Задачи окна** — задачи модели, у которых строка первого старта (`first_start_index`) в `(i, j)` и её `session_id
   = S`. `ordinal` — 1, 2, … по `first_start_index`. Поля `role`, `description`, `state`, `started_at`, `ended_at`,
   `session_last_event_at` — из задачи модели как есть (правила D1 п. 4.2); `description = null` — показывается «—».
4. **Статус** — `state` последней строки основной сессии (`mainRows`), начатой в `[i, j)` (служебное сообщение внутри
   окна начинает свою строку основной сессии — она последняя); `finished_at` — `time` последней доверенной строки
   `Stop` сессии `S` без `agent_id` в `(i, j)`, иначе `null`.
5. **Записи ORCH** — строки вида B с `request_time`. Кандидаты — сообщения владельца с `time === request_time`. Один
   кандидат — он (даже если `session_id` записи другой: критерий 11, время решает). Несколько — тот, чей `session_id`
   равен `session_id` записи, если такой ровно один; иначе запись ни к чему не относится. Без `request_time` — ни к
   чему не относится. **Последняя** — наибольшее `Date.parse(time)`, при равенстве — бо́льший индекс; более ранние —
   только в хронологии.
6. **Заголовок** — `note.req_id` есть: `"<req_id> — " + firstLine(note.text, 120)`; иначе `text` есть:
   `firstLine(text, 120)`; иначе `HISTORY_TITLE_NO_TEXT` со временем.
7. **Хронология** — строка сообщения, все доверенные строки сессии `S` в `(i, j)` и записи ORCH запроса; порядок —
   `Date.parse(time)`, при равенстве — индекс (запись ORCH — после строки с тем же временем). `who`: основная сессия —
   `MAIN_LABEL`, событие субагента — роль (`ROLE_UNKNOWN`, если пусто), `PostToolUse` — роль вызвавшего или
   `MAIN_LABEL`, запись ORCH — `HISTORY_WHO_ORCH`. `what`: слова таблицы `EVENT_TABLE` по случаю события (`eventWords(eventCase(…))`, REQ-045), служебное
   `UserPromptSubmit` — слова случая 4, запись ORCH — `HISTORY_NOTE_BY` (без изменений). **Устарело после REQ-036/044/045 (прогон `REQ044-20261014-01`, правка DOC-UPDATER 2026-10-14): см. `docs/design/REQ-036-044-045-interactive.md`, п. 3.5.** (Прежде: `EVENT_LABELS[вид]`,
   служебное — `HISTORY_SERVICE`.) `detail`: описание у `PostToolUse` и у старта задачи с
   описанием, `note_text` у записи ORCH, иначе `null` (у сообщения — `null`: текст в «Исходном запросе»).
8. **Открытие** (ответ на вопрос I1 описания): строка журнала `UserPromptSubmit` owner → своё окно; кнопка «открыть
   историю запроса» карточки задачи панели «Задачи» → `windowOfTask`; та же кнопка карточки строки основной сессии →
   `windowOfMainRow` (окно, в которое попал её `start_index`). Нет окна — кнопки и строки «открыть историю запроса» нет.
   Из карточки агента (REQ-007 п. 7) окно **не открывается** (N2, решение ORCH).
9. Ни одна запись ORCH не меняет `tasks`, `mainRows`, `marks`, `sessions` и состояние офиса (они строятся без вида B).

### 7.4 Пределы (вопрос I2 описания)

Числа строк хронологии и таблицы не ограничиваются: окно строится из уже загруженного журнала, тело окна листается.

## 10. Пункт роли ORCH (критерий 16)

В `.claude/agents/orchestrator.md`, раздел «### Запускать агентов», после пункта о Pixel Office — пункт (текст для
BACKEND-DEV, дословно):

> - На каждое сообщение владельца, с которого начинается работа, ORCH до раздачи агентам записывает, как он понял
>   сообщение, одной командой: `cd tools && npm run pixel-office-note -- --text "<как понял>" --req REQ-NNN`
>   (`--req` — только когда номер требования известен). Ключ сессии и время запроса ORCH не передаёт: своей сессии
>   он не видит, и сервер сам привязывает запись к последнему сообщению владельца в журнале (в окне — «привязано
>   автоматически»). В запись не вписываются секреты и персональные данные из сообщения. Если сервер не запущен,
>   команда не удалась или хранение текста отключено, ORCH запись не придумывает и называет это в отчёте владельцу.
>   Ничего сверх `decisions/0011` эта запись не хранит.

Требования к тексту для BACKEND-DEV — их проверяют выражения критерия 16 r4 **буквально** (DC-02, F3):

| # | Проверка критерия 16 | Ожидание |
|---|---|---|
| G1 | `grep -nE "pixel-office-note" .claude/agents/orchestrator.md` | не пусто |
| G2 | `grep -nE "до раздачи\|до запуска агентов" .claude/agents/orchestrator.md` | не пусто |
| G3 | ``grep -nE 'pixel-office-note[^`]*--text' .claude/agents/orchestrator.md`` | не пусто |
| G4 | ``grep -oE 'pixel-office-note[^`]*' .claude/agents/orchestrator.md \| grep -c -e '--session'`` | `0` (код выхода `grep -c` — 1) |

Отсюда: команда записана в обратных кавычках и **в одной строке** файла, от `pixel-office-note` до `--text` нет
обратной кавычки и переноса (иначе G3 пуст); внутри обратных кавычек любой команды с `pixel-office-note` в файле роли нет
`--session` — G4 смотрит только текст от `pixel-office-note` до закрывающей обратной кавычки или конца строки, поэтому
пояснение **после** закрывающей кавычки в той же строке (например «`--session` не передаётся» в своих кавычках или без
них) проверку не ломает, а `--session` внутри кавычек команды — ломает. Пункт выше пишет «Ключ сессии» словами — G4
даёт 0 и так. Обратная проверка: команда без обратных кавычек в строке, где после неё стоит «--session не передаётся»,
дала бы 1 — поэтому команда стоит именно в кавычках. `npm run check` файл роли не переформатирует (`format:check` —
`prettier` по каталогу `tools/`, проверено по `tools/package.json`).
