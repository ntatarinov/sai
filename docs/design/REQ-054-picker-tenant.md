## 0. Кратко

1. **Один проход проверки** (п. 7.4): байты файла → UTF-8 → строгий читатель JSON (свой, п. D2) → чистая функция
   `validateTenant(объект) → список ошибок` → упорядочивание по месту в файле → не больше 100 строк. Код модуля — `tools/src/picker/`,
   11 файлов (п. 3); десять из них не импортируют ничего из `node:*` (чистое ядро и вход), с диском и путями работает только `load.js`.
2. **Строка ошибки** — «`<имя файла>: <место>: <код>: <текст>`»; на одно место — не больше одной ошибки (D4); порядок строк — по
   месту в файле (D5); тексты на «вы», каждый не длиннее 18 слов, без английских слов разборщика, без слов «ты…» даже в цитате
   (D8). Тексты (п. 6) — часть контракта: на них опирается REQ-060.
3. **Команда** `npm run picker -- check <файл>` — диспетчер команд (`cli.js`, сейчас одна команда `check`). Коды: 0 — в порядке
   (одна строка), 1 — найдены ошибки (stdout), 2 — неверный вызов или файл нельзя прочитать (одна строка в stderr). Файл только
   читается: ни записи, ни временных файлов (п. 7, 8).
4. **Загрузка файла** (`load.js`): не ссылка, обычный файл, не больше 512 КБ, чтение без блокировки на каналах; режим
   `baseDir` для сервера (REQ-056): путь внутри папки и без ссылок на пути (D9).
5. **Данные для стенда**: два вымышленных арендатора и по три набора ответов (п. 9) — скелет с id, типами, условиями и баллами
   зафиксирован здесь (на нём REQ-055 получит исходы «явный лидер», «близкие варианты», «ничего не подошло»; расчёт сделан
   прототипом); тексты для посетителя пишет разработчик в рамках правила E_TEXT.
6. **Тесты** (пишет TEST-DESIGNER после кода): `picker-config.test.js` (критерии 1–8, идентификаторы PK-1…PK-8), три файла
   свойств и общий `picker-helpers.js`; 44 файла-образца в `tools/test/fixtures/picker/` (п. 10).
7. **Подшаги** 2a–2e (п. 11). Прототип на копии метки вне проекта: на каждом подшаге существующие 1622 теста — **0** красных
   (`# tests 1622 # pass 1622 # fail 0`). Красными становятся только ловушки п. 13.1: скрипт не на своём месте — HO-54; слово
   `child_process` (даже в комментарии) — TR-4c; неверный `.json`-файл-образец — `format:check`.
8. **Мутанты**: 25 мутантов прототипа убиты набором образцов п. 10 (п. 13.2): образцы подобраны так, что каждая граница,
   порядок и особый случай меняют вывод.
9. **Открытые вопросы ORCH** — О1–О6 (п. 16); предложение записи `decisions/0066` — п. 16.2.

## 2. Решения проекта

| № | Вопрос | Решение | Почему |
|---|---|---|---|
| D1 | Состав модуля | 11 файлов `tools/src/picker/` (п. 3). Десять не импортируют `node:*`: `limits.js`, `utf8.js`, `json.js`, `text-rules.js`, `places.js`, `conditions.js`, `validate.js`, `report.js`, `check.js`, `cli.js`. Диск и `node:path` — только `load.js`. Зависимости: `cli → check → (load, json, utf8, validate, report) ; validate → (conditions, text-rules, places, limits)`; циклов нет | Ядро проверяется на любом компьютере (как движок REQ-055); все вызовы `fs` — через объект `fs` по умолчанию (`fs.lstatSync(…)`), чтобы `test/fault-inject.js` мог их ломать |
| D2 | Разбор JSON | Свой строгий читатель `parseJson` (п. 5.3), а не `JSON.parse` | Нужны: позиция ошибки «строка, знак» на русском (Ф6); отказ на повтор ключа (Ф7: иначе правило с дублем `points` молча теряет значение); места всех значений для упорядочивания (D5); объекты без прототипа; предел глубины. Совпадение с `JSON.parse` проверено (Ф17) и закрепляется тестом PK-P1 |
| D3 | Чистое ядро | `validateTenant(doc, {fileName}) → Issue[]` не меняет вход, не бросает исключений ни на каком значении, полученном из JSON, не читает часы, среду и диск | Q10; повторяемость; прототип — Ф19 |
| D4 | Сколько ошибок на место | **Не больше одной.** Порядок проверок одного места: тип (E_FIELD) → шаблон (E_ID) → границы (E_LIMIT) → повтор (E_DUP) → ссылка (E_REF, E_ORDER) → правило текста (E_TEXT); побеждает первая сработавшая | Одно место — одно исправление; иначе тесты «по файлу на случай» получают лишние строки. Следствие: слишком длинный текст показывает E_LIMIT, а E_TEXT — после исправления длины (образцы E_TEXT делают из коротких слов, п. 10) |
| D5 | Порядок строк | По месту в файле: смещение начала ключа члена объекта (или начала элемента списка) в тексте; пропавшее поле и ошибка корня — смещение родителя; равные места — порядок обнаружения (стабильно) | Требует «в порядке мест в файле»; порядок обхода схемы ему не равен (E_UNREACHABLE находится последним, а стоит у `solutions`) — образец `e-sort-order` |
| D6 | Какой код у случаев, которых список не называет | Таблица в п. 4.12: значение не из допустимых (`schema`, `type`, элемент `contact_fields`) — E_FIELD; длина и состав id — E_ID; повтор в `contact_fields` — E_DUP; `min >= max` вопроса и `min > max` условия — E_LIMIT; пустой после обрезки текст — E_LIMIT; несколько видов условия или ни одного — E_COND; повтор ключа JSON, не UTF-8, глубина > 20 — E_JSON | Кодов ровно десять (требование); новых не вводится |
| D7 | Что сверх описания добавляет проект | (а) предел файла 512 КБ (код 2); (б) BOM допускается и не считается; (в) все четыре поля `result` и все шесть полей `leads` обязательны (у `leads` — если сам блок есть); (г) `needs_from_you` и `not_suitable_when` обязательны, могут быть `[]`; (д) пункты этих списков и `next_steps` — 1–150 знаков, как у `includes`; (е) `--help`; (ж) граница условия: `min > max` — E_LIMIT, `any_of`/`none_of` — 1–8 id | Каждый пункт — буквальное чтение или защита от «молча принято» (п. 16, О1, О2, О5); принять или отклонить — ORCH |
| D8 | Тексты ошибок | Каждый — не длиннее 18 слов целиком (слова — по правилу E_TEXT), на «вы», без слов `Unexpected`, `token`, `undefined`, `null`, `NaN`, без стека. Подставляемое значение проходит `show()` (п. 5.5): пробелы и управляющие знаки → `_`, не больше 40 знаков, слова «ты…» заменяются на `(скрыто)` | Критерий 4; чужой id не должен ломать правило «без слов ты…» |
| D9 | Чтение файла | `lstat` до открытия (ссылка, папка, не обычный файл — отказ до `open`, канал не блокирует); `open` с `O_RDONLY\|O_NOFOLLOW\|O_NONBLOCK`; `fstat` по дескриптору; чтение не больше 512 КБ + 1 байт. Режим `baseDir`: путь лексически внутри папки (после `path.resolve`), ни одного звена ниже папки — ссылка | Q8/Q10; гонка между `lstat` и `open` закрыта флагом `O_NOFOLLOW`; предки самой папки не проверяются (в macOS `/var` — ссылка) |
| D10 | Команды | `cli.js` держит `Map` «имя → обработчик»; сегодня одна запись `check`; `--help` печатает справку (код 0); любое другое — код 2. REQ-056/059/060 добавят свои записи, не меняя `check` | Одна точка входа `npm run picker` для всех частей сайта (решение 0065, п. 1) |
| D11 | Потоки | Код 0 и код 1 — в stdout; код 2 — в stderr в виде `picker: <текст>`; каждая строка заканчивается `\n`; ошибка программы (не из ОС) не перехватывается, как в других командах Sai | Как `handoffs-check`; тест считает потоки |
| D12 | Образцы-файлы | Образцы, которые не разбираются как JSON или не в UTF-8, имеют расширение `.txt`; остальные — `.json`, форматированные prettier (`npx prettier --write`) | Ф11, Ф12; REQ-060 берёт строки примера из вывода `check` на этих файлах |
| D13 | Демо-арендаторы | Скелет (id, порядок, типы, границы, условия, баллы, настройки) — контракт п. 9; тексты пишет разработчик | Исходы REQ-055 получены на этом скелете (Ф16) |
| D14 | Генератор случайного | В `tools/src/picker/` нет `Math.random`; тесты берут свой генератор с закреплённым зерном | Критерий 7; повторяемость |
| D15 | Время, среда, сеть | Модуль не читает часы, `process.env`, не открывает сокеты и не запускает процессы | Критерий 7; решение 0065 |
| D16 | Зависимости | Нет новых (ни рабочих, ни разработческих); `package.json` меняется одной строкой в `scripts` | Решение 0002; критерий 7 |

## 4. Файл арендатора

Один файл — один арендатор. Имя файла — `<id>.json`. Кодировка — UTF-8 (BOM допускается и не считается). Корень — объект.

### 4.1. Общие правила (применяются ко всем полям; номера — для ссылок)

| № | Правило |
|---|---|
| Р1 | **Типы.** «Строка» — строка JSON. «Целое» — число JSON, для которого `Number.isSafeInteger` истинно (2,5, `1e400` и числа за пределами ±(2^53−1) — не целые). «Список», «объект» — массив и объект JSON (не `null`). Не тот тип → E_FIELD, текст «Ожидается строка/целое число/значение true или false/список/объект. Исправьте значение.» |
| Р2 | **Лишнее и пропавшее.** Поле, которого нет в таблице объекта, → E_FIELD «Лишнее поле X. Удалите его.», место — путь лишнего поля. Обязательное поле, которого нет, → E_FIELD «Нет поля X. Добавьте его.», место — путь пропавшего поля. Разбор имён — `Object.hasOwn`; `__proto__`, `constructor` — обычные чужие поля |
| Р3 | **Длина строки** — число знаков (кодовых точек Unicode) после обрезки пробелов по краям; границы включительно; пустая после обрезки — длина 0 → E_LIMIT «Знаков: N, допустимо от A до B. Исправьте текст.» |
| Р4 | **Размер списка** — границы включительно → E_LIMIT «Элементов: N, допустимо от A до B. Исправьте список.», место — сам список; элементы всё равно проверяются |
| Р5 | **Число с границами** → E_LIMIT «Число N вне границ от A до B. Исправьте значение.» (у границы «от 1» без верхней — «Число N вне границ: не меньше 1. Исправьте значение.») |
| Р6 | **Идентификаторы.** *Идентификатор арендатора*: 3–32 знака из `a–z`, `0–9`, `-`; первый и последний знак — не дефис. *Внутренний идентификатор* (вопроса, варианта, решения, правила, гипотезы): 1–40 знаков из тех же; дефис в начале и конце допустим. Не по шаблону (в том числе длиной) → E_ID |
| Р7 | **Повторы** — среди вопросов, среди вариантов одного вопроса, среди решений, среди правил, среди гипотез (вариант с тем же id у другого вопроса — не повтор; id вопроса и id решения — разные области). Ошибка стоит у **второго** (и следующих) → E_DUP «Идентификатор X уже есть в P. Выберите другой.» (P — путь первого) |
| Р8 | **Поиск по id** — по первому появлению; в таблицу попадает любой id-строка, в том числе не прошедшая Р6 (чтобы исправление Р6 не открывало новых ссылок-ошибок) |
| Р9 | **Тексты для посетителя** (в таблицах — «Т»): к строке применяется правило E_TEXT (п. 4.11). Проверка идёт только если строка прошла Р1 и Р3 (D4) |
| Р10 | **Одна ошибка на место** и порядок проверок — D4; порядок строк в выводе — D5 |

### 4.2. Верхний уровень

| Поле | Обязательно | Тип | Границы и правила | Нарушение |
|---|---|---|---|---|
| `schema` | да | строка | ровно `sai-picker-tenant/1` | не строка → E_FIELD; другое значение → E_FIELD «Допустимо только: sai-picker-tenant/1. Исправьте значение.» |
| `id` | да | строка | идентификатор арендатора (Р6); `<id>.json` равно имени файла | не по шаблону → E_ID; имя файла другое → E_ID «Имя файла должно быть X.json. Переименуйте файл или исправьте id.» (проверка имени — только если шаблон выполнен) |
| `name` | да | строка Т | 1–60 знаков | E_FIELD / E_LIMIT / E_TEXT |

| `solutions` | да | список | 1–20 | то же |

### 4.3. Вопрос (`questions[i]`)

| Поле | Обязательно | Тип | Границы и правила |
|---|---|---|---|
| `id` | да | строка | внутренний идентификатор (Р6), уникален среди вопросов (Р7) |
| `title` | да | строка Т | 1–200 |
| `help` | нет | строка Т | 1–300 (пустой `help` — E_LIMIT: уберите поле) |
| `type` | да | строка | `single`, `multiple` или `number`; другое → E_FIELD «Допустимо только: single, multiple, number. Исправьте значение.» |
| `required` | да | true/false | — |
| `options` | у `single`, `multiple` | список | 2–8 вариантов (п. 4.4); у `number` — лишнее поле |
| `min`, `max` | у `number` | целые | оба обязательны; `min` строго меньше `max`, иначе E_LIMIT «Число min должно быть меньше max. Исправьте границы.» (место — `max`); у `single`, `multiple` — лишние поля |
| `unit` | нет | строка Т | 1–20, только у `number`; у остальных — лишнее поле |
| `show_if` | нет | список условий | 0–3 (п. 4.5), условие на вопрос не ниже этого — E_ORDER |

Пока `type` не прошёл проверку (нет, не строка, не из трёх), `options`, `min`, `max`, `unit` не называются лишними и не называются
пропавшими: проверяется только их форма. Условия, ссылающиеся на такой вопрос, проверяются по ссылке и порядку (п. 4.6, У5) и по форме вида (У7); соответствие вида типу (У6) и варианты (У8) не проверяются.

### 4.4. Вариант (`questions[i].options[j]`)

`id` — внутренний идентификатор, уникален внутри вопроса; `label` — строка Т, 1–100. Других полей нет.

### 4.5. Условие (в `show_if`, `when` правил и гипотез)

Объект ровно одного из трёх видов; ключ `question` обязателен в каждом.

| Вид | Поля | Верно, если |
|---|---|---|
| `any_of` | `question`, `any_of`: список id вариантов, 1–8 | среди выбранных есть хотя бы один из списка (только у `single`, `multiple`) |
| `none_of` | `question`, `none_of`: то же | вопрос отвечен и ни один из списка не выбран (только у `single`, `multiple`) |
| диапазон | `question`, `min` и/или `max`: целые, хотя бы одно | ответ в границах включительно (только у `number`); при обоих `min` не больше `max`, иначе E_LIMIT «Граница min больше max. Условие никогда не сработает.» (место — `max`) |

Условие, ссылающееся на неотвеченный или скрытый вопрос, неверно — так считает движок (REQ-055); проверка файла этого не вычисляет.

### 4.6. Проверка условия — шаги У1–У8 (порядок обязателен; `ownIndex` — номер вопроса для `show_if`, для `when` — нет)

| Шаг | Что проверяется | Ошибка и место |
|---|---|---|
| У1 | условие — объект; иначе | E_FIELD «Ожидается объект…» — место условия; остальные шаги пропущены |
| У2 | ключи вне `question`, `any_of`, `none_of`, `min`, `max` | E_FIELD «Лишнее поле…» — место ключа |
| У3 | `question` есть и строка | E_FIELD «Нет поля question…» / «Ожидается строка…» — место `….question` |
| У4 | видов ровно один: сколько из {`any_of`, `none_of`, (`min` или `max`)} присутствует; не один → E_COND «Условие должно быть одного вида: any_of, none_of или min и max.» — место условия; ссылку (У5) это не отменяет, шаги У6–У8 пропущены | E_COND |
| У5 | вопрос найден (Р8): нет → E_REF «Вопрос X не найден. Укажите id вопроса из списка questions.» (место `….question`), дальше только форма вида (У7). Для `show_if`: номер найденного вопроса не меньше `ownIndex` → E_ORDER «Вопрос X стоит не выше этого. Ссылайтесь только на вопросы выше.» (место `….question`), остальные шаги этого условия пропущены | E_REF, E_ORDER |
| У6 | вид подходит типу вопроса (если тип известен): `any_of`, `none_of` у `number` и `min`/`max` у `single`/`multiple` не подходят → E_COND «Условие K не подходит вопросу типа T. Используйте min и max.» (у `number`) / «…Используйте any_of или none_of.» (у остальных); K — первый присутствующий ключ вида (для вида min/max первым считается `min`, затем `max`, а не порядок в файле; уточнено 2026-10-19, DOC-UPDATER, шаг 10, замечание N5 ворот `step-01c`), место — этот ключ; остальные шаги пропущены | E_COND |
| У7 | форма вида: `any_of`/`none_of` — список (Р1), размер 1–8 (Р4), элементы — строки (Р1); `min`/`max` — целые (Р1), `min` не больше `max` | E_FIELD, E_LIMIT |
| У8 | варианты найдены (только если вопрос найден и его тип `single` или `multiple`): нет в `options` этого вопроса → E_REF «Вариант X у вопроса Q не найден. Укажите id варианта этого вопроса.» — место элемента списка | E_REF |

**Цикл.** Условие показа может ссылаться только на вопрос, стоящий в списке раньше. Если вопросы A (номер 0) и B (номер 1) ссылаются
друг на друга, ошибкой является только условие A на B (смотрит вперёд): E_ORDER одна, условие B на A верно (О3, п. 16).

### 4.8. Правило и гипотеза

Правило (`rules[i]`): `id` (внутренний, уникален среди правил); `when` (список условий, 1–3, все должны быть верны; без условий — E_LIMIT);

10. Исправьте значение.»); `text` (строка Т, 1–200).
Гипотеза (`hypotheses[i]`): `id` (внутренний, уникален среди гипотез); `title` (Т, 1–100); `explanation` (Т, 1–300); `when` (1–3 условия).

### 4.11. Правило понятности (E_TEXT)

Применяется к каждой строке Т: `name`, `intro`, `title` и `help` вопроса, `unit`, `label`, все тексты решений (`name`, `summary`, пункты
четырёх списков, `price_text`, `duration_text`), `text` правила, `title` и `explanation` гипотезы, `no_match_text`, `operator_name`,
`consent_text`, `privacy_contact`.

* **Фраза** — текст до знака «.», «!», «?» или «…», за которым пробельный знак или конец текста (точка внутри «1.5» не разрезает).
  Остаток после последнего знака — тоже фраза. **Слово** — часть между пробельными знаками, в которой есть буква или цифра («—» не слово).
* Фраза длиннее 18 слов → E_TEXT «Фраза длиннее 18 слов (в ней N). Разбейте её точкой.»
* Слова `ты`, `тебя`, `тебе`, `тобой`, `твой`, `твоя`, `твоё`, `твои` целиком (границы — не буква и не цифра), без учёта регистра →
  E_TEXT «Обращение не на «вы». Перепишите текст в форме «вы».» (слово в тексте ошибки не повторяется). При обоих нарушениях в одном
  месте называется второе правило (обращение).
* Подстрока в другом слове («цветы», «тыква») нарушением не является.

| Случай | Код | Место |

| id не по шаблону, в том числе слишком длинный или пустой | E_ID | поле `id` |
| имя файла не `<id>.json` (в том числе расширение другое) | E_ID | `id` |
| повтор значения в `contact_fields` | E_DUP | второй элемент |
| `min >= max` вопроса; `min > max` условия; пустой `when`; пустой после обрезки текст | E_LIMIT | `max` / `max` / `when` / поле |
| ни одного вида в условии или два вида | E_COND | условие |
| повтор ключа в JSON; файл не в UTF-8; вложенность глубже 20 | E_JSON | «строка L, знак C» |

## 5. Формы данных и функции по файлам

Все пути — от `tools/src/picker/`. Модули ES (`"type": "module"`). Экспорты ниже — контракт; внутренние помощники называет разработчик.
«Место» — путь поля: список сегментов (строка — ключ, число — номер элемента); пустой список — весь файл.

### 5.1. `limits.js`

Заморожённые экспорты: `FORMAT_ID` = `"sai-picker-tenant/1"`; `MAX_FILE_BYTES` = 524288; `MAX_DEPTH` = 20; `MAX_LINES` = 100;
`MAX_WORDS` = 18; `SHOWN_CHARS` = 40; `ERROR_CODES` = `["E_JSON","E_FIELD","E_ID","E_DUP","E_LIMIT","E_REF","E_ORDER","E_COND","E_UNREACHABLE","E_TEXT"]`
(ровно десять, в этом порядке); `SECOND_PERSON_WORDS` = `["ты","тебя","тебе","тобой","твой","твоя","твоё","твои"]`; `QUESTION_TYPES` =
`["single","multiple","number"]`; `CONTACT_FIELDS` = `["phone","email"]`. Границы полей (п. 4) — локальные константы `validate.js`.

### 5.2. `utf8.js`

`firstInvalidUtf8(bytes: Uint8Array) → number` — индекс первого байта, на котором последовательность перестаёт быть правильным UTF-8,
или −1. Правильность — по таблице Unicode «Well-Formed UTF-8 Byte Sequences»: `00–7F`; `C2–DF 80–BF`; `E0 A0–BF 80–BF`; `E1–EC 80–BF 80–BF`;
`ED 80–9F 80–BF`; `EE–EF 80–BF 80–BF`; `F0 90–BF 80–BF 80–BF`; `F1–F3 80–BF 80–BF 80–BF`; `F4 80–8F 80–BF 80–BF`. Лишний продолжающий байт,
`C0`, `C1`, `F5–FF`, суррогаты `ED A0–BF`, обрывок на конце — плохие; индекс указывает на ведущий байт. Результат совпадает с `TextDecoder("utf-8",{fatal:true})`
по «принимает/отвергает» (Ф18). Контрольные вызовы: `7b ff 7d` → 1; `e2 82` → 0; `ed a0 80` → 0; `c0 80` → 0; байты строки «я😀» → −1.

### 5.3. `json.js`

* `parseJson(text: string) → ParseOk | ParseFail`.
  * `ParseOk` = `{ ok: true, value, positions }`; `positions` — `Map<string, number>`: ключ `positionKey(path)`, значение — смещение в тексте (единицы
    UTF-16): у члена объекта — начало его ключа (открывающая кавычка), у элемента списка — начало значения, у корня — начало значения.
  * `ParseFail` = `{ ok: false, kind, offset, line, column, key? }`; `kind`: `end` (текст кончился раньше, `offset` = длина текста), `char` (первый знак,
    после которого правильного JSON быть не может), `trailing` (после значения есть не-пробел), `control` (знак < 0x20 внутри строки), `depth` (контейнер
    открыт на уровне глубже `MAX_DEPTH`), `dup` (второе появление ключа в одном объекте; `offset` — его открывающая кавычка, `key` — ключ).
* Грамматика — RFC 8259: пробельные знаки — только пробел, табуляция, LF, CR; числа `-?(0|[1-9][0-9]*)(.[0-9]+)?([eE][+-]?[0-9]+)?` (знак сразу после числа из
  `[0-9A-Za-z.+-]` — ошибка `char` на нём); строки с escape `\" \\ \/ \b \f \n \r \t \uXXXX` (одиночные суррогаты допустимы, как у `JSON.parse`); слова `true`, `false`, `null`.
* Значения: объекты создаются без прототипа (`Object.create(null)`), так что `__proto__` — обычный ключ; списки — обычные массивы; числа — `Number`. Вложенность: корень — уровень 0;
  двадцать вложенных контейнеров допустимы, двадцать первый — `depth`.
* `lineColumn(text: string, offset: number) → { line, column }` — строка: 1 + число LF до смещения; знак: 1 + число кодовых точек после последнего LF (CR перед LF — знак
  прежней строки).
* `positionKey(path) → string` — `JSON.stringify(path)`.
* Принимает и отвергает **то же, что `JSON.parse`**, кроме: повтор ключа (`dup`) и глубина (`depth`) — отказ; BOM снимает вызывающий (п. 5.9) — в тексте, поданном читателю, его нет.

Контрольные вызовы (прототип): `{"a":1,}` → `char`, строка 1, знак 8; `{"a":1,"a":2}` → `dup`, 1:8, ключ `a`; `` (пусто) → `end`, 1:1; `{"a":1} x` → `trailing`, 1:9;
`{⏎  "a": 1⏎  "b": 2⏎}` → `char`, 3:3; 20 раз `[` и 20 раз `]` → ok; 21 раз → `depth`, 1:21.

### 5.4. `text-rules.js`

`trimmedLength(s) → number` — число кодовых точек `s.trim()`; `phrasesOf(text) → string[]` — фразы по п. 4.11; `wordCount(phrase) → number`;
`textProblem(text) → null | { kind: "formal" } | { kind: "long", words: number }` — сначала обращение (`formal`), затем первая фраза длиннее `MAX_WORDS`.
Контрольные вызовы: девятнадцать слов «раз» → `{kind:"long", words:19}`; восемнадцать → `null`; «Ты тут» → `formal`; «Цветы и тыква» → `null`.

### 5.5. `places.js`

* `ROOT_PLACE` = `"весь файл"`.
* `pathText(path) → string`: пустой путь → `ROOT_PLACE`; число → `[n]`; ключ из `[A-Za-z_][A-Za-z0-9_]*` → `.ключ` (первый сегмент — без точки); любой другой ключ → `["<show(ключ)>"]`.
  `["questions",3,"show_if",0,"question"]` → `questions[3].show_if[0].question`.
* `show(value) → string` — вставка значения в текст: `String(value)`, каждый пробельный и управляющий знак → `_`; больше `SHOWN_CHARS` кодовых точек → первые 40 и `…`; если в результате есть слово из `SECOND_PERSON_WORDS`
  (по правилу п. 4.11) — `(скрыто)`. `show("a b")` → `a_b`; `show("ты")` → `(скрыто)`.

### 5.6. `conditions.js`

`checkCondition(ctx, path, value, ownIndex) → void` — шаги У1–У8 п. 4.6. `ctx` собирает `validate.js`: `add(code, path, text)` (с защитой D4), `wrong(path, kind)`, `int(path, v, min, max)`, `list(path, v, min, max)` → true/false
по Р1, Р4, Р5, и `questions` — `Map<id, {index, type|null, options: Set<id>}>` (Р8). `ownIndex` — номер вопроса для `show_if`, `null` для `when`.

### 5.7. `validate.js`

* `validateTenant(doc: unknown, options?: { fileName?: string }) → Issue[]`; `Issue` = `{ code: <из ERROR_CODES>, path: (string|number)[], text: string }`. `fileName` — имя файла вместе с `.json`; если не передано, имя не сверяется.
* Порядок обхода (порядок обнаружения): В1 корень — объект или `весь файл`; В2 таблицы поиска (Р8): вопросы по первому id, варианты, решения; В3 поля по таблицам п. 4.2–4.10, вложенно (у каждого объекта сначала лишние
  ключи в порядке файла, затем поля в порядке строк таблицы: пропавшее обязательное — ошибка, имеющееся — проверка значения); В4 E_UNREACHABLE по `solutions` в порядке файла.
* Не меняет `doc`; на любом значении, полученном из JSON (в том числе объекты без прототипа), возвращает список, а не исключение; результат не зависит от часов и среды.
* Контрольные вызовы: `validateTenant({})` — 8 ошибок E_FIELD «Нет поля…»: `schema`, `id`, `name`, `intro`, `questions`, `solutions`, `rules`, `result` (`hypotheses`, `leads` необязательны); `validateTenant([])` — одна E_FIELD, место пусто; пример п. 4.13 с `fileName: "ok-minimal.json"` — `[]`.

### 5.8. `report.js`

* `orderIssues(issues: Issue[], positions: Map) → Issue[]` — новая устойчиво отсортированная по смещению места (D5): смещение места — `positions.get(positionKey(path))`, а если такого нет — смещение самого длинного существующего начала пути; для пустого пути — 0.
* `formatIssues(fileName: string, issues: Issue[], positions: Map) → string[]` — упорядочивает, берёт первые `MAX_LINES`, строки `"<show(fileName)>: <pathText(path)>: <code>: <text>"`; если ошибок больше — последней строкой `"И ещё ошибок: N."` (N = все − `MAX_LINES`).

### 5.9. `load.js` (единственный файл с `node:fs` и `node:path`; все вызовы — `fs.lstatSync`, `fs.openSync`, `fs.fstatSync`, `fs.readSync`, `fs.closeSync` через объект `fs`)

* `class PickerError extends Error` — ожидаемый отказ (текст — одна строка по-русски, п. 7.5). Любая другая ошибка — ошибка программы и пробрасывается как есть. Ошибка ОС (есть строковые `code` и `syscall`) становится `PickerError` по таблице п. 7.5.
* `readTenantFile(file: string, options?: { baseDir?: string }) → { bytes: Uint8Array, fileName: string }` — шаги Ч1–Ч6 п. 7.5. `fileName` — последнее звено пути.
* `decodeTenantBytes(bytes) → { ok: true, text } | { ok: false, line, column }` — BOM (EF BB BF) в начале отбрасывается и не считается; `firstInvalidUtf8`; при отказе — позиция первого плохого байта (строка и знак считаются по декодированному префиксу до него).

### 5.10. `check.js`

* `CheckResult` = `{ exitCode: 0 | 1 | 2, stdout: string[], stderr: string[], tenant?: object }` (строки без `\n`; `tenant` — разобранный объект, только при коде 0, для REQ-055/056).
* `checkBytes(bytes: Uint8Array, fileName: string) → CheckResult` — шаги С1–С5 п. 7.4 (без диска; код 0 или 1).
* `checkFile(file: string, options?: { baseDir?: string }) → CheckResult` — `readTenantFile` + `checkBytes`; `PickerError` → код 2, `stderr: ["picker: <текст>"]`.

### 5.11. `cli.js`

Исполняется как точка входа (`node src/picker/cli.js …`); импортирует только `check.js`. `COMMANDS` — `Map` «имя → обработчик(аргументы) → CheckResult»; сегодня одна запись `check`. Печатает `stdout` и `stderr` строками с `\n`, ставит `process.exitCode` (без `process.exit`). Порядок разбора — п. 7.1.

### 5.12. Интерфейс для REQ-055, REQ-056, REQ-059, REQ-060 (меняется только вместе с ними)

* REQ-055 (движок) получает объект с `checkBytes(...).tenant` или после `validateTenant(...)` равного `[]`; формата файла не повторяет.
* REQ-056 (сервер) читает файлы так: `readTenantFile(путь, { baseDir })` → `checkBytes(bytes, fileName)` → при коде 1 печатает `stdout` под строкой «Арендатор <имя файла> не обслуживается:»; ошибку `PickerError` — как отказ файла. Новые команды — записи `COMMANDS`.
* REQ-060 копирует строки примера из вывода `check` на образцах п. 10: тексты п. 6 — контракт.

### 7.5. Загрузка файла (`readTenantFile`) — шаги Ч1–Ч6

| Шаг | Что делает | Отказ → `PickerError`, текст (X — `show(последнее звено пути)`) |
|---|---|---|
| Ч1 | путь пустой или содержит NUL | «Путь к файлу пустой или с недопустимым знаком. Проверьте путь.» |
| Ч2 | при `baseDir`: `path.resolve` пути лежит внутри `path.resolve(baseDir)` (не совпадает с ним; сравнение по звеньям, а не по началу строки); каждое звено ниже папки (кроме последнего) — не ссылка (`fs.lstatSync`) | «Файл X лежит вне папки арендаторов. Положите его в эту папку.» / «Файл X лежит за ссылкой на папку. Положите его в саму папку арендаторов.» |
| Ч3 | `fs.lstatSync(абсолютный путь)`: не найден; ссылка; папка; не обычный файл (канал, сокет, устройство) | «Файл не найден: X. Проверьте путь.» / «X — ссылка. Укажите сам файл, а не ссылку.» / «X — папка, а не файл. Укажите файл арендатора.» / «X — не обычный файл. Укажите файл арендатора.» |
| Ч4 | `fs.openSync(путь, O_RDONLY \| O_NOFOLLOW \| O_NONBLOCK)` (константы, которых нет на платформе, считаются 0); `ELOOP` | «X — ссылка…» (как выше); `EACCES`, `EPERM` — «Нет права читать файл X. Проверьте права.»; `ENOENT`, `ENOTDIR` — «Файл не найден…» |
| Ч5 | `fs.fstatSync(fd)`: не обычный файл; размер больше `MAX_FILE_BYTES` | «X — не обычный файл…» / «Файл X больше 512 КБ. Сократите его.» |
| Ч6 | чтение не больше `MAX_FILE_BYTES + 1` байт; получено больше `MAX_FILE_BYTES` (файл вырос) | «Файл X больше 512 КБ. Сократите его.» |

Дескриптор закрывается всегда (`finally`). Любая другая ошибка ОС на шагах Ч3–Ч6 — «Не удалось прочитать файл X (КОД). Проверьте файл.» (КОД — строка `code`, например `EIO`). В режиме без `baseDir` ссылки в самих путях выше файла разрешены (в macOS
`/var` — ссылка); ссылкой нельзя быть только последнему звену.

* Права `chmod 000` под учётной записью root не мешают чтению: отказ «нет права» проверяется через `fault-inject.js` (PK-L2), а не через права.
* `mtime` сравнивается как число миллисекунд из `fs.statSync`; файл перед запусками не трогать.
* Образцы `e-*` с одной ошибкой не должны давать следствий: поэтому в основе `rush` ссылается на `count` и `kind`, а повторы и ссылки в образцах `e-dup-*` и `e-ref-*` ведут на неиспользуемые вопросы (п. 10.1).
* Цикл в `e-order-cycle` даёт одну строку (О3).

### 16.2. Предложение записи `decisions/0066-picker-tenant-check-conventions.md` (номер назначает ORCH)

* **Вопрос:** как устроена проверка файла арендатора там, где требование REQ-054 допускает несколько прочтений.
* **Варианты:** (1) разбор через `JSON.parse` и перевод его сообщений; (2) свой строгий читатель; для порядка строк — порядок обхода схемы или порядок места в файле; для каждого места — все найденные ошибки или одна.
* **Выбор:** свой читатель (позиция «строка, знак» на русском, отказ на повтор ключа, места значений для порядка, предел глубины); порядок — по месту в файле; на место — одна ошибка в порядке «тип → шаблон → границы → повтор → ссылка → правило текста»;
  коды неоднозначных случаев — п. 4.12; предел файла 512 КБ; BOM допускается; ошибки — в stdout.
* **Причина:** Ф6, Ф7 (английские сообщения, молчаливый повтор ключа); тесты «по файлу на случай» требуют одной строки на случай; «в порядке мест в файле» — буквально.
* **Граница:** не меняет формат файла арендатора и список из десяти кодов (REQ-054); ответ ORCH на О1–О6 вносится в эту запись.
