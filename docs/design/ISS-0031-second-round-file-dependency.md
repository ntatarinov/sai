## 1. Что не так и что выбрано

Исполнитель получает файлы только задач из `task.depends_on` (`depsOf`, `tools/src/team/runner.js`). Руководитель проекта во втором
круге плана не видит имён принятых файлов (в подсказке только список задач, замечания сверки цели и сообщения), а проверка плана
(`validatePlan`, `tools/src/team/engine/plan.js`, проверки 1–5) смотрит схему, число задач, роли, ссылки и цикл — но не смысл текста.
Задача «правь one_pager.md» с пустым `depends_on` проходит проверку и запускается с пустой рабочей папкой и без раздела зависимостей
(п. 2).

**Выбор: вариант Г** (`decisions/0043`): (1) подсказка планировщику получает блок «Принятые файлы проекта»; (2) `validatePlan`
после проверки цикла достраивает `depends_on` задачи задачами-источниками принятых файлов, которые её `text` или `done_when` называют
по правилу критерия 15, и которых в её `depends_on` ещё нет. Расписание, `depsOf`, `buildPrompt`, ядро и формат журнала не меняются:
задача получает файл через уже работающую зависимость. Варианты А (отклонить план и запросить новый), Б и В и причины выбора — в
`decisions/0043`. Коротко: Г не нарушает критерий 4 и EN-25, не добавляет порока плана (критерий 1 и EN-02 не меняются), не стоит
повторного платного запуска планировщика и не создаёт тупика «ждёт решения пользователя» на настоящей модели.

Исход критерия 15, который выбран проектом и который проверяет тест, — **первый: задача получила файл через зависимость** (план не
отклоняется, второго запроса планировщику нет). Исход «план отклонён, второй запрос» этим проектом не используется.

## 4. Формы и тексты

Новых файлов в `tools/src/` нет (новый модуль в WF-03 писал бы BACKEND-DEV; здесь код — в существующем `plan.js`). Все новые функции
**чистые**: ни ввода-вывода, ни часов, ни случайности, не бросают на любом `state` (как `planNote` сегодня).

### 4.1. Формы данных

```
AcceptedFile = {
  task:     "t-NNNN",               // задача-источник; её статус "done"
  name:     "t-NNNN-N-<original>",  // принятое имя (из task.files)
  original: string,                 // имя после "t-NNNN-N-"; по шаблону PATTERNS.name, без папок; всё принятое имя ≤ 80 знаков, значит у original не больше 71
  attempt:  integer ≥ 1             // N
}
```

Хранимые данные и форматы файлов **не меняются**: ни событий, ни полей состояния, ни каталога `reason`; запись `PLAN_RECEIVED`
хранит уже достроенный `depends_on` (поле то же, `list(≤40, taskId)`). Файлы не читаются и не пишутся (по имени из состояния; содержимое
берёт прежний `depsOf` позже, на запуске задачи). Запись «всё или ничего» не затронута: достройка меняет значение в памяти до
`tw.append(PLAN_RECEIVED)`, а событие пишет прежнее ядро одной строкой.

### 4.2. `executor.js`

`parseAccepted(dep: {task, name}) → { original, attempt } | null` — **единственное изменение: слово `export`** (функция и её поведение
прежние). Она остаётся единственным разбором принятого имени: и `acceptedFilesText` (исполнителю), и `plan.js` (планировщику) идут через
неё. Других изменений в `executor.js` нет.

### 4.3. `plan.js`: единый источник, правило, достройка

```
acceptedFiles(state: ProjectState) → AcceptedFile[]
namesFile(text: string, original: string) → boolean
missingSources(item: { text, done_when, depends_on }, accepted: AcceptedFile[]) → string[]   // id задач
PLAN_DETAIL.too_many_deps(key) → string            // новая строка каталога
```

**`acceptedFiles`** — единственная точка расчёта «принятые файлы проекта». **Порядок результата один и тот же для подсказки, обрезки и проверки (F2):** задачи — в порядке `state.tasks` (номер задачи по возрастанию), внутри задачи — файлы в порядке `task.files` (номер попытки по возрастанию); порядок событий `RESULT_FILE` (`seq`) не используется: он может не совпадать (задача t-0002 способна принять файл раньше t-0001). «Более ранний» файл — стоящий раньше в этом порядке. Для каждой задачи `state.tasks` в этом порядке со
статусом `"done"` и для каждого имени из её `files` (по номеру попытки): `parseAccepted({task: id, name})`; запись берётся, если разбор не
`null`. Файлы задач не в статусе «готово» (в работе, на проверке, `failed`, `waiting_user`, закрытые) не берутся (критерий 15). Файлы
черновиков (`kind: draft`) берутся так же, как их берёт `depsOf` (по имени из `task.files`). Нет таких задач — `[]`. Мусор в состоянии
(имя не по шаблону ядра) пропускается без исключения. Результат не изменяет `state`.

**`namesFile(text, original)`** — единственное место правила «называет файл» (критерий 15, дословно): совпадение — `original` целиком,
с расширением, регистрозависимо; перед ним начало строки или знак вне `[A-Za-z0-9._/-]`; после него конец строки, или знак вне
`[A-Za-z0-9_.-]`, или точка, за которой конец строки или знак вне `[A-Za-z0-9_-]`. Поле `original` ищется как буквальная строка (точка
в имени не «любой знак»: имя экранируется как данные), текст — как есть, без приведения регистра и без нормализации. Имя с папкой
(«out/one_pager.md») правилом не названо: слева от `one_pager.md` стоит `/` — и этим поведение для папки исчерпано (ISS-0028 не входит,
отдельного поведения не вводится). Это же правило применяется к полям `text` и `done_when`, и только к ним. Таблица случаев — п. 7.1.

**`missingSources(item, accepted)`** — задачи-источники, которых не хватает: id задачи `a.task` из `accepted` (порядок первого появления
в `accepted`, без повторов), для которых `namesFile(item.text, a.original) || namesFile(item.done_when, a.original)` и `a.task` ∉
`item.depends_on`. `item.depends_on` здесь — уже **переведённый** список id (F1); источник «назван», только если там стоит его id; задача того же плана,
зависящая от источника, не считается (критерий: «его `depends_on` не называет задачу — источник»). Если исходное имя принято у нескольких задач,
в результат входит каждая (критерий: «получает файлы каждой»). Выбор «последней попытки» одной задачи не делается (ISS-0024): попытки
одной задачи — один id.

**`validatePlan`** получает **проверку 6** (после проверки 5, цикл). Порядок (F1, однозначно): для каждой задачи годного плана (в порядке
`orderPlan`) **сначала** её `depends_on` переводится из ключей в id тем же способом, что сегодня (если строка совпала с ключом плана, это
ключ — ключ имеет преимущество, как в текущем коде; иначе строка остаётся номером существующей задачи), **затем**
`added = missingSources({text, done_when, depends_on: переведённый список}, acceptedFiles(state))` и добавляется в конец списка в
порядке `accepted`. Достроенные id никогда не проходят перевод ключей. Почему коллизии нет: id новых задач плана — от
`state.tasks.length + 1` и выше, а источник — всегда существующая задача, её id не больше `state.tasks.length`. Поэтому ключ плана,
совпавший по виду с номером существующей задачи («t-0001»), не путает источник с задачей плана: переведённый ключ — новый id (больше), а
источник остаётся своим id. Следствия: задача не может получить зависимость на саму себя; достроенный id всегда меньше id задачи, ради
которой он добавлен, поэтому цикла и нарушения правила ядра «зависимость только на меньший номер» (И5) не бывает (N1; SF-03 проверяет:
каждый достроенный номер меньше номера своей задачи). Шаблон ключа не меняется, новых отказов за вид ключа нет, формат журнала и
критерий 1 не затронуты. Итоговый список — без повторов, не длиннее `LIMITS.PLAN_TASKS_MAX` (40), иначе
`{ ok: false, reason: "too_many", detail: PLAN_DETAIL.too_many_deps(item.key) }` (существующий `reason`; каталог не меняется). Порядок проверок
1–5, их `reason` и тексты `detail` прежние; на плане без названных принятых файлов результат **побайтно прежний**
(`{ ok: true, tasks }` с теми же полями и тем же порядком).

Текст нового `detail` (постоянная строка, `key` только после проверки шаблоном): «Задача <key> получила бы больше 40 зависимостей».

### 4.4. `plan.js`: подсказка планировщику

`planNote(state, facts, rejection)` — сигнатура прежняя. Если `acceptedFiles(state)` не пуст, после блока «Задачи проекта» и до блока
«Закрытые задачи после прошлого плана» вставляется один блок (постоянные заголовок и правило, имена и номера — данные ядра):

```
Принятые файлы проекта:
— <original> (задача <task>, принят как <name>)
… (строки, не больше ACCEPTED_LINES_MAX = 50 из executor.js: последние в порядке п. 4.3 (по номеру задачи и попытки; F2); если файлов больше — первой строкой «— и ещё N более ранних файлов»,
    где N — число отброшенных файлов, стоящих раньше в том же порядке)
Если text или done_when задачи называет такой файл, пиши в тексте именно исходное имя (первое в строке, не принятое), и укажи в её depends_on номер задачи, которая его
сдала: файл получит только задача с такой зависимостью. Если не укажешь, ядро добавит эту зависимость само.
```

Принятое имя в строке показано, чтобы Руководитель проекта связал его с именами в замечаниях сверки цели (проверяющий видит их под принятыми именами); правило-предложение прямо велит писать исходное имя, потому что принятое правило критерия 15 не называет (N2; решение об его включении — отдельная находка, п. 12). Правила: каждая строка проходит `maskSecrets` (имя файла выбирает исполнитель; в журнал и вход имя попадает и сегодня, но здесь оно
маскируется ещё раз, и проверка плана по маскированной строке не работает — она берёт имена из состояния, а не из подсказки). Содержимого
файлов в блоке нет, и это проверяется. Блока нет, если принятых файлов нет — подсказка побайтно прежняя (`rejection` — первый абзац — не
меняется). Блок не ограничивает подсказку: 50 строк ≈ до 8 000 знаков при пределе подсказки 200 000 (`PROMPT_MAX`, `0018`).
