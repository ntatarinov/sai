## 2. Файл проверки `.github/workflows/check.yml` (новый, BACKEND-DEV)

### 2.1. Правила формы

- Блочный стиль YAML, отступ два пробела, окончания строк `\n`, без табуляций и без `\r`, без якорей и ссылок (`&`, `*`), без многострочных значений `run: |` и `run: >` — каждое значение `run` в одну строку. Это нужно, чтобы тест читал файл построчно, без библиотеки (`decisions/0002`: во время выполнения зависимостей нет).
- Ключей верхнего уровня ровно пять: `name`, `on`, `permissions`, `concurrency`, `jobs`; задание одно — `check`; шагов ровно четыре, в этом порядке.
- Нет: `|| true`, `|| :`, `continue-on-error`, `if:`, `secrets.`, `env:`, `GITHUB_TOKEN`, `token:`, `pull_request_target`, `workflow_run`, `workflow_dispatch`, `schedule`, `actions/cache`, `cache:` (кроме `package-manager-cache: false`), `docker://`, `curl`, `wget`, `http://`, `https://`, `set +e`, `exit 0`, `${{` кроме одного места в `concurrency` (п. 2.2).

### 2.2. Форма файла (конфигурация, не код; значения буквальные)

```
name: check

on:
  push:
    branches:
      - "**"
  pull_request:

permissions:
  contents: read

concurrency:
  group: check-${{ github.ref }}
  cancel-in-progress: true

jobs:
  check:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    steps:
      - name: Get the code
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
          persist-credentials: false
      - name: Install Node 22
        uses: actions/setup-node@820762786026740c76f36085b0efc47a31fe5020 # v7.0.0
        with:
          node-version: "22"
          package-manager-cache: false
      - name: Install dependencies
        working-directory: tools
        run: npm ci
      - name: Run the check
        working-directory: tools
        run: npm run check
```

### 2.3. Почему так

| Строка | Причина |
|---|---|
| `on.push.branches: "**"` | правило «на каждый push» (критерий 1): без `branches` запускалась бы и отправка меток (`base/*` ставит каждый прогон) — лишние минуты; все ветки, включая `main` и с косой чертой, проверяются |
| `on.pull_request` | критерий 1; `pull_request_target` не нужен и опасен (запускает код с правами записи) — запрещён тестом |
| `permissions: contents: read` | токен задания только читает (Q7, наименьшие права); записи в репозиторий нет |
| `concurrency` + `cancel-in-progress` | новая отправка в ту же ветку отменяет прежний, ещё не законченный запуск — экономия минут (п. 6, остаточный риск 2); запуск `main` для промежуточного коммита может быть отменён, поэтому критерий 2 сравнивает `headSha` с `origin/main` |
| `runs-on: ubuntu-24.04` | образ закреплён, а не `ubuntu-latest`: проверка не меняется молча при смене «последнего» образа (Ф16) |
| `timeout-minutes: 15` | зависание не съедает 360 минут по умолчанию (Q10); запуск ≈ 3–5 минут (п. 6) |
| `fetch-depth: 0` | Ф9, Ф10; метки не нужны |
| `persist-credentials: false` | токен не остаётся в настройке git для следующих шагов (Q7, Ф15) |
| закрепление по SHA | тег можно перенести на другой коммит, SHA — нет; закреплена версия, существование которой проверено в Ф12–Ф14. Выбраны `checkout v7.0.1` (последняя из ветки v7) и `setup-node v7.0.0`, а не `v7.1.0`: `v7.1.0` вышла 2026-10-08, четыре дня назад, `v7.0.0` — 90 дней назад; проект не берёт версии моложе двух недель. Обновление — отдельной правкой с повтором проверки Ф12–Ф14 (открытый вопрос V2) |
| `node-version: "22"` | как `engines` (`>=22 <23`): тест CI-3 держит их согласованными; `check-latest` не задан, берётся последняя 22.x из манифеста действия |
| `package-manager-cache: false`, `cache:` нет | ruling ORCH 5: безопасность встроенного кэша здесь не доказывается, поэтому его нет; цена — скачивание пакетов при каждом запуске (`npm ci` по `tools/package-lock.json`: 4 прямых зависимости, `found 0 vulnerabilities`, Ф9) |
| `npm ci`, затем `npm run check`, оба в `tools/` | та же команда, что у владельца (`decisions/0002`, Q4); отдельных шагов форматирования или тестов нет — один шаг, один код выхода |

### 2.4. Что видит владелец и что остаётся неизменным при отказах

| Отказ | Что происходит | Чем отличим |
|---|---|---|
| `npm ci` не прошёл (lock-файл не совпал, сеть недоступна) | шаг красный, следующие не выполняются; запуск `failure` | `gh run list --workflow check.yml --json conclusion` → `failure` |
| `npm run check` код не 0 | шаг красный, запуск `failure`; код не продолжается ни в какой другой шаг | то же |
| Не скачалась Node или действие | шаг красный, запуск `failure` | то же; повтор — вручную, без автоповтора (`|| true` и повторов нет, Q6) |
| Зависание дольше 15 минут | запуск прерван, `cancelled`/`failure`, красный | `conclusion` не `success` |
| Исчерпан лимит минут (возможно, только если репозиторий приватный) | запуск не стартует — **записи о запуске нет** | критерий 2: `gh run list` пуст или `conclusion` не `success` → шаг P-2 не пройден (не «молчит как зелёный») |
| Новая отправка в ту же ветку | прежний запуск `cancelled` | у каждого коммита проверяется последний запуск по его `headSha` |
| Изменение прав или ветки на GitHub | файл репозитория и код не меняются — запись в репозиторий проверкой невозможна (`contents: read`) | — |

## 3. Хук `.githooks/pre-push` (новый, BACKEND-DEV; исполняемый)

Вход: git вызывает хук перед отправкой с аргументами `<имя удалённого> <адрес удалённого>` (Ф11) и строками на stdin `<локальная ссылка> <локальный хеш> <удалённая ссылка> <удалённый хеш>`. Выход: код 0 — отправка идёт; не 0 — git отменяет **всю** отправку, на удалённой стороне ничего не меняется (Ф11).

### 3.1. Форма

Файл `#!/bin/sh` (первая строка), окончания строк `\n`, права на исполнение (режим `100755` в индексе — п. 5.3), только встроенные команды `sh`, `git`, `npm`. Нет: `--no-verify`, `||` (любые, в том числе `|| true`, `|| :`), `set +e`, `exit 0` больше одного раза, `eval`, `curl`, `wget`, адресов. Адрес удалённого (второй аргумент) **не печатается и не используется**: он может содержать учётные данные (Q7).

### 3.2. Алгоритм по шагам

| Шаг | Действие | Код выхода и сообщение |
|---|---|---|
| H1 | Прочитать stdin построчно (встроенным `read`). Строка — удаление, если её второе поле (локальный хеш) состоит только из символов `0` (40 или 64 знака) | — |
| H2 | Если строки были **и все** — удаления: напечатать «pre-push: отправляются только удаления, кода нет — проверка не нужна» и выйти | **0** (единственный явный `exit 0` в файле) |
| H3 | Корень: `git rev-parse --show-toplevel`; не вышло | **1**, «pre-push: это не git-репозиторий» |
| H4 | Папки `tools` в корне нет | **1**, «pre-push: нет папки tools — проверять нечем» |
| H5 | Команды `npm` нет в `PATH` (`command -v npm` не нашла) | **1**, «pre-push: не найден npm (нужен Node 22)» |

### 3.3. Почему удаления пропускаются

Критерий 3 требует удалить ветку с падающим тестом (`git push origin --delete <ветка>`); в Ф11 хук вызывается и на удаление, и при красной проверке он его отклонил бы — владелец не смог бы убрать красную ветку, не снимая хук. Удаление не отправляет код, поэтому проверка ему не нужна. Отправка метки с кодом проверяется: метка может указывать на неотправленный коммит. Цена — лишние 2 минуты при отправке меток `base/*` (остаточный риск 1).

### 3.4. Чего хук не может, и это записано

- `git push --no-verify` пропускает хук; сам хук обойти флаг не может (git не вызывает его). Запрет обхода — правило процесса (Q6), сеть безопасности — проверка на GitHub (п. 2).
- Без `git config core.hooksPath .githooks` хук не работает (настройка хранится в `.git/config` и в репозиторий не попадает). Репозиторий этого не может принудить; README.md говорит это прямо.
- Хук запускает `npm run check` на **рабочей папке** (с неотправленными правками и неотслеживаемыми файлами), а не на коммите, который уходит: отправка другой ветки или чистого коммита проверяется по чужому состоянию, а красная рабочая папка может остановить отправку зелёного коммита. Хук не делает чистую выгрузку коммита — это дороже и вне критерия; вторая линия — проверка на GitHub, она идёт по отправленному коммиту.
- Файл без права на исполнение git молча пропускает (с предупреждением); защита — тест PH-1 (права в рабочей папке) и шаг П-1 (режим `100755` в индексе после коммита).

### 7.2. Критерий 4 — проверка перед отправкой (автотесты)

### 7.4. Критерии 2 и 3 — шаги после отправки (не автотесты; ruling ORCH 2)

Шаг П-1 выполняется **до** коммита (RELEASE-FINALIZER). Шаги П-2, П-3 и П-3b выполняются **после** того, как владелец подтвердил мерж (R1) и отправка в `main` сделана: исполнитель — RELEASE-VALIDATOR отдельным шагом после отправки (по рулингу O1; в handoff-ах прогона это шаг 12 — расширение этого прогона, в WF-02 такого шага нет) (со своим запуском команд), ORCH сверяет его вывод с файлами и учётом. П-2 только читает; **пишут** П-3 (отправка красной ветки на GitHub) и П-3b (удаление ветки).

| Шаг | Критерий | Команды | Ожидаемое |
|---|---|---|---|
| П-1 | 4 (режим файла) | до коммита RELEASE-FINALIZER: `git ls-files -s .githooks/pre-push` (после `git add`) | начинается с `100755` |
| П-2 | 2 | после отправки: `git fetch origin`, затем `gh run list --workflow check.yml --branch main --limit 1 --json conclusion,headSha,status,url,databaseId` (повторять через минуту, пока `status` не `completed`; ждать не больше 15 минут) и `git rev-parse origin/main` | `conclusion` = `success`; `headSha` = вывод `git rev-parse origin/main`; ссылка `url` и длительность записываются (для остаточного риска 2). Если запуска нет, `conclusion` ≠ `success` или `headSha` другой — критерий не выполнен |
| П-3 | 3 | **только с отдельным согласием владельца.** В копии клона вне проекта (`git clone <корень Sai> <scratch>/red`, настройка `core.hooksPath` в копии не задана). Клон из локальной папки ставит `origin` на эту папку, а не на GitHub, поэтому **сначала** `origin` копии заменяется на адрес GitHub проекта: `git -C <scratch>/red remote set-url origin "$(git remote get-url origin)"`, где внутренняя команда выполняется в рабочем репозитории проекта (адрес в файлы и отчёты не записывается). **Проверка перед отправкой:** `git -C <scratch>/red remote get-url origin` равен выводу `git remote get-url origin` в проекте; не равен — шаг прерывается, ничего не отправлено. Дальше: ветка `check-red-REQ030-20261012` от `main`, один новый файл `tools/test/zz-red.test.js` с одним тестом, который падает (`assert.fail`); файл **отформатирован prettier и проходит eslint**, чтобы падал именно тест, а не раньше него шаг форматирования или lint; **проверка до отправки** в копии (после `npm ci`): `npm run format:check`, `npm run lint`, `npm run traces`, `npm run handoffs-check` — все код 0, а `npm test` — код ≠ 0 (иначе файл исправить, не отправлять); коммит, `git push origin check-red-REQ030-20261012`; затем **в рабочем репозитории проекта** (каталог проекта, тот же GitHub-репозиторий, что у `origin` копии, — адрес копии проверен выше) `gh run list --branch check-red-REQ030-20261012 --limit 1 --json status,conclusion,headSha,url,databaseId`; если `status` не `completed` — повторять через минуту, но не дольше 15 минут (после предела шаг не пройден, запись об этом в отчёт; ветка при этом всё равно удаляется в П-3b); затем в том же каталоге `gh run view <databaseId> --json jobs --jq '.jobs[].steps[] | [.name,.conclusion] | @tsv'` | `conclusion` = `failure`; `headSha` = хеш коммита ветки; ссылка записана; упал именно шаг `Run the check` (`failure`), шаги `Get the code`, `Install Node 22`, `Install dependencies` — `success` (в журнале упавшего шага, `gh run view <databaseId> --log-failed`, виден `not ok` теста `zz-red`; если упал шаг установки или форматирование/lint, критерий не доказан: красным должна быть проверка, а не окружение). Ветка `main` не затронута (`git ls-remote --heads origin main` — тот же хеш, что до шага). **В самом проекте ветка не появилась:** `git branch -a` и `git for-each-ref refs/heads | grep check-red` в проекте — пусто |
| П-3b | 3 (уборка) | в копии (адрес `origin` проверен, как в П-3): `git push origin --delete check-red-REQ030-20261012`, затем в **проекте** `git ls-remote --heads origin check-red-REQ030-20261012` (запрос к GitHub, а не к копии) | вывод пуст; `git branch -a` в проекте по-прежнему без `check-red-…`. Красная ветка удалена в той же операции проверки; если удаление не вышло — шаг не закрыт, ORCH сообщает владельцу. Предупреждение: красный запуск шлёт владельцу письмо GitHub о падении — сказать об этом при запросе согласия |

Критерии 2 и 3 нельзя проверить до отправки; пока П-2 и П-3 не выполнены, REQ-030 не может стать `done` (рулинг ORCH по O1, п. 11: RELEASE-VALIDATOR даёт PASS по критериям 1, 4, 5 до отправки; критерии 2 и 3 проверяются отдельным шагом после отправки в `main`; статус `done` — после П-2 и П-3; пока владелец не дал согласие на П-3, REQ-030 остаётся `in_progress`). Порядок после отправки: П-2 → DOC-UPDATER правит строку README «Автоматической проверки на GitHub (CI) нет…» в разделе «Что ещё не готово» (п. 5.1; не раньше успешного П-2) → П-3, П-3b → `done`.

## 10. Предложение записи в `decisions/` (файл не создаётся: номер и строку в `decisions/README.md` даёт ORCH)

**0045 — Проверка на GitHub: версии действий по SHA, полная история, без кэша, правила хука** (предложение CODE-DESIGNER, 2026-10-12; принимает ORCH/владелец)

- Вопрос: как закрепить версии официальных действий; сколько истории получать; нужен ли кэш; когда хук пропускает проверку.
- Варианты: (1) закрепление по тегу `@v7` / по полному SHA; (2) получение одного коммита / полная история; (3) встроенный кэш npm / без кэша; (4) хук проверяет всё / пропускает отправку, где только удаления.
- Выбор: по SHA (тег — подвижная ссылка, SHA — нет; проверено Ф12–Ф14); полная история (`fetch-depth: 0`; без неё `npm run check` красный, Ф9); без кэша (безопасность кэша не доказана, ruling ORCH 5); хук пропускает только удаления (иначе красную ветку не удалить, Ф11).
- Граница: решение не включает защиту ветки (`0023`, D1), не разрешает обход хука и не меняет `npm run check`.
- Основание: ruling ORCH 1–5 в задании прогона `REQ030-20261012-01`; `0023`; `0044`.
