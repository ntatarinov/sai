## 1. Что не так и что выбрано

`readBlobs` в `tools/src/handoffs/git-history.js` — единственный из шести вызовов `execFileSync`, у которого есть ввод: запросы `<rev>:<путь>` идут на стандартный ввод `git cat-file --batch`. Если git вышел раньше, чем ему записали запросы (так ведут себя подставные git в тесте GH-6: ответили и вышли с кодом 0, ввод не читали), запись даёт ошибку, а `execFileSync` кладёт в неё статус выхода git — 0. Функция `gitFailure` видит число 0 и говорит «git не смог выполнить команду (код 0)». Текст ложен: git ошибочного кода не вернул. Какая ветка сработает — решает гонка записи и выхода; на Linux-раннере GitHub гонку проиграли (1475 из 1476, GH-6 случай 2, строка 243 теста).

**Выбор** (`decisions/0047`, вариант А): в `gitFailure` ошибка со статусом выхода, равным нулю, превращается в `E_TRACE_GIT` «вывод git не разобран» — тот же код и тот же текст, что у нечитаемого ответа и что ждёт GH-6. Статус не 0 остаётся как есть: 128 — `E_TRACE_NOT_GIT`, остальные числа — «код N». Условие — по одному статусу, а не по коду `EPIPE` (п. 2, расхождение Р2). Тесты: подставные git GH-6 (случаи 1 и 2) читают ввод до ответа, чтобы GH-6 проверял разбор ответа, а не исход гонки; новый детерминированный тест GH-7 (с контролями GH-7b) создаёт условие «git вышел, не прочитав запросы» вводом больше буфера канала.

### Расхождения с заданием (quality-bar §6, п. 2)

- **Р1. Размер ввода.** Задание и диагноз называют запрос в 200 000 знаков. Измерено: на macOS вместимость между 64 КиБ и 128 КиБ (Ф4), 200 000 хватает. Но стандартный ввод дочернего процесса — сокет, а размер буфера сокета на Linux зависит от настроек ядра (по документации ядра значение по умолчанию порядка 200 КиБ — **не измерено**, Linux нет); запрос в 200 000 знаков может целиком уместиться в него, запись не оборвётся и тест «до» не покраснеет на Linux. Проект берёт запрос в **4 МиБ** (`"HEAD:" + 4 × 1024 × 1024 знаков "x"`): на macOS проверен (Ф4: 4 МиБ — `EPIPE`), на Linux он на два порядка больше значения по умолчанию. Если 4 МиБ всё же уместится, исход «после» не меняется: ответ подставного git разбирается и даёт тот же текст (п. 4.1).
- **Р2. Условие ветки.** Диагноз предлагает `err.code === "EPIPE"` при статусе 0 («только EPIPE записи ввода»). Измерено только на macOS (Ф3). Какой код даёт Linux, когда git вышел с непрочитанным вводом, проект не измерил и не берёт на веру: ветка по `EPIPE` рискует не сработать там, где дефект и найден. Проект ставит условие **по статусу 0** после веток `ENOENT`, `ETIMEDOUT`, `ENOBUFS` и 128: ошибка вызова с кодом выхода 0 не может означать «git не смог выполнить команду» ни при каком коде записи. Остальное в диагнозе (механизм, места, тексты) подтверждено.
- Других расхождений нет. Неверные факты первой редакции файла дефекта диагноз уже назвал (его `I1`); правка файла `ISS-0053` — DOC-UPDATER, п. 9.

## 4. Изменения

### 4.1. `tools/src/handoffs/git-history.js`, функция `gitFailure`

Сигнатура и место не меняются: `gitFailure(err) → TraceError | err`, не экспортируется, вызывается из шести функций того же файла. Меняется порядок и состав веток — одна ветка добавляется.

| № | Условие (по порядку проверки) | Результат | Меняется? |
|---|---|---|---|
| 1 | `err` не объект или `null` | `err` как есть | нет |
| 2 | `err.code` равен `"ENOENT"` | `TraceError("E_TRACE_GIT", "git не найден")` | нет |
| 3 | `err.code` равен `"ETIMEDOUT"` | `TraceError("E_TRACE_GIT", "git не ответил за 30 с")` | нет |
| 4 | `err.code` равен `"ENOBUFS"` | `TraceError("E_TRACE_GIT", "вывод git слишком велик")` | нет |
| 5 | `err.status` равен 128 | `TraceError("E_TRACE_NOT_GIT", NOT_GIT)` | нет |
| **5a** | **`err.status` строго равен числу 0** | **`TraceError("E_TRACE_GIT", "вывод git не разобран")`** | **новая** |
| 6 | `err.status` — число (кроме 0 и 128) | `TraceError("E_TRACE_GIT", "git не смог выполнить команду (код N)")` | нет (0 теперь до неё не доходит) |
| 7 | `err.code` — строка | `TraceError("E_TRACE_GIT", "git не запустился (<код>)")` | нет |
| 8 | иначе | `err` как есть | нет |

Правила ветки 5a:

- Стоит **после** веток 2–5 и **до** ветки 6; в таком порядке «код 0» никогда не печатается (ветка 6 получает статусы, отличные от 0).
- Сравнение строгое (`=== 0`): `null` (процесс убит сигналом), `undefined` (процесс не запускался) и любое иное значение в неё не попадают и идут по веткам 6–8, как сейчас (вопрос О1).
- Код ошибки записи (`err.code`) не проверяется: платформа может дать `EPIPE` (измерено на macOS) или другой код (Linux не измерен); смысл один — git завершился успешно, а вызов не довёл обмен до конца (Р2).
- Текст — ровно `вывод git не разобран`, побайтно как в `parseBatch`, `commitSeconds` и `fileHistory` того же файла (там он записан литералом в трёх местах; общую константу вводить не нужно — это рефакторинг вне дефекта, AP-019). Код — `E_TRACE_GIT`, тот же, что у нечитаемого ответа.
- Достижима только из `readBlobs` (Ф6): у остальных пяти вызовов ошибки со статусом 0 не бывает; для них поведение не меняется ни на байт.

Что видит человек: одна строка `<команда>: E_TRACE_GIT: вывод git не разобран`, код выхода 2, без стека (формат — как у всех сбоев git, `cli.js` строка 69); вместо прежней `… git не смог выполнить команду (код 0)`. Для настоящего git ветка недостижима (он читает ввод до ответа); пользователь её не видит.

Комментарии в файле: допустимо дополнить комментарий над `gitFailure` одной английской фразой о ветке (стиль файла — английские комментарии). **В тексте файла, включая комментарии, не должно быть слов из списка Ф7** (`shell`, `exec(`, `execSync`, `spawn`, `fork`, `execFile(`, `require(`): `HC-RT-1b` красный, если они появятся. Проверка: `grep -nE 'shell|exec\(|execSync|spawn|fork|execFile\(|require\(' tools/src/handoffs/git-history.js` — пусто.

Исходы по сочетаниям (git × ввод), выбор которых раньше решала гонка:

| Что сделал git | Ввод уместился в буфер, запись не оборвалась | Запись оборвана (ввод больше буфера или git вышел раньше записи) |
|---|---|---|
| вышел 0, вывод пуст или мусор | разбор: `вывод git не разобран` | **«после»: `вывод git не разобран`** («до»: `(код 0)`) |
| вышел 0, вывод полный и верный | результат | **«после»: `вывод git не разобран`** («до»: `(код 0)`) — настоящий git так не поступает; подставной git должен читать ввод |
| вышел 3 | `код 3` | `код 3` (не затирается) |
| вышел 128 | `E_TRACE_NOT_GIT` | `E_TRACE_NOT_GIT` (не затирается) |

После исправления для подставных git, чей ответ — мусор (GH-6, GH-7), исход один и тот же в обеих колонках: от гонки не зависит ни одно из ожиданий этих тестов. Правда, «вышел 0, вывод полный и верный» при оборванной записи даёт ошибку, а при уместившемся вводе — результат; такой подставной git тестами не используется, и настоящий git так не бывает (п. 5).

## 5. Пути отказа (Q10): что видит человек и что остаётся неизменным

Команда проверки и команды, использующие git-history, ничего не пишут ни при одном отказе git (`0037`, п. 9 проекта REQ-038); исправление этого не меняет.

| Отказ вызова `readBlobs` | Было | Стало | Код выхода команды | Состояние |
|---|---|---|---|---|
| git не найден | `E_TRACE_GIT` «git не найден» | то же | 2 | неизменно |
| git не ответил за 30 с | `E_TRACE_GIT` «git не ответил за 30 с» | то же | 2 | неизменно |
| вывод больше 256 МиБ | `E_TRACE_GIT` «вывод git слишком велик» | то же | 2 | неизменно |
| git вышел с 128 (не репозиторий), в том числе при оборванной записи | `E_TRACE_NOT_GIT` | то же | 2 | неизменно |
| git вышел с кодом N (кроме 0 и 128), в том числе при оборванной записи | `E_TRACE_GIT` «код N» | то же | 2 | неизменно |
| **git вышел с кодом 0, запись запросов оборвана** | `E_TRACE_GIT` «git не смог выполнить команду (код 0)» (ложь) | **`E_TRACE_GIT` «вывод git не разобран»** | 2 | неизменно |
| git вышел с кодом 0, ответ нечитаем | `E_TRACE_GIT` «вывод git не разобран» | то же | 2 | неизменно |
| git убит сигналом | ошибка, не `TraceError` (Ф8) | **не меняется** (вопрос О1) | непойманная ошибка со стеком | неизменно |

Во всех строках, кроме последней, сообщение — одна строка без стека и без пути компьютера; stderr git не печатается (`0038`).

Защита стоит в той же операции, что и действие: превращение ошибки вызова в `TraceError` — это `catch` вокруг `execFileSync` в `readBlobs` (`throw gitFailure(err)`), без отдельного вызова «проверить потом»; новая ветка живёт внутри `gitFailure` и срабатывает в том же `catch`.
