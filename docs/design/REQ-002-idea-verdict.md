## 1. Что строим

Workflow **WF-06 «Выбор идеи»**. Идеи-кандидаты превращаются в проверенную
рекомендацию и следующие задачи конвейера.

```
Шаг 0  ORCH             prepare-run: run.json + очищенные копии источников
Шаг 1  IDEA-ANALYST×3   раунд 1 — оценки со своей точки зрения
Шаг 2  IDEA-ANALYST×3   раунд 2 — проверяет КАЖДУЮ чужую оценку: согласен / не согласен
Шаг 3  IDEA-ANALYST×3   раунд 3 — отвечает на КАЖДОЕ несогласие со своими оценками:
                        пересматривает балл или держится с доказательством
Шаг 4  IDEA-JUDGE       verdict-N.json + .md — итоговый вердикт (первый агент запроса)
Шаг 5  VERDICT-EXECUTOR сам перепроверяет → verdict-review-N.json (второй агент запроса)
                        REJECT и N < 3 → назад на шаг 4
                        ACCEPT → apply-verdict: блок рекомендации + proposed-actions.json
                        REJECT и N = 3 → apply-verdict: блок эскалации
Шаг 6  ORCH             сверяет artifacts_out исполнителя; по proposed-actions создаёт
                        handoff-ы (только ORCH создаёт handoff-ы, docs/workflows/handoffs.md)
Шаг 7  владелец         принимает решение; агенты его не принимают
```

Агенты общаются **файлами** в `runs/<RUN-ID>/`; движение работы — handoff-ы в
`handoffs/<RUN-ID>/`. Правила контрактов проверяет код `tools/` (REQ-002), а не
доверие к агенту.

**Совместность анализа** — раунды 2 и 3: несогласие одного аналитика обязано получить
ответ владельца оценки и может изменить балл. Вердикт привязан к итоговым баллам,
поэтому разногласия реально влияют на результат.

**Бизнес-логика второго агента** (VERDICT-EXECUTOR): он не просто пересылает вердикт.
Он независимо перепроверяет его, отклоняет плохой (возврат судье), а принятый
превращает в состояние проекта (блок в STATE.md) и в очередь следующих задач
конвейера (`proposed-actions.json`), которую исполняет ORCH. Решение о старте продукта
остаётся за владельцем.

## 2. Роли

| Роль | Производит | Кто проверяет | На что похожа |
|---|---|---|---|
| IDEA-ANALYST, lens = `market` / `execution` / `owner_fit` | `assessment-<lens>.json`, `crossreview-<lens>.json`, `response-<lens>.json` | validate; два других аналитика (раунд 2); судья | роль, параметризованная точкой зрения: одна роль — три запуска с разными `lens` |
| IDEA-JUDGE | `verdict-N.json`, `verdict-N.md` | validate; VERDICT-EXECUTOR | одна рекомендация по нескольким заключениям, разбор разногласий |
| VERDICT-EXECUTOR | `verdict-review-N.json`; через apply-verdict — блок в STATE.md, `proposed-actions.json`, `apply-report.json` | apply-verdict отказывает без ACCEPT; ORCH сверяет artifacts_out | RELEASE-VALIDATOR (перепроверяет сам) + DOC-UPDATER (применяет изменения) |

Все роли — **разные запуски агентов**. Аналитик одной точки зрения во всех трёх
раундах — один и тот же запуск (продолжение, а не новый агент). ORCH назначает каждой
роли метку (`instance`) в `run.json`; каждый артефакт указывает `produced_by`, validate
сверяет. Идентификатор реального запуска агента ORCH записывает в handoff в поле
`context.agent_run_id` сразу после запуска (§8). Метки объявляются, а не доказываются —
честное ограничение; доказуемыми их сделают события хуков из REQ-001.

## 3. Идентификаторы, места, корень

- `RUN-ID`: `WF06-YYYYMMDD-NN` (UTC-дата, NN — номер за день, с 01).
- Папка прогона: `<root>/runs/<RUN-ID>/`; `run_id` в каждом артефакте равен имени папки.
- `idea_id`: `^[0-9]{2}-[a-z0-9-]+$` — имя файла идеи без `.md`; файл
  `<root>/ideas/<idea_id>.md`.
- Корень проекта `<root>`: опция `--root <dir>`; по умолчанию — родитель папки
  `tools/`. Тесты всегда передают `--root` на временную копию и реальный `sai/` не
  трогают.
- Время: ISO 8601 UTC `YYYY-MM-DDTHH:MM:SSZ`, из часов, не из памяти.

## 4. Контракты

Общее для всех JSON: поле `schema` с точным значением; поле `run_id`; поле
`produced_by: {"role": "...", "instance": "..."}` (кроме run.json — его создаёт
prepare-run). Лишние поля верхнего уровня — ошибка `E_SHAPE`. Повтор элемента, который
должен быть уникальным, — `E_DUPLICATE`.

### 4.1 `run.json` и `sources/` — создаёт `prepare-run` (ORCH, шаг 0)

```
npm run prepare-run -- WF06-20260925-01 \
  --candidates 01-alpha,02-beta,03-gamma,04-delta \
  --context ideas/05-drugie-idei.md,docs/quality-bar.md \
  --analyst market=analyst-market --analyst execution=analyst-execution \
  --analyst owner_fit=analyst-owner-fit --judge judge --executor executor
```

Результат:

```json
{
  "schema": "sai.wf06-run/1",
  "run_id": "WF06-20260925-01",
  "created_at": "2026-09-25T12:00:00Z",
  "candidates": ["01-alpha", "02-beta", "03-gamma", "04-delta"],
  "sources": [
    { "path": "ideas/01-alpha.md", "original_sha256": "...", "clean_sha256": "..." }
  ],
  "roster": {
    "analysts": { "market": "analyst-market", "execution": "analyst-execution", "owner_fit": "analyst-owner-fit" },
    "judge": "judge",
    "executor": "executor"
  }
}
```

и очищенные копии `runs/<RUN-ID>/sources/<path>`.

Правила prepare-run (и validate для run.json):
- `RUN-ID` в формате §3; по пути папки прогона нет ничего — ни папки, ни файла любого
  типа (в том числе канала или сокета), ни ссылки, даже битой (проверка `lstat`, без
  перехода по ссылке) — иначе `E_USAGE`, код 2 (P12). Правило «цель — не обычный файл»
  (§5.3, W1.2) — только для целей apply-verdict; у prepare-run любая запись по этому пути
  — `E_USAGE`.
  Если `lstat` не удался (ENOENT, ENOTDIR — например, `runs` оказался файлом, EACCES и
  любая другая ошибка), записи по этому пути считаются отсутствующими: что не так, скажут
  проверка и запись (§5.3, P1–P4) кодом `E_WRITE`.
- Кандидатов ≥ 2, формат `idea_id`, файл существует — иначе `E_CANDIDATE`.
- Источники = файлы всех кандидатов + `--context`. Путь соответствует
  `^(ideas|docs)/[A-Za-z0-9._/-]+\.md$`, без `..`, файл существует, и это **не**
  `ideas/README.md` (там таблица статусов) — иначе `E_SOURCE_PATH`.
- Все пять меток различны и не пустые — иначе `E_ROSTER`.
- Ошибка проверки — код 1, **ничего не создаётся** (всё собирается в памяти, потом
  пишется).
- **Запись — всё или ничего** (ISS-0002; §5.2–§5.7, вариант «новая папка»). Папка
  прогона собирается во временной папке `runs/.<RUN-ID>.sai-tmp/` и одним переименованием
  становится `runs/<RUN-ID>/`. Если нет `runs/`, так же собирается и переименовывается
  сама `runs/` (временная папка `.runs.sai-tmp/`). `runs` — файл или ссылка; временная
  папка осталась от прерванного запуска; ошибка ОС при создании папок, записи, сбросе
  на диск или переименовании — `E_WRITE`, код 1, ничего не создано (строгий список
  `<root>` не меняется, §5.2).
- validate дополнительно: каждая копия в `sources/` существует и её sha256 равен
  `clean_sha256` — иначе `E_SOURCE_CHANGED`. Если оригинал ещё совпадает со своим
  `original_sha256`, validate заново очищает его и сравнивает результат с копией; не
  совпало — `E_SOURCE_CHANGED` (защита от правки копии вместе с её хешем). Оригиналы
  после шага 0 можно менять: тогда прогон проверяется по своим копиям и остаётся
  проверяемым.
- **Печать прогона.** prepare-run печатает `seal <sha256 файла run.json>`. `run.json`
  содержит `clean_sha256` каждой копии, поэтому печать закрепляет и копии. ORCH
  записывает печать в `context.run_seal` handoff-а шага 0 и в свой отчёт владельцу —
  вне папки прогона. `validate --seal <hex>` сверяет печать; не совпала — `E_SEAL`.
  RELEASE-VALIDATOR запускает validate с печатью из handoff-а шага 0. (Коммит в git на
  шаге 0 был бы надёжнее, но коммиты делаются только с разрешения владельца.)

### 4.2 Очистка источников — чтобы выбор не был круговым

Файлы идей уже содержат прошлые выводы («Статус: выбрана», колонка «Итог»). Аналитики
получают копии без них. Правила, по порядку:

1. Области между строками `<!-- conclusion:start -->` и `<!-- conclusion:end -->`
   удаляются вместе с маркерами. Маркеры непарные или вложенные — `E_SOURCE_MARKERS`.
   Выводы в файлах идей размечает ORCH до шага 0.
2. Абзац (подряд идущие непустые строки), первая строка которого начинается с
   `Записано:` или `Статус:`, удаляется целиком.
3. В таблицах Markdown удаляется колонка, заголовок которой после снятия `*` и обрезки
   пробелов по краям равен `Итог`, `Статус` или `Почему нет` — во всех строках этой
   таблицы.
4. Остальной текст не меняется ни на байт.

**Что аналитики и судья читают.** Очистка защищает не только цитаты, но и чтение:
роли IDEA-ANALYST и IDEA-JUDGE читают **только** `runs/<RUN-ID>/` (очищенные копии и
артефакты прогона) и `docs/quality-bar.md`. Оригиналы в `ideas/`, `ideas/README.md`,
`STATE.md`, `docs/requirements.yaml`, `decisions/` им запрещены — это записано в их
мандатах и перекрывает стартовое чтение из `CLAUDE.md` (REQ-003 AC3).

**Остаточная утечка, которую убрать нельзя.** `CLAUDE.md` загружается в каждого агента
автоматически и называет продукт проекта. Аналитики поэтому знают, какая идея стала
проектом. Это ограничение записывается в §11 и в каждом `verdict-N.md` в разделе
`## Ограничения` (проверяет validate, `E_VERDICT_MD`).

### 4.3 Точки зрения и критерии — фиксированы в `tools/src/contract.js`

| lens | Критерии, балл 1–5 |
|---|---|
| `market` | `demand_evidence` — насколько доказаны проблема и готовность платить; `competition_gap` — насколько свободно место |
| `execution` | `cost_to_test` — насколько дёшево и быстро проверить спрос; `build_fit` — насколько подходят имеющаяся база и планка качества |
| `owner_fit` | `owner_goals` — насколько отвечает целям владельца: доход, свой продукт, интерес; `no_selling_self` — насколько обходится без продажи себя, продаж крупным компаниям и доступа к чужому коду |

Шкала: 1 — сильно против, 3 — нейтрально или не ясно, 5 — сильно за. Веса равны.

### 4.4 Доказательство (evidence) — общее правило

`{"source": "<путь из run.sources>", "quote": "<дословный текст>"}`

- `source` — один из `run.sources[].path` — иначе `E_EVIDENCE_SOURCE`.
- `quote` — не короче 12 символов — иначе `E_QUOTE_SHORT`.
- `quote` дословно есть в **очищенной копии** `runs/<RUN-ID>/sources/<source>`:
  сравнение после замены любой последовательности пробельных символов на один пробел в
  обоих текстах — иначе `E_QUOTE_NOT_FOUND`. Вывод, удалённый очисткой, процитировать
  невозможно.

### 4.5 `assessment-<lens>.json` — IDEA-ANALYST, раунд 1

```json
{
  "schema": "sai.idea-assessment/1",
  "run_id": "WF06-20260925-01",
  "produced_by": { "role": "IDEA-ANALYST", "instance": "analyst-market" },
  "lens": "market",
  "ideas": [
    {
      "idea_id": "02-beta",
      "scores": {
        "demand_evidence": { "score": 4, "evidence": [ { "source": "...", "quote": "..." } ], "comment": "..." },
        "competition_gap": { "score": 4, "evidence": [ ... ], "comment": "..." }
      },
      "summary": "..."
    }
  ]
}
```

- `lens` известна и совпадает с именем файла — иначе `E_LENS`.
- `produced_by` = `IDEA-ANALYST` и метка `roster.analysts[lens]` — иначе `E_PRODUCER`.
- Каждый кандидат ровно один раз, у каждого ровно критерии своей точки зрения — иначе
  `E_COVERAGE`.
- `score` — целое 1–5 — иначе `E_SCORE_RANGE`.
- У каждой оценки ≥ 1 доказательство по 4.4 — иначе `E_EVIDENCE_MISSING`; `comment` и
  `summary` не пустые — иначе `E_SHAPE`.

### 4.6 `crossreview-<lens>.json` — IDEA-ANALYST, раунд 2

```json
{
  "schema": "sai.idea-crossreview/1",
  "run_id": "...",
  "produced_by": { "role": "IDEA-ANALYST", "instance": "analyst-market" },
  "lens": "market",
  "items": [
    { "lens": "execution", "idea_id": "02-beta", "criterion": "cost_to_test", "their_score": 4,
      "stance": "agree", "note": "..." },
    { "lens": "owner_fit", "idea_id": "03-gamma", "criterion": "owner_goals", "their_score": 4,
      "stance": "disagree", "proposed_score": 2, "note": "...",
      "evidence": [ { "source": "...", "quote": "..." } ] }
  ]
}
```

- `items` покрывают **каждую** пару (кандидат, критерий) **обеих** других точек зрения
  ровно один раз; своих критериев нет — иначе `E_REVIEW_COVERAGE`. Пустой cross-review
  невозможен.
- `their_score` равен баллу раунда 1 — иначе `E_THEIR_SCORE`.
- `stance` — `agree` или `disagree` — иначе `E_SHAPE`; `note` не пустой — иначе
  `E_SHAPE`. У `disagree` есть `proposed_score` 1–5, отличный от `their_score`, и ≥ 1
  доказательство по 4.4 — иначе `E_DISAGREE_SHAPE`.

### 4.7 `response-<lens>.json` — IDEA-ANALYST, раунд 3

```json
{
  "schema": "sai.idea-response/1",
  "run_id": "...",
  "produced_by": { "role": "IDEA-ANALYST", "instance": "analyst-owner-fit" },
  "lens": "owner_fit",
  "responses": [
    { "raised_by": "market", "idea_id": "03-gamma", "criterion": "owner_goals",
      "action": "revise", "from": 4, "to": 3, "reason": "..." },
    { "raised_by": "execution", "idea_id": "02-beta", "criterion": "no_selling_self",
      "action": "hold", "reason": "...", "evidence": [ { "source": "...", "quote": "..." } ] }
  ]
}
```

- На **каждое** несогласие (раунд 2) с оценками этой точки зрения — ровно один ответ;
  лишних нет — иначе `E_RESPONSE_COVERAGE`. Если несогласий нет, `responses` пустой.
- `action`: `revise` — `from` равен баллу раунда 1, `to` 1–5 и ≠ `from`; `hold` — ≥ 1
  доказательство по 4.4. `reason` не пустой. Иначе `E_RESPONSE_SHAPE`.
- Несколько `revise` на одну пару с разными `to` — `E_RESPONSE_CONFLICT`.

**Итоговый балл** пары = `to` из `revise`, если он есть, иначе балл раунда 1.

### 4.8 `verdict-N.json` и `verdict-N.md` — IDEA-JUDGE, N = 1…3

```json
{
  "schema": "sai.idea-verdict/1",
  "run_id": "...",
  "produced_by": { "role": "IDEA-JUDGE", "instance": "judge" },
  "version": 1,
  "created_at": "2026-09-25T13:00:00Z",
  "ranking": [ { "idea_id": "02-beta", "rank": 1, "total": 25, "rationale": "..." } ],
  "chosen": "02-beta",
  "confidence": "medium",
  "reasons": [ { "text": "...", "refs": [ { "lens": "market", "idea_id": "02-beta", "criterion": "demand_evidence" } ] } ],
  "dissent": [ { "raised_by": "market", "lens": "owner_fit", "idea_id": "03-gamma", "criterion": "owner_goals", "resolution": "..." } ],
  "conditions": ["..."],
  "kill_criteria": ["..."],
  "owner_decision_required": true,
  "next_actions": [ { "to_agent": "REQ-ANALYST", "task": "...", "acceptance_criteria": ["..."] } ]
}
```

- `version` равен N в имени файла — иначе `E_VERSION`. `created_at` в формате ISO UTC —
  иначе `E_SHAPE`.
- `ranking`: каждый кандидат ровно один раз — `E_RANKING_COVERAGE`; ранги 1…K подряд —
  `E_RANK_SEQUENCE`; `total` = сумма итоговых баллов (4.7) — `E_TOTAL_MISMATCH`; порядок
  по убыванию суммы — `E_RANK_ORDER`; `rationale` не пустой — `E_SHAPE`.
- `chosen` — идея с рангом 1 — `E_CHOSEN_NOT_FIRST`.
- `confidence` ∈ `low`/`medium`/`high` — `E_SHAPE`.
- `reasons`: ≥ 2; каждая ссылка — на существующую оценку; ≥ 2 причин ссылаются на
  `chosen` — иначе `E_REASONS`.
- `dissent`: **каждое** несогласие, на которое ответили `hold`, есть в `dissent` ровно
  один раз с непустым `resolution` — `E_DISSENT_MISSING`.
- `conditions`, `kill_criteria` не пустые — `E_SHAPE`.
- `owner_decision_required` строго `true` — `E_OWNER_DECISION`.
- `next_actions`: 1–5 элементов — `E_SHAPE`; `to_agent` ∈ {`REQ-ANALYST`, `BA-ANALYST`,
  `ORCH`} — `E_NEXT_ACTION_AGENT`; `task` и `acceptance_criteria` не пустые — `E_SHAPE`.
- `verdict-N.md` существует, содержит строку `chosen` и заголовок `## Ограничения` —
  иначе `E_VERDICT_MD`.

### 4.9 `verdict-review-N.json` — VERDICT-EXECUTOR

```json
{
  "schema": "sai.verdict-review/1",
  "run_id": "...",
  "produced_by": { "role": "VERDICT-EXECUTOR", "instance": "executor" },
  "version": 1,
  "decision": "ACCEPT",
  "checks": [ { "name": "tool_validate", "result": "PASS", "detail": "..." } ],
  "issues": []
}
```

- Обязательные `checks`, каждый ровно один раз: `tool_validate` (запуск
  `validate --stage verdict`, в `detail` — его вывод), `totals_recomputed`,
  `quotes_spot_checked` (сам открыл очищенные копии для ≥ 2 причин выбранной идеи),
  `dissent_covered`, `next_actions_in_scope`. `result` ∈ `PASS`/`FAIL`, `detail` не
  пустой. Иначе `E_REVIEW_CHECKS`.
- `ACCEPT` только если все `PASS`; `REJECT` только с непустым `issues` — иначе
  `E_REVIEW_DECISION`. `version` равен N — иначе `E_VERSION`.

### 4.10 Версии и цикл доработки

- Первая версия — `verdict-1`. `verdict-N` при N > 1 допустим, только если есть
  `verdict-review-(N-1)` = `REJECT`. `verdict-review-N` — только если есть
  `verdict-N`. Иначе `E_VERSION`.
- N ≤ 3: файл с N ≥ 4 — `E_REVIEW_LIMIT`.
- Текущая версия — наибольшая N. После `verdict-review-3` = `REJECT` прогон
  **эскалирован** владельцу.

### 4.11 Разделение ролей

`produced_by.instance` каждого артефакта совпадает с меткой своей роли из `roster`
(аналитик — своей точки зрения, судья, исполнитель) — иначе `E_PRODUCER`. Метки в
`roster` различны (4.1), поэтому судья не может быть аналитиком, а исполнитель —
судьёй.

## 5. apply-verdict — бизнес-логика второго агента

Вход: папка прогона. **Сначала вся проверка, потом все записи.**

1. Полная проверка прогона (`--stage review`). Ошибка — код 1, ни одной записи.
2. Режим по последней проверке N:
   - `ACCEPT` → режим **recommend**;
   - `REJECT` и N < 3 → `E_NOT_ACCEPTED`, код 1, ни одной записи (идёт доработка);
   - `REJECT` и N = 3 → режим **escalate**.
3. Подготовить в памяти:
   - **Блок STATE.md**, режим recommend:

     ```
     <!-- sai:wf06:start -->
     ### Рекомендация агентов (WF-06)

     Прогон `<RUN-ID>`, вердикт версии <N> от <YYYY-MM-DD из created_at вердикта>.
     Рекомендованная идея: **<первая строка очищенной копии runs/<RUN-ID>/sources/ideas/<chosen>.md без «# »>** (`<chosen>`), уверенность: <низкая|средняя|высокая>.

     Причины:
     - <reasons[i].text, первые три>

     Условия:
     - <conditions>

     Остановиться, если:
     - <kill_criteria>

     Решение принимает владелец. До его записи код продукта не пишется.
     Подробно: `runs/<RUN-ID>/verdict-<N>.md`; следующие шаги для ORCH: `runs/<RUN-ID>/proposed-actions.json`.
     <!-- sai:wf06:end -->
     ```

     Режим escalate:

     ```
     <!-- sai:wf06:start -->
     ### Рекомендация агентов (WF-06)

     Прогон `<RUN-ID>`: агенты не пришли к принятому вердикту за 3 проверки.
     Нужно решение владельца.

     Последние замечания исполнителя:
     - <issues из verdict-review-3>

     Решение принимает владелец. До его записи код продукта не пишется.
     Подробно: `runs/<RUN-ID>/verdict-3.md`, `runs/<RUN-ID>/verdict-review-3.json`.
     <!-- sai:wf06:end -->
     ```

   - **Размещение блока.** Если маркеров нет — блок и одна пустая строка после него
     вставляются непосредственно перед строкой `### Что делать дальше — по порядку`;
     нет такой строки — `E_STATE_ANCHOR`. Если маркеры есть — заменяется текст от
     начального до конечного маркера включительно. Маркеров должно быть ровно по одному
     и начальный раньше конечного — иначе `E_STATE_MARKERS`.
   - **Защита раздела владельца.** Раздел владельца — от строки
     `### Решение владельца о старте` до первой следующей строки, которая начинается с
     `### ` **или равна** `<!-- sai:wf06:start -->` (не включая её). Нет строки
     заголовка — `E_STATE_ANCHOR`. Раздел вычисляется в исходном и в новом тексте; если
     отличается — `E_OWNER_SECTION`, ни одной записи. (Блок вставляется перед
     следующим заголовком, поэтому при правильной работе раздел владельца всегда
     совпадает; проверка ловит, например, маркеры, перенесённые внутрь раздела
     владельца.)
   - **`proposed-actions.json`** — только в режиме recommend:
     `{"schema":"sai.wf06-proposed-actions/1","run_id","verdict_version":N,"actions":[{"step":"10","to_agent","task","acceptance_criteria"}, ...]}`
     — шаги `10`, `11`, … по порядку `next_actions`. Handoff-ы по ним создаёт **ORCH**
     (шаг 6), не исполнитель.
   - **`apply-report.json`**:
     `{"schema":"sai.wf06-apply-report/1","run_id","verdict_version":N,"mode":"recommend|escalate","written":[{"path","sha256"}]}`
     — хеши итогового содержимого STATE.md и (в режиме recommend) proposed-actions.json.
4. Всё содержимое выводится только из артефактов прогона и его очищенных копий —
   никакого текущего времени, случайных значений и чтения оригиналов в `ideas/`.
   Повторный запуск даёт те же байты.
5. **Записать — всё или ничего** (§5.1–§5.7). Цели в порядке фиксации:
   `runs/<RUN-ID>/proposed-actions.json` (только recommend),
   `runs/<RUN-ID>/apply-report.json`, `STATE.md` — последней. Заменяются только цели,
   байты которых отличаются от новых. Совпадают все — на диске ничего не меняется, вывод
   `unchanged`, код 0. Иначе вывод `applied <mode>`, код 0. Сбой записи — `E_WRITE`
   (§6), код 1, и на диске всё как до запуска (§5.2).

Обработанный сбой — любое из: цель или папка на пути к ней не такая, как требует §5.3
(W1, P1); остаток прерванного или параллельного запуска; ошибка ОС при проверке,
подготовке, фиксации или уборке (EACCES, EPERM, EROFS, ENOSPC, EDQUOT, EFBIG, EIO — и
любая другая ошибка ОС).

При обработанном сбое команда:

1. завершается с кодом 1; stdout пуст; в stderr — только строки `E_WRITE` (§5.6); строк
   трассировки (`^\s+at `) нет;
2. оставляет строгий список `<root>` (§9.2) таким, каким он был до запуска: те же
   записи (папки, файлы, ссылки), те же типы и права; у файлов — те же байты и то же
   время изменения; у ссылок — тот же текст. **Время изменения папок не сравнивается:**
   временный файл создаётся и удаляется в папке цели, и ОС меняет время этой папки.
   Время доступа и время изменения метаданных (atime, ctime) не сравниваются;
3. после устранения причины и удаления названных остатков повторный запуск с теми же
   аргументами (у prepare-run — с тем же `--created-at`, §7) даёт те же байты целей, что
   запуск без сбоя. Вывод при этом — `applied <mode>`, если что-то осталось заменить, или
   `unchanged`, если заменять уже нечего (W15, W46); у prepare-run — `prepared`.

Исключения, о которых команда говорит отдельными строками (§5.6):

- двойной сбой — не удалось убрать свой временный файл или вернуть уже заменённую цель:
  итог первой строки говорит об этом, каждая оставшаяся запись названа своей строкой,
  остальное — как до запуска;
- сбой уборки после фиксации (§5.3, W4): применение состоялось — цели новые, как после
  чистого применения, — но осталась названная строкой `.sai-old`; код 1.

**Прерывание** (процесс убит сигналом SIGKILL в любой момент): каждая цель целиком
старая или целиком новая, никогда не обрезанная. Если STATE.md среди заменяемых целей,
он заменяется последним, поэтому если запуск уже заменил STATE.md — остальные заменяемые
цели уже новые. Если STATE.md заменять не нужно (его байты уже равны новым, W1.5), он в
замене не участвует: после прерывания между переименованиями он новый, а другая цель
может быть ещё старой, — но так было и до запуска, и запуск такого расхождения не
создаёт. У prepare-run цель — папка прогона: её либо нет, либо она есть целиком, потому
что появляется одним переименованием (W47, W48; P13, P14). Рядом с целями могут остаться
`.sai-tmp` и `.sai-old`; следующий запуск отказывается (`E_WRITE … leftover …`), пока
их не удалят; после удаления запуск сходится.

**Отключение питания и сбой ОС** в гарантию не входят: проверить это тестом нельзя (Q3).
Мера принята — временный файл сбрасывается на диск до переименования, чтобы после
сбоя ОС цель не оказалась пустой, — но результат не заявляется.

### 5.3 Порядок записи (D2)

Все шаги — в помощнике `writeAllOrNothing` (§5.7). Цели — в порядке фиксации (п. 5).
Для цели `<имя>` в её же папке: `.<имя>.sai-tmp` — новая версия,
`.<имя>.sai-old` — старая (жёсткая ссылка).

**W1. Проверка** — на диске ничего не меняется. Проверяются все цели, каждая — до
первого нарушения; все нарушения выводятся сразу, в порядке целей (как «все найденные»
в §6). Есть нарушение — дальше не идём.

1. Папки между `<root>` и целью (`runs`, `runs/<RUN-ID>`) — настоящие папки, не
   ссылки (`lstat`).
2. Сама цель (`lstat`, по ссылке не переходим): нет — будет создана; обычный файл —
   годится; папка, ссылка (в том числе битая), канал, сокет, устройство — нарушение.
3. Рядом с целью нет `.<имя>.sai-tmp` и `.<имя>.sai-old` (записи любого типа) — иначе
   нарушение «остаток». Проверяется и у цели, которую менять не нужно.
4. Существующая цель читается целиком (байты) — иначе нарушение.
5. Цель, байты которой равны новым, дальше не участвует (п. 6 к ней не применяется).
   Если нарушений нет ни у одной цели и так со всеми — `unchanged`, код 0, на диске
   ничего не изменилось; нарушение у любой цели (например, остаток у неизменной цели,
   W15) важнее — код 1.
6. Существующую цель, которую нужно изменить, этот пользователь может записать
   (`fs.accessSync`, `W_OK`) — иначе нарушение: EACCES — права; EPERM — например, файл
   «Заблокирован» в Finder (флаг `uchg`: проверено на этом Mac, `access` даёт EPERM).

`lstat` в пп. 1–3 (`fs.lstatSync`): ENOENT — «записи нет»; любая другая ошибка ОС —
нарушение `cannot be checked` (§5.6). Порядок пп. 2 и 4 не случаен: канал или сокет на
месте цели отсеивается до чтения, поэтому чтение не может зависнуть.

**W2. Подготовка** — только изменяемые цели, в порядке фиксации:

1. `fs.writeFileSync(<.sai-tmp>, <новые байты>, { flag: "wx", flush: true })`: файл
   создаётся, только если такого имени нет; записываются все байты; до закрытия
   файл сбрасывается на диск (на Node 22.21.1 проверено: с `flush: true` вызывается
   `fs.fsyncSync`). Права новой цели — по умолчанию (0666 с учётом umask), как сейчас.
2. Цель существует: `fs.chmodSync(<.sai-tmp>, <права цели> & 0o777)`, затем
   `fs.linkSync(<цель>, <.sai-old>)`.

Сбой — уборка (ниже), одна строка `E_WRITE`, итог `nothing was changed`.

**W3. Фиксация**: `fs.renameSync(<.sai-tmp>, <цель>)` по порядку; STATE.md, если он
среди заменяемых, — последним: его переименование — точка фиксации. Если STATE.md
заменять не нужно, точка фиксации — переименование последней из заменяемых целей. Сбой
на цели k — откат уже заменённых целей 1..k-1 в обратном порядке: цель существовала —
`fs.renameSync(<.sai-old>, <цель>)` (возвращается прежний файл: те же байты, права,
время изменения, inode); цели не было — `fs.unlinkSync(<цель>)`. Затем уборка
`.sai-tmp` и `.sai-old` целей k..n. Строка
`E_WRITE <цель k>: cannot be replaced (<код>); nothing was changed`.

**W4. Уборка после фиксации**: `fs.unlinkSync(<.sai-old>)` каждой заменённой цели, в
порядке фиксации (прямом: это порядок целей и порядок строк §5.6; общее правило «в
обратном порядке создания» относится к уборке и откату при сбое, не к W4). Цикл не
останавливается на неудаче: каждая цель получает свою попытку, каждая неудавшаяся — свою
строку. Сбой — применение состоялось, но остался файл: строка
`E_WRITE <.sai-old>: applied, but …` (§5.6), код 1 (W46: сбой на последней уборке; W55: на
первой, и остальные всё равно убраны).

**Общие правила.**

- Уборка и откат удаляют только то, что создал этот запуск (список в памяти), в
  обратном порядке создания. Каждый шаг уборки выполняется, даже если предыдущий не
  удался; сбой шага уборки или отката — дополнительная строка (§5.6).
- В `E_WRITE` превращаются только ошибки ОС — исключения, у которых `code` и `syscall` —
  строки (так Node описывает ошибки `fs`). Любое другое исключение — ошибка программы:
  откат и уборка выполняются, затем исключение идёт дальше без изменений (трассировка,
  код 1 от Node). Перехватывать «всё» нельзя: это спрятало бы ошибку программы (REVIEWER
  отметил это в ISS-0001). `main` в `cli.js` по-прежнему ловит только `UsageError`.
- Если при ошибке программы откат или уборка тоже не удались, строк `E_WRITE` об этом
  нет: исключение идёт дальше без изменений (трассировка, код 1 от Node), а то, что
  осталось на диске (`.sai-tmp`, `.sai-old`, временная папка prepare-run, цель с новым
  содержимым и прежним в `.sai-old`), называет следующий запуск строкой «leftover» (W1.3,
  P1) и отказывает, пока остаток не удалят. Строки теста на это нет.
- Все вызовы fs — через объект по умолчанию (`import fs from "node:fs"`, вызов
  `fs.renameSync(…)`), как во всех модулях `tools/src` сейчас; пути — лексические
  (`path.join(root, rel)`), а не `realpath`. Тесты (§9.2) подменяют методы этого объекта
  и узнают вызов по пути.
- Папки на диск не сбрасываются: без этого после сбоя ОС цель может оказаться старой, а
  это гарантия «старая или новая» допускает.

**Вариант «новая папка» — prepare-run** (§4.1; помощник `createFolderAllOrNothing`,
§5.7). Вершина — самая верхняя папка, которой ещё нет: `runs/<RUN-ID>`, а если нет
`runs` — сама `runs`. Временная папка — `.<имя вершины>.sai-tmp/` рядом с вершиной.

- P1. Проверка: `runs` (`lstat`): нет — вершина `runs`; настоящая папка — вершина
  `runs/<RUN-ID>`; ссылка — нарушение (ELOOP); иное — нарушение (ENOTDIR); другая
  ошибка ОС — нарушение `cannot be checked`. Остаток `.<имя вершины>.sai-tmp` —
  нарушение «остаток». Что по пути папки прогона ничего нет, проверено раньше
  (`E_USAGE`, §4.1).
- P2. Подготовка: `fs.mkdirSync(<временная папка>)` без `recursive` (занято — EEXIST,
  «остаток»); затем для каждого файла — сначала копии в порядке `run.sources`, потом
  `run.json` — `fs.mkdirSync(<папка файла>, { recursive: true })` внутри временной папки
  и `fs.writeFileSync(<файл>, <текст>, { flag: "wx", flush: true })`.
- P3. Фиксация: одно `fs.renameSync(<временная папка>, <вершина>)`. Если по пути
  вершины кто-то успел создать непустую папку или файл, переименование падает
  (ENOTEMPTY, ENOTDIR) — обычный сбой. Пустую папку POSIX заменяет; данных при этом не
  теряется.
- P4. Сбой P2 или P3 — `fs.rmSync(<временная папка>, { recursive: true, force: true })`,
  строка `E_WRITE`, итог `nothing was changed`; сбой удаления — дополнительная строка.

**Охрана — в самой операции** (правило Sai для CODE-DESIGNER). Безопасность держат сами
операции, а не предварительные проверки: (1) байты пишутся только в новый файл,
созданный эксклюзивно (`wx`), — цель нельзя обрезать; (2) замена — переименование, а
оно никогда не идёт по ссылке на месте цели; (3) эксклюзивное создание временного
файла, жёсткой ссылки и временной папки — второй одновременный запуск получает EEXIST и
ничего не меняет. Проверки W1 и P1 — правила (что команда отказывается делать) и ранние
понятные сообщения. Если цель или папка изменится между проверкой и переименованием — а
одновременную запись в один файл конвейер не допускает (AP-008, мандат ORCH), — худшее,
что может случиться: будет заменён файл, только что ставший ссылкой или файлом только
для чтения, или временный файл появится в папке, только что ставшей ссылкой. Обрезанной
цели и наполовину применённого набора это не даёт.

### 5.5 Временные имена (D4)

- Файл: `.<имя цели>.sai-tmp` — новая версия до переименования; `.<имя цели>.sai-old` —
  жёсткая ссылка на прежнюю версию на время фиксации. Оба — в папке цели. Папка
  (prepare-run): `.<имя вершины>.sai-tmp/` рядом с вершиной —
  `runs/.WF06-20260930-01.sai-tmp/` или `.runs.sai-tmp/`.
- **validate их не примет за артефакт.** Сканирования папки прогона —
  `^(assessment|crossreview|response)-(.+)\.json$` (`validate.js:143`),
  `^verdict-(\d+)\.(json|md)$` и `^verdict-review-(\d+)\.json$` (`validate.js:607–608`) —
  все начинаются с буквы и кончаются на `.json` или `.md`; наши имена начинаются с точки
  и кончаются на `.sai-tmp` или `.sai-old`. Папка `runs/.<RUN-ID>.sai-tmp/` не проходит
  `RUN_ID_RE`, и validate её не видит: он смотрит только внутрь одной папки прогона.
  `validate.js` не меняется.
- **snapshot и snapshot-diff видят остаток-файл и временную папку с файлом внутри; пустую
  временную папку — нет.** `snapshot` перечисляет только файлы (`listFiles` берёт записи
  с `isFile()`) и пропускает только `tools/node_modules` и `.git`. Поэтому
  `.STATE.md.sai-tmp`, `.STATE.md.sai-old` и временная папка prepare-run, где уже есть
  файл, попадают в snapshot-diff, а пустая временная папка (прерывание сразу после её
  создания) — нет (проверено 2026-10-01 на `snapshot.js`). Безопасность это не снижает:
  проверка остатков самой команды (W1.3, P1) видит и пустую папку и отказывает.
  Разрешение-файл (`--allow STATE.md`) не разрешает `.STATE.md.sai-tmp` (§7), поэтому
  остаток-файл в корне виден в snapshot-diff (REQ-004 AC4, REQ-006). Остаток внутри
  `runs/<RUN-ID>/` разрешён разрешением-папкой, но apply-verdict сам не запустится, пока
  он есть. `snapshot.js` не меняется.
- **Замок.** Имена постоянные; файл создаётся с `wx`, а `linkSync` и `mkdirSync` сами
  отказывают, если имя занято. Второй одновременный запуск на той же цели получает
  EEXIST и ничего не меняет — отдельный файл-замок не нужен.
- **Остаток** (после SIGKILL, отключения питания или двойного сбоя): команда
  отказывается (`E_WRITE … leftover …`, EEXIST) — и при изменяемой, и при неизменной
  цели, — пока его не удалят. Сама не удаляет: это может быть файл другого, ещё идущего
  запуска, а после прерывания записи в STATE.md должен посмотреть человек или ORCH. Цели
  при этом всегда целые (старые или новые), поэтому удалить остаток безопасно; после
  удаления повторный запуск сходится.
- **Сброс на диск**: `flush: true` у каждого временного файла; папки не сбрасываются.
  Устойчивость к отключению питания не заявляется (§5.2).

### 5.6 E_WRITE: сообщения (D5)

Строка: `E_WRITE <файл>: <причина> (<код ОС>); <итог>`. `<файл>` и пути внутри причины
— пути от `<root>` через `/` (`STATE.md`, `runs/WF06-20260925-01/apply-report.json`,
`.STATE.md.sai-tmp`); у файла вне `<root>` (правило для ISS-0003, в этой работе таких
целей нет) — как в командной строке. Причины и коды — ровно такие:

| Шаг | Причина | Код |
|---|---|---|
| W1.1 | `folder <папка> is a symbolic link` | ELOOP |
| W1.2 | `is a folder` | EISDIR |
| W1.2, P1 (`runs` — ссылка) | `is a symbolic link` | ELOOP |
| W1.2 | `is not a regular file` | EINVAL |
| P1 (`runs` — не папка и не ссылка) | `is not a folder` | ENOTDIR |
| W1.1–W1.3, P1 (ошибка `lstat`, кроме ENOENT) | `cannot be checked`; `<файл>` — путь, чей `lstat` не удался: цель, папка на пути к ней, остаток `.<имя>.sai-tmp` или `.<имя>.sai-old`, временная папка prepare-run | код ОС |
| W1.3, P1; EEXIST на W2 и P2 | `leftover <путь>[, <путь>] from an interrupted or concurrent run` (сначала `.sai-tmp`, потом `.sai-old`) | EEXIST |
| W1.4 | `cannot be read for comparison` | код ОС |
| W1.6 | `is read-only and must change` | код ОС (EACCES, EPERM) |
| W2.1 | `cannot write the temporary file <путь>` | код ОС |
| W2.2 | `cannot copy the permissions to <путь>` | код ОС |
| W2.2 | `cannot keep the old version as <путь>` | код ОС |
| W3 | `cannot be replaced` | код ОС |
| P2 | `cannot create the temporary folder <путь>` (файл — конечный путь вершины) | код ОС |
| P2 | `cannot create the folder` (файл — конечный путь папки) | код ОС |
| P2 | `cannot write` (файл — конечный путь файла) | код ОС |
| P3 | `cannot be moved into place` (файл — конечный путь вершины) | код ОС |

Итог:

- `nothing was changed` — строгий список как до запуска (§5.2);
- `no target was changed; leftovers are listed next` — не удалось убрать своё; дальше
  по строке на каждый остаток;
- `rollback incomplete; see the next lines` — не удалось вернуть заменённую цель; дальше
  по строке на каждую такую цель. Если к тому же не удалось что-то убрать — итог тот
  же, а строки об остатках идут следом.

У причины «leftover» после итога добавляется
`; if no other command is running, delete and re-run`.

Дополнительные строки:

- `E_WRITE <путь>: could not remove this temporary file (<код>); delete it by hand` —
  у папки `temporary folder`;
- `E_WRITE <.sai-old>: could not remove this backup of the old version (<код>); delete it by hand`;
- `E_WRITE <цель>: rollback failed (<код>); it holds the new content, the old content is in <.sai-old>`
  — цель существовала;
- `E_WRITE <цель>: rollback failed (<код>); it was created by this run and is still there`
  — цели не было;
- после фиксации (W4):
  `E_WRITE <.sai-old>: applied, but this backup of the old version could not be removed (<код>); delete it by hand`
  — единственная строка, код 1, stdout пуст.

Порядок строк: нарушения W1 и P1 — в порядке целей; при сбое позже — строка причины,
затем дополнительные строки в порядке целей.

**Для ISS-0003.** `E_WRITE` годится для её случаев записи: a (STATE.md 444 — закрыт здесь,

## 7. Командная строка

```
cd tools
npm run prepare-run -- <RUN-ID> --candidates <ids> [--context <paths>] --analyst <lens>=<label> ×3 --judge <label> --executor <label> [--created-at <YYYY-MM-DDTHH:MM:SSZ>] [--root <dir>]
npm run validate -- ../runs/<RUN-ID> [--stage run|assessments|crossreviews|responses|verdict|review] [--seal <hex>] [--root <dir>]
npm run apply-verdict -- ../runs/<RUN-ID> [--root <dir>]
npm run snapshot -- <out-file> [--root <dir>]
npm run snapshot-diff -- <before> <after> --allow <prefix> [--allow <prefix> ...]
npm run check
```

- Стадии validate накопительные, по порядку: `run` → `assessments` → `crossreviews` →
  `responses` → `verdict` → `review`. `--stage X` проверяет все стадии до X
  включительно и требует их файлы. По умолчанию — `review`.
- `snapshot`: строки `<sha256>  <путь>` по всем файлам `<root>`, отсортированные по
  пути, кроме `tools/node_modules/` и `.git/`.
- `snapshot-diff`: `<before>` и `<after>` — обычные файлы (не папка, не канал вроде
  `<(…)`); иначе `E_USAGE`, код 2. Печатает `changed|added|removed <путь>` для каждого
  отличия вне разрешённого; код 1, если такие есть, иначе 0. Значение `--allow`,
  оканчивающееся на `/`, разрешает папку целиком; любое другое — ровно один файл
  (`STATE.md` не разрешает `STATE.md.bak`).
- `apply-verdict`: в stdout — `applied <mode>` или `unchanged`, код 0. При любой ошибке
  (`E_*`, в том числе `E_WRITE`) stdout пуст, код 1 (у `E_USAGE` — 2).
- `prepare-run`: в stdout — `prepared <RUN-ID>` и `seal <hex>`, код 0; при ошибке stdout
  пуст. `--created-at` задаёт `run.json.created_at` (по умолчанию — текущее время UTC;
  другой формат — `E_USAGE`, код 2, `cli.js:71`, `prepare.js:28–34`). Тесты передают его,
  чтобы повторный запуск давал те же байты (§5.2, п. 3; §9.5).
- Временные имена рядом с целями (§5.5): `.<файл>.sai-tmp`, `.<файл>.sai-old`; у
  prepare-run — папка `.<папка>.sai-tmp/`. После успешной команды их нет. Прерванная
  команда может их оставить; тогда следующая откажется работать
  (`E_WRITE … leftover …`), пока их не удалят. Удалять — только убедившись, что никакая
  команда `tools/` сейчас не работает.
- `snapshot` перечисляет файлы, поэтому остаток-файл и временная папка prepare-run с
  файлом внутри попадают в `snapshot-diff`; пустая временная папка — нет (§5.5).

**Строгий список — `tree(root, ...extra)`** в `helpers.js`. Заменяет нынешний `tree()`,
поэтому и прежние проверки «ничего не записано» (REQ-002 AC6, AC7, `cli.test.js`)
становятся строже. Одна строка на запись: `<тип> <права> <размер> <содержимое> <время> <путь>`.

- Результат — одна строка текста: записи, соединённые `"\n"`, как у нынешнего `tree()`;
  `extra` необязателен. Поэтому прежние сравнения `assert.equal(tree(root), before)` в
  `apply.reject.test.js`, `apply.state.test.js`, `apply.accept.test.js` и `cli.test.js`
  работают без правки.
- Тип: `d` папка, `f` файл, `l` ссылка, `o` иное. Права — 4 восьмеричные цифры
  (`mode & 0o7777`). Права входят в строку, поэтому существующие тесты с `chmod`
  (`cli.test.js` — «unreadable verdict-1.md», он сравнивает список; `validate.run.test.js`
  — нечитаемая копия, списка там нет, но правится так же) возвращают права, прочитанные
  до `chmod` (`fs.statSync`), а не литерал `0o644`: при `umask 077` файл фикстуры
  создаётся с правами 0600, и литерал даёт разницу в списке (проверено 2026-10-01: до
  0600, после возврата `0o644` — 0644; при `umask 022` разницы нет).
- Файл: размер в байтах; sha256 байтов (не читается — `unreadable`); время изменения в
  наносекундах.

## 11. Сознательные решения

- **Выбор привязан к итоговым баллам.** Судья не может выбрать идею не с первого места.
  Влияние судьи и разногласий — через раунды 2–3 и `dissent`. Если окажется слишком
  жёстко — менять через решение владельца.
- **Выводы убираются из источников, а не фильтруются по словам.** Фильтр слов и
  пропускал выводы, и отсекал факты; разметка `conclusion` + очистка — явная и
  проверяемая.
- **Handoff-ы создаёт только ORCH** (`docs/workflows/handoffs.md`, «Кто что пишет»).
  Исполнитель готовит `proposed-actions.json`.
- **Служебный код на Node 22** (`decisions/0002`) не предрешает стек продукта; номер
  `0001` оставлен за решением о стеке.
- **Метки ролей объявляются, а не доказываются** — честное ограничение до REQ-001.
- **Аналитики знают название проекта.** `CLAUDE.md` загружается в каждого агента и
  называет продукт; убрать это без отдельной папки без `CLAUDE.md` нельзя. Поэтому
  выбор честно называется **перепроверкой** уже сделанного выбора, а ограничение
  пишется в каждом вердикте (`## Ограничения`).
- **Запись — переименованием, откат — жёсткими ссылками** (ISS-0002, §5.3). Варианты:
  (1) запись на месте с проверками до неё — отклонено: M2 остаётся, а ENOSPC, EFBIG и
  EIO проверкой заранее не поймать; (2) временный файл и переименование без отката,
  STATE.md последней, в сообщении — что уже заменено, — отклонено: при сбое фиксации
  список файлов меняется, обещание §5 «ни одной записи» нарушено; (3) то же, но откат из
  копий старых байтов — отклонено: откат требует ещё одной записи, которая сама может
  сломаться, и возвращает другой файл (новое время изменения, новый inode); (4) выбрано:
  жёсткие ссылки — откат без записи, возвращается тот же файл. Цена — файловая система
  должна уметь жёсткие ссылки (APFS умеет; на FAT будет отказ без изменений).
- **Отказ, а не обход** (§5.4): цель только для чтения, цель-ссылка, ссылка на пути к
  цели, папка только для чтения. Отказ для папки только для чтения — новый (раньше
  запись на месте проходила) — сознательно: иначе вернулась бы M2.
- **Постоянные временные имена; остаток команда сама не удаляет** (§5.5): замок без
  файла-замка; после прерывания записи в STATE.md смотрит человек или ORCH.
- **Файл сбрасывается на диск, но при отключении питания ничего не обещается** (§5.2):
  проверить нельзя (Q3); папки не сбрасываются — гарантия «старая или новая» и так
  выполняется.
- **Только POSIX** (macOS, Linux): переименование поверх файла, права, жёсткие ссылки.
  Windows не поддерживается, как и прежде (тесты с `chmod`).
- **Чтение по ссылке на папку прогона принято** (ISS-0002, §5.4; AP-014 — место того же
  класса, оставленное сознательно, записано там, где его будет искать следующий читатель):
  `validate` и фаза чтения `apply-verdict` переходят по ссылке `runs/<RUN-ID>` (или
  `runs`) на папку вне `<root>`: `resolveRunDir` (`cli.js:37–55`) сравнивает пути, а
  существование проверяет `statSync`. Они только читают, а запись за пределы `<root>`
  закрыта (W1.1; W13, W13b), поэтому `cli.js` и `validate.js` не меняются. Принял ORCH
  2026-10-01; записано в `decisions/0004-write-phase-rename-and-hardlink-rollback.md`
  вместе со стратегией записи. Чтобы запретить такое чтение, нужны отдельное решение,
  правка `resolveRunDir` и тест на `E_USAGE`, код 2.
