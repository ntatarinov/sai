## 0. Кратко

1. **Один файл** `tools/src/picker/engine.js`, чистый модуль без единого `import` (ни `node:*`, ни соседних файлов): его можно проверить
   на любом компьютере и загрузить без сборки (п. D1). Четыре экспорта: `ANSWER_REASONS`, `visibleQuestions`, `resolveAnswers`,
   `computeResult` (п. 5).
2. **Два прохода по вопросам в порядке файла** (п. 6.2): мягкий (`visibleQuestions` — видимость, ничего не отвергает) и строгий
   (`resolveAnswers` / `computeResult` — тот же проход плюс проверка ответов). Строгий проход возвращает первую ошибку; ошибка —
   `{ code: "E_ANSWER", question, reason }`, где `reason` — одно из девяти слов `ANSWER_REASONS`; русских текстов ошибки движок не пишет (п. D4).
3. **Формула** (п. 6.5–6.8): балл решения — сумма `points` сработавших правил этого решения; порядок — по баллам по убыванию, при
   равенстве — по месту в `solutions`; рекомендованные — первые `top` с баллом не меньше `min_score`; «явный лидер» — рекомендовано
   одно или разрыв первого и второго не меньше `clear_lead_gap`. Пометка в результате — `clear_leader`: `true`, `false` или `null`
   (ничего не рекомендовано) — не слово, потому что слов, которых нет в файле арендатора, в результате быть не может (критерий 7).
4. **Объяснение** (п. 6.9): у каждого рекомендованного решения список `rules` — сработавшие правила в порядке файла (`id`, `points`,
   `text`, `because` — по записи на каждое условие правила: id вопроса и выбранные варианты или число). Сумма `points` равна баллу.
5. **Все шесть исходов** наборов ответов REQ-054 (п. 9.4 того проекта) движок даёт именно такими, как там записано: расчёт прототипом

## 2. Решения проекта

| № | Вопрос | Решение | Почему |
|---|---|---|---|
| D1 | Состав модуля | Один файл `tools/src/picker/engine.js`, **без единого `import`**. Ни `node:*`, ни соседних модулей (`limits.js` и других) | Критерий 8 (поиски по файлу); `PK-7c` не должен находить слово `node:` в новом файле; движок можно загрузить без сборки и проверить на любом компьютере. Один файл — поиски критериев 6 и 8 идут по одному пути, как в требовании |
| D2 | Откуда условия | Движок вычисляет условия сам (п. 6.3). Модуль `conditions.js` (проверка формы) не используется и не меняется; оракул тестов `visibleQuestionIds` в `src/` не берётся | Ф4: вычисления в `src/` нет. Независимость оракула тестов от кода — условие того, что тест видимости что-то доказывает (quality-bar §6, п. 1) |
| D3 | Что с ответом на скрытый вопрос | Он **полностью игнорируется**: не участвует в баллах, не проверяется на форму и не бывает ошибкой — даже если мусор (неизвестный вариант, не тот вид). Неизвестный *вопрос* (id нет в файле) — ошибка в любом случае | Буквальное чтение «ответ на невидимый вопрос в подсчёте не участвует и ошибкой не считается». Посетитель мог вернуться и сменить прошлый ответ — его прежний ответ скрытому вопросу остаётся в хранилище страницы (вопрос О3) |
| D4 | Форма ошибки | `{ code: "E_ANSWER", question: <id или null>, reason: <слово из ANSWER_REASONS> }`; одна — **первая** по порядку п. 6.4. Русского текста ошибки движок не пишет и ошибок списком не отдаёт | «Движок не сочиняет слов»; текст для посетителя — дело сервера и страницы (REQ-056: «код 400 и понятный текст»); одна ошибка достаточна для исправления и ограничивает размер ответа при враждебном вводе (вопрос О5) |
| D5 | Нормализация ответов | Выбранные варианты `single` и `multiple` в объяснении и в `resolveAnswers` — **список id в порядке `options` файла** (у `single` — из одного id); число `-0` становится `0`. Порядок элементов в присланном списке `multiple` на результат не влияет | «Одинаковые ответы дают побайтно одинаковый результат»: список `["b3","b1"]` и `["b1","b3"]` — одни и те же ответы. Критерий 6 проверяет и это |
| D6 | Как назвать пометку | Поле `clear_leader`: `true` — «явный лидер», `false` — «близкие варианты», `null` — ничего не рекомендовано (пометки нет). Строк-слов в результате нет | Критерий 7: каждое строковое значение результата равно строке файла арендатора. Слова «явный лидер» и «близкие варианты» — тексты страницы (REQ-058) |
| D7 | Числа в результате | Только: `score` (баллы решения), `points` (баллы правила) и — в `because` — число, которое посетитель ответил на вопрос `number` (`value`). Других чисел (счётчиков, мест, процентов) нет | Критерий 7 («чисел, кроме баллов, в результате нет»): ответ посетителя на вопрос `number` — не число движка, а эхо входа; без него объяснение «вы ответили 120» невозможно (вопрос О1) |
| D8 | Рейтинг всех решений | В результате есть `ranking` — все решения файла в порядке движка с баллом каждого, включая не рекомендованные | Нужен критерию 3 (порядок и ничьи проверяются на всех пяти решениях, как в таблице п. 9.4 REQ-054) и объяснению порядка. Что из этого уходит посетителю — решает сервер (вопрос О4) |
| D9 | Тексты решений | У каждого рекомендованного решения копируются поля `id`, `name`, `summary`, `includes`, `needs_from_you`, `next_steps`, `price_text` и `duration_text` (**только если поле есть в файле**: нет поля — нет ключа, не `null`), `not_suitable_when`; списки копируются новыми массивами | REQ-056: «результат — объект движка с текстами решений»; REQ-058: раздел «Цена» есть только при заданном поле. Копия не даёт изменить файл арендатора через результат |

## 4. Формы данных

### 4.1. Вход

* **Арендатор** — объект, который отдаёт REQ-054 (`checkFile(...).tenant` или `checkBytes(...).tenant` при коде 0; формат — п. 4 проекта REQ-054).
  Условие вызова: объект прошёл `validateTenant` с пустым списком ошибок. Объект не меняется.
* **Ответы** — «значение, полученное из JSON»: ожидается объект «id вопроса → ответ»; всё остальное (`null`, список, число, строка, `true`) — тоже допустимый
  вход, на который движок отвечает ошибкой, а не исключением. Ответ на вопрос: `single` — строка (id варианта); `multiple` — непустой список строк
  (id вариантов, без повторов); `number` — целое число (`Number.isSafeInteger`) между `min` и `max` включительно. Чужие и унаследованные свойства
  не читаются: берутся только собственные перечислимые строковые ключи. Ответы не меняются. Объекты с getter-ами и прокси вне контракта (из JSON
  таких не бывает).

### 4.2. Ошибка ответов

```
AnswerError = { code: "E_ANSWER", question: string | null, reason: string }
```

`question` — id вопроса (для неизвестного вопроса — присланный ключ); `null` только у `not_object`. `reason` — одно из девяти слов `ANSWER_REASONS`
(в этом порядке):

| `reason` | Когда |
|---|---|
| `not_object` | ответы — не объект (`null`, список, число, строка, `true`) |
| `unknown_question` | в ответах есть ключ, которого нет среди `questions` |
| `wrong_kind` | ответ не того вида: у `single` не строка; у `multiple` не список или в списке не строка; у `number` не число (`null`, строка, `true`, список, объект) |
| `unknown_option` | id варианта (у `single` — присланная строка, у `multiple` — элемент) не из `options` этого вопроса |
| `duplicate_option` | в списке `multiple` вариант встретился второй раз |
| `empty_list` | у `multiple` пустой список |
| `not_integer` | у `number` число не целое или не безопасное целое (`2.5`, `1e21`, `Infinity` — так читается `1e400`) |
| `out_of_range` | у `number` целое меньше `min` или больше `max` |
| `missing_required` | видимый вопрос с `required: true` без ответа |

### 4.3. Результат

```
EngineOutcome = { ok: true, result: Result } | { ok: false, error: AnswerError }     // ключа result при ok:false нет

Result = {
  clear_leader:  true | false | null,            // D6
  recommended:   Recommended[],                  // 0..top записей, в порядке движка
  no_match_text: string | null,                  // text no_match_text файла, если recommended пуст; иначе null
  ranking:       { solution: string, score: number }[],      // все решения файла в порядке движка (D8)
  hypotheses:    { id: string, title: string, explanation: string }[]   // в порядке файла
}

Recommended = {
  id, name, summary, includes[], needs_from_you[], next_steps[],
  price_text?, duration_text?,                   // только если поле есть в файле (D9)
  not_suitable_when[],
  score: number,
  rules: { id: string, points: number, text: string, because: Because[] }[]       // D10
}

Because = { question: string, selected: string[] }     // вопрос single или multiple: id выбранных вариантов в порядке options
        | { question: string, value: number }          // вопрос number: ответ посетителя
```

Порядок ключей в `Result`, `Recommended` и записях — ровно как написано (тест сверяет `Object.keys`, п. 12.1, PE-7d). Строк-слов в результате нет: каждое
строковое значение — строка файла арендатора (текст или id). Чисел, кроме `score`, `points` и `value`, нет (D7).

### 4.4. Результат строгой проверки ответов

```
Resolved = { ok: true, visible: string[], answers: { [id: string]: string[] | number } } | { ok: false, error: AnswerError }
```

`visible` — id видимых вопросов в порядке файла; `answers` — нормализованные ответы **только** на видимые вопросы, с ответом, в порядке файла (D5): список id
в порядке `options` или целое число. Это то, что нужно заявкам (REQ-059) от «ответов после проверки движком».

## 5. Функции модуля `engine.js`

Модуль ES (`"type": "module"`). Экспорты — контракт; внутренние помощники называет разработчик (не экспортируются).

### 5.1. Экспорты

| Экспорт | Сигнатура | Что делает |
|---|---|---|
| `ANSWER_REASONS` | `readonly string[]` (заморожен) | девять слов п. 4.2, в том порядке |
| `visibleQuestions` | `(tenant, answers) → string[]` | мягкий проход (п. 6.2): id видимых вопросов в порядке файла. Не отвергает ничего: ответы не объект — как пустые ответы; неизвестные ключи не читаются; ответ с неверной формой считается отсутствующим. Читает только `tenant.questions` (D12). Не бросает исключений |
| `resolveAnswers` | `(tenant, answers) → Resolved` | строгий проход (п. 6.4): первая ошибка или видимые вопросы с нормализованными ответами. Читает только `tenant.questions` (D12) |
| `computeResult` | `(tenant, answers) → EngineOutcome` | `resolveAnswers`, затем баллы, порядок, рекомендованные, пометка, гипотезы, объяснение (п. 6.5–6.10). На ошибку ответов — `{ ok: false, error }` |

Ни одна функция не меняет аргументы, не бросает исключений на допустимом арендаторе и любом значении ответов, не читает часы, среду, диск и сеть, не хранит
состояния между вызовами (никаких переменных модуля, кроме неизменяемых констант); два вызова с равным входом дают равный результат.

### 5.2. Контрольные вызовы (для разработчика, не тесты)

На малом файле п. 9 (`pico`): `visibleQuestions(pico, {})` → `["a","b","c"]`; `visibleQuestions(pico, { a: "a1", d: "d1" })` → `["a","b","c","d","g"]`;
`computeResult(pico, { a: "a1", b: ["b1"], c: 0, d: "d1", g: "g1" })` → `ok: true`, `ranking` `sol-m 7, sol-b 5, sol-k 0, sol-z 0`, `clear_leader: true`;
`computeResult(pico, { a: "a1", b: ["b1"], c: 5 })` → `{ ok: false, error: { code: "E_ANSWER", question: "d", reason: "missing_required" } }`; `computeResult(pico, null)` →
`reason: "not_object"`, `question: null`. На демо-арендаторах REQ-054 — п. 8.

### 5.3. Связь с общей функцией REQ-054

Все места, где используется формат файла арендатора, — в проекте REQ-054; движок их не меняет и не дублирует: формат берётся из объекта, поля `type`, `required`,
`options`, `min`, `max`, `show_if`, `when`, `solution`, `points`, `text`, `result` — по п. 4.2–4.10 того проекта. Если REQ-054 когда-нибудь изменит эти поля,
движок меняется вместе с ним (п. 13).

### 5.4. Что движок не делает

Не читает файлы, не ищет арендатора по id, не отвечает по сети, не пишет журнал, не строит слов, не округляет, не знает о других арендаторах (критерий 8): он получает
один объект арендатора и ничего больше; два вызова на разных арендаторах подряд дают то же, что каждый отдельно (PE-8e).

### 5.5. Что нужно от движка следующим требованиям (не их проект)

* Сервер (REQ-056) — `computeResult`; на `ok: false` решает, какой текст показать по `reason`.
* Страница анкеты (REQ-057) — видимость по уже данным ответам: `visibleQuestions` читает только список вопросов (D12) и не имеет импортов, поэтому одно и то же
  вычисление возможно на сервере и в странице; как страница получает модуль — проект REQ-057.
* Заявки (REQ-059) — `resolveAnswers` (ответы только видимых вопросов) и `computeResult` (рекомендованные решения пересчитываются сервером).
* Меняются эти контракты только вместе с названными требованиями.

## 6. Правила

### 6.1. Условие (в `show_if` вопроса, `when` правила и гипотезы)

Состояние — набор «id вопроса → нормализованный ответ» для вопросов, которые видимы **и** отвечены (п. 6.2). Условие верно, если вопрос `question` есть в состоянии и:

| Вид | Верно, если |
|---|---|
| `any_of` | среди выбранных вариантов есть хотя бы один из списка (у `single` выбран один) |
| `none_of` | вопрос в состоянии (отвечен и виден) и ни один выбранный вариант не входит в список |
| `min` и/или `max` | ответ-число не меньше `min` (если есть) и не больше `max` (если есть); границы включительно |

Вопроса нет в состоянии (не отвечен, скрыт, ответ неверной формы) — условие неверно, **в том числе `none_of`**. Группа условий (`show_if`, `when`) верна, если верны **все**
её условия. У вопроса без `show_if` (или с пустым списком) группы нет — вопрос виден; у правила и гипотезы `when` не бывает пустым (REQ-054: 1–3 условия).

### 6.2. Проход по вопросам (общий для мягкого и строгого)

Для каждого вопроса файла по порядку:

1. Вопрос **виден**, если у него нет `show_if` или группа условий верна по состоянию, собранному из вопросов выше. Условие на вопрос ниже или на себя (в корректном
   файле такого нет) неверно, потому что в состоянии его ещё нет.
2. Невидимый вопрос пропускается целиком: его ответ не читается, не проверяется, в состояние не попадает (D3).
3. Видимый — добавляется в `visible`.
4. Видимый без собственного ключа в ответах: если `required` — запоминается ошибка `missing_required` (если ошибок ещё не было); дальше — следующий вопрос.
5. Видимый с ответом — проверка по виду вопроса, останавливаясь на первой беде. `single`: не строка → `wrong_kind`; строка не из `options` → `unknown_option`. `multiple`: не список → `wrong_kind`;
   пустой → `empty_list`; затем по элементам с первого: не строка → `wrong_kind`, не из `options` → `unknown_option`, уже встречался → `duplicate_option`. `number`: не число → `wrong_kind`; не безопасное целое → `not_integer`;
   меньше `min` или больше `max` → `out_of_range`. Верный ответ нормализуется (п. 6.3) и попадает в состояние. Неверный — запоминается первая ошибка, вопрос считается неотвеченным.

Мягкий проход (`visibleQuestions`) возвращает `visible` и не смотрит на запомненные ошибки. Строгий — п. 6.4.

### 6.3. Нормализация ответа

`single`: верная строка → список из одного id. `multiple`: список → id в порядке `options` файла. `number`: число (`-0` → `0`).

### 6.4. Строгая проверка (порядок ошибок)

1. Ответы — не объект (`null`, список, число, строка, `true`) → `not_object`, `question: null`.
2. Среди ключей ответов есть id, которого нет в `questions` → `unknown_question`; берётся **наименьший** такой ключ по порядку кодовых единиц (не первый по порядку ключей). Это
   проверяется до прохода: лишний ключ важнее ненайденного ответа.
3. Проход по вопросам (п. 6.2); побеждает первая запомненная ошибка в порядке вопросов файла.
4. Ошибок нет → `Resolved` с `visible` и нормализованными `answers`.

### 6.5. Баллы

Балл решения = сумма `points` тех правил, у которых `solution` равно `id` решения и верны все условия `when` (п. 6.1) по состоянию после прохода. Правил нет — 0. Баллы целые;
отрицательные правила вычитаются; предел баллов не накладывается (минимум и максимум задаёт сумма правил файла).

### 6.6. Порядок и рекомендованные

1. Порядок (`ranking`): по баллам по убыванию; при равных баллах — по месту решения в `solutions` (раньше — выше). Ничья решается сравнением места, а не устойчивостью сортировки (D13).
2. Рекомендованные: из упорядоченных решений берутся те, у кого балл **не меньше** `result.min_score` (равный — берётся), и первые `result.top` из них. Если их нет —
   `recommended` пуст, `no_match_text` равен `result.no_match_text`; иначе `null`.

### 6.7. Пометка «явный лидер»

`recommended` пуст → `clear_leader: null`. Рекомендовано одно → `true`. Рекомендовано два или три → `true`, если балл первого минус балл второго **не меньше** `result.clear_lead_gap`
(разрыв, равный настройке, — «явный лидер»; на 1 меньше — «близкие варианты»), иначе `false`. Сравниваются первый и второй из **рекомендованных**.

### 6.8. Гипотезы

Гипотезы файла, у которых верны все условия `when`, — в порядке файла; в результате у каждой `id`, `title`, `explanation`. Не зависят от того, рекомендовано ли что-нибудь. Поля `hypotheses`
нет в файле — пустой список.

### 6.9. Объяснение

Для каждого рекомендованного решения `rules` — все его правила с верными условиями (положительные и отрицательные), в порядке файла. У записи: `id`, `points`, `text` правила
и `because` — по записи на каждое условие правила в порядке `when`: `question` — id вопроса условия; `selected` — нормализованный ответ (D5) для `single`/`multiple` либо `value` — число для `number`.
Сумма `points` записей равна `score`. Рейтинг и баллы нерекомендованных решений показываются только в `ranking`.

### 6.10. Тексты результата

Названия, тексты решений, тексты правил, гипотезы и `no_match_text` — копии строк файла арендатора; других слов в результате нет; чисел, кроме `score`, `points`, `value`, нет.

## 7. Пути отказа (Q10, Q5): что видит вызывающий и что остаётся неизменным

Во всех случаях: арендатор и ответы не меняются (глубокое сравнение с копией и вызов на глубоко замороженных объектах), состояния между вызовами нет, исключения нет.

| Случай | Что возвращается |
|---|---|
| ответы `null`, список, число, строка, `true` | `computeResult`/`resolveAnswers`: `{ ok: false, error: { code: "E_ANSWER", question: null, reason: "not_object" } }`; `visibleQuestions`: видимость как при пустых ответах |
| ключ, которого нет в файле, в том числе `__proto__` из `JSON.parse` | `unknown_question` с этим ключом (наименьшим из лишних) |
| ответ неверного вида / неизвестный вариант / повтор / пустой список / число не целое / вне границ | `wrong_kind` / `unknown_option` / `duplicate_option` / `empty_list` / `not_integer` / `out_of_range` с id вопроса |
| видимый обязательный вопрос без ответа | `missing_required` с id вопроса |

### 11.3. Помощники тестов (`tools/test/picker-engine-helpers.js`)

* **Малый файл** `pico` (п. 9) — литерал; функция «копия с другими настройками `result`».
* **Генератор наборов** `generateAnswers(tenant, rng)` с **зерном** (`makeRng` из `picker-helpers.js`; зерно закреплено константой; `Math.random` не используется): идти по `questions` в порядке файла; вопрос виден, если `visibleQuestionIds(tenant, ответы_пока)` (оракул
  `picker-helpers.js`) его содержит; обязательный видимый получает ответ всегда, необязательный — в 70% случаев; `single` — случайный вариант; `multiple` — случайное непустое подмножество в случайном порядке; `number` — в 15% `min`, в 15% `max`, иначе случайное
  целое в границах, причём с вероятностью около 30% — **граница условия** (число из `min`/`max` любого условия на этот вопрос, а также на 1 больше/меньше, если оно в границах вопроса); в 10% наборов к ответам добавляется допустимый ответ на скрытый вопрос (проверка D3). Только допустимые ответы на видимые вопросы (кроме добавки).
* **Второе вычисление** `expectedOutcome(tenant, answers)` — независимая запись формулы из описания требования (множества фактов, другие структуры, не копия кода движка): видимые вопросы (через оракул), верные правила в порядке файла, баллы, рейтинг по баллам и месту, рекомендованные, пометка, гипотезы.

* `shuffleKeys(answers, rng)` и `shuffleLists(answers, rng)` — для PE-6a. `deepFreeze(x)`, `deepCopy(x)`. `allStrings(tenant)` — множество всех строковых значений файла (для PE-7a), `numbersIn(result)` — пути всех чисел результата (для PE-7b).

### 16.2. Предложение записи `decisions/0067-picker-engine-contract.md` (номер назначает ORCH)

* **Вопрос:** как устроен контракт движка подбора там, где требование REQ-055 допускает несколько прочтений.
* **Варианты:** (1) ошибки списком и текстами по-русски или одна ошибка со словом-причиной; (2) ответ на скрытый вопрос проверяется или игнорируется; (3) пометка лидера — слово или булево значение; (4) числа ответов посетителя в объяснении — есть или нет; (5) рейтинг всех
  решений в результате — есть или нет; (6) движок — один файл без импортов или несколько файлов.
* **Выбор:** одна ошибка `{ code, question, reason }` со словом из девяти; скрытый ответ игнорируется полностью; пометка `clear_leader` — `true`/`false`/`null`; числа ответов посетителя есть только в `because[k].value`; `ranking` есть; один файл `engine.js` без импортов;
  выбранные варианты в объяснении — в порядке `options`; результат строится обходом файла.
* **Причина:** критерий 7 запрещает слова и числа, которых нет в файле; критерий 6 требует побайтно равного результата; одна ошибка и один файл — меньше поверхности и проще поиски критериев 6 и 8; страница и сервер получают общее вычисление видимости.
* **Граница:** не меняет формат файла арендатора и ничего в REQ-054; ответ ORCH на О1–О5 вносится в эту запись.
