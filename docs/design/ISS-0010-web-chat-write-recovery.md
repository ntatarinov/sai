## 4. Контракт ядра

### 4.1. `tools/src/team/lock.js`

Состояние модуля (только память процесса, на диск не пишется; ключ везде — `path.resolve(projectDir)`):

| Имя | Тип | Правило |
|---|---|---|
| `HELD` (не экспортируется; r3, F1) | `Map<string, LockTicket>` | значение — билет **последнего** успешного `acquireLock` этого процесса на эту папку; ставится при успешном `linkSync`, заменяется следующим успешным захватом; `releaseLock` его не трогает (билет закрытого писателя больше не используется). Размер — не больше числа папок, которые процесс открывал |
| `ORPHANED` (не экспортируется) | `Set<string>` | элемент есть ⇔ сломанный писатель этого процесса закрыт, **ещё держа замок** (условие `noteOrphanedLock`), и после этого этот процесс не брал замок на эту папку успешно |

Форма `LockTicket` (r3, F1): замороженный объект `{ bytes: string }` — точное содержимое файла-замка, которое записал этот
захват (`{"pid","since"[,"holder"]}` и перевод строки). Билет сравнивается по ссылке (`===`): два захвата одного процесса в
одну миллисекунду дают одинаковые `bytes`, но разные билеты. Вне `lock.js` и `store.js` билет не передаётся и не
сериализуется.

Функции:

| Сигнатура | Экспорт | Вход → выход | Ошибки |
|---|---|---|---|
| `acquireLock(projectDir, pid, since, holder) → {stalePid, ticket}` | да; **форма возврата расширена** полем `ticket` (единственный вызывающий — `store.js` `openWriter`; тесты `acquireLock` не вызывают — `grep -rn acquireLock tools/test` пуст) | шаг «замок занят»: `if (holdsLive(holder, projectDir)) throw busy(holder)` вместо `isAlive`; при успешном `linkSync` — новый билет с `bytes` = записанное содержимое, `HELD.set(key, ticket)`, `ORPHANED.delete(key)`, затем вернуть `{stalePid, ticket}` | как сейчас |
| `noteOrphanedLock(projectDir: string, ticket: LockTicket): boolean` | да | (r3, F1) отмечает папку, **только если этот писатель ещё держит замок**: (1) `HELD.get(key) === ticket` — после захвата этим писателем процесс не брал замок на папку снова; **и** (2) файл `writer.lock` сейчас — обычный файл не больше 4096 байт, и его содержимое байт-в-байт равно `ticket.bytes` (в нём pid этого процесса и время этого захвата — та же сверка содержимого, что `acquireLock` делает при снятии устаревшего замка). Оба условия — `ORPHANED.add(key)`, вернуть `true`; иначе ничего не менять, вернуть `false`. Файлов не пишет | не бросает никогда: ошибка чтения файла — `false` (папка не отмечена; проект занят для этого процесса до его выхода — прежнее поведение, остаточный риск `0026`) |
| `holdsLive(pid: number, projectDir: string): boolean` | **да** (r3, F2: нужен `channel.js`, п. 4.3) | `isAlive(pid) && !(pid === process.pid && ORPHANED.has(key))` — **единственное** место правила R2 | не бросает |
| `lockHolder(projectDir)` | да (без изменения формы) | `{pid, alive, holder}` или `null`; `alive` = `holdsLive(pid, projectDir)` | как сейчас (`E_LOCK_BAD`, `E_DISK` чтения) |
| `releaseLock`, `assertLockHeld`, `cleanLockLeftovers`, `isAlive` | да | **не меняются** (`cleanLockLeftovers` по-прежнему не трогает `.new`/`.stale-` живых pid; свои остатки `acquireLock` убирает сам) | — |

Инварианты:

- И-1. Ключ попадает в `ORPHANED` только из `Writer.close()` сломанного писателя (п. 4.2) и только при обоих условиях
  `noteOrphanedLock`. `markBroken()` ключ не добавляет (R3: пока писатель не закрыт, замок его).
- И-1а (r3, F1). Писатель, который замка уже не держит, папку не отмечает — какой бы ни была причина поломки: замок потерян
  (`E_LOCK_LOST` — файла нет, в нём чужой pid или другое содержимое) или после его захвата этот процесс взял замок снова
  (другой писатель, другой билет). Поэтому поздний `close()` такого писателя не делает «устаревшим» замок здорового писателя
  этого процесса: третье открытие — `E_PROJECT_BUSY`, как сейчас (Ф7).
- И-2. Свой замок считается не живым только при двух условиях сразу: pid в файле — pid этого процесса **и** ключ в
  `ORPHANED`. Чужой живой pid — всегда живой (P12 для других процессов).
- И-3. Проверка «не живой» и снятие замка — в одном синхронном вызове `openWriter` (`lockHolder` шаг 2 и `acquireLock` шаг 4
  одного вызова); между ними нет `await`, а в процессе один поток — другой писатель этого процесса вклиниться не может.
  Другой процесс вклиниться не может, потому что для него pid жив. Сверка `noteOrphanedLock` и отметка — тоже в одном
  синхронном вызове `close()`.
- И-4. После успешного `acquireLock` ключа нет, а билет в `HELD` — новый: здоровый писатель этого процесса, открытый после
  снятия, снова защищён от второго открытия (TM-11), а поздний `close()` прежнего сломанного писателя его не отмечает (И-1а).

## 11. Открытые вопросы и предложения

- **I-1.** `E_DISK` при **чтении** журнала внутри `openWriter` (отправка чата) ядро отдаёт тем же кодом без признака «чтение»;
  сервер покажет «Диск не принимает записи…». Предложение: отдельный дефект — `fromOsError` кладёт `details.action`
  (`"read"`/`"write"`), сервер для чтения показывает `TEXT.readFailed`. Меняет форму `details` у всех `E_DISK` ядра — вне этой
  работы, решает ORCH.
- **I-2.** (r3: решено ORCH) Команда из терминала видит «занят» (pid сервера), пока сервер со своим брошенным замком сам не
  откроет проект или не выйдет. Записано в `0026` как остаточный риск решения, **не** как исключение из планки: Q10 не
  нарушен — отказ правдив, сервер работает, снимается штатным действием (п. 9, Q10). Сервер сам свой замок сразу не снимает:
  это запись в журнал без запроса человека.
- **I-3.** (r3: закрыт, F3) `0026` принято ORCH 2026-10-10; владелец может отменить.
- **I-4.** (r3: решено ORCH — входит в работу) Запись в `docs/anti-patterns.md` «ORCH записывает нарушение планки как
  принятый риск в своём решении» (W9) — пишет DOC-UPDATER на шаге 10 (п. 10).
- **I-5.** Диагноза ISSUE-FIXER (WF-03, шаг 1) по ISS-0010 нет; факты п. 0 получены моими запусками. Если ORCH требует шаг 1
  формально — он идёт до шага 3 и может дополнить п. 2.
