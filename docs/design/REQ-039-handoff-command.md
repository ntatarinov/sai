## 3. Команда

### 3.1. Вызов

```
cd tools && npm run handoff -- new --run <RUN-ID> --step <ШАГ> --role <КОД РОЛИ> --workflow <WF-NN> --task "<текст>"
                              [--criterion "<пункт>"]… [--requirement <REQ-NNN>]… [--artifact-in "<путь или пояснение>"]…
                              [--write-set "<текст>"]… [--route "<текст>"] [--qualifier <уточнение>]
                              [--suffix <rN|runN|vN>] [--priority HIGH|NORMAL|LOW] [--rework-of <путь handoff-а>]
cd tools && npm run handoff -- close <путь handoff-а от корня> --status COMPLETED|FAILED
cd tools && npm run handoff -- --help
```

- Вход — `tools/src/handoffs/handoff.js`; скрипт `handoff` = `node src/handoffs/handoff.js`. Корень репозитория — `repoRoot(process.cwd())` (`traces/git-files.js`); все пути в аргументах и в выводе — от этого корня. Из `tools/` корень находится поднятием по git. Ключа `--root` нет (в списке ключей требования его нет; дополнить — только изменением требования, вопрос О5).
- `npm run` печатает перед выводом команды две строки заголовка; чтобы получить чистый вывод, ORCH запускает `npm run -s handoff -- …` или `node src/handoffs/handoff.js …` из `tools/` (рецепт — в README, п. 9).
- Имена ключей — **закреплены требованием**: `run`, `step`, `role`, `workflow`, `task`, `criterion`, `requirement`, `artifact-in`, `write-set`, `route`, `qualifier`, `suffix`, `priority`, `rework-of`, у `close` — `status`. Других ключей нет; нужен сверх списка — вопрос в `result.issues`, не ключ.

### 3.2. Таблица ключей `new`

| Ключ | Обязателен | Повторяется | Правило значения (при нарушении — код 1, `E_HO_INPUT`) | Куда пишется |
|---|---|---|---|---|

Принимаются `PROD-20261011-01`, `ISS-0002-20260930-01`, `AUD-001-20261012-01`; отклоняются `prod-20261011-01`, `PROD-2026-10-11-01`, `PROD-20261011-1`. Календарная правильность даты не проверяется (вопрос О12) | `run_id`, папка, `handoff_id`, метка `base/…` |

| `--workflow` | да | нет | `^WF-0[1-7]$` | `workflow_id` |

| `--route` | нет | нет | непустой после обрезки | `context.route` |

`close` принимает ровно один позиционный аргумент (путь) и ключ `--status` со значением `COMPLETED` или `FAILED`.

### 3.3. Разбор аргументов (`args.js`)

`parseArgv(argv) → { help: true } | { cmd: "new", opts } | { cmd: "close", opts }`; ошибка разбора — `HandoffError` кода `E_HO_USAGE`, выход 2.

- Если среди аргументов есть `--help` — печатается справка, код 0 (как у `handoffs-check`; остальные аргументы не разбираются).
- Первый аргумент — подкоманда `new` или `close`; иначе — отказ вызова (нет подкоманды / неизвестная подкоманда).
- Таблица ключей — `Map` (имя, унаследованное от `Object.prototype`, просто неизвестно, как в `handoffs-check/cli.js`). Аргумент, который не начинается с `--` и не является значением предыдущего ключа (у `close` — вторым позиционным), — «лишний аргумент».
- Значение ключа — следующий аргумент; если его нет **или он начинается с `--`**, у ключа нет значения (код 2). Следствие: текст, начинающийся с `--`, как значение передать нельзя (О4).
- Неповторяемый ключ, заданный дважды, — код 2. Нет обязательного ключа — код 2. Значение, не прошедшее правило таблицы 3.2, — код 1: **вызов разобран, значение не принято**.
- Порядок проверок значений фиксирован: `run`, `step`, `workflow`, `qualifier`, `suffix`, `priority`, `requirement` (по порядку ввода), `rework-of`, `task`, `criterion`, `artifact-in`, `write-set`, `route`; дальше — всё, что требует диска и git (п. 4.1). Печатается первое нарушение, одна строка.

### 3.4. Справка `--help` (stdout, код 0)

Текст по-русски; содержит обе подкоманды, **все** ключи таблицы 3.2 и ключ `--status`, оба вида кодов выхода и ссылку на `tools/README.md`. Форма (слова ключей — дословно как в требовании):

```
Использование:
  npm run handoff -- new --run <RUN-ID> --step <ШАГ> --role <КОД РОЛИ> --workflow <WF-NN> --task "<текст>" [ключи]
  npm run handoff -- close <путь handoff-а от корня> --status COMPLETED|FAILED
  npm run handoff -- --help
Ключи new (повторяемые помечены «…»):
  --run, --step, --role, --workflow, --task          обязательные
  --criterion… --requirement… --artifact-in… --write-set…   списки в порядке ввода
  --route, --qualifier, --suffix, --priority, --rework-of    по одному
Коды выхода: 0 — сделано; 1 — отказ по правилам; 2 — ошибка вызова или окружения.
```

(Каждый ключ — отдельной строкой с правилом значения; точные строки закрепляет `HO-04`: проверка по ключам, а не по тексту.)

### 4.2. Список ролей (`roles.js`)

`readRoles(root) → string[]` (коды, отсортированные по байтам, без повторов). Читаются файлы `<root>/.claude/agents/*.md` (обычные файлы, до 1 МиБ каждый). В файле берётся блок между первой строкой `---` и следующей `---`; в нём строка, начинающаяся с `name:`; код — текст внутри **последней** пары скобок в конце строки, по образцу `^[A-Z][A-Z0-9-]*$`. Файл без такой строки код не даёт и пропускается без ошибки. Нет папки, нет ни одного кода, файл не читается — `E_HO_ROLES`, выход 2 (список ролей — часть окружения; «роли нет в списке» — отказ значения, код 1). Число кодов на 2026-10-11 — 37 (Ф1); код не хранит число: `HO-06` сравнивает результат с независимым подсчётом тем же правилом по строкам `name:` в копии папки.

### 4.3. Имена и идентификаторы (`build.js`)

| Что | Правило | Пример (`--run PROD-20991231-01 --step 05b --role TEST-DESIGN-VALIDATOR --qualifier req999 --suffix r1`) |
|---|---|---|
| хвост имени | `-<уточнение>` если задано, затем `-<суффикс>` если задан | `-req999-r1` |
| путь файла `rel` | `handoffs/<RUN-ID>/step-<ШАГ>-<роль строчными>` + хвост + `.json`; роль строчными — код как есть в нижнем регистре (дефисы сохраняются) | `handoffs/PROD-20991231-01/step-05b-test-design-validator-req999-r1.json` |
| `handoff_id` | `step<ШАГ>` + `-<уточнение>` + `-<суффикс>` + `-<RUN-ID>` (части, которых нет, пропускаются) | `step05b-req999-r1-PROD-20991231-01`; без уточнения и суффикса — `step05b-PROD-20991231-01` |

Порядок ключей верхнего уровня (как в примере `handoffs.md`; `round` — после `step`, как у 417 из 431 живых файлов с этим полем, Ф14):

| 3 | `workflow_id` | `--workflow` |
| 4 | `step` | `--step` (строка) |
| 5 | `round` | только при `--suffix rN`: число N |
| 6 | `from_agent` | `"ORCH"` |
| 7 | `to_agent` | `--role` |
| 8 | `file` | `rel` |
| 9 | `status` | `"PENDING"` |
| 10 | `priority` | `--priority` или `"NORMAL"` |

| 12 | `task` | `{ "description": <--task>, "acceptance_criteria": [<--criterion>…] }` (пустой список, если ключа не было) |

`context`, ключи в порядке: `requirement_ids` (список, пустой если нет), `agent_run_id` (`null`), `artifacts_in` (список, пустой если нет), затем **только заданные**: `route`, `write_set` (список строк), `base_tag` (`"base/<RUN-ID>"`, при любом процессе, если метка `base/<RUN-ID>` есть в репозитории; нет метки — у WF-02 отказ, у остальных поля нет), `rework_of`.

`write_set` — список, а не строка, даже при одном значении: так записано у 430 из 482 живых файлов с этим полем и так читается «повторяемые ключи дают списки в порядке ввода»; пример в `handoffs.md` показывает строку — это расхождение документа с данными, правка примера входит в п. 9, подтверждение — О1.

### 4.5. Поиск повтора `handoff_id` (`create.js`)

`findHandoffId(root, handoffId) → string | null`: обход `handoffs/` (`readdirSync` с типами, без захода в ссылки), каждый обычный файл `*.json` до 16 МиБ читается и разбирается; если это объект с `handoff_id` строкой, равной искомой, возвращается путь от корня (первый по байтам). Файл не JSON — пропускается (его нарушение покажет `handoffs-check`). Файл не читается (ОС) — `E_HO_IO`, выход 2: неполный обход зелёным не бывает (как в `handoffs-check`). Объекты со вложенным `handoff_id` не считаются: смотрится только верхний уровень.

### 4.6. Запись (`createExclusive`) — выбор способа фиксации

`createExclusive(root, rel, text, handoffId) → void`; бросает `HandoffError`.

Выбрана **жёсткая ссылка с отказом при занятом имени** (запись `decisions/0039`, варианты и причины там). Порядок:

1. Папка `handoffs/<RUN-ID>/` (F3): звенья `handoffs`, затем `<RUN-ID>` создаются `mkdirSync` без `recursive`. `EEXIST` у звена — **нормальный ход**, не ошибка: звено создал другой запуск или оно было; через `lstatSync` проверяется, что это настоящая папка (не ссылка, не файл), иначе `E_HO_IO`, выход 2; такое звено в список «созданных этим запуском» **не вносится**. В список вносятся только звенья, чей `mkdirSync` прошёл. Иной сбой `mkdirSync` — `E_HO_IO`, 2.
2. Временный файл `handoffs/<RUN-ID>/.<имя файла>.sai-tmp` создаётся **исключительно** (`flag: "wx"`, `flush: true`, режим `0o644`, байты — `Buffer`, чтобы `flush` не отключился: заметка из `util.js`). `EEXIST` — `E_HO_BUSY` (остаток прерванной записи или параллельный `new` с тем же именем; временный файл **чужой, не удаляется**), код 1. `ENOENT` (папку прогона убрала из-под запуска очистка другого запуска) — `E_HO_IO: папка прогона исчезла во время записи; повторите вызов`, выход 2, на диске ничего своего не остаётся.
3. `linkSync(временный, итоговый)`. `EEXIST` — **файл уже есть**: **свой временный файл удаляется** (`unlinkSync`), итоговый файл (чужой) не трогается; звенья папок убирает общая очистка шага 6 по её правилу — только созданные этим запуском и только пока пусты (после проигрыша в гонке папка непуста, поэтому остаётся), `E_HO_EXISTS`, выход 1; если удаление временного файла само упало — выход 2, `E_HO_IO: файл уже есть, но временный файл не удалён: <путь>; удалите его вручную` (F2). `EPERM`, `ENOTSUP`, `EOPNOTSUPP`, `ENOSYS`, `EXDEV` — файловая система не умеет жёсткие ссылки: `E_HO_IO`, выход 2, текст с причиной; запасного пути через `rename` **нет** (он заменил бы файл, Ф11). Любой иной сбой — `E_HO_IO`, 2.
4. Сразу после создания ссылки: `findHandoffId(root, handoffId)` без учёта самого `rel`. (а) Нашёлся другой файл с тем же `handoff_id` — итоговый файл **удаляется** (`unlinkSync`, только своё имя) и выдаётся `E_HO_EXISTS` («`handoff_id` уже есть…»), выход 1. Это закрывает гонку двух `new` с одним `handoff_id` и разными ролями: остаётся не больше одного (худший исход — отказ у обоих, повтор безопасен; доказательство в п. 8). (б) **Поиск не удался** (нечитаемый чужой файл, сбой обхода, `E_HO_IO`) — защита не сработала, поэтому созданный файл **не остаётся**: итоговая ссылка удаляется (как в (а)), затем шаг 6; код 2, `E_HO_IO: повторный поиск handoff_id не удался (<код ОС>); handoff не создан`. Если удалить итоговую ссылку не удалось — выход 2, `E_HO_IO: … файл <путь> создан, но не подтверждён; удалите его вручную` (F4).
5. Временный файл удаляется. Не удалился (ответ ORCH на N2) — файл **создан**, но выход 2: **stdout пуст** (п. 4.7 печатается только при выходе 0), в stderr одна строка `handoff: E_HO_IO: файл создан (<путь от корня>, <handoff_id>), но временный файл не удалён: <путь от корня>`. Путь и `handoff_id` созданного файла берутся из этой строки; остаток убирается вручную.
6. **Очистка при любом исходе, кроме успеха** (шаги 2–4): свой временный файл удаляется во всех исходах, где он создан этим запуском (в том числе при `EEXIST` на шаге 3 — F2); затем звенья папок, **созданные этим запуском** (шаг 1), в обратном порядке `rmdirSync` (непустая папка остаётся — например, если победитель уже положил в неё файл; ошибка `ENOTEMPTY` и `ENOENT` очисткой не считается сбоем). Победитель параллельной записи по этой причине не теряет папку: очистка проигравшего убирает только звенья, созданные им самим, и только пока они пусты; если очистка победителя при его сбое уберёт папку из-под проигравшего, тот получит `ENOENT` на шаге 2 и отказ шага 2. Сбой самой очистки — к тексту ошибки добавляется `; остался <путь>`, выход 2.

`writeFileSync` встречается в `tools/src/handoffs/` **один раз** — запись временного файла в `create.js`; `renameSync` в `create.js` нет вообще (`HO-43`).

### 5.2. Путь (`E_HO_PATH`)

Путь — от корня репозитория (команду запускают из `tools/`, поэтому путь не относительный к рабочей папке). Отказ, если: пуст или содержит управляющий знак или `\`; абсолютный; содержит часть `..`, `.` или пустую; не начинается с `handoffs/` или не кончается `.json`; на пути (`handoffs`, `handoffs/<RUN-ID>`) или в самом файле — ссылка; файл — папка или не обычный файл. Причины `readText` (она не бросает ошибку ОС, а возвращает причину пропуска, F6): `deleted` (файла нет) — `E_HO_FILE: файла нет`, код 1; `unreadable` (ОС отказала в чтении; кода ОС `readText` не отдаёт) — `E_HO_IO: файл не читается`, код 2, текст без кода ОС. Ссылка за корень, не обычный файл, слишком большой, не UTF-8/двоичный (причины `readText`) переводятся в текст без пути: `ссылка за корень`, `не обычный файл`, `файл больше 16 МиБ`, `не текст UTF-8`.

### 5.3. Условия состояния (первое невыполненное — отказ; значения не печатаются, кроме слов)

| № | Условие | Отказ |
|---|---|---|

| С2 | `status` — `PENDING` или `IN_PROGRESS` | `E_HO_STATE`: `status сейчас <слово>: закрываются только PENDING и IN_PROGRESS` (закрытый, отменённый и недопустимый) |

### 5.4. Замена значений в тексте (`spliceTopLevel`)

`spliceTopLevel(text, edits) → string`, `edits = { status: <слово>, completed_at: <время> }`. Сканер идёт по тексту уже разобранного JSON-объекта один раз, как `locate.js`, но на верхнем уровне запоминает **границы значений** ключей `status` и `completed_at` (смещения начала и конца токена значения; вложенные ключи с теми же именами, например `result.status`, не затрагиваются). Заменяются ровно два токена: значение `status` на `"COMPLETED"`/`"FAILED"` и `null` у `completed_at` на `"<время>"`. Все остальные байты — прежние: отступы, порядок ключей, форма массивов, перевод строк, наличие или отсутствие финального перевода строки.

Самопроверка в той же операции (шаг 7): новый текст разбирается `JSON.parse`; результат равен старому документу, у которого изменены только `status` и `completed_at` (глубокое сравнение), порядок ключей верхнего уровня тот же; иначе — `E_HO_INTERNAL`, выход 2, на диске ничего не изменено. Так ошибка сканера не превратится в испорченный файл.

Почему не `JSON.stringify` целого документа: он переформатировал бы чужой файл (живые handoff-ы набраны по-разному), то есть изменил бы поля, которых закрытие не касается.

### 5.5. Запись

`writeAllOrNothing` (`tools/src/util.js`, `decisions/0004`) в единственной цели: временный `.<имя>.sai-tmp` в той же папке с `wx` и сбросом на диск, права прежние, резерв прежнего файла жёсткой ссылкой `.<имя>.sai-old`, `renameSync`, откат из резерва при сбое, удаление резерва. Она сама отказывает при ссылке на пути и при уже лежащих `.sai-tmp`/`.sai-old` (на шаге 9 команда проверяет их заранее и выдаёт русский `E_HO_BUSY`).

**Сообщение об ошибке записи — целиком по-русски (F5, ответ ORCH).** Английские тексты `issues` общего писателя не печатаются и не копируются; сам `writeAllOrNothing` не меняется. Команда берёт из `issues` только **код ОС** — буквенный код в скобках `(EXXXX)` в сообщении (формат `<причина> (<код>); <исход>` закреплён в `util.js`; нет кода — «код не определён») — и строит русский текст сама:

| Код ОС | Причина в тексте |
|---|---|
| `EACCES`, `EPERM`, `EROFS` | нет права записи в папку или файл (или только чтение) |
| `ENOSPC`, `EDQUOT`, `EFBIG` | на диске нет места или файл слишком велик для записи |
| `EIO` | ошибка ввода-вывода диска |
| `ELOOP` | на пути ссылка |
| `EEXIST` | остался временный или резервный файл прерванной или параллельной записи |
| `EMFILE`, `ENFILE` | слишком много открытых файлов |
| любой другой | ошибка записи (код ОС) |

Состояние файла в строке команда определяет **сама**, а не из текста писателя: перечитывает цель — байты прежние → «файл прежний»; иначе «файл мог измениться: проверьте его»; затем `lstat` `.<имя>.sai-tmp` и `.<имя>.sai-old` — остались → «остались <путь от корня>; удалите вручную». Итоговая строка: `handoff: E_HO_WRITE: запись не удалась: <путь от корня>: <причина>; <состояние>` (одна строка; абсолютных путей и английского текста нет, `HO-42` проверяет оба условия). Ограничение О7 снято.

Если у `writeAllOrNothing` несколько записей `issues` (основной сбой, затем откат и остатки), код ОС берётся из **первой** записи (она описывает основной сбой), остальные только дают состояние «остались <путь>; удалите вручную» (по `lstat`, а не по тексту). **Случай «записано, но резервный файл не убран»** (запись удалась, `issues` непуст, потому что не удалился `.<имя>.sai-old`): команда определяет его сама — цель перечитана и равна **новому** тексту — и печатает не «запись не удалась», а `handoff: E_HO_WRITE: файл закрыт (<путь от корня>), но резервный файл не удалён: <путь от корня>; удалите его вручную`, выход 2, stdout пуст; файл при этом уже закрыт и цел.

Остаточный риск (окно сужено, F9): перед записью (шаг 9b) команда перечитывает файл и сравнивает байты с прочитанными на шаге 4, поэтому изменение, сделанное раньше этого сравнения, не теряется; окно между шагом 9b и переименованием внутри `writeAllOrNothing` (общий писатель сравнивает байты цели только с новыми, не с прочитанными) остаётся — полностью закрыть его без блокировки нельзя. Окно — миллисекунды; получатель закрывает свой handoff в конце хода, ORCH в это время его не пишет (правило «Кто что пишет»); последующий `handoffs-check` поймает расхождение статуса (H4). Принято, записано в `decisions/0039`.

### 6.2. `checkText` (`one-file.js`)

`checkText({ rel, text, nowSec, commitOf }) → Violation[]`: байты текста → `parseHandoff` → `locate` → `checkFile({ rel, bytes, parsed, loc, dirty: true, nowSec, commitOf })` + `checkHomePaths({ rel, text, loc, excepted: () => false })`. `dirty: true` — потому что файл ещё не в коммите: `PENDING` и `IN_PROGRESS` допустимы (H4), как у любого рабочего handoff-а. База исключений `tools/handoffs/exceptions.tsv` и исключения `traces` **не применяются**: у нового файла их быть не может (О8). H3 «повтор `handoff_id` между файлами» проверяет не `checkText`, а `findHandoffId` (п. 4.5).

`historyReader(root, rel) → commitOf`: `fileHistory(root).get(rel) ?? []`, `readBlobs(root, <хеш>:<rel> для каждого коммита)`, `versionReader(коммиты, версии)`. Файл ещё не в истории → `commitOf` всегда `null`. Репозиторий без коммитов — `E_HC_GIT` из `git-history.js`, выход 2.

`violationLines(violations) → string[]` — обёртка над `formatReport` (п. 6.1). Печать нарушений — в stdout, `E_HO_RULES` — в stderr.

Правка модуля REQ-038 в `check.js` — одно слово `export` (п. 2). Проверка, что поведение `handoffs-check` не изменилось: набор тестов `handoffs-*.test.js` без правки (кроме п. 10.1) и вывод `handoffs-check` на фикстуре старого вида до и после (`HO-91`), а на самом проекте — команды `HO-93`.

### 6.3. Метка базы без нового места `child_process` (`tagExists`)

Вопрос ORCH: проверять метку чтением `.git/refs` и `packed-refs` или вызовом git. Выбор — **вызов git в `git-history.js`**, потому что чтение `.git` ненадёжно: в рабочем дереве `git worktree` и в подмодуле `.git` — файл-указатель, метки лежат в общем каталоге; после `git gc` метки уходят в `packed-refs`; формат ссылок может быть иным (`reftable`). Любая из этих разновидностей давала бы ложное «метки нет» и блокировала бы каждый WF-02. Новых мест `child_process` нет: слово остаётся только в `git-history.js`, `TR-4c` не меняется (Ф6).

`tagExists(root, runId, timeoutMs = TIMEOUT_MS) → boolean`:

- До вызова `runId` проверяется образцом RUN-ID (п. 3.2); иначе `TraceError("E_HO_BASE_TAG", …)` — ни одного вызова git. Ссылка собирается как `"refs/tags/base/" + runId + "^{commit}"`: начинается с `refs/`, параметром-ключом git стать не может.
- Вызов: `execFileSync("git", ["-c", "core.fsmonitor=false", "rev-parse", "--verify", "--quiet", ref], { cwd: root, timeout: 30 с, maxBuffer, stdio: ["ignore", "pipe", "pipe"], encoding: "buffer" })` — шестой вызов модуля, без оболочки. Код выхода 1 → `false` (метки нет, в том числе когда `base/<RUN-ID>` — ветка, а не метка); 0 → `true` (легковесная и аннотированная метка); прочее — `gitFailure` (общие тексты). Метка, указывающая не на коммит, даёт `false`.
- Место в файле — **перед** `readBlobs`, чтобы вызов `cat-file --batch` оставался последним (тесты `HC-RT-1` различают его по месту).

## 8. Защита в той же операции

| Что защищаем | Где стоит защита | Чем |
|---|---|---|
| файл не заменяется | в самой операции создания | `linkSync` на занятое имя — `EEXIST`; ссылка либо создана целиком, либо нет (читатель не видит половину файла; при замке было бы видно) |
| один `handoff_id` на один файл | предварительный поиск (быстрый отказ без записи) **и** повторный поиск сразу после создания ссылки, с удалением своей ссылки | остаётся не больше одного файла: пусть A и B — два `new` с одним `handoff_id`; `tA`, `tB` — моменты ссылок, `sA`, `sB` — моменты их повторных поисков (`tA < sA`, `tB < sB`); если оба остались, то A не увидел B (`tB > sA`), B не увидел A (`tA > sB`), откуда `tB > sA > tA > sB > tB` — противоречие. Оба могут отказать (оба создали ссылку до обоих поисков) — безопасно, повтор. Остаточный риск: убитый процесс между шагами 3 и 4 п. 4.6 оставит файл без повторного поиска — его покажет `handoffs-check` (H3, повтор `handoff_id`) |
| закрытый файл правилами REQ-038 | `checkText` на **новом тексте до записи**, в том же вызове | нарушение — файл не меняется; проверка и запись не разнесены по разным вызовам |
| время не из будущего | один `nowSec` и в записи, и в `checkText` (H6) | отдельного перечитывания часов нет |
| только значения `status` и `completed_at` | подмена токенов + самопроверка глубоким сравнением в той же операции | расхождение — `E_HO_INTERNAL`, не запись |
| запись только в `handoffs/<RUN-ID>/` | `rel` собирается только из проверенных частей; `close` принимает путь только с префиксом `handoffs/` | `HO-44`, `HO-35` |
| «всё или ничего» для `new` | порядок п. 4.6 (временный → ссылка → очистка) | `HO-41` |
| «всё или ничего» для `close` | `writeAllOrNothing` | `HO-42` |

Остаточные риски, принятые (записаны в `decisions/0039`): потерянное обновление при одновременной правке файла чужим писателем (п. 5.5); файл без повторного поиска при убийстве процесса; остаток `.sai-tmp` после убийства (виден в `git status`, не мешает `handoffs-check`, следующий `new` того же имени откажет `E_HO_BUSY`, а не заменит).

## 12. Открытые вопросы (не решены догадкой; до ответа действует написанное в проекте)

- **О1 — закрыт ответом ORCH:** `context.write_set` всегда список (п. 4.4); пример в разделе «Поля» `handoffs.md` не правится, в «Кто что пишет» — одна фраза (п. 9.3).
- **О2.** Критерий 7, подсчёт по README (`grep -c 'npm run handoff' tools/README.md` не меньше 2) выполнен **до** работы (Ф10) и ничего не доказывает; проект закрывает критерий строгими тестами `HO-50`…`HO-53`. Текст критерия не менялся.
- **О3.** Критерий 8, последняя часть («handoff-ы самого прогона созданы и закрыты этой командой, проверка — по выводу команд в self_check») и `HO-92`–`HO-94` — не автотесты внутри `npm run test`: красить `check` проверкой, зависящей от метки конкретного прогона, нельзя. Они проверяются командами RELEASE-VALIDATOR и записями ORCH (`HO-92`–`HO-94`); автотест на этот пункт невозможен (команда не оставляет следа, отличающего её вывод от ручного набора, а ключи сверх списка запрещены). Прошу CODE-DESIGN-VALIDATOR подтвердить, что это допустимо для этого пункта.
- **О4.** Дополнения сверх текста требования, нужные для защиты: (а) проверка правилами REQ-038 и для **нового** файла `new` (иначе путь домашней папки в `--task` дал бы файл, красящий `handoffs-check`); (б) повторный поиск `handoff_id` после ссылки; (в) значение, начинающееся с `--`, считается отсутствующим (текст задачи не может начинаться с `--`); (г) `REQ-NNN` — ровно три цифры; (д) `--rework-of` проверяется по форме, существование файла не проверяется; (е) предел длины уточнения 40 знаков. Если что-то из этого лишнее — слово ORCH.
- **О5.** Ключа `--root` нет (нет в списке требования). Тесты запускают команду с рабочей папкой во временном репозитории. Если нужен `--root` — дополнение требования.
