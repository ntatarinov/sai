## 4. Формы и тексты

### 4.1. `executor.js`: пояснение и соответствие имён

```
acceptedFilesText(deps: Dep[]) → string        // чистая, без ввода-вывода, не бросает
Dep = { task: string, name: string, content: string }   // как сейчас (depsOf)
ACCEPTED_LINES_MAX = 50
```

Результат — пустая строка, если `deps` пуст (раздела зависимостей тогда нет, и задание байт в байт прежнее — тест RF-08). Иначе:

1. Абзац-пояснение, постоянный текст `ACCEPTED_FILES_INTRO`: «Ниже — файлы, которые ядро уже приняло. Принятый файл хранится под
   именем t-NNNN-N-<имя>: t-NNNN — задача, N — номер попытки, <имя> — имя, под которым исполнитель сохранил файл (без папок).
   Исходный файл после приёма удалён, поэтому в текущей папке этих файлов нет, и это не недостаток.»
2. Если есть хотя бы одна строка соответствия — строка «Соответствие имён:» и строки, по одной на зависимость-файл, в порядке
   `deps` (задачи — в порядке `depends_on`, файлы — в порядке приёма):
   `— <исходное имя> → <принятое имя> (задача <t-NNNN>, попытка <N>)`.
3. Разбор имени: от `dep.name` отрезается префикс `<dep.task>-`; остаток должен быть `<N>-<исходное имя>` с `N` из цифр
   (`/^([0-9]+)-(.+)$/`). Если `deps` не массив — результат пустая строка. Если элемент `deps` не объект, `dep.task` или `dep.name` не строка,
   префикса нет или остаток не подходит — строка для этого файла **не пишется** (файл остаётся виден по заголовку `###`; ошибки
   нет). `dep.content` функция не читает, поэтому его вид на неё не влияет. Обещание «не бросает» относится только к
   `acceptedFilesText`; `buildPrompt` на входах не формы `Dep` ведёт себя как сейчас (`depsOf` всегда отдаёт объекты формы `Dep`).
4. Строк больше `ACCEPTED_LINES_MAX` — пишутся первые 50, затем строка «— и ещё K файлов (их имена — в заголовках ниже)», `K` —
   число непоказанных строк.

Ограничения: исходное имя и принятое имя — не текст пользователя, а имена по шаблону ядра (`PATTERNS.name`: латиница, цифры, `.`,
`-`, `_`, до 80 знаков; перевода строки и пробела нет), поэтому построчное соответствие не может внести в задание свою строку
(Q7; инъекция в подсказку через имя невозможна). Содержимое файлов в этих строках не повторяется; чужих задач (не из `depends_on`)
в строках нет — так же, как в разделе.

`buildPrompt(request)`: раздел зависимостей = `HEADERS.deps` + перевод строки + `acceptedFilesText(deps)` + пустая строка +
части с `###` (как сейчас). Длина пояснения вычитается из `room` так же, как длина заголовка раздела, **до** обрезки содержимого:
весь текст по-прежнему не длиннее `PROMPT_MAX` = 200 000 знаков (проверка RF-07). Остальные разделы, их порядок, `RULES`, обрезка
с пометкой «[обрезано]» — без изменений.

### 4.2. `engine/review.js`: правило оценки

```
SAVED_AS_RULE: string        // постоянный текст, экспорт review.js
```

Текст: «Если критерий требует файл с некоторым именем («сохранён в X»), он выполнен, когда файл с исходным именем X назван среди
принятых файлов раздела «Результаты задач, от которых зависит эта» — в списке соответствия имён или в заголовке «### t-NNNN-N-X» —
и его содержимое подходит. То, что в текущей папке такого файла нет, критерием не является. Если среди принятых файлов такого
имени нет (или раздела нет совсем — принятых файлов нет), критерий не выполнен: скажи об этом в notes.»

`reviewContext`: `note` = прежняя фраза («Проверь результат задачи строго по критерию готовности. Ответ: passed — true, если критерий
выполнен полностью; notes — замечания по пунктам.») + пробел + `SAVED_AS_RULE`. `goalContext`: первый абзац `note` = прежняя фраза
(«Сверь результаты задач с целью проекта. …») + пробел + `SAVED_AS_RULE`; второй абзац («Задачи проекта: …») прежний.
Правило не ослабляет проверку: имя, которого нет среди принятых, остаётся невыполненным критерием (часть (г) критерия 14).

### 4.3. Что не меняется

Схемы ответов (`REVIEW_ANSWER_SCHEMA`, `GOAL_ANSWER_SCHEMA`), события журнала, их поля, `store.js`, `files.js`, `runner.js`,
`engine/single-run.js`, `engine/engine.js`, `role-internal.js`, `RULES`, `package.json`, формат файлов проекта. Новых файлов данных и
новых мест записи нет. Права файлов и папок проекта не затрагиваются.

## 6. Поддельный claude для теста (отдельный файл, AP-025)

Путь: `tools/test/fixtures/team/fake-claude-reads.js` (создаётся этой работой; права 0755, как `fake-claude.js`; строка в

Тесты указывают на него через `execEnv(sb, { SAI_TEAM_CLAUDE_BIN: <путь> })` и `assertSafeEnv` (форма 1: файл внутри
`fixtures/team`, исполняемый). Модели не вызывает, в сеть не ходит, читает только свою `cwd`, stdin и план из `$HOME`.

**План теста** — `$HOME/fake-claude-reads/plan.json` (HOME — временная папка теста; fake отказывается работать, если `HOME` не
абсолютный путь):
`{ plan: { tasks: [...] }, work: [ { files: [{ path, content }], answer: [path, …] } по номеру запуска работы ], reassign_role: string, review_task?: "yes" }`.

**Что за запуск — определяет сам fake, не план**: по схеме ответа в аргументе `--json-schema` (ключи `required`): есть `tasks` →
план; есть `passed` → проверка; есть `role` → выбор роли; иначе работа. Проверка задачи от проверки цели отличается наличием
раздела «## Задача» в stdin.

**Правило ответа проверки (одно для А и Б; выбор варианта фиксирует не оно, а тест RF-01, F6)**.

*Извлечение имени `X` (одно правило для проверки задачи и проверки цели).* Текст берётся из раздела stdin: у проверки задачи
(в stdin есть строка `## Задача`) — «## Критерий готовности», у проверки цели — «## Цель проекта»; раздел идёт от своего
заголовка до следующей строки, начинающейся с «## ». В тексте раздела ищется первое совпадение выражения
`/сохран(?:ён|ен|ена|ено|ить)\s+в\s+(\S+)/u` (формы «сохранён», «сохранен», «сохранена», «сохранено», «сохранить»). Из
найденного слова снимаются: в начале — знаки `« " ' ( [`, в конце — знаки `. , ; : ! ? » " ' ) ]` (в любом числе). Что осталось —
`X`. Результат выражения на дословных фразах проекта — Ф7. Если совпадения нет или после снятия знаков остаток пуст, `X`
**не найден**: fake отвечает `passed: false`, `notes` = «в критерии нет имени файла (fake)», в журнале fake `X: null`,
`by: "none"`; к правилу «папка/подсказка» он не переходит. Так сломанное извлечение краснит тесты (RF-12, строка «имя не
найдено»), а не превращается в «всегда да».

*Ответ.* При найденном `X` ответ `passed: true`, если выполнено хотя бы одно:

- **папка:** `X` есть в `readdir(cwd)` (обычный файл);
- **подсказка:** среди строк **области связи** есть строка, в которой одновременно стоит `X` отдельным словом (границы —
  начало/конец строки, пробел, кавычки «»"', скобки, `,;:`; соседний знак `-`, `_`, `.`, буква или цифра границей **не** считается) и
  слово `t-NNNN-N-X` (`/^t-[0-9]{4}-[0-9]+-<X>$/` как отдельное слово).

*Область связи (F3).* Строки между строкой-заголовком «## Результаты задач, от которых зависит эта» (не включая её) и первой после
неё строкой, начинающейся с «### t-» или с «## » (не включая её). Это место пояснения и соответствия имён (п. 4.1: они стоят
**до** первого `###`). Всё, что стоит ниже, — тела принятых файлов (текст агента), «## Замечания», «## Правила» — областью
связи не является и связью не считается, даже если там стоят оба слова и даже если тело файла содержит строку, имитирующую
«## Правила» или «## Замечания». Если заголовка раздела в stdin нет, области нет и «подсказка» невозможна.

Если не выполнено ни одно, `passed: false`, `by: "none"`, `notes` содержит «файл X отсутствует в текущей рабочей папке» (тот же текст,
что в журнале настоящего запуска) и, если в stdin есть `t-NNNN-N-X` вне области связи, — «содержимое под принятым именем есть, но
связи с X нет». Строка `### t-0001-1-memo_research.md` одна **не** считается связью (она вне области, и слова `memo_research.md`
как отдельного слова в ней нет). Критерий в тексте «Критерий готовности» тоже связью не является.

*Только для RF-02.* Поле плана `review_task: "yes"` — на запуск проверки **задачи** fake отвечает `passed: true`, `by: "plan"`, не
применяя правило (иначе при критерии без имени файла проверка задачи в RF-02 падала бы раньше проверки цели и проверка цели не
запускалась бы). По умолчанию поля нет, и действует правило. Проверка цели правилом всегда.

**Работа:** файлы из `plan.work[n]` пишутся в `cwd`, ответ — `{summary, files:[{path, kind:"result"}]}`; расход 0,01.
**План / выбор роли:** ответ из плана теста (форма `tasks[{key, role, text, done_when, depends_on, critical}]`, как в
`stream-engine-plan.jsonl`; `{role, reason}`).

**Журнал fake** — `$HOME/fake-claude-reads/log.jsonl`: `{n, purpose, cwd_files, X, by: "folder"|"prompt"|"plan"|"none", passed}` (у запусков плана, работы и выбора роли — только `n` и `purpose`); stdin каждого
запуска — `$HOME/fake-claude-reads/stdin-<n>.bin` (тест ищет в них приманку (в) — HOME лежит вне папки проекта).

**Охрана AP-025:** файл лежит в `fixtures/team`; `assertSafeEnv` проверяет временные `HOME` и `SAI_TEAM_HOME`; fake ничего не пишет
вне `$HOME/fake-claude-reads/` и своей `cwd`; свою пригодность доказывает тест самого fake (RF-12): правило не пустое и не «всегда да».

## 8. Связи и порядок работы

1. Общий контракт — тексты п. 4 (`ACCEPTED_FILES_INTRO`, `SAVED_AS_RULE`, форма строки) — фиксируется этим проектом; fake читает их

   формы строки — ломает (и падает RF-01).
2. Порядок: BACKEND-DEV (CODE-FIXER) правит `executor.js` и `engine/review.js` → TEST-DESIGNER пишет fake и тесты (fake можно
   писать до кода: он читает только stdin и `cwd`) → README.

## 9. Граница доказательства (Q3)

Критерий 14 доказывает, что **при записанном правиле** задание проверяющего даёт верный ответ, и что соответствие истинно и не
ослабляет проверку. Он не доказывает, что настоящая модель последует пояснению: это проверяется только повторным запуском на
настоящем Claude (критерий 13 REQ-013), который по условию требования ждёт письменного согласия владельца. До него дефект считается
исправленным на уровне поведения задания, а риск записан в `decisions/0035` («Остаточный риск и условие пересмотра»). Если
настоящий запуск провалится — решение 0035 пересматривается новой записью (вариант А с правкой критерия 2 REQ-009 и TM-04).

## 11. Что не входит (попутные находки, не чинятся здесь)
