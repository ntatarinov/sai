## Что сделано

- Диагноз (шаг 1): причина — не разница оболочек dash и bash, как предполагал файл дефекта, а гонка записи на стандартный ввод
  подставного git. Подставной git теста GH-6 выходит с кодом 0 сразу и свой ввод не читает; если процесс завершился раньше, чем
  Node записал запрос, запись даёт EPIPE при статусе 0, и `gitFailure` называет это «git не смог выполнить команду (код 0)».
  Текст ложен: git не вернул ошибочный код, не удалась запись ему. Какая из двух веток сработает, решает гонка; на macOS всегда та,
  что нужна тесту, на Linux-раннере иногда нет.
- Проект (шаг 3, одна доработка по замечаниям F1, N1, N2) и его ворота (шаг 3b: первая проходка FAIL, вторая PASS). Выбран вариант А
  решения 0047: в `gitFailure` одна ветка — ошибка вызова со статусом строго 0 даёт `E_TRACE_GIT` «вывод git не разобран»;
  статусы 128 и N не меняются.
- Код (шаг 4): `tools/src/handoffs/git-history.js` — три строки (комментарий и две строки ветки). Других файлов в `tools/src`
  выпуск не меняет (`git diff --stat -- tools/src`: один файл, 3 вставки).
- Безопасность и ревью (шаг 5): оба PASS.
- Тесты (шаг 6, `tools/test/handoffs-git.test.js`): подставные git случаев 1 и 2 в GH-6 читают ввод встроенным `while read`, ожидание
  GH-6 не менялось; новые GH-7 (git вышел с кодом 0 и не принял запросы на 4 МиБ ввода — «вывод git не разобран», не «код 0») и
  GH-7b (контроли: `exit 3` — «код 3», `exit 128` — `E_TRACE_NOT_GIT`). Ворота тестов — шаг 7 (PASS).
- Решение 0047 принято ORCH, не владельцем; владелец может его отменить.
- Учёт (шаг 10): файл дефекта ISS-0053 исправлен по диагнозу и остаётся `open`; AP-078; ISS-0054, ISS-0055, ISS-0056 заведены
  (все LOW); `STATE.md`; `decisions/README.md`; фраза о статусе 0 в проекте REQ-038.

## Что не сделано и почему

- **Поведение на Linux не проверено.** Linux на машине нет; все запуски — на macOS (под sh и dash). Тесты GH-7 и GH-7b построены так,
  чтобы исход не зависел от гонки (ввод 4 МиБ больше буфера сокета), но сработают ли они на Linux-раннере, покажет только GitHub.
- **ISS-0053 остаётся `open`** до зелёного запуска `check.yml` на GitHub (шаг 12, отдельно, после отправки). Запуск этим шагом не
  ожидается и не проверяется; закрыть дефект после шага 12 может только DOC-UPDATER.
- **REQ-030 остаётся `in_progress`:** критерий 2 (зелёный `check.yml` на GitHub) не выполнен; критерий 3 ждёт согласия владельца.
- **main на GitHub красный с коммита 02ff306.** Репозиторий публичный, красная отметка видна всем. До шага 12 она остаётся.
- ISS-0054, ISS-0055, ISS-0056 только заведены, не исправлены (все LOW): git, убитый сигналом, даёт не понятную ошибку (ISS-0054);
  тесты HK-12b и HK-31 пишут в ввод `hook.sh` без обработчика ошибки записи — тот же класс гонки (ISS-0055); комментарий «five calls»
  в `git-history.js` при шести вызовах git (ISS-0056).
- Вне границы решения 0047: другие вызовы git, место `child_process`, HK-12b и HK-31, текст критерия REQ-038, общая константа текста.

## Остаточные риски

- Решение 0047 принято ORCH, не владельцем; отмена владельцем потребует пересмотра ветки `gitFailure` (условие пересмотра записано
  в самом решении).
- Если на Linux окажется иной код записи при обрыве ввода, ветка по статусу 0 всё равно сработает (она не смотрит на `err.code`),
  но другая причина красного `check.yml` возможна и будет видна только после шага 12.
