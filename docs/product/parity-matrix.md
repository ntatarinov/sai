# Сравнение с [образцом]: что у него есть, чего нет у Sai, как сделать лучше

Составлено 2026-10-06 (прогон PROD-20261006-01, шаг 01b) чтением репозитория [образца] только на чтение. Всё, что сказано об [образце], проверено по его коду и документам; где не нашёл — так и написано.

## 1. Главное, что надо знать сразу

**[образец] — это не то, что описал владелец.** Это платформа для бизнес-процессов (BPM): сервер на Elixir и веб-интерфейс на React. Человек рисует схему процесса, запускает экземпляры, получает задачи в «Входящие», завершает их формой. ИИ-агентов, которые сами планируют и работают, в нём **нет**: модуль «агенты во время работы» записан как отложенный и не построен. Чата с агентами, цели «сделай мне запуск продукта», планировщика и Pixel Office в нём **не нашёл** (поиск по коду сервера и интерфейса: ни одного вызова модели, ни одного чата, ни слова про Pixel Office; страницы обновляются опросом раз в 10 секунд, сокетов и потоков событий нет). Агенты в [образце] — это только конвейер, которым его самого строят (роли, ворота, handoff-ы) — то же, что у Sai в `.claude/agents/`.

Что это значит для задачи «не хуже [образца]»:

- По **устройству продукта для пользователя** планка [образца] ниже, чем в видении владельца: у него нет ни целей, ни виртуальной команды, ни живого офиса. Превзойти его в этом — значит просто построить то, что владелец описал.
- По **инженерной зрелости** (права, аудит, повторы, очереди ошибок, мультиарендность, тесты, согласования) [образец] сильно впереди: у Sai сегодня нет вообще продукта, а есть только служебный код конвейера и страница Pixel Office, которая показывает запуски агентов Claude Code (`tools/README.md`).
- Поэтому паритет — это не «догнать функции», а «получить минимально надёжное ядро» (хранение состояния, права, журнал, повторы), на которое потом ставится видение владельца.

## 2. Как устроен [образец] (по прочитанному)

- **Рабочие пространства.** Мультиарендность: каждая организация — отдельная схема в базе, у каждой своя настройка, роли, пользователи и ключи доступа. Есть регистрация новой организации с отслеживанием хода, паспорт организации, редактирование. «Проектов» как у владельца (цель с командой) нет — есть определения процессов и их экземпляры.
- **Процессы.** Определение — граф узлов (человеческая задача, сервисная задача, ветвления, подпроцессы, таймеры). Есть визуальный редактор схем, проверка схемы, черновики, продвижение определения между средами с обязательным согласованием (план, различия, отказ при конфликте), откат, выгрузка и загрузка.
- **Выполнение.** Экземпляр запускается транзакцией в базе, а не отдельным процессом; параллельные действия решаются блокировками строк в базе. Все изменения пишутся в журнал событий (только добавление). Состояние экземпляра можно восстановить по журналу и «прокрутить» назад ползунком на странице экземпляра.
- **Задачи и зависимости.** «Входящие»: взять, назначить, переназначить, завершить с формой. Зависимости между задачами — это стрелки схемы процесса (кто за кем), а не план, который строит сам исполнитель.
- **Сервисные задачи (внешние вызовы).** Вызов по адресу с защитой от обращения к внутренним адресам, повторы, затем попадание в «очередь мёртвых писем» (DLQ), откуда человек может повторить или отбросить. Для названных в каталоге услуг заглушка пока всегда отвечает «не зарегистрировано» — каталог услуг на деле не подключён.
- **Таймеры.** Планировщик раз в такт берёт сработавшие таймеры с блокировкой, чтобы два сервера не взяли один и тот же; после исчерпания повторов — в DLQ.
- **Согласования.** Двухсторонняя подпись (две роли) и согласование продвижения определений с невозможностью пропуска.
- **Результаты и документы.** Отдельного «хранилища результатов проекта» не нашёл. Есть записи сущностей (таблицы данных с формами), экзамены с сертификатом в PDF, публичное чтение по закрытой ссылке.
- **Память/контекст.** Общей памяти проекта для агентов не нашёл. Есть переменные экземпляра с проверкой схемы.
- **Наблюдаемость.** Неизменяемый журнал аудита с цепочкой хэшей, метрики для мониторинга, четыре сигнала тревоги (завис экземпляр, глубина DLQ, отставание планировщика, приостановка вебхука), журнал вебхуков с повторами и автоматической приостановкой после 5 сбоев подряд, страницы «Здоровье» и «Метрики».
- **Права и пользователи.** Вход через внешнюю службу входа, роли (администратор платформы, оператор, проектировщик, работник), группы, ключи доступа, отдельные ограничения на поля.
- **Шаблоны.** «Пакеты решений» — набор определений, форм и сущностей, которые можно установить в организацию (один готовый пакет — экзамены).
- **Интерфейсы.** Веб — большой (более 40 страниц и экранов: панель, определения, редактор схем, экземпляры, задачи, администрирование, DLQ, вебхуки, экзамены). Мобильное приложение — **только описание, кода нет**; три нужных серверу пункта для него числятся как пробелы.
- **UX цели.** Пользователь сначала должен знать, какой процесс он запускает: выбирает определение и нажимает «Запустить». Цели обычным языком нет.
- **Язык.** Сообщения интерфейса частично на английском прямо в коде страниц (например, приветствие панели); есть слой переводов и язык сессии, но он применяется не везде.

### Что у [образца] слабо или не доделано (честно)

1. Нет ИИ вообще в самом продукте; «агенты во время работы» отложены.
2. Бизнес-пользователю надо знать устройство процессов (узлы, токены, выражения); интерфейс — инструмент администратора и проектировщика.
3. Нет реального времени: страницы опрашивают сервер раз в 10 секунд.
4. Мобильного приложения нет.
5. Каталог услуг для сервисных задач — заглушка; в README описано, что веб-интерфейс на момент переноса не работал сквозь с сервером, а часть утверждений в README устарела (число требований, пометки «ещё не построено») — доверять нужно коду, а не README.
6. В большинстве документов много терминов-«мостов» к прошлой системе: новому человеку входить тяжело.
7. Нет общей памяти, нет итоговых документов проекта, нет «что от меня требуется» одним взглядом (есть только «Входящие» по задачам).
8. Много узлов настройки, мало «просто сделай» — нет режима «по умолчанию просто».

## 6. Предложение: тонкий вертикальный срез

**Цель среза:** один сквозной сценарий — «Подготовь коммерческое предложение» (или другая цель) → план → задачи → выполнение агентами → результат → видно в Pixel Office и чате. Всё настоящее, без заготовленных демо.

Состав и порядок:

1. **Хранение проекта и журнал событий** (возможности 1, 2) — основа; всё остальное пишет сюда и читает отсюда.
2. **Задачи с зависимостями** (3) — минимум: ждёт / в работе / готово / ошибка, «после чего».
3. **Запуск агентов и результат** (4, 6 в минимуме) — один запуск за раз, потом параллельно двух независимых; результат — файл в проекте.
4. **Проверка «готово» другим агентом** (7) — иначе Done не засчитывается.
5. **Простой интерфейс: ввод цели, список задач, результаты, чат-окно «что происходит»** (10, 12, часть Г).
6. **Pixel Office, читающий тот же журнал** (11, В) — клик по сотруднику показывает его задачу и результат.
7. **Планировщик цели → задачи** (А) — сначала шаблонный (минимальный набор ролей), затем живой; но даже первый вариант строит план по настоящему вызову агента, а не из заготовки.
8. **Повтор при ошибке и окно «требуется ваше решение»** (5, 8) — вторым шагом, как только первые семь работают.

Почему такой порядок: пункты 1–2 нужны всем; 3–4 дают исполнение и честное «готово»; 5–6 дают то, что видит человек; 7 — главное отличие от [образца]; 8 — надёжность. Правила: все статусы берутся из состояния, в сценарии нет заглушек; граница среза — готовое состояние проекта, результаты и тесты сквозного прогона.
