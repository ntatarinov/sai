# REQ-036, REQ-045, REQ-044 — сценарии приёмки: строки «Сейчас», журнал понятными словами, карточка агента по нажатию

WF-02, шаг 8, п. 1 (BA-ANALYST), прогон `REQ044-20261014-01`, 2026-10-14. Требования — блоки REQ-036 (критерии 1–10),
REQ-045 (критерии 1–9) и REQ-044 (критерии 1–11) в `docs/requirements.yaml`; описание интерфейса —
`docs/design/REQ-036-044-045-ui.md` (доработки r1, r2); проект — `docs/design/REQ-036-044-045-interactive.md`; решения
`decisions/0053` (плашка под названием), `0054` (интерактивность первой; дополнение 2, п. 2 — приёмка только на стенде),
`0055` (роль Sai — только «Sai … (КОД)»; «повторное начало»), `0056` (секреты в описании и роли — «[скрыто]»). Слова
владельца — `docs/owner-requests/2026-10-14-pixel-office-interactive.md`. Документ остаётся в проекте и при следующих
изменениях Pixel Office выполняется снова как регрессия.

**Кто действует.** Владелец Sai: человек, который не программирует и не знает, как устроен Claude Code. Он открывает
Pixel Office в браузере и хочет понять, что делают агенты. Его слова: «Когда я нажимаю на рабочий стол агента, либо на
агента, когда я вижу журнал, тому прочее, это должно быть более интерактивно. Потому что там написано все непонятно для
пользователя.» Люди и данные — вымышленные (AP-004): сессии и агенты с номерами `sample-…`, описания со словом «Образец».

**Как писались «Ожидается».** Строго по тексту критериев: где критерий даёт текст, он приведён буквально; где текста нет,
взят текст описания интерфейса (в нём помечены «[т]» — из требования и «[о]» — предложенные описанием); числа и слова,
которые даёт стенд (время, возраст, номера), — правилом, а не значением. Названия ролей простыми словами — значения
таблицы страницы (критерий 1 REQ-036 требует таблицу, а формулировки выбирает FRONTEND-DEV); в сценариях приведены
нынешние значения: «Проверка безопасности», «Запуск проверки», «Ревью кода», «Проект кода», «Учёт и документы»,
«Исправление кода», «Поиск причины дефекта», «Написание тестов». Если значение таблицы поменяли — сверяется новое
значение таблицы, а не слово этого документа.

**Применимость планки.** Q1, Q3 — применимы (у каждого видимого критерия есть сценарий; «работает» — только с
доказательством с запущенного стенда). Q7 — сценарии 43, 44. Q10 — плохие условия: сценарии 24, 37–42. Q8, Q9, Q11, R3 —
не применимы: данных клиентов, запросов к базе и адресов, по которым ходит сервер, у Pixel Office нет, фото людей нет
(`decisions/0033`). R2 — содержание документа: на экране нет ни одной фразы, названия и числа, которых нет в журнале, записях
запуска сервера, часах страницы и константах страницы.

## Как читать сценарий

- **Стенд.** Каждый сценарий — на отдельном сервере Pixel Office, не рабочем: новый пустой каталог состояния вне проекта
  (`<scratch>/uat044/<стенд>`), свой порт (не 4780) и свой секрет (его создаёт сервер). Журнал владельца, его копии и
  снимки с них не используются (`decisions/0054`, дополнение 2, п. 2; критерий 10 REQ-044, критерий 8 REQ-045).
  Подробно — «Как готовится стенд».
- **Окна браузера:** 1470 × 784 (основное), 375 × 812 и 320 × 568 (описание интерфейса); для критериев REQ-036 —
  ещё 1920 × 1080, 480 × 800 и 390 × 844, как они названы в критериях 1, 3, 4. Окно меняется без перезапуска сервера.
- **Свежесть.** Строки «в работе» живут 60 минут без новых событий; стенд, подготовленный больше 35 минут назад,
  готовится заново (иначе «в работе» само станет «нет свежих данных», и это ошибка подготовки, а не находка).
- **Доказательство.** На каждый шаг UAT-RUNNER записывает: ответ сервера на заново сделанный запрос
  (`GET /api/events?after=0` — строки и записи запусков), снимок страницы и её текст после действия; для фокуса —
  какой элемент в фокусе и его стиль кольца; для замеров — числа без округления. Тишина на экране результатом не бывает.
  Фразы в «Ожидается» проверяются на странице; «Доказательство» может называть файлы, команды и свойства страницы — это
  работа UAT-RUNNER, а не фраза для владельца. Итог и снимки — `docs/uat/REQ-036-044-045-RUN.md`.
- **Важность провала.** БЛОК — провал идёт в WF-03 в этом же прогоне, подпись FAIL. ВЫС — WF-03, решение о подписи по
  критерию. СРЕД — находка.
- **Настоящий Claude Code не запускается:** все события стенда идут через настоящую программу-хук (`hook.sh`) и
  настоящую команду записи оркестратора (`pixel-office-note`) или положены в журнал стенда до запуска (критерий 10
  REQ-044 это разрешает). Исключение по критерию 8 REQ-036 — раздел «Вопросы».
- **Повторяет сам RELEASE-VALIDATOR** (шаг 9): REQ-044, шаги 1, 3, 5, 6 и замеры 7 (сценарии 19, 22, 25, 27, 34);
  REQ-045, шаги 2, 3, 4 (сценарии 12, 13, 18).

## Как готовится стенд

Подготовка — работа UAT-RUNNER; владелец её не видит. Рецепт (кроме окон браузера) проверен BA-ANALYST на тестовом стенде
в `<scratch>`: сервер принимает события через `hook.sh` и запись через `pixel-office-note`, страница строит из них
ожидаемые состояния, связи, слова журнала и пометки (проверено функциями страницы на ответе сервера). Сами сценарии не
проходились.

**1. Сервер.** Из каталога `tools/`:

    SAI_PIXEL_OFFICE_DIR=<scratch>/uat044/<стенд> npm run pixel-office -- --port <порт стенда>

Переменная нужна и серверу, и хуку (ключа `--dir` хуку не хватает — `tools/README.md`, ограничение 12; критерий 10 REQ-044
называет `--dir`, переменная задаёт тот же каталог). Перезапуск — остановить и запустить ту же команду на том же каталоге и
порту.

**2. События через настоящий хук.** Из `tools/`:
`printf '%s' '<JSON>' | SAI_PIXEL_OFFICE_DIR=<каталог стенда> sh src/pixel-office/hook.sh`. Входы хука:

| Событие                    | JSON                                                                                                                                                                                                                                                                                                                 |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| начало сессии              | `{"hook_event_name":"SessionStart","session_id":"<сессия>"}`                                                                                                                                                                                                                                                         |
| запрос владельца           | `{"hook_event_name":"UserPromptSubmit","session_id":"<сессия>","prompt":"Образец: <цель>"}`                                                                                                                                                                                                                          |
| служебное сообщение        | то же, `"prompt":"<system-reminder>Образец служебного сообщения</system-reminder>"`                                                                                                                                                                                                                                  |
| начало агента              | `{"hook_event_name":"SubagentStart","session_id":"<сессия>","agent_id":"<агент>","agent_type":"<роль>"}`                                                                                                                                                                                                             |
| окончание агента           | то же, `"hook_event_name":"SubagentStop"`                                                                                                                                                                                                                                                                            |
| передача задания           | `{"hook_event_name":"PostToolUse","session_id":"<сессия>","tool_name":"Agent","tool_use_id":"<вызов>","tool_input":{"subagent_type":"<роль запускаемого>","description":"<описание>"},"tool_response":{"agentId":"<запускаемый>"}}`; если передаёт агент — ещё `"agent_id":"<передающий>","agent_type":"<его роль>"` |
| конец ответа, конец сессии | `{"hook_event_name":"Stop","session_id":"<сессия>"}`, `{"hook_event_name":"SessionEnd","session_id":"<сессия>"}`                                                                                                                                                                                                     |

Запись оркестратора: `SAI_PIXEL_OFFICE_DIR=<каталог стенда> npm run pixel-office-note -- --text "Образец: …" --req REQ-044
--session <сессия>`.

**3. Строки, положенные в журнал стенда.** Только в `events.jsonl` каталога стенда, только `sample-…` и «Образец»
(R2): (а) **до запуска** — строки с пометкой «не из хуков» (источник не `REAL`; строка `REAL` со временем на 15 минут раньше
предыдущей — конфликт времени); (б) **после запуска** (рецепт `docs/uat/REQ-042.md`) — давняя работа, которая должна
стать «нет свежих данных»: живым хуком событие старше 60 секунд не записать. Время строки — момент подготовки минус
указанные минуты; строки по возрастанию времени, кроме намеренного конфликта.

**4. Номера.** Страница показывает первые 8 знаков номера, а `sample-` занимает 7, поэтому восьмой знак у каждого агента и
каждой сессии одного стенда свой: агенты `sample-a…` … `sample-v…`, сессии `sample-0…` … `sample-5…` (на стенде СТ-М это
невозможно — там 8 знаков совпадают, сценарий 42 проверяет числа, а не номера).

**Роли** (`agent_type` — в форме файлов ролей Sai, `decisions/0055`, п. 1): A — `Sai Security Reviewer (SECURITY-REVIEWER)`

кода»); W — `Sai Code Designer (CODE-DESIGNER)` («Проект кода»); D — `Sai Documentation Updater (DOC-UPDATER)` («Учёт и
