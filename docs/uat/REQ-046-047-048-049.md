## Как читать сценарий

- **Стенд.** Каждый сценарий — на отдельном сервере Pixel Office, не рабочем: новый пустой каталог состояния вне проекта
  (`<вне проекта>/uat048/<стенд>`), свой порт (не 4780) и свой секрет (его создаёт сервер). Журнал владельца, его копии и
  снимки с них не используются (`decisions/0054`, дополнение 2, п. 2). Рабочую страницу владельца ни один сценарий этого
  документа не открывает; если её всё же открывают, то только на чтение, запросами `GET` (`decisions/0054`, дополнение 3).
  Нетронутость журнала владельца UAT-RUNNER подтверждает только командами счёта без вывода текстов: число строк и число
  строк с `"session_id":"sample-` — до и после прогона. Подробно — «Как готовится стенд».
- **Окна браузера:** 1470 × 784 (основное), 1920 × 1080, 375 × 812 (их называют критерии), 390 × 844 и 320 × 568 (их
  называет описание). Окно меняется без перезапуска сервера.
- **Свежесть.** Строки «в работе» живут 60 минут без новых событий своей сессии; стенд, подготовленный больше 35 минут
  назад, готовится заново (иначе «в работе» само станет «нет свежих данных», и это ошибка подготовки, а не находка).
- **Доказательство.** На каждый шаг UAT-RUNNER записывает: ответ сервера на заново сделанный запрос
  (`GET /api/events?after=0` — строки и записи запусков), снимок страницы и её текст после действия; для фокуса — какой
  элемент в фокусе и его стиль кольца (`getComputedStyle`: `outline-style` не `none` или `box-shadow` не `none`); для
  замеров — числа без округления. Тишина на экране результатом не бывает. Фразы в «Ожидается» проверяются на странице;
  «Доказательство» может называть файлы, команды и свойства страницы — это работа UAT-RUNNER, а не фраза для владельца.
  Итог и снимки — документы `docs/uat/REQ-046-RUN.md`, `REQ-047-RUN.md`, `REQ-048-RUN.md`, `REQ-049-RUN.md` (имена
  называют критерии; можно один общий итог `docs/uat/REQ-046-047-048-049-RUN.md` и указатели — по решению ORCH); снимки —

## Как готовится стенд

Подготовка — работа UAT-RUNNER; владелец её не видит. Механика рецепта проверена BA-ANALYST на трёх тестовых стендах вне

`SAI_PIXEL_OFFICE_DIR`; `pixel-office-note` с `--session` и без `--request-time` ответила «записано; привязано к сообщению
владельца …», в журнале у записи `request_time_auto: true`; строки `SIMULATION`, положенные до запуска, помечены по
источнику; строки сессии `sample-0-old` с временем −2 ч 05 мин и −2 ч, положенные сразу после запуска, дали строку основной
сессии «нет свежих данных»; после перезапуска сервера роль из «(а)» сценария 41 открыла `E1`, роль из «(б)» — `G1`. На ответе
сервера функции страницы дали: «Агент» = «Проверка безопасности» — 7 строк, вместе с «Тип события» = «Агент получил
задание и начал работу» — 2, «Задача» A1 — 4, поиск «повторная проверка формы входа» — 5, поиск «луна» — 0, «Агент» = «main» —
1 строка, отдельно от «Основная сессия»; карточка основной сессии по умолчанию — строка второго запроса, «кого запустила в
этом запросе» — A1 и A2; «Основная сессия» у W0 ведёт на первую строку сессии. Пакет из 310 запусков СТ-Н, окна браузера и
сами сценарии не проходились.

**1. Сервер.** Из каталога `tools/`:

    SAI_PIXEL_OFFICE_DIR=<вне проекта>/uat048/<стенд> npm run pixel-office -- --port <порт стенда>

Переменная нужна и серверу, и хуку (ключа `--dir` хуку не хватает — `tools/README.md`, ограничение 12; критерии называют
`--dir`, переменная задаёт тот же каталог). Перезапуск — остановить и запустить ту же команду на том же каталоге и порту.

**2. События через настоящий хук.** Из `tools/`:
`printf '%s' '<JSON>' | SAI_PIXEL_OFFICE_DIR=<каталог стенда> sh src/pixel-office/hook.sh`. Входы хука:

| Событие                    | JSON                                                                                                                                                                                                                                                                                                                 |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| начало сессии              | `{"hook_event_name":"SessionStart","session_id":"<сессия>"}`                                                                                                                                                                                                                                                         |
| запрос владельца           | `{"hook_event_name":"UserPromptSubmit","session_id":"<сессия>","prompt":"Образец: <цель>"}`                                                                                                                                                                                                                          |
| служебное сообщение        | то же, `"prompt":"<system-reminder>Образец служебного сообщения</system-reminder>"`                                                                                                                                                                                                                                  |
| начало агента              | `{"hook_event_name":"SubagentStart","session_id":"<сессия>","agent_id":"<агент>","agent_type":"<роль>"}`                                                                                                                                                                                                             |
| окончание агента           | то же, `"hook_event_name":"SubagentStop"`                                                                                                                                                                                                                                                                            |
| передача задания           | `{"hook_event_name":"PostToolUse","session_id":"<сессия>","tool_name":"Agent","tool_use_id":"<вызов>","tool_input":{"subagent_type":"<роль запускаемого>","description":"<описание>"},"tool_response":{"agentId":"<запускаемый>"}}`; если передаёт агент — ещё `"agent_id":"<передающий>","agent_type":"<его роль>"` |
| конец ответа, конец сессии | `{"hook_event_name":"Stop","session_id":"<сессия>"}`, `{"hook_event_name":"SessionEnd","session_id":"<сессия>"}`                                                                                                                                                                                                     |

«Начало и передача» ниже — сначала передача задания от названного передающего (по умолчанию — от основной сессии), затем
начало агента. Запись оркестратора: `SAI_PIXEL_OFFICE_DIR=<каталог стенда> npm run pixel-office-note -- --text "Образец: …"
--req <REQ-NNN> --session <сессия>` — без `--request-time` (сервер сам привязывает запись к последнему сообщению владельца
этой сессии, на странице — «оркестратор не указал запрос — запись отнесена к последнему запросу владельца»).

**3. Строки, положенные в журнал стенда.** Только в `events.jsonl` каталога стенда, только `sample-…` и «Образец» (R2):
(а) **до запуска** — строки с источником не `REAL` (на странице — «не подтверждена»); (б) **сразу после запуска на пустом
каталоге, до первого живого события** (рецепт `docs/uat/REQ-042.md`) — давние строки, которые должны стать «нет свежих
данных»: живым хуком событие старше 60 секунд не записать. Время строки — момент подготовки минус указанные минуты; строки
по возрастанию времени (иначе правило чтения пометит их «не подтверждена» по конфликту времени).

**4. Номера.** Страница показывает первые 8 знаков номера, а `sample-` занимает 7, поэтому восьмой знак у каждого
агента и каждой сессии одного стенда свой: у агентов — буквы, у сессий — цифры (исключение — пакет `sample-z-…` стендов

  подсказка, списки выбора, «в работе: N», подпись на холсте на полу и у стены, название на доске.
- **Ожидается:** у каждого текста не ниже 4,5 : 1 (описание даёт 6,74; 6,12; 10,43; 11,72; 4,97; 4,97; 6,84–7,06 и 5,12;
  9,87–12,46).
- **Доказательство:** цвета и расчётный контраст.
- **Если не так:** СРЕД — находка.

## Понятность для владельца

Это **наблюдение, а не провал по критерию**: критерии требуют точных слов, а здесь UAT-RUNNER записывает, какие слова
человек без знания Claude Code видит на каждом экране и понятны ли они без объяснения. Итог идёт владельцу как список «что
осталось техническим». Предварительный разбор (по описанию интерфейса и константам страницы, до прогона):

Code» и «В сессию пришло служебное сообщение»; (2) строка журнала «Открыт разговор с Claude Code» и в той же линии 8 знаков
сессии; (3) раскрытие этой строки — «В Claude Code начат новый разговор (сессия) …» и поле «Сессия»; (4) карточка основной
сессии — «сессия sample-1», «Другие сессии», «Полный номер сессии», а в «Вся основная сессия» — «разговоров идёт: N»; (5)

…»; (6) пустой журнал — «Видны только разговоры с Claude Code …» и фильтр «все сессии». Связь двух слов объяснена только в
раскрытиях случаев 1 и 2 («разговор (сессия)»).

UAT-RUNNER по каждому экрану стендов СТ-О и СТ-Н записывает: полный список слов, которые нельзя понять без знания Claude
Code, и где они стоят; места, где «разговор» и «сессия» видны на одном экране. BA-ANALYST при подписи передаёт список
владельцу как наблюдение (выбор одного слова — решение ORCH через WF-01, F6), не как провал.

## Вопросы

1. **Прежний документ приёмки и его слова.** `docs/uat/REQ-036-044-045.md` и указатели `docs/uat/REQ-044.md`,
   `docs/uat/REQ-045.md` ждут прежних слов и прежнего места кода роли: «экземпляр», «Экземпляры этой роли», «Полные
   идентификаторы», «Сессия Claude Code открыта», «LIVE», «REAL — события хуков Claude Code», «не из хуков», «хук Claude
   Code», «привязано автоматически», «идущих сессий: N», «порог свежести», код роли под заголовком карточки, «Основная
   сессия» без кнопки у «Кто запустил», возврат фокуса на легенду последней карточки. Как регрессия он теперь даёт ложные
   провалы. Этот шаг его не правит (не в `write_set`). Предложение: DOC-UPDATER на шаге 10 пишет в его начале и в указателях,
   что слова и место кода роли — по таблице «было → стало» REQ-048, а сценарии 01–52 этого документа заменяют его сценарии
   там, где они расходятся; решение — ORCH.
2. **Имена документов.** Критерии 7 REQ-048, 5 REQ-049, 6 REQ-046 и 6 REQ-047 называют `docs/uat/REQ-048.md`,
   `REQ-049.md`, `REQ-046.md`, `REQ-047.md` (итоги — `…-RUN.md`); задание этого шага — один общий документ и указатели под
   эти имена. Сделано по заданию; как назвать итог прогона — решение ORCH (раздел «Как читать сценарий»).
3. **F6 — одно слово для «разговор» и «сессия».** Не вопрос этого шага: места собраны в разделе «Понятность для владельца»;
   выбор слова — ORCH через WF-01 (как предлагает ревью), слова «было → стало» выбирает ORCH по `decisions/0057`, дополнение,
   п. 4.
