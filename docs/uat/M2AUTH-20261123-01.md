WF-02, step 8, item 4 (UAT-RUNNER), run `M2AUTH-20261123-01`, handoff `step-08-uat-runner.json`, 2026-11-24. There is no
scenario file of BA-ANALYST for this run: the scenarios are those the handoff names (setup, the second setup, login with a

## Result

**Verdict: FAIL on one finding (F-1, major, not blocking); every flow works.** S1 to S9 and X1 to X4 PASS on their flow
and on the repeated state request; F-1 is a layout failure of the TOTP enrolment view at 390 x 844: the instruction
sentence and the `otpauth://` address run past the right edge of the panel and are cut (the page shows no horizontal
scroll because the panel clips its overflow). Remarks that are not failures (AP-117) are at the end.

## Findings

**F-1 (major, not blocking) - the TOTP enrolment view is cut at 390 x 844.** Scenario X2 (ru, 390, light), the step
after «Начать настройку». Expected: every text of the view readable in the window (the task names 390 x 844). Received:
the sentence «Добавьте ключ или адрес в приложение-аутентификатор, ...» ends at «приложение-аутенти» at the right edge
of the panel, and the address `otpauth://totp/Sai:...?secret=...&issu` is cut after `&issu`; the key itself fits. The
document shows no horizontal scroll because `body` has `overflow-x: hidden` and `.panel` `overflow-x: clip`
(`app/public/css/site.css`), so the overflow is clipped instead of wrapped. Evidence: stand 3 snapshots
`05-totp-secret-ru-390-light.png` and `06-totp-wrong-code-ru-390-light.png`. The enrolment still works (the key can be
typed). Proposed: let the long words and the address wrap in this view (for example `overflow-wrap: anywhere` on the
note and on `#otpauth-text`), then repeat X2 at 390 and 320 in ru and en.

## Remarks (not failures, AP-117)

- **M-1.** Chrome writes «Failed to load resource» to the console for every refusal the pages expect, the commonest
  being `GET /api/auth/me` 401 on every visit of a signed-out page. They are browser lines, not page errors.
- **M-2.** On `reset.html` in a browser that still holds a session (the admin opened his own link while signed in), the
  first `POST /api/auth/reset` is refused 403 `csrf_refused` and `api.js` repeats it after `GET /api/auth/me` (200; the
  design 5.1 names this one repeat). Without a session (X3) the first request passes. One extra refused request.
- **M-3.** The setup code field of `setup.html` shows the token in clear text (a text field). The owner types it once on
  his own screen; BA-ANALYST may ask whether a password field is wanted.
- **M-4.** The request for the second factor («Введите код из приложения или резервный код.») is shown under the label
  «ОШИБКА» / «ERROR», like a refusal.
- **M-5.** The `__Host-sai_s` cookie and its Secure flag cannot appear on a local http stand; they are in the post-deploy
  record (design 14).
- **M-6.** On Windows the stop of a server by its process id ends it at once (exit code 1); no graceful stop was
  observed. A property of the platform, not of the app.
- **M-7.** One step of X3 (a made-up link opened in the same tab) was a same-document navigation and did not reload the
  page, so it proves nothing and is not counted; the used-once check of S7 (a new page) stands.
