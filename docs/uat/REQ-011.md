# REQ-011 — сценарии приёмки: Sai Team, бизнес-интерфейс

WF-02, шаг 8, п. 1 (BA-ANALYST), прогон `PROD-20261010-01`, 2026-10-10. Требование — блок REQ-011 в
`docs/requirements.yaml` (критерии 1–15); описание интерфейса — `docs/design/REQ-011-ui.md` r3.2. Документ остаётся в
проекте и при следующих изменениях страницы выполняется снова как регрессия.

**Кто действует.** Владелец Sai: человек, который не программирует, открывает Sai Team в браузере на своём компьютере,
пишет цель, смотрит шесть ответов, пишет в чат. Это служебная страница для владельца, не страница покупательницы и не экран магазина:
фото (R3) и данные магазинов не участвуют. Люди и данные — вымышленные (AP-004).

## Как читать сценарий

- **Стенд.** Сервер Sai Team запускает UAT-RUNNER (или ORCH до запуска, WF-02 шаг 8, п. 3) из каталога `tools/`:
  `npm run team-web -- --port 0 --executor scripted --scenario <сценарий>`, с новой пустой папкой данных
  (`SAI_TEAM_HOME`) и новым домашним каталогом вне проекта (`<scratch>/uat011/…`). Рабочие данные владельца не
  трогаются. Адрес сервер печатает сам. Браузер — любой на этом же компьютере; окна: 1470 × 784 и 375 × 812.
- **Тестовый исполнитель.** Все сценарии идут на `scripted` (модель не вызывается, расходов нет). Такие проекты
  помечены на странице «тестовый исполнитель» — это часть проверки (сценарий 02).
- **Доказательство.** Для каждого шага UAT-RUNNER записывает: ответ сервера на заново сделанный запрос (код и тело), снимок
  страницы после действия, при проверке «ничего не изменилось» — список файлов папки данных с хешами до и после. Тишина
  на экране результатом не бывает.
- **Важность провала.** БЛОК — провал идёт в WF-03 в этом же прогоне, подпись FAIL. ВЫС — провал идёт в WF-03, решение о
  подписи по критерию. СРЕД — записывается в находки.
- **Что значит «не выполняем».** Сценарии с настоящим Claude Code тратят лимит владельца: нужны отдельный потолок расходов
  и согласие владельца заранее (WF-02, шаг 8, п. 2). Согласия нет, поэтому они записаны, но **не выполняются**: итог
  «не выполнен: нет согласия владельца».

Подготовка проектов для сценариев (UAT-RUNNER делает через команды ядра и движка, как пользователь в терминале, или
через саму страницу): проект «выполнен» (две задачи готовы); проект «в работе» с задержками; проект «ждёт решения» с
вопросом движка в чате; проект с задачей «не удалось»; проект с двумя готовыми задачами разной длительности для срока.
Если подготовить нужный проект нечем — сценарий «не выполнен» с причиной, а не пропуск.

## 01. Запуск и адрес только этого компьютера (критерий 1)

- **Кто:** владелец.
- **Исходные условия:** сервер не запущен; папка данных новая и пустая.
- **Шаги:** 1) Владелец запускает Sai Team командой из инструкции. 2) Читает напечатанную ссылку и открывает её в
  браузере. 3) Пробует открыть тот же сервер по адресу другой сетевой карты компьютера (если она есть). 4) Просит
  сервер ответить по чужому имени узла (запрос с именем `evil.test` и с чужим портом).
- **Ожидается:** ссылка вида `http://127.0.0.1:<порт>/`; страница открывается, сверху «Sai Team». По адресу другой сетевой
  карты соединение отклонено. Чужое имя узла — отказ «Запрос отклонён», в ответе нет цели ни одного проекта (создаётся
  проект с узнаваемой целью до проверки). По `localhost:<порт>` страница открывается.
- **Доказательство:** строка с ссылкой из вывода команды; список «кто слушает порт» (только 127.0.0.1); коды ответов
  (отказ соединения, 403, 200); тело отказа с поиском цели проекта (0 вхождений); снимок страницы.
- **Если не так:** БЛОК — данные проекта доступны с чужого узла; WF-03.

## 02. Список проектов с честными подписями (критерии 2, 7)

- **Кто:** владелец.
- **Исходные условия:** три проекта в разных статусах («выполнен», «в работе», «ждёт решения пользователя»); один на
  `scripted`; цель одного — «Рынок вырос на 12% — подготовить вывод».
- **Шаги:** 1) Открыть главную страницу. 2) Прочитать каждую карточку: цель, статус, «N из M задач», пометки. 3) Сверить
  статус и число задач с тем, что печатает команда `npm run team -- project <id>` для того же проекта.
- **Ожидается:** у каждой карточки цель, статус словами (те же, что у команды), «N из M задач» равно числу готовых и
  всех задач; у проекта «ждёт решения» пометка «нужно ваше решение»; у проекта на тестовом исполнителе пометка
  «тестовый исполнитель»; в подписях, которые формирует Sai, нет знака «%» и слова «процент»; цель с «12%» показана
  буквально.
- **Доказательство:** ответ списка проектов (поля цели, статуса, прогресса, пометок); вывод команды `project`; снимок
  главной страницы; поиск «%» и «процент» в подписях (0), цель с «12%» без изменений.
- **Если не так:** ВЫС — владелец видит неверный статус или процент; WF-03.

## 07. Шесть ответов на странице проекта (критерии 4, 11)

- **Кто:** владелец.
- **Исходные условия:** проект на `scripted` в работе с несколькими задачами в разных статусах.
- **Шаги:** открыть страницу проекта и найти ответы на шесть вопросов: что происходит; кто занимается; когда будет
  готово; есть ли проблема; нужно ли что-то от меня; результат.
- **Ожидается:** (1) последние пять фраз, старые сверху; (2) только роли, у которых задача в работе или на проверке, —
  человеческие названия; (3) срок или «срок пока не оценить»; (4) «Проблем нет» либо задачи «не удалось» с причиной;
  (5) «Ничего не нужно» либо число вопросов; (6) имена файлов результата с задачей и ролью. Прогресс «N из M задач»,
  процентов нет. Всё совпадает с тем, что печатает команда `project` для этого проекта.
- **Доказательство:** ответ страницы проекта по каждому полю; сверка с выводом команды; снимок в обоих окнах.
- **Если не так:** БЛОК — ради этого и сделана страница; WF-03.

## 08. Срок (критерий 4)

- **Доказательство:** три ответа сервера (поле срока), вычисление из журнала (медиана и округление) записано
  UAT-RUNNER рядом.
- **Если не так:** ВЫС — владелец получает выдуманный срок (R2); WF-03.

## 09. Проблема и вопрос команды (критерии 4, 5)

- **Кто:** владелец.
- **Исходные условия:** проект, где одна задача «не удалось» (с причиной), а проект «ждёт решения пользователя», и
  движок открыл вопрос в чате; в этом же проекте закрытый ответом вопрос.
- **Шаги:** открыть страницу проекта; прочитать «Есть ли проблема» и «Нужно ли что-то от меня»; нажать «Перейти к
  вопросам».
- **Ожидается:** в «Есть ли проблема» — задача «не удалось» с причиной словами и причина ожидания; карточка выделена
  красной рамкой; в «Нужно ли что-то от меня» число вопросов, равное числу открытых (вопрос, где «ждёт решения» и
  задача, и проект, считается один раз; закрытый не считается), карточка выделена; кнопка прокручивает чат к первому
  вопросу; вопрос команды виден в чате с меткой «ждёт ответа».
- **Доказательство:** ответ страницы проекта (число и тексты); открытые и закрытые ожидания, посчитанные UAT-RUNNER из
  журнала (`npm run team -- project <id>`); снимок.
- **Если не так:** ВЫС — владелец не увидит, что от него ждут; WF-03.

## 26. Сообщение доходит до движка только через канал (критерий 15)

- **Кто:** владелец.
- **Исходные условия:** проект на `scripted`, движок — отдельный процесс.
- **Шаги:** А) отправить сообщение при работающем движке. Б) остановить движок на паузу сигналом (SIGSTOP) и отправить
  сообщение; после — вернуть работу (SIGCONT). В) отправить сообщение больше 64 КиБ. Г) убить движок (SIGKILL) и
  отправить сообщение. Д) отправить сообщение с вымышленным ключом-приманкой.
- **Ожидается:** А — «Отправлено», одно событие, тот же держатель замка до и после. Б — ответ не раньше 10 и не позже

  текстом нет. В — понятный отказ до записи. Г — сообщение записано сервером ровно один раз, событие о снятом
  устаревшем замке есть. Д — приманки нет нигде в папке проекта.
- **Доказательство:** коды, замеры времени, журнал до/после, список файлов очереди сообщений, поиск приманки (0).
- **Если не так:** БЛОК — потеря или дубль сообщений владельца; WF-03.
