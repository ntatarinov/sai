## How to read a scenario

- **The stand.** ORCH starts the app on this computer (`node app/server/node-main.js` on a free port, in-memory data) and
  passes its address; in this file it is `<APP>`. The stand serves the local set of the site: the examples page, the
  order texts and the Kazakh button exist on it. Two scenarios need a second stand and are said to: `<APP-PUBLIC>` (the
  public set of the open build, L-34) and `<APP-BROKEN>` (a copy whose demo file is damaged, L-33). UAT-RUNNER makes
  these two stands itself, from fresh copies outside the project (ORCH's decision on the open question of this
  handoff). If a stand still cannot be started, that scenario is "not run: no stand" with the reason, never a skip, and the sign-off names the criterion that only
  tests cover.
- **The browser.** Real Chrome, a fresh temporary profile for every scenario (nothing stored) unless a scenario says
  otherwise. The three windows are 1470×784, 390×844 and 320×568; the themes are light (the theme button on «Светлая»)
  and dark («Тёмная»); the languages are ru and en. `curl` never replaces a browser step.
- **Cells.** A cell is one window × theme × language. FULL = all 12 cells. CORE = six cells: 1470×784 light ru, 1470×784
  dark en, 390×844 light en, 390×844 dark ru, 320×568 light ru, 320×568 dark en (every window in both themes and both
  languages). Each scenario names its cells; the runner may run more, never fewer.
- **Bad conditions in a real Chrome.** The runner makes a failure at the browser itself (the debugging protocol): it
  holds, replaces or breaks the answer of one request; it emulates the system setting «prefers-reduced-motion» and the
  system dark or light theme; it slows the network; it switches JavaScript off by the browser setting; it injects a
  script at the start of the page; it moves the tab to the background by opening another tab. A step "stop the stand
  and open the page" is never written: a browser with the server down shows its own error page (AP-125).
- **Names the runner may use.** The scene is the element `#stage`; it reports `data-frames` (the frames drawn since the
  load) and `data-figure` (the figure's height in CSS pixels); the list of the scene for screen readers is `#stage-text`;
  the live region is `#live`; the two required lines are `#test-mode` and `#ai-disclosure`; the theme button is `#theme`.
  These are the names the design gives (section 4.3 and 4.6); they are in the evidence, never in a phrase for the owner.
- **Console.** Criteria 12 and 13 declare the only allowed console lines: the browser's one line for a page answered with
  404 (status and path, once per such page; `decisions/0118` О2) and, in the failure scenarios, the browser's line of the
  failed request (once each, with its status or error and its address). Any other line is a failure. A warning or a line
  that no criterion forbids is a remark (AP-117).
- **Expected and remark.** "Expected" is taken from the criterion verbatim. "Remark" is wider than the criterion (the
  look, a decision, the design): a mismatch there goes to the findings as a remark and is never a failure of the
  scenario (AP-117, AP-082).
- **Evidence.** For each step the runner records the observable state it asked for again after the action: the text and
  the state of the page, the value it read (a count, a contrast, a storage listing), and a snapshot. Silence is never a
  result. Snapshots lie outside the project and are listed in the handoff.
- **Severity if it fails.** High - the visitor cannot use the page or sees a wrong or unsafe thing, goes to WF-03 in this
  run and the sign-off is FAIL; Medium - blocks as well; Low - goes to the findings. Critical, High and Medium block.
- **Kazakh.** kk is built and tested but hidden on production (G9), and its texts wait for a native speaker
  (`decisions/0124` О43, AP-114). The button «ҚАЗ» exists on the local stand. No scenario presses it. The kk scenarios are
  one entry, K-01, "not run: kk hidden, G9", and are not failures.

wrong against Part B (never shown to the reader); at least 11 of 12 must be right. The questions, the key, the answers and

**Scoring rule (Part B).** An answer is right when it names all the "must" points of its row in its own words (the words
need not be the page's) and states nothing that contradicts the site (for example, that Sai builds servers, that a visitor
can order or sign up now, or that agents never make mistakes). An answer that says "not found" is wrong. A point that is
only implied is not named. A right answer that names an extra true thing stays right.
