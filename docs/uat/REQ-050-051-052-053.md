**Кто действует.** Владелец малого бизнеса, который не программирует и не знает, как устроен Claude Code. Он открывает Pixel
Office впервые и хочет понять без посторонней помощи: что это за страница, кто из агентов что делает, где нужно его
решение. Слова владельца Sai о гайде: «гайд должен быть максимально для рядового пользователя понятен и не блокирущий
функционал». Люди и данные — вымышленные (AP-004): сессии и агенты с номерами `sample-…`, описания со словом «Образец».

**Как писались «Ожидается».** Строго по тексту критериев и таблиц Т1–Т4 описания: где критерий даёт текст, он приведён
буквально (значения констант страницы сверены чтением); где числа даёт стенд (время, возраст, номера, M) — правилом, а не
значением. Понятность проверяют не эти сценарии, а отдельный читатель без контекста (сценарии 31–35, `decisions/0061`,
дополнение): его вопросы — в отдельном файле `docs/uat/REQ-050-053-reader-questions.md`, ожидаемые ответы — только в
разделе «Только для BA-ANALYST» этого документа.

**Применимость планки.** Q1, Q3 — применимы: у каждого видимого критерия есть сценарий, «работает» — только с
доказательством с запущенного стенда. Q7 — сценарий 29 (тексты — только текст, только `GET`, нет адресов). Q10 — плохие

## Как читать сценарий

- **Стенд.** Каждый сценарий — на отдельном сервере Pixel Office, не рабочем: новый пустой каталог состояния вне проекта
  (`<вне проекта>/uat050/<стенд>`), свой порт (не 4780), свой секрет. Журнал владельца, его копии и снимки с них не
  используются; рабочая страница владельца не открывается. Нетронутость журнала владельца — только командами счёта: число
  строк и число строк с `"session_id":"sample-` до и после прогона.
- **Профиль браузера.** Приглашение в тур зависит от памяти браузера для адреса стенда (ключ `pixel-office-tour`).
  «Чистый профиль» — новый профиль браузера без данных сайтов; «профиль с «closed»» — профиль, в котором на этом стенде уже
  нажали «Не сейчас». Где не сказано иначе — профиль с «closed», чтобы приглашение не меняло раскладку шапки.
- **Окна:** 1470 × 784 (основное), 1920 × 1080, 390 × 844, 320 × 568 (их называют критерии). Окно меняется без перезапуска
  сервера.
- **Два момента.** Замеры, которые критерии требуют «в два момента», делаются через 5 секунд и через 61 минуту после
  последнего события стенда: часы сдвигаются только в странице (подмена `Date.now` и `new Date()` до её скриптов), сервер и
  журнал стенда не меняются (AP-100; так делалось в прогоне `REQ048-20261015-01`).
- **Доказательство.** На каждый шаг UAT-RUNNER записывает: ответ сервера на заново сделанный `GET /api/events?after=0`,
  снимок и текст страницы после действия, элемент в фокусе и стиль его кольца (`getComputedStyle`: `outline-style` не
  `none` или `box-shadow` не `none`), числа `getBoundingClientRect` без округления. Фразы «Ожидается» проверяются на
  странице; «Доказательство» может называть свойства страницы и команды — это работа UAT-RUNNER. Итог и снимки —
  `docs/uat/REQ-050-RUN.md`, `REQ-051-RUN.md`, `REQ-052-RUN.md`, `REQ-053-RUN.md` (имена называют критерии; можно общий
  итог с указателями — по решению ORCH); снимки — вне проекта.
- **Важность провала.** БЛОК — WF-03 в этом же прогоне, подпись FAIL. ВЫС — WF-03, решение о подписи по критерию. СРЕД —
  находка. Провал шага читателя (31–35) — доработка текстов по WF-03, как велят критерии.
- **Порядок.** Сценарии, которые меняют стенд (новые события, остановка сервера, замена журнала), идут после сценариев
  того же стенда, которые только читают, или на стенде, приготовленном заново.
- **Повторяет сам RELEASE-VALIDATOR** (шаг 9): REQ-050, шаги 1, 2, 3, 6 (сценарии 02, 03, 04, 07); REQ-051, шаги 1, 3, 4
  (09); REQ-052, шаги 1, 2, 3, 4, 6, 7 (11, 12, 13, 14, 16, 17); REQ-053, шаги 1, 2, 4, 5 (22, 23, 25, 26).

## Как готовится стенд

Подготовка — работа UAT-RUNNER; владелец её не видит. Команда сервера, входы `hook.sh` и правила номеров — как в
`docs/uat/REQ-046-047-048-049.md`, раздел «Как готовится стенд», пп. 1, 2 и 4 (переменная `SAI_PIXEL_OFFICE_DIR` — одна
для сервера и хука). Роли (`agent_type` — форма файлов ролей Sai): A — `Sai Security Reviewer (SECURITY-REVIEWER)`
(«Проверка безопасности»); B — `Sai Test Runner (TEST-RUNNER)` («Запуск проверки»); C — `Sai Reviewer (REVIEWER)` («Ревью
кода»).

- **СТ-Б — «образец»** (критерий 8 REQ-050, критерий 9 REQ-052, стенд Б). Пустой каталог; живым хуком, сессия
  `sample-1-main`: начало сессии; запрос владельца «Образец: проверить страницу оплаты»; **A1** `sample-a-sec1`: передача
  от основной сессии «Образец: проверка безопасности страницы оплаты» и начало (без окончания); **B1** `sample-b-run1`:
  передача **от A1** «Образец: запуск проверки после правки» и начало (без окончания); **C1** `sample-c-rev1`: передача
  «Образец: ревью страницы оплаты», начало, окончание. Итог: три роли, две «в работе», одна закончила работу, строка
  основной сессии «в работе».
- **СТ-А — «пусто»** (стенд А): пустой каталог, событий нет. Сценарии, которые подают «первое событие», шлют хуком начало
  сессии `sample-1-main`.
- **СТ-Б+ — «много»:** как СТ-Б, плюс 225 запусков роли C `sample-z-001` … `sample-z-225` (начало и окончание, скриптом
  через `hook.sh`) — не меньше 450 строк журнала.
- **СТ-Б2 — «карточки»** (сценарий 36; добавлен 2026-10-18, подпись, П1): как СТ-Б, плюс агент роли «Аудит сторонних пакетов»
  `sample-k-dep1` (`Sai Dependency Auditor (DEPENDENCY-AUDITOR)` — самое длинное описание таблицы Т2) с передачей и
  началом, второй запуск роли C `sample-e-rev2` (передача, начало) и агент роли вне таблицы `sample-x-expl` с ролью `Explore`
  (передача, начало).
- **Хранилище недоступно** (сценарий 20): в настройках браузера для адреса стенда запрещено хранить данные сайта (или тот
  же запрет через протокол отладки) — обращение страницы к хранилищу браузера кончается отказом; сервер и журнал не
  меняются.

## 01. Основной путь: приглашение → тур → справка → агент и моё решение → подсказка «?» (050.1–050.3, 051.1, 051.2, 052.1–052.5, 053.1)

- **Исходные условия:** СТ-Б, окно 1470 × 784, чистый профиль.
- **Шаги:**
  1. Открыть страницу; прочитать шапку.
  2. Нажать «Показать»; прочитать шаг 1; нажимать «Далее» и читать шаги 2–5.

## Только для BA-ANALYST

Этот раздел читателю без контекста не передаётся. Файл вопросов `docs/uat/REQ-050-053-reader-questions.md` ответов не

**Правило прохождения** (одно для 31–35; с 2026-10-18, подпись — по `decisions/0063`, слово владельца): шаг пройден, если ответ верен
по смыслу, читателю не понадобилась подсказка и ответ найден не больше чем за 3 шага (шаг — одно действие на странице:
нажатие, клавиша, наведение, открытие раздела; чтение шагом не считается); перечитанные фразы записываются одной записью
дефекта понятности и правятся следующим прогоном. Прежнее правило (до 0063): шаг не пройден, если ответ неверен по смыслу, читателю понадобилась

## Вопросы

1. **Имена документов.** Критерии 8 REQ-050, 6 REQ-051, 9 REQ-052 и 7 REQ-053 называют `docs/uat/REQ-050.md` …
   `REQ-053.md` (итоги — `…-RUN.md`); задание — общий документ и указатели. Сделано по заданию.
2. **Сколько читателей.** Критерии описывают шаг читателя в каждом требовании (новый запуск агента) и ещё одного нового
   читателя для пяти вопросов вместе (REQ-053, шаг 7). Документ планирует пять запусков (31–35); если ORCH считает, что
   31–34 может пройти один читатель последовательно, — правило «новый, без контекста» для каждого требования тогда
   выполняется только для первого вопроса; решение — ORCH до прогона.
3. **Средство для читателя.** Читателю нужен браузер, которым он нажимает и читает страницу (снимки и текст страницы), и
   ничего больше. Что именно ему дают и что запрещают (файлы проекта, поиск по коду) — ORCH пишет в его задании; файл
   вопросов этого не решает.
4. **Шаг 7 критерия 9 REQ-052 и критерий 3.** Шаг приёмки называет для стенда А «шаги 2 и 3 без подсветки с запасными
   текстами», а критерий 3 (и тест TU-03, описание п. О-9) — что после первого ответа сервера блок «Сейчас» виден и шаг 3
   показывает его с подсветкой и основным текстом; запасной текст шага 3 — только до первого ответа. Сценарий 17 записан по
   критерию 3 (подробное правило), запасной текст шага 3 проверяется в сценарии 06, шаг 2 (тур из справки до первого
   ответа). Правка текста шага 7 — WF-01; если ORCH считает иначе — сценарий 17 поправить до прогона.
