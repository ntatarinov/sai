# 0017 — Ядро Sai Team: хранение, замок, каталог событий, маскирование и границы записи (REQ-009)

Статус: принято (2026-10-06, ORCH). Владелец может отменить. Уточняет `0015` (хранение проектов и чата) и опирается на
`0011` и `0013` (маскирование). Основание — проект `docs/design/REQ-009-team-core.md`, раздел 19, предложения P1–P12 и решения
ORCH внутри прогона PROD-20261006-01.

## Вопрос

Ядро продукта (журнал событий проекта, состояние, писатель, замок, восстановление после аварии) — первое, на чём стоят
REQ-010 и REQ-013. Как оно хранит данные, кого пускает к записи, что маскирует, а что нет, и какие риски остаются?

## Варианты

1. Оставить детали на усмотрение кода — расхождения между REQ-009, REQ-010 и REQ-013 неизбежны.
2. Записать решения проекта целиком: хранение, замок, каталог событий, маскирование, восстановление, остаточные риски.
3. Взять базу данных вместо журнала-файла — противоречит `0015` (Node 22 без зависимостей).

## Решение

Вариант 2. Принято:

- **P1. Замок.** Временный файл + `linkSync` (атомарное «создать, если нет»); снятие устаревшего замка — `renameSync` с
  проверкой содержимого; ложное «занят» при повторном pid — допустимая сторона.
- **P2.** Производного файла состояния нет: состояние всегда воспроизводится из журнала.
- **P3.** Каталог из 37 типов событий, редьюсер (таблица п. 5.3 проекта) и таблица языка фиксируются проектом REQ-009; новые
  типы — только новой редакцией проекта. `PLAN_RETRY` — отдельный тип без смены статуса; `PLANNING_STARTED` пишется один раз за
  этап и без `attempt`.
- **P4.** `say` отклоняет текст длиннее 4000 знаков; тексты агентов обрезает вызывающий (`prepareText`).
- **P5.** Права шире ожидаемых: писатель сужает их (после замка и проверки журнала), чтение только предупреждает.
- **P6.** Файлы результата не перезаписываются (`E_FILE_EXISTS`).
- **P7. Маскирование не применяется к полям id, hash и кодам** — проверка шаблоном (`^[0-9a-f]{64}$` для хеша), потому что
  маскирование превратило бы sha256 в `[скрыто]` (M10 из `0013`). Хеш считает только ядро: `RESULT_FILE` пишется только путями
  ядра, `append` его отклоняет.
- **P8. Имена файлов результата не маскируются**, проверка шаблоном (латиница, цифры, `.`, `-`, `_`, не больше 80 знаков, без
  `..`, не начинаются с точки). Имя, похожее на ключ, ядро сохранит как есть: отклонять его сравнением с `maskSecrets(name)`
  значило бы отклонять и обычное `plan.v2.md`.
- **P9. Не маскируются:** копия сценария `scripted` (тестовый файл из `tools/test/fixtures/team/`, копируется **побайтово**:
  ядро получает `Buffer` и пишет его же; критерий 16 REQ-010 сверяет хеш) и содержимое рабочей папки агента `work/` (черновики
  агента, папка 0700, **вне журнала**). В `files/` и в журнал из них попадает только маскированное. Из `work/` принимаются
  **только текстовые файлы UTF-8**; двоичные (например, картинки дизайнера) отклоняются `E_WORK_FILE`.
- **P10.** Помощник тестов `tools/test/team-helpers.js` и расширение `tools/test/fault-inject.js` (для тестов ядра) — в границе
  `0015` как тестовый код; `0015` буквально называет только `tools/test/team-*.test.js`. Расширение `fault-inject.js` делает
  TEST-DESIGNER.
- **P11. Восстановление после аварии — по СОСТОЯНИЮ журнала** (r5, r8, r10). Восстановление делает тот, кто получил замок, если
  последняя строка журнала оборвана **или** в журнале есть открытые запуски либо задачи в `running`; признак «снят устаревший
  замок» не нужен (`LOCK_STALE_REMOVED` — только уведомление снявшего). После штатного `close()`, закрывшего свои запуски,
  восстановления нет: штатно закрытый проект ничего не получает. Оно закрывает все открытые запуски (`RUN_FINISHED
  interrupted`), прерывает задачи в `running` и задачи в `review`, чей запуск `review` оно закрыло; задача `review` без открытого
  запуска остаётся `review`. Если что-то прервано, проект в `planning` или `running` переводится в `paused` событием
  `PROJECT_RECOVERED` (причина «прервано аварией», `paused_by = "recovery"`) — настоящая смена статуса; работа продолжается только
  после `PROJECT_RESUMED {after:"recovery"}` (`paused → running`). События закрытия запусков, прерывания задач и
  `PROJECT_RECOVERED` пишутся **одним пакетом**: один `write`, один `fsync`, при сбое один откат `ftruncate` (проверка замка до
  пакета) — пакет записан весь или журнал остаётся как был (см. P13).
- **P12. Сломанный писатель оставляет замок** (r6). Сбой записи оставляет проект «как после аварии»: при `close()` сломанного
  писателя замок не снимается, и следующий открывающий либо восстанавливает проект по P11 (pid мёртв), либо получает
  `E_PROJECT_BUSY` (pid жив). Здоровый писатель замок снимает. Вызывающий закрывает свои запуски на всех путях выхода, а если
  не может — `markBroken()`. Остаточный риск: ложное «занят» при повторном pid и «занят» для самого сломавшегося процесса до
  его выхода (для долгоживущего движка REQ-013 нужно правило «сломанный писатель — выход из процесса», решает его проект).
  Поправка `0026` (2026-10-10, ISS-0010): для того же процесса замок его собственного закрытого сломанного писателя считается устаревшим: следующее открытие снимает его штатным путём (`LOCK_STALE_REMOVED` со своим pid) и восстанавливает проект по журналу; для других процессов P12 не меняется (`decisions/0026-team-core-reclaim-own-broken-lock.md`).

- **P13. Пакет восстановления и признак по журналу** (r8, r10). Признак аварии не принадлежит процессу: восстановление делает
  получивший замок по журналу (обрыв или незакрытая работа), ровно один раз; в гонке открывающих `LOCK_STALE_REMOVED` может
  потеряться, восстановление — нет. Пакет записывается целиком или не записывается. Отвергнутый вариант — маркер аварии на диске
  (`writer.lock.crashed-<pid>`): новый файл и новое место записи, а признак по журналу уже однозначен.
- **P14. Остаточный риск учёта расхода (S2).** Если процесс исполнителя был запущен, а `RUN_FINISHED` или `BUDGET_SPENT` не
  записались (процесс умер между ними или писатель сломан), восстановление закрывает запуск `interrupted` без `BUDGET_SPENT`:
  расход этого запуска не учитывается, `spent_usd` не растёт; фактические траты больше учтённых не более чем на потолок такого
  запуска (`0018` P4). Учёт «по худшему случаю» при восстановлении не вводится.
- **P15. Остаточный риск пакета восстановления (F-1).** Смерть процесса или сбой питания в середине записи пакета оставляет
  часть пакета — начало (например закрытие review-запуска) без `PROJECT_RECOVERED`; следующий держатель замка этого не
  восстанавливает. Возможное закрытие — прерывать и задачу `review`, чей последний запуск `review` закрыт как `interrupted`, —
  **не введено**: пока остаточный риск.
- **S6. Редкая гонка замка `lock.js`.** При трёх и более одновременных открывающих на устаревшем замке проигравший теряет замок и
  получает `E_LOCK_LOST` (допустимые исходы проигравшего: «открыт», `E_PROJECT_BUSY`, `E_LOCK_LOST`); его запуски закроет
  следующий держатель замка как `interrupted` по признаку «незакрытая работа» — журнал остаётся согласованным. Проверка pid
  уведомления в тесте гонки TM-67 сужена: уведомление может потеряться, восстановление — нет.

Решения ORCH внутри прогона (дополнение к P1–P12):

- **Исполнитель.** У всех событий агента заполнено поле `executor`.
- **Кто пишет какие события.** Пять типов и два значения, относящиеся к восстановлению и замку (`LOCK_STALE_REMOVED`,
  `JOURNAL_RECOVERED`, `PROJECT_RECOVERED`, `TASK_INTERRUPTED {cause:"recovery"}`, `RUN_FINISHED {outcome:"interrupted"}`),
  пишет только ядро; `append` их от вызывающего отклоняет.
- **I3.** Пока движок REQ-013 держит замок, команды `say`, `answer`, `pause`, `stop`, `budget`, `resume`, `add-task`, `run-task`
  из другого процесса получают `E_PROJECT_BUSY`; канал приёма таких команд движком решает проект REQ-013.

## Остаточный риск (назван намеренно)

- **Замок: окно `EEXIST` при возврате замка.** При гонке трёх процессов на устаревшем замке процесс Б, чей замок снял
  процесс А, может не вернуть его: свободное имя успел занять процесс В, возврат даёт `EEXIST`. Тогда Б и В **короткое время
  оба считают себя писателями**. Б узнаёт об этом при следующем `append` (`E_LOCK_LOST`, Б сломан и больше не пишет); одну строку,
  которую Б успел записать в промежутке между проверкой замка и записью, частично ловит проверка размера (`E_CONFLICT`) у того,
  кто пишет вторым. Условие: три процесса одновременно на одном проекте с уже устаревшим замком. Закрыть полностью
  нельзя без блокировок ядра ОС — это вне стека `0015`. Риск назван в README ядра (раздел «Sai Team — ядро»).
- **Хеш.** 64-hex строку по шаблону не отличить от секрета, но значение всегда вычислено ядром (P7).
- **Имена файлов результата.** Имя, похожее на ключ, сохраняется как есть (P8).
- **Повторный pid.** Pid умершего писателя может достаться живому процессу: проект считается занятым, пока тот жив — ложное
  «занят», а не две записи (P1).

## Почему

Эти правила нужны, чтобы REQ-010 и REQ-013 строились на одном и том же ядре без догадок, а проверки (TM-01…TM-68) имели
точное поведение для проверки. Каждый отказ от маскирования закрыт другим способом (шаблон, значение считает ядро, папка
0700, вне журнала), каждый остаточный риск назван, а не спрятан (Q3, Q12).

## Граница

Решение касается `tools/src/team/` и тестов `tools/test/team-*` по `0015`. Границы `0002`, `0003`, `0011`, `0013`, `0015`
(Node 22 без зависимостей, права 0600/0700, ничего не уходит с компьютера) не меняются. Решение не разрешает хранить что-либо
вне журнала проекта и папки `work/`.
