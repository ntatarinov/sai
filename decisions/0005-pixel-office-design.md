# 0005 — Pixel Office: решения проекта (REQ-001, REQ-007)

Статус: принято (2026-10-01). Подготовил ORCH по проекту `docs/design/REQ-001-pixel-office.md`
(версия 2), который прошёл две проверки CODE-DESIGN-VALIDATOR — часть REQ-001 и часть
REQ-007 (`handoffs/PO-20260930-01/step-01b-code-design-validator-req001-r2.json` и
`…-req007-r2.json`, обе PASS). Пробы, на которые ссылаются решения, — в приложении A проекта
(команда и вывод). Каждое решение владелец может отменить отдельно, одной фразой.

Решение D9 («закрывать ли открытую строку основной сессии запуском сервера») принято текстом
требования — критерий 6(г) REQ-001, редакция раунда 5, REQ-VALIDATOR PASS — и отдельной записи
не требует.

## Основание

- Поручения владельца — дословно в `decisions/0003-pixel-office-as-pipeline-tooling.md`:
  запустить Pixel Office и дать ссылку, чтобы смотреть, какие задачи выполняют агенты.
- Стек и граница — `decisions/0003` (служебный код в `tools/`) и `decisions/0002` (Node 22, без
  зависимостей во время выполнения).
- Планка R2: Pixel Office показывает только правду — события из реальных хуков Claude Code с
  реальным временем.

## Решения

Формат каждого: вопрос → варианты → выбрано → почему. Ссылки «п.» — на разделы проекта.

**D1. Кто ставит время события.** Варианты: (1) обработчик при запуске; (2) сервер при приёме.
Выбрано (1). Это момент срабатывания; критерий 2 требует хранить присланное время и отклонять
расхождение больше 60 с, что осмысленно, только если время идёт в запросе. Цена: порядок в файле
и порядок времени могут разойтись на доли секунды, поэтому «раньше/позже» везде по номеру
строки (п. 6.4).

**D2. Тип и режим обработчика.** Варианты: (1) `command` синхронный; (2) `command` с `async`;
(3) `http`; (4) `mcp_tool`. Выбрано (1), exec-форма со стражем, `timeout: 4`. Критерии 1(в),
1(ж), 10; `async` теряет последние события в `-p` и не ограничен по времени; `http` не работает
на `SessionStart` и показывает сбой пользователю (пробы P2, P3, P6; п. 1.3).

**D3. Как хук доказывает серверу, что он источник.** Варианты: (1) секрет в заголовке;
(2) HMAC-подпись тела. Выбрано (2). На порту, оставшемся от остановленного сервера, может
слушать чужой процесс; подпись раскрывает ему только один запрос, а не секрет. Цена — десяток
строк в `protocol.js` и тест HK-14.

**D4. Чем связывать описание с запуском.** Варианты: (1) `PostToolUse` Agent (`agentId` ==
`agent_id`); (2) `PreToolUse` и порядок событий; (3) оба. Выбрано (1). Единственная связь без
угадывания (критерий 6(з)); одно событие несёт и описание, и запустившего; порядок событий
меняется между версиями (P2 и P8). `PreToolUse` не подключается (п. 1.1).

**D5. Как узнать, что «после начала задачи был запуск сервера».** Варианты: (1) по времени;
(2) по номеру строки журнала (`journal_lines` в записи запуска); (3) строка-маркер в самом
журнале. Выбрано (2). Время строки — часы хука, они расходятся с часами сервера до 60 с; маркер
в журнале нарушил бы «в журнале только события хуков» и правило (а); номер строки точен (п. 3.4).

**D6. Как хук находит Node 22.** Варианты: (1) путь Homebrew в `settings.json`; (2) `node` из
`PATH`; (3) путь, записанный сервером, затем `PATH`, затем каталоги Homebrew. Выбрано (3).
`PATH` у хука — то, что дали Claude Code (проба P1), и на этом Mac по умолчанию Node 25; путь в
общем файле — свойство одного компьютера; запись сервера покрывает nvm, volta и прочее (п. 1.4,
проба P5).

**D7. Как отличить ответы обработчиков Pixel Office в потоке `stream-json`.** Варианты:
(1) по счёту и порядку; (2) метка `sai-pixel-office` в stderr (+ `--setting-sources project`).
Выбрано (2). В сообщениях нет текста команды, при нескольких обработчиках имя одинаково; stderr
при коде 0 пользователю не виден (п. 1.7, проба P6).

**D8. Что такое «офис воспроизводится из журнала».** Варианты: (1) проигрывание истории с начала
(как в osnova); (2) состояние вычисляется из массива, анимируются только новые маршруты.
Выбрано (2). Проигрывание и скорости — вне области REQ-001; вычисление даёт «место зависит
только от журнала» и «состояние сразу по событию» (п. 4.5).

**D10. Как устроены файлы страницы.** Варианты: (1) один скрипт; (2) чистые ES-модули без DOM и
Node (`schema`, `format`, `model`, `layout`, `office-*`) плюс тонкий слой DOM. Выбрано (2). Одну
и ту же функцию вызывают страница и тест (критерий 2 REQ-001: «та же функция правила, что и
страница»); нет сборки; тесты без браузера (п. 2.1).

**D11. Сколько столов в офисе.** Варианты: (1) 24 (нижняя граница требования); (2) 28.
Выбрано (2). На 24 столах части ролей Sai не хватило бы стола: встроенные типы
(`general-purpose`, `Explore`, `Plan`) тоже получают столы по порядку появления, журнал не
чистится (23 + 3 + 1 = 27); требование «не меньше 24» и его тест на 24 столах сохранены через
параметр `desks` (п. 4.4, проба P16).

**D11, дополнение (2026-10-02, ORCH).** Ролей стало больше: в `.claude/agents/` 27 файлов, шаг
2c итерации 2 добавляет ещё, а столы получают и встроенные типы, и роли сессий из папки, где
стоят хуки по `decisions/0007`; по расчёту самого D11 (роли + основная сессия + 3) нужен уже
31 стол. Поэтому: столы добавляются по числу ролей, у которых в журнале есть задача, — у каждой
роли с задачей свой стол при любом их числе; уже занятые столы при этом не сдвигаются. Прежняя
нижняя граница «не меньше 24» больше не нужна: её покрывает это правило (REQ-007, критерий 1
после правки). Основание: REQ-007 после правки по образцу
владельца от 2026-10-02 (прогон `PO-20261002-01`, вопрос I2 в
`handoffs/PO-20261002-01/step-00a-req-analyst.json`). Владелец может отменить.

**D12. Протокол опроса страницы.** Варианты: (1) `setInterval` без ограничений; (2) один запрос
в полёте, предел 3 с, проверка `from`, опрос при возвращении вкладки. Выбрано (2). Остановленный
сервер принимает соединение и молчит — без предела страница выглядела бы живой (проба P11);
неверный `from` сдвинул бы все номера строк, на которых стоят правила (п. 4.6).

**D13. Подпись персонажа на холсте.** Варианты: (1) полное имя роли; (2) короткая подпись
`roleLabel` с `maxWidth`. Выбрано (2). Настоящие `agent_type` — до 49 символов; подписи полным
именем накладываются друг на друга и выходят за холст (проба P15); полное имя остаётся в
легенде и карточке (п. 4.5).

**D14. Что делать с записью запуска сервера, чей `journal_lines` больше числа строк журнала.**
Варианты: (1) учитывать; (2) не учитывать; (3) чинить файл. Выбрано (2). Запись невозможна при
журнале, который только дописывается; это след удалённого или обрезанного журнала; чинить
файлы пользователя страница не должна (п. 3.4).

## Отклонено

Перенос эталона на .NET 8 (`decisions/0003`, вариант 3); долгоживущий процесс-посредник для
хуков; запись хука прямо в файл журнала в обход сервера (нарушила бы «один путь записи»);
хранение секрета в `settings.json` или переменной окружения.

## Граница

- Решения касаются служебного кода Pixel Office в `tools/` и `.claude/settings.json`; это не
  продукт и не выбор стека продукта (`decisions/0001` остаётся за решением о старте).
- Хуки настраиваются только в `sai/.claude/settings.json`; журнал и секрет — в
  `~/.sai-pixel-office/`, вне репозитория; сервер слушает только `127.0.0.1`.
- Известное ограничение: хуки из `sai/.claude/settings.json` работают в сессиях, начатых в
  `sai/`; работа сессии, начатой в другой папке (например, соседней), в Pixel Office не видна.
- Дополнение (2026-10-02, ORCH): после `decisions/0007` те же обработчики есть и в настройках
  папки, где начинаются сессии владельца на этом компьютере, — временная мера, не часть Sai;
  внутри Sai обработчики по-прежнему только в `.claude/settings.json`, в пользовательских
  настройках Claude Code их нет (REQ-001, критерий 12 после правки в прогоне `PO-20261002-01`).
