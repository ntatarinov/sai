# 0079 — Описания агентов, инструкции и workflow приводятся к практике (ответы на вопросы аудита)

Статус: **принято** (ORCH, 2026-10-25, по просьбе владельца 2026-10-25 «обнови описание и инструкции и workflow агентов, мне нравится то как они работают, а именно их шаги…» и аудиту `docs/design/AGENTS-workflow-audit.md`, раздел 6; владелец может отменить).

## Решение

1. **Push в main (Q1, Q8).** Слова владельца от 2026-10-11 («отправлять коммиты в main после PASS RELEASE-VALIDATOR»; `decisions/0048`) становятся записанным правилом: RELEASE-FINALIZER коммитит файлы прогона по именам и отправляет в `main` после PASS; иные ветки, метки, force-push, `--no-verify` — только по слову владельца. Промежуточный коммит `092cd04` (REQ-057 с красными тестами) отправлен по прямой просьбе владельца 2026-10-25 и не меняет правила: это исключение по его слову, красные тесты названы в сообщении коммита.
2. **Известный нестабильный тест (Q2).** Повтор целой команды не допускается (планка, `docs/quality-bar.md`, §6 п. 4, не меняется). Исключение для тестов открытого дефекта (сейчас ISS-0065, ISS-0083) может дать только владелец письменно с причиной и сроком (§1 планки); вопрос владельцу задан 2026-10-25, до его ответа действует прежнее правило. (Уточнено ORCH 2026-10-25 по F1 ворот `handoffs/AGENTS-20261025-01/step-03-release-validator.json`.)
3. **AP-018 и AP-020 (Q3).** 16 ролей со сноской «предложение, которое владелец не принял» в этом проходе не меняются; вопрос — владельцу.
4. **Лимит доработок (Q4).** До трёх проходов ворот на шаг: первый и два повтора; третий FAIL — остановка и доклад владельцу. Формулировка «не больше трёх доработок» в процессах приводится к этому.
5. **DOC-UPDATER и блоки требований (Q5).** Разрешено исправлять имя, ссылку, число и устаревший факт без смены смысла, с `before_copy` в результате; любая смена смысла критерия — микроправка WF-01 с воротами REQ-VALIDATOR.
6. **Приёмка без BA-сценария (Q6).** Допустима, когда критерий и проект сами описывают шаги приёмки (команды и окна); UAT-RUNNER пишет `docs/uat/REQ-NNN-RUN.md`; подпись BA-ANALYST нужна, когда есть файл сценариев `docs/uat/REQ-NNN.md`.
7. **Переводы (Q7).** Выполняет роль, пишущая код (BACKEND-DEV или FRONTEND-DEV), проверяют читатели (BA-ANALYST + новые запуски) в 2–3 круга; спорные строки после двух кругов отдаются владельцу (AP-114); отдельной роли нет.
8. **Форма доработок (Q9).** Единая форма — следующая буква шага (`05c`); `-rN` в новых прогонах не используется.
9. **Окна приёмки страниц (Q10).** Набор 1470 × 784, 390 × 844, 320 × 568, светлая и тёмная темы, три языка; прежние размеры в AP — история.
10. **Аудит документации по WF-05 (Q11).** В измерение «Документация» добавляется сверка описаний ролей и процессов с последними прогонами раз в 30 дней.
11. **Число ролей (Q12).** Тридцать семь файлов в `.claude/agents/`; числа в README и процессах приводятся к факту.
12. **Общие правила (Q13).** Правила, общие для всех ролей (свежий clone вместо `git checkout`, `orch_check` в каждом шаге, метка `base/<RUN-ID>`, `handoffs-check` и `traces` перед `close`, коммит по именам без незакрытого handoff-а), записываются один раз в `docs/workflows/handoffs.md` (AP-014), роли ссылаются на него.
13. **Интерфейс без образца (Q14).** Вариант WF-02/WF-04: описание интерфейса пишет GUI-DESIGN-ANALYST, DESIGN-QA-VALIDATOR не запускается, приёмка — UAT-RUNNER в настоящем Chrome по матрице окон, тем и языков со снимками.

## Почему

Владельцу нравится порядок шагов, который подтверждён 12 свежими прогонами (19–25 октября); записан он беднее, чем есть. Правки только по доказательствам из аудита.

## Граница

Не меняет код продукта, требования и решения 0001–0078; не принимает AP-018/AP-020 как правила планки без слова владельца; не разрешает платных подключений и публикации в интернет.
