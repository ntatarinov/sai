# 0049 — Pixel Office: объём работы по просьбе владельца 2026-10-13 и ответы на вопросы изучения

Статус: **принято** (ORCH, 2026-10-13, по просьбе владельца `docs/owner-requests/2026-10-13-pixel-office.md`; владелец может отменить). Основа — изучение `handoffs/PIXEL-20261013-01/step-00-architecture-auditor.json`.

## Вопрос

Владелец поручил довести Pixel Office до законченного центра наблюдения на настоящих данных: сначала достоверность, затем основной сценарий, затем вид. Изучение показало: приём событий и защита записи работают; на странице есть показатели без источника (полоска прогресса, «задач n/m · ролей k», «Идёт» без `SessionEnd`, «в работе» без возраста); нет событий об ошибках и ожидании человека; нет перехода от агента к задаче и событию, нет итога сессии. Нужно решить объём, порядок и четыре вопроса изучения.

## Решение

**Порядок.** Три новых требования и существующее REQ-036, по одному прогону WF-01 → WF-02 на требование, в этом порядке:

1. **REQ-042 — достоверность состояний** (P0): «нет свежих данных» вместо вечного «в работе» и «Идёт»; убрать полоску прогресса и «n/m · ролей k»; «Завершена» → «закончила работу, итог не записан»; пометка после перезапуска сервера; ошибка чтения журнала отличается от «нет связи»; одинаковые тела ошибок. Правит принятые критерии REQ-001 (6) и REQ-007 (1, 2, 7, 9, 15) отдельным шагом WF-01.
2. **REQ-036** — как записан (строка «Сейчас» на каждого агента, полные названия ролей).
3. **REQ-043 — обзор: агент → задача → событие → запрос, итог сессии** (P1): идентификаторы в карточке, переходы, открытие события словами, фильтры по сессии/роли/задаче/типу и поиск, итог сессии из имеющихся данных с пометкой «SessionEnd не пришёл».
4. **REQ-044 — новые события хуков** (P1): `Notification` («ждёт человека»), `StopFailure` (ошибка), плюс `prompt_id`, `source`, `reason`. Хранятся только перечисленные безопасные поля, без текста сообщений.
5. REQ-037 (стадия прогона) — после 1–4. P2 (вид, клавиатура, адаптивность) — после P1, по описанию интерфейса GUI-DESIGN-ANALYST. REQ-012 (зеркало Sai Team) и события каждого инструмента — вне этой работы.

**Ответы на вопросы изучения.**

- **Порог «нет свежих данных»:** 60 минут без событий этой задачи и сессии; одна именованная константа; на экране всегда показывается возраст последнего события, «нет свежих данных» — не «завершена» и не «ошибка». Основание: медиана задачи 333 с, возобновления бывают через часы, а призраки в данных живут днями.
- **Итог агента:** хвост ответа `last_assistant_message` не хранится; `decisions/0011`, п. (а), не меняется без слова владельца. Результат берётся из записи оркестратора (`/api/note`), если она есть; если нет — «итог не записан».
- **Новые события:** подписываются `Notification` и `StopFailure`, хранится только тип; `PostToolUseFailure`, `PermissionRequest` и события каждого инструмента не подписываются (частота, синхронный хук на каждый вызов, риск смешать сбой инструмента с провалом задачи). Точные имена событий и полей проверяет CODE-DESIGNER по документации Claude Code и пробой на копии, без настоящих запусков сверх решения `0048`.
- **Следы:** дословный файл просьбы владельца хранит название прежнего проекта владельца как «[прежний проект владельца]» (правило `0021` не допускает исключений для названий).

## Почему

Владелец: «Сначала достоверность, затем функциональность, затем визуальная полировка». Показатели без источника хуже их отсутствия; ошибки и ожидание человека без сбора событий показать нечем.

## Граница

Решение не меняет `0011`, не вводит новый сервер, базу, протокол агентов или хранение текста ответов и входов инструментов. Подписки хуков в папке сессий владельца меняются только после проекта, ворот и подтверждения владельцем `/hooks` (как в `0007`). Мерж — по R1.
