# 0020 — Движок Sai Team: канал команд `inbox/`, поправка к 0017 (I3), граница файлов тестов и правила движка (REQ-013)

Статус: **принято** (ORCH, 2026-10-06, после ворот проекта: step-21 PASS; владелец может отменить); предложил CODE-DESIGNER; строку в `decisions/README.md` добавляет ORCH. Владелец
может отменить. Уточняет `0015` (старт продукта), `0017` (ядро; меняет пункт I3) и `0018` (исполнители; расширяет границу
файлов тестов P9).

## Вопрос

Пока движок REQ-013 держит право записи проекта, пользователь (терминал или страница REQ-011) должен писать в чат и давать
команды `say`, `answer`, `pause`, `resume`, `stop`, `budget`, не получая «проект занят», а журнал по-прежнему пишет один
писатель (критерий 9 REQ-013). По `0017` (I3) другой процесс получал `E_PROJECT_BUSY`, а канал оставлен проекту REQ-013.
Нужно записать механизм канала, его границы, поправку к I3, границу файлов тестов движка и оспоримые правила движка.

## Варианты

1. Локальный сокет — нужен `node:net`: нарушает правило «в движке нет сетевого кода» (критерий 6 REQ-013, проверки REQ-010 и
   REQ-011).
2. Файл-очередь `inbox/` в папке проекта (решение ORCH по критерию 9).
3. Оставить I3 как есть («проект занят») — невыполнимы критерий 9 REQ-013 и случай (а) REQ-011.

## Решение

Вариант 2.

**Канал.**

- Папки `inbox/`, `inbox/taken/`, `inbox/ack/` в папке проекта создаёт только движок, права 0700; файлы сообщений и
  подтверждений — 0600; вне папки проекта канал ничего не создаёт. Код канала — один модуль
  `tools/src/team/engine/channel.js` (пятое место записи по критерию 2 REQ-009; события журнала он не пишет).
- Движок виден из файла-замка: замок движка `{"pid","since","holder":"engine"}`; замок остальных писателей — прежний.
- Отправитель (команда или сервер REQ-011, только через `channel.js`): замка нет или pid мёртв — пишет сам через API ядра,
  как прежде; замок у живого не-движка — «проект занят» (`E_PROJECT_BUSY`), в `inbox/` ничего не создаётся; замок у живого
  движка — проверяет ввод, маскирует текст `maskSecrets`, пишет временный файл в `inbox/` и публикует его жёсткой ссылкой под
  именем `m-<номер>.json` без замены существующего (имя — только номер; pid и время — в теле). Номер — на единицу больше
  наибольшего из номеров в `inbox/` и числа в файле движка `inbox/taken/high` (нет файла — 0); занятый номер (`EEXIST`) —
  следующий, не больше 50 попыток. Файл ≤ 64 КиБ, больше — отказ до записи. Число жёстких ссылок не проверяется.
- Движок читает `inbox/` каждые 100 мс (в том числе на паузе и в ожидании решения) и обрабатывает сообщения по одному:
  берёт переименованием в служебное имя `taken/.taking-…`; номер не больше `high` — ack «номер устарел», отправитель
  переотправляет; иначе **сначала** записывает `high` (временный файл и переименование), затем проверяет файл (обычный, 0600,
  свой владелец, ≤ 64 КиБ, разбирается, свой id проекта, известная команда), пишет события сам через API ядра, кладёт ack и
  удаляет сообщение (исполненное — после события, отклонённое — после ack). Наибольший взятый номер хранит только движок в
  `taken/high`. После начала остановки (`stop`) новые сообщения не исполняются — ack «проект останавливается». Событие несёт
  имя файла и `nonce` сообщения; двух событий с одним именем или одним `nonce` ядро не принимает.
- Отправитель ждёт ack не больше 10 с и проверяет жизнь только того pid движка, что прочитал из замка при отправке; ack,
  не прошедший проверку (не обычный файл, чужой, права шире 0600, больше предела, не разбирается), не принимает. Код 0 — только после ack «принято»; ack с отказом — его текст; ack нет —
  отправитель отзывает своё сообщение, если движок его не взял (тогда событий нет и не будет), а если взял — сообщает
  «подтверждение не пришло вовремя, проверьте журнал». Сам отправитель журнал в этом случае не пишет и сообщение повторно не
  шлёт: событие записывается не больше одного раза.
- Движок, завершающий работу штатно, до снятия замка исполняет или отклоняет все лежащие сообщения. Сообщения, найденные при уборке
  `inbox/` на старте движка (остатки аварии и опубликованные до готовности), не исполняются; сообщение опознаётся по `nonce`
  из тела, а не по имени файла (дубль с тем же номером — другое сообщение). Порядок: прочитать; уже исполненные (`nonce` в
  журнале) — только удалить; поднять `high`; события ENGINE с числом и `nonce` невыполненных — по 100 в событии, все одним
  пакетом; ждущим отправителям — ack «не выполнено»; удалить. Падение посреди уборки не даёт двойного счёта; число файлов не
  ограничено, проект всегда открывается. Предел отправителя «не больше 100 сообщений в `inbox/`» — мягкая защита, не гарантия.

**Поправка к `0017`, I3.** Было: «Пока движок REQ-013 держит замок, команды `say`, `answer`, `pause`, `stop`, `budget`,
`resume`, `add-task`, `run-task` из другого процесса получают `E_PROJECT_BUSY`; канал приёма таких команд движком решает
проект REQ-013». Стало: пока замок держит живой движок (`holder: "engine"`), команды `say`, `answer`, `pause`, `resume`,
`stop`, `budget` передаются движку каналом `inbox/` и `E_PROJECT_BUSY` не получают; `add-task`, `run-task` и второй `start`
получают отказ «Проект сейчас ведёт запущенный процесс Sai Team (pid N): эта команда доступна после его остановки» без
записи; если замок держит не движок — всё, как в `0017` (`E_PROJECT_BUSY`). Остальное в `0017` не меняется.

**Правила движка.**

- Движок — долгоживущий процесс `start`/`resume`; в «на паузе» и «ждёт решения пользователя» он не выходит и принимает
  сообщения; Ctrl-C — пауза и выход.
- Параллельные запуски резервируют потолок: сумма потолков открытых запусков не больше остатка проекта.
- Критическая задача проходит проверку Проверяющего, затем ждёт решения пользователя; одобрение не совершает действий вовне.
- Предложения правки ядра, без которых часть критериев REQ-013 невыполнима (выбор ORCH; проект REQ-013, I-1, I-2, I-8):
  задачи, отклонённые пользователем, и зависящие от них закрыты и не мешают завершению проекта (C1); другую роль выбирает
  Руководитель проекта отдельным запуском (C2); поле `holder` в замке движка (C4); имя файла сообщения в событии и запрет
  повтора (C6). ORCH выбрал C1, C2, C4, C6 и публикацию сообщения `linkSync` (2026-10-06, прогон PROD-20261006-02); правки
  ядра записаны в `docs/design/REQ-009-team-core.md`, раздел 20 «Правки r13»; код ядра меняет BACKEND-DEV первым раундом
  REQ-013 с перепроверкой тестов ядра.

## Почему

Файл-очередь не требует сетевых модулей и держится на тех же средствах защиты, что ядро (0600/0700, без ссылок, «создать,
если нет»); один писатель журнала сохраняется; отказ без повтора исключает двойные события ценой честного «не подтверждено»
в редком случае. Поправка к I3 записана, чтобы код не разошёлся с `0017` молча (Q12).

## Остаточные риски

- Движок взял сообщение и умер (или ack опоздал, например при долгой остановке процессов `stop`) — отправитель получает «не
  подтверждено», событие записано ноль или один раз; повтор — новое действие пользователя.
- `stop` через канал подтверждается в пределах 10 с, только если группы процессов уходят за 8 с; иначе отправитель получает
  «не подтверждено» при уже записанном событии (без дубля) — риск принят ORCH.
- Опрос папки раз в 100 мс — задержка приёма до 100 мс.
- Ложный `holder` или файл в `inbox/` может создать только тот же пользователь (папки 0700) — граница доверия та же, что у
  замка `0017`; три процесса на устаревшем замке — риск `0017`.

## Граница

Решение касается `tools/src/team/` (движок, канал, замок) и файлов тестов из таблицы. Не меняет `0002`, `0003`, `0011`,
`0013`, `0015`, `0018` (кроме расширения границы тестов) и `0017` (кроме I3). Не разрешает настоящий запуск `claude` без
согласия владельца и потолка расходов и не меняет статус требований.
