# 0047 — Git вышел с кодом 0, а запись запросов ему не удалась: ошибка «вывод git не разобран», а не «код 0» (ISS-0053)

Статус: **принято** (ORCH, 2026-10-13T02:32:38Z, после PASS CODE-DESIGN-VALIDATOR step-03b-r1; предложено CODE-DESIGNER, прогон `ISS-0053-20261013-01`, шаг 3; владелец может отменить). Проект — `docs/design/ISS-0053-readblobs-epipe.md`; требование — критерий «Вывод, коды и сбои» REQ-038 (Q10) и критерий 2 REQ-030.

## Вопрос

`readBlobs` (`tools/src/handoffs/git-history.js`) — единственный вызов git с вводом: запросы идут на стандартный ввод `cat-file --batch`. Если git вышел раньше, чем ему записали запросы, `execFileSync` бросает ошибку записи, у которой статус выхода git равен 0. Функция `gitFailure` видит число 0 и пишет «git не смог выполнить команду (код 0)». Текст ложен: git не вернул ошибочный код. В тесте GH-6 подставной git отвечает и выходит, не читая ввод; на Linux-раннере GitHub тест иногда красный (запуск 38331440082, 1475 из 1476). Как называть этот сбой в коде?

## Варианты

| # | Вариант | Что даёт | Что стоит |
|---|---|---|---|
| А | Любая ошибка вызова со статусом выхода 0 (после веток ENOENT, ETIMEDOUT, ENOBUFS и статуса 128) — `E_TRACE_GIT` «вывод git не разобран»; статус ≠ 0 — как раньше | Не зависит от того, какой именно код ошибки записи дала платформа (на macOS проверено `EPIPE`; на Linux код не измерен: нет Linux); текст GH-6 тот же; одна ветка в `gitFailure` | Текст «вывод git не разобран» описывает здесь «ответ git нельзя принять как полный», а не буквально ошибку разбора |
| Б | Только `err.code === "EPIPE"` при статусе 0 (формулировка диагноза) | Узкое условие, повторяет диагноз | Если на Linux запись, оборванная выходом git, даёт другой код (ошибка соединения), ветка не сработает и «(код 0)» останется; проверить это нечем |
| В | Отдельный код ошибки («git не принял запросы») | Точный текст | Новый код в каталоге `E_TRACE_*`; GH-6 ждёт `E_TRACE_GIT` и «вывод git не разобран», тест пришлось бы переписать; пользователю этот сбой недостижим с настоящим git (он читает ввод) |
| Г | При ошибке записи со статусом 0 разобрать то, что git успел вывести (`err.stdout`), и вернуть результат, если ответ полон | Исход подставного git не зависит от гонки совсем | Принимает ответ git, который не прочитал запросы; лишняя ветка разбора; зависит от того, что `stdout` попадает в ошибку (проверено на macOS) |
| Д | Код не менять, а только заставить подставные git читать ввод | Тест перестаёт зависеть от гонки | В коде остаётся ложный текст «(код 0)»; регрессионного теста на него нет |

## Решение

Вариант **А**, плюс два изменения тестов (проект, п. 4.3): подставные git GH-6 читают ввод до ответа; новый детерминированный тест GH-7 проверяет ветку с вводом больше буфера.

## Почему

1. Сбой, при котором git вышел успешно, а запись ему не удалась, не может называться «код 0»: этот текст всегда ложен (Q10: понятное сообщение; сообщение называет то, что случилось).
2. Условие по одному статусу не зависит от кода платформы. Единственный измеренный случай — `EPIPE` на macOS; код ошибки на Linux проект не измерял и не должен на него полагаться (AP-012).
3. Ветка не задевает ни статус 128 (`E_TRACE_NOT_GIT`), ни прочие числа («код N»): контроли GH-7b и прежний GH-4.
4. `E_TRACE_GIT` и текст остаются теми, что ждёт GH-6; тексты, которые сверяет `HC-8k`, не меняются; число вызовов git (шесть) и место `child_process` (`0038`, `0040`) не меняются.

## Что теряется

- Статус «убит сигналом» (статус `null`) по-прежнему даёт старый исход (непойманная ошибка либо «git не запустился (…)»); это другой сбой, он вынесен отдельным дефектом (проект, п. 3, М10, и вопрос О1).
- Проверка на Linux — только запуском `check.yml` на GitHub после отправки; в этой работе ничего не отправляется (R1).

## Граница

Решение касается одной ветки `gitFailure` в `tools/src/handoffs/git-history.js` (ошибка вызова со статусом выхода 0) и тестов `tools/test/handoffs-git.test.js` (GH-6, GH-7, GH-7b). Оно не касается:

- других вызовов git и мест `child_process`: число вызовов (шесть), их аргументы, `stdio`, `input`, таймаут и единственное место `child_process` в модуле остаются по `0038` и `0040`; остальные пять функций вводом не пользуются;
- `tools/src/traces/git-files.js` и его `gitFailure` (там ввода нет, файл менять нельзя по `0038`);
- git, убитого сигналом (статус `null`): исход прежний, это отдельный дефект LOW (вопрос О1 проекта);
- `HK-12b` и `HK-31` в `tools/test/pixel-office-hook.test.js` (запись в ввод `hook.sh` без обработчика `'error'`): отдельный дефект LOW по диагнозу;
- текста критерия «Вывод, коды и сбои» REQ-038: он не расширяется, текст этой ветки закреплён тестами, а не критерием;
- общей константы для текста «вывод git не разобран» и других рефакторингов `git-history.js`;
- запуска `check.yml` на GitHub и любой отправки: нужны подтверждение владельца (R1) и отдельный шаг проверки после отправки.

## Условие пересмотра

Если запуск `check.yml` на GitHub после исправления снова покажет красный GH-6 или GH-7 с сообщением про код 0 или с иным текстом, ветка записи на Linux устроена иначе, чем предполагает проект, и вопрос открывается заново.
