# 0025 — Сервер бизнес-интерфейса Sai Team (REQ-011): движок в процессе сервера, защита записи, исполнитель новых проектов, край правила срока

Статус: **принято** (ORCH, 2026-10-10, по 0015; владелец может отменить). Предложил CODE-DESIGNER. Открытые вопросы проекта решены так: кнопок «пауза / продолжить / остановить» в REQ-011 нет — добавляются отдельным требованием REQ-035 «Управление проектом на странице» (до тех пор остановленный проект продолжается командой из терминала, это сказано в README); признак «нужно ваше решение» в списке следует статусу проекта, как в критерии 2; после перезапуска сервера проекты сами не возобновляются (текст на странице: «Проект приостановлен, продолжите его командой resume»; возобновление кнопкой — REQ-035).

## W1. Как сервер запускает движок

Вопрос: движок REQ-013 для нового проекта — отдельный процесс или в процессе сервера?

Варианты:

1. Отдельный процесс (`child_process` из `tools/src/web/`).
2. В процессе сервера: `createEngine(id, {mode:"start"})` из `tools/src/team/engine/engine.js`, `run()` без ожидания конца.

Выбор: **вариант 2**.

Причины:

- Критерий 4 REQ-014 и тест `traces-runtime` (TR-4c) разрешают `child_process` только в `team/executors/claude-cli.js` и `traces/git-files.js`. Вариант 1 потребовал бы правки требования REQ-014 (WF-01).
- «Один писатель» REQ-009 сохраняется: право записи — замок ядра с держателем `engine` (C4 решения 0020), pid замка — pid сервера. Сообщение чата со страницы идёт через `deliver` → канал → движок того же процесса. Это проверено запуском на текущем коде: `deliver` вернул `via:"engine"` и событие `CHAT`, а после остановки движка — `via:"self"`.
- Критерий 9 REQ-013 и критерий 15 REQ-011 не меняются: сервер не знает пути к `inbox/`, пишет только через `deliver`.

Последствия:

- Остановка сервера (Ctrl-C, SIGTERM) — это сигнал для всех его движков: `requestStop("signal")`, проекты встают на паузу так же, как после Ctrl-C у `npm run team -- start` (п. 12.4 проекта REQ-013). На всё даётся не больше 15 с, потом процесс выходит, а при следующем открытии проект восстанавливается (п. 14 REQ-013).
- Если в коде движка вылетит необработанное исключение, оно уронит и сервер. Это принятый остаточный риск: движок уже ловит свои сбои сам (п. 17 REQ-013), а сервер не ставит глобальный обработчик, который скрывал бы ошибки (Q6).
- Отдельный процесс движка из терминала (`start`/`resume`) по-прежнему работает с сервером через канал (случай (а) критериев 5 и 15).

## W2. Защита записи

Вопрос: какой механизм не даёт чужому сайту в браузере пользователя создать проект или написать в чат?

Выбор: три проверки в каждом запросе записи, до чтения тела:

1. `Host` — ровно `127.0.0.1:<порт>` или `localhost:<порт>`. Проверяется в каждом запросе, в том числе в запросах чтения.
2. `Origin` — есть и равен `http://127.0.0.1:<порт>` или `http://localhost:<порт>`.
3. Ключ страницы — заголовок `X-Sai-Page`, равный ключу этого запуска сервера. Сравнение — `crypto.timingSafeEqual` при равной длине. Тип тела — `application/json`: значение `Content-Type` до первого `;`, без пробелов по краям и без учёта регистра, равно `application/json`; параметры после `;` допустимы (дополнено в r2 проекта REQ-011).

Ключ правильного вида, но не этого запуска (страница открыта до перезапуска сервера), получает отдельный отказ с признаком «обновите страницу» (`reload: true`), чтобы человек не застрял на странице, где каждая отправка отклоняется. Ответы API всегда идут с `Content-Type: application/json; charset=utf-8` и `X-Content-Type-Options: nosniff`, чтобы чужая страница не подключила их как скрипт.

Ключ — 32 случайных байта (64 hex). Он создаётся при запуске сервера, хранится только в памяти, нигде не пишется и не печатается. Страница получает его в `<meta name="sai-page">` при запросе `GET /`.

Причины:

- Чужая страница не может поставить свой заголовок без предварительного запроса CORS, а сервер не отдаёт заголовков `Access-Control-*`.
- Прочитать `GET /` с ключом чужая страница тоже не может: ответ без CORS ей недоступен, а подмену DNS отсекает проверка `Host`.
- Это не секрет в смысле Q7: ключ живёт только в памяти, на один запуск, и не хранится ни в git, ни в файлах. Граница доверия — пользователь этого компьютера, как у Pixel Office.

Принятый остаточный риск: любой процесс на этом компьютере (в том числе программа другого пользователя ОС) может открыть `GET /`, прочесть ключ страницы и читать и менять все проекты Sai Team через API. Защита записи закрывает только чужие сайты в браузере, а не программы на самом компьютере. Риск принят так же, как у Pixel Office: сервер слушает только 127.0.0.1, а вход и пользователи — отдельное требование REQ-018.

Отвергнуто: только `Origin`. Некоторые запросы приходят без него, а одна проверка — слабая защита.

## W3. Исполнитель новых проектов

Вопрос: кто выбирает исполнителя проекта, созданного со страницы?

Выбор: **команда запуска сервера**, а не страница.

- Без параметров — `claude-cli`.
- С `--executor scripted --scenario <файл>` — тестовый исполнитель. Файл сценария читается и проверяется один раз при запуске, и каждый новый проект получает копию этих байтов.

В запросе страницы есть только цель и потолок, поля исполнителя там нет.

Причины:

- Решение 0015, D-B: тестовый исполнитель — только для тестов и приёмки.
- Человек на странице не должен выбирать технический параметр.
- Приёмке (UAT, критерий 11) и тестам нужен сервер на scripted.

Проект на `claude-cli` без `SAI_TEAM_REAL_RUNS=1` сервер отклоняет до создания папки. Защита внутри `run()` исполнителя (0018) от этого не убирается.

## W4. Край правила срока

Правило требования действует как есть: X = медиана × ⌈незавершённые / предел⌉, округлённая вверх до минуты. Дополнения:

1. Медиана чётного числа длительностей — среднее двух средних.
2. Задача «готово», у которой в журнале нет `TASK_STARTED`, в медиану не входит. Если измеримых длительностей меньше двух, показывается «срок пока не оценить».
3. Если произведение не больше 0, показывается «срок пока не оценить». Равно 0 — незавершённых задач нет, а проект ещё не в конечном статусе (например, идёт сверка цели): «примерно через 0 мин» было бы неправдой, оценивать нечего. Меньше 0 — медиана отрицательная, так бывает только при часах, переведённых назад между событиями: «примерно через −N мин» тоже было бы неправдой (дополнено 2026-10-10, проект REQ-011 r3, по замечанию REVIEWER).
4. Предел параллельности — `state.parallel`, а если его нет — `PARALLEL_DEFAULT` (2), как у расписания движка.

## W5. Ссылка на карточку исполнителя

Роль в адресах API — номер в каталоге ролей (1…10, порядок `ROLES`), а не код роли. Код роли не уходит из ядра (`view.js`, REQ-009, критерий 10).

## W6. Файлы страницы

Сервер читает файлы `tools/src/web/public/` один раз при запуске и держит их в памяти. Берутся только обычные файлы, не ссылки, с именем по шаблону и расширением `.html`, `.js`, `.css` или `.svg`. Запрос пути никогда не доходит до файловой системы: выйти за папку нельзя, а в `tools/src/web/` нет `openSync` (критерий 9).

## W7. Тексты страницы после перезапуска и до окна решений

- Проект на паузе (после Ctrl-C сервера, команды `pause` или восстановления после сбоя) показывает на своей странице текст «Проект приостановлен, продолжите его командой resume» — поле `pause_text` ответа сервера (проект REQ-011, п. 5.5). Кнопка возобновления — REQ-035.
- Пока нет окна решений REQ-017, при открытых вопросах под их числом идёт пояснение «Ответить на вопрос можно будет в окне решений — оно появится позже. Сообщение в чате вопрос не закрывает.» — поле `waits.note_text`. Оно убирается вместе с полем в работе по REQ-017.

## W8. Какие файлы страница показывает в «Результате»

Дополнено 2026-10-10 (ORCH, по замечаниям F1 и I2 REVIEWER прогона PROD-20261010-01; проект REQ-011 r3, п. 7.1 (6)).

Вопрос: ядро хранит в состоянии и файлы без задачи — вход, который записал тестовый исполнитель для запуска плана и проверки цели (`r-…-plan-input.md`, `r-…-goal-input.md`). Показывать ли их владельцу в «Результате»?

Выбор: в «Результате» — только файлы с задачей (`state.files[].task !== null`), у каждого — задача и роль. Файлы без задачи сервер не отдаёт, и в счёт «и ещё N» они не входят.

Причины:

- Критерий 4 (6) REQ-011 говорит о файлах результата «с задачей и ролью»; у файла без задачи нет ни задачи, ни роли.
- Для владельца вход исполнителя — не результат работы команды.

Отвергнуто: показывать все файлы, а у файлов без задачи ставить `null` в полях задачи и роли — на странице появились бы «результаты», которые ни к чему не ведут.

Не решено здесь: входные файлы задач (`t-…-input.md`) остаются в «Результате» — различать вход и итог задачи должно ядро (REQ-015 или новое требование).

## W9. Сбой диска при записи в чат без движка (принятый остаточный риск, ORCH 2026-10-10) — **отменён: исправлено решением [0026](0026-team-core-reclaim-own-broken-lock.md) (ISS-0010)**

Если при отправке сообщения в чат без работающего движка случается сбой диска, ядро оставляет замок записи за процессом сервера до конца процесса (правило ядра «сломанный писатель держит замок», `0017`). Все следующие сообщения этого проекта получают 409 «повторите через несколько секунд», и повтор не поможет до перезапуска Sai Team. Это принято: сбой диска — исключительный случай, перезапуск сервера его снимает, правило ядра не меняется. Остаток записан в `ISS-0010`; точный текст для такого случая — задача REQ-012 или отдельного дефекта. Тест WEB-10a проверяет то, что требует критерий 10 (понятный текст, журнал не изменён, сервер отвечает).
