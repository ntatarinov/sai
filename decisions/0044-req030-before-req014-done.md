# 0044 — REQ-030 строится при незавершённой зависимости REQ-014

Статус: **принято** (ORCH, 2026-10-12, решение о ходе работы по `CLAUDE.md`, «Роли», закрытый список ORCH; владелец может отменить). Образец — `0027`, `0029`, `0034`.

## Вопрос

REQ-030 (проверка на GitHub при каждой отправке) записан с `depends_on: [REQ-014]`: клон репозитория с GitHub и `npm ci && npm run check` на чистой машине — работа REQ-014. REQ-014 остаётся `in_progress`: его открытые пункты — зависимость REQ-009 (через него REQ-002) и повтор шага 9, а не код проверки следов, который входит в `npm run check` с 2026-10-09. Нужно ли ждать `done` у REQ-014, чтобы строить файл проверки на GitHub.

## Варианты

1. Ждать `done` у REQ-014 — очередь в `PLAN.md` (итерация 8, пункт 4) этого не предполагает, а сам файл проверки от REQ-014 не зависит.
2. Начать работу по REQ-030 при `in_progress` у REQ-014 — исключение по порядку работ, не по критериям и не по планке.

## Решение

Вариант 2. REQ-030 может начинаться и проходить ворота до `done` у REQ-014; исключение касается только порядка работ. REQ-030 не станет `done`, если владелец отменит это исключение, пока REQ-014 не `done`. Проверки критериев REQ-030, которые требуют внешних действий на GitHub (запуск на `main`, красная проверка на ветке), выполняются в отдельном шаге после отправки и, для ветки с падающим тестом, — только с отдельным согласием владельца.

## Почему

Файл проверки и хук не используют код REQ-014 сверх уже работающего `npm run check`; ожидание `done` у REQ-014 только задержало бы очередь.

## Граница

Решение не касается критериев и планки, не заменяет подтверждения владельца для отправки не в `main` и не отменяет `0023` (D1: защиты ветки нет).

## Основание

`PLAN.md`, итерация 8, пункт 4 (REQ-030, WF-02); `docs/requirements.yaml`, блок REQ-030 (`depends_on`); `decisions/0023`, `decisions/0034`. Отдельных слов владельца об этом решении нет — оно принято ORCH и может быть отменено владельцем.
