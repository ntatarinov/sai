# 0026 — Ядро Sai Team: процесс снова открывает проект после своего сломанного писателя (поправка к 0017 P12; ISS-0010)

Статус: **принято** (ORCH, 2026-10-10, по общему поручению владельца «сам всё закрой»; предложил CODE-DESIGNER, WF-03, шаг 3, дефект ISS-0010). Владелец может отменить. Код по проекту `docs/design/ISS-0010-web-chat-write-recovery.md` строится после ворот CODE-DESIGN-VALIDATOR.

## Вопрос

По P12 сломанный писатель (сбой записи журнала) при `close()` оставляет замок со своим pid, и следующий открывающий
восстанавливает проект, когда процесса уже нет. Для короткой команды это верно: она выходит сразу. Сервер интерфейса
(REQ-011) и движок в его процессе (`0025` W1) живут долго: после одного `ENOSPC` или `EIO` при записи сообщения чата замок
остаётся за живым pid сервера, и каждое следующее сообщение проекта получает 409 «повторите через несколько секунд» — до
перезапуска. Повтор не помогает, текст неправдив (Q10). Как вернуть процессу право записи без перезапуска и не ослабить
«один писатель» и восстановление по журналу?

## Варианты

1. **Только сервер (`tools/src/web/`): честный текст «перезапустите Sai Team».** Текст становится правдивым, но запись
   по-прежнему невозможна до перезапуска — это то же принятие риска, а не исправление; Q10 («ошибка одного запроса не ломает
   работу других») остаётся нарушенным.
2. **Только сервер: снять замок самому** (`releaseLock` из `lock.js` после `E_DISK`). Сервер не знает, оставил ли сломанный
   писатель открытые запуски (движок в процессе сервера), обходит правило ядра молча (Q12), а удаление файла из
   `tools/src/web/` — запись мимо API ядра (критерий 9 REQ-011, решение `0024`). Отвергнут.
3. **Только сервер: дочерний процесс для записи.** `child_process` в сервере запрещён (`0025` W1, критерий 4 REQ-014), а
   замок живого pid сервера дочерний процесс всё равно получил бы как «занят». Отвергнут.
4. **Ядро: сломанный писатель всегда снимает замок при `close()`** (отмена P12). После r8 восстановление идёт по состоянию
   журнала (P11, P13), поэтому следующий открывающий всё равно восстановит проект. Но меняется поведение для **других**
   процессов (TM-66 (1), TM-47 и TM-13 в дочернем процессе, EX-53, EN-68 — замок мёртвого pid и событие о снятом замке), и
   другой процесс мог бы взять проект, пока процесс сломанного писателя ещё жив и, возможно, что-то доделывает. Шире, чем
   нужно для дефекта.
5. **Ядро: замок своего закрытого сломанного писателя — устаревший для этого же процесса.** Процесс помнит в памяти папки
   проектов, чей замок оставил его сломанный писатель, закрытый, пока ещё держал этот замок (R1). Для этого процесса такой замок — как замок мёртвого
   pid: `openWriter` снимает его штатным путём `acquireLock` (переименование с проверкой содержимого), пишет
   `LOCK_STALE_REMOVED {pid}` со своим pid и восстанавливает проект по журналу (P11, P13) — ровно как после смерти процесса.
   Для всех других процессов замок по-прежнему живой: они получают `E_PROJECT_BUSY`, пока процесс жив (P12 для них не
   меняется).

## Решение

**Вариант 5.** Правила:

- **R1. Признак «свой брошенный замок».** Модуль `tools/src/team/lock.js` держит в памяти процесса множество папок проектов.
  Папку туда добавляет только `close()` сломанного писателя (в том числе после `markBroken()`) **и только если этот писатель
  ещё держит замок** (r3): его захват — последний успешный захват этого процесса на эту папку (билет захвата в памяти), и
  файл-замок байт-в-байт тот, что записал этот захват (pid этого процесса и время захвата — сверка содержимого, как при
  снятии устаревшего замка). Писатель, который замок потерял (`E_LOCK_LOST`) или после захвата которого этот процесс взял
  замок снова, ничего не отмечает: его поздний `close()` не делает «устаревшим» замок здорового писателя этого процесса.
  Убирает папку из множества любой успешный `acquireLock` этого процесса на эту папку. На диске признак не хранится: новых
  файлов и мест записи нет (пять мест записи критерия 2 REQ-009 не меняются).
- **R2. Кто считается живым держателем.** Держатель замка жив, если его pid жив **и** не (pid равен pid этого процесса **и**
  папка в множестве R1). Правило одно для `lockHolder` (его читают `openWriter` шаг 2, `sendToEngine`, `engineHolder`,
  `open()` движка), для `acquireLock` (шаг снятия устаревшего замка) — проверка и снятие в одном синхронном вызове
  `openWriter` — и (r3) для проверки «движок ещё жив» в ожидании подтверждения `sendToEngine`: сломанный и закрытый движок
  процесса сервера не держит отправителя до конца срока ожидания.
- **R3. Пока писатель не закрыт, замок его.** Сломанный, но не закрытый писатель в множество не попадает: тот же процесс
  получает `E_PROJECT_BUSY`, как сейчас. Второй здоровый писатель в одном процессе по-прежнему невозможен (TM-11).
- **R4. Снятие — штатное.** Снятие своего брошенного замка идёт тем же путём, что снятие замка мёртвого процесса:
  `renameSync` в `writer.lock.stale-<pid>`, проверка содержимого, `linkSync` нового замка; `stalePid` = свой pid; событие
  `LOCK_STALE_REMOVED {pid}` и восстановление по журналу (открытые запуски → `RUN_FINISHED interrupted`, задачи
  `running` → `TASK_INTERRUPTED`, проект на паузу `PROJECT_RECOVERED`; оборванная строка — `JOURNAL_RECOVERED`). Новых типов
  событий нет (P3 не меняется).
- **R5. Сбой повторяется.** Если при снятии или восстановлении запись снова не удалась, новый писатель сломан, `close()` из
  `openWriter` снова кладёт папку в множество R1 — следующая попытка снова штатная. Журнал после каждой неудачи — как был
  (откат ядра) или с отброшенной оборванной строкой при следующем удачном открытии.
- **R6. Условие для вызывающих (уже выполняется).** `close()` означает «писатель больше не используется и ничего от его имени не
  выполняется»: движок перед `close()` прерывает и дожидается всех своих действий (`abortAll`, `inFlight` пуст — п. 17 проекта
  REQ-013), `runTask` и одиночный запуск вызывают `markBroken()` после конца процесса исполнителя, `deliver` закрывает
  писателя в `finally` синхронного участка. Новый вызывающий ядра обязан соблюдать то же.
- **R7. Правило REQ-013 «сломанный писатель — выход из процесса или `close()` без повторного открытия»** остаётся для самого
  движка (он не открывает проект повторно сам), но повторное открытие тем же процессом другим вызывающим (сервер, `deliver`)
  больше не даёт `E_PROJECT_BUSY` от собственного pid: оно идёт с восстановлением, как в новом процессе.

## Почему

- Исправляет причину ISS-0010, а не прячет её: после освобождения места сообщение отправляется без перезапуска, а при
  повторе сбоя человек видит правдивый текст (Q10, R2 — журнал пишет только правду: событие о снятом замке и восстановление).
- Достоверно только внутри процесса: процесс точно знает, что его писатель закрыт и ничего не делает. Другой процесс этого
  знать не может, поэтому для него P12 не меняется — «один писатель» REQ-009 и TM-11, TM-12, TM-66 (1), TM-47, EX-53, EN-68
  остаются как есть.
- Ни нового файла, ни нового типа события, ни новой зависимости (0002, 0015, 0017 P3, пять мест записи REQ-009).

## Остаточный риск (назван намеренно)

Это риски решения, а не исключения из планки (`docs/quality-bar.md`, §1 п. 3: исключение даёт только владелец): ни один
пункт планки ими не нарушен.

- **Другой процесс видит «занят».** Пока процесс со своим брошенным замком жив и сам не открыл проект заново, команда из
  терминала (`npm run team -- say` и др.) получает `E_PROJECT_BUSY` с pid этого процесса. Снимается первой же записью в проект
  из этого процесса (сообщение со страницы) или его выходом. Два сервера на одной папке данных — тот же случай.
  Почему это не нарушение Q10: для человека поведение верное и текст правдив. Отказ называет pid живого процесса, который
  действительно держит проект и может в нём доделывать свою работу; другой процесс этого проверить не может, поэтому снимать
  замок живого процесса ему нельзя («один писатель», P12). Ошибка одного запроса не ломает работу других: сервер отвечает,
  запись со страницы проходит (и снимает замок), после неё команда из терминала тоже проходит; выход сервера снимает риск
  полностью. Сервер сам свой замок сразу не снимает: это была бы запись в журнал без запроса человека.
- **Замок не прочитан при `close()`.** Если `close()` сломанного писателя не смог прочитать файл-замок (сбой чтения), папка
  не отмечается — проект занят для этого процесса до его выхода, как до этого решения. Отметить без сверки нельзя: это
  ослабило бы R1 (находка F1).
- **Сломанный писатель без `close()`.** Если вызывающий не закрыл сломанного писателя, проект занят для этого процесса до его
  выхода (как сейчас). Все нынешние вызывающие закрывают (R6).
