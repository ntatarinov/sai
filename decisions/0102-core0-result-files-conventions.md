# 0102 — CORE-0 (byte-exact result files): conventions before the design gate

Status: **accepted** (ORCH, 2026-10-28; the owner may cancel). Closes the open questions of the code design of defect ISS-0093 (run `ISS-0093-20261028-01`) from the diagnosis in `handoffs/ISS-0093-20261028-01/step-01-issue-fixer.json`. Narrows decision 0095 in the points below; nothing else in 0095 changes.

## Question

The diagnosis of ISS-0093 compared the facts with the CORE-0 row of `docs/program/public-v1/ARCHITECTURE.md` §10 (the draft the design starts from). Where it disagrees with a recorded decision or with the measured code, which one wins?

## Options

- A (chosen): the recorded decisions and the measured facts win; CORE-0 is adjusted in three points and kept in all others.
- B (rejected): build CORE-0 exactly as drafted; it would reverse decisions 0018 P6 and 0035 silently and leave three guard tests out of the table.

## Decision

1. **Stored copy.** Accepted result files are stored byte-exact (sha256 of the original), by one new content check in `tools/src/pixel-office/mask.js` (`findSecrets`, linear time, the rules of CORE-0). `maskSecrets` stays unchanged and keeps serving journal text and the owner's Pixel Office. Both call sites that touch result-file content use the new check: `#publish` (`store.js`, on write) and `depsOf` (`runner.js`, on every read for the reviewer and dependent tasks); fixing only one leaves the corruption (diagnosis, I-items on `depsOf`).
2. **A real secret is refused, not stored masked.** CORE-0 stays as drafted: the file is refused with reason `secret` and a message the user can read (Q10). The design must name the failure path for a task that only quotes an example key (retry cost, wording) and test that a refused file leaves the state unchanged.
3. **"Accepted sources stay in `work/`" is NOT adopted.** Decision 0018 P6 and decision 0035 stay in force: sources of accepted files are removed from `work/` as today. With an exact stored copy the removal loses nothing. The README line about the unmasked copy is changed only as the design says.
4. **Guard tests: eight, not five.** The "was → became" table covers TM-57, TM-58, TM-63, RF-03, SF-13 and also TM-43, EX-41 and EX-51 (diagnosis: removing masking from result files turns exactly these eight red). HK-21 (with the M7-file, M7-jwt and M10 rows), HK-24, MK-01…MK-05, NM-06 and TM-44 stay green and unchanged.
5. **No shared acceptance helper for `engine/single-run.js`**: it has no `work/` source and no deletion; the design shares only what both paths really share.
6. **Order with ISS-0058 and ISS-0045.** ISS-0093 first. The change of M7 and M10 for journal text (ISS-0058 together with ISS-0045) is a later, separate run; the write sets overlap (`mask.js`, `tools/README.md`, `pixel-office-helpers.js`), so they never run in parallel.
7. **Criterion first.** No requirement says that ordinary content stays byte-exact (diagnosis: REQ-009 criterion 12 is about events; the right anchors are REQ-010 criterion 16(б) and REQ-013 criteria 14 and 15). WF-03 step 2: REQ-ANALYST writes the criterion as the first requirement of PUBLIC-V1 (P-code R0.1) and REQ-VALIDATOR passes it before CODE-DESIGNER starts.
8. **Q7 question for SECURITY-REVIEWER:** whether file content keeps a long-unprefixed-string rule like M10 (protects unprefixed long secrets but corrupts lockfile integrity hashes). The design proposes; SECURITY-REVIEWER rules; a residual risk is named in the design and in the release report, never hidden.

## Why

A recorded decision wins over the plan until a new record replaces it (program plan §0.1); items 3 and 4 follow from the measured code; item 2 keeps the plan's safer default for Q7.

## Boundary

Writes no code. Does not change journal masking, the 37-event catalogue, or the quality bar. `docs/program/public-v1/ARCHITECTURE.md` is not edited: the change is a dated row in the "Plan amendments" table of `PROGRESS.md`.

## Addition (ORCH, 2026-10-28, after the criterion step REQ-102; closes issues I2 of `handoffs/ISS-0093-20261028-01/step-02-req-analyst.json`)

9. **A file refused for a secret leaves `work/` too.** Item 3 keeps the removal of accepted sources (0018 P6, 0035). This extends P6 and 0035 to refused files and weakens nothing.
10. **No rule like M10 for file content (the plan's seed).** AC0.3 R1 of the program plan says that a 40-character identifier is stored as-is, so a long-unprefixed-string rule is not part of the scan. The residual risk — a long secret with no known prefix inside a generated file is not detected — is named in the design and in the release report. SECURITY-REVIEWER rules on it (item 8); a wish to add such a rule changes AC0.3 and needs the owner's word.
11. **Extra refusal forms.** `password=<literal>` and `Authorization: Bearer <literal>` stay refused (they were hidden by the old rules M2 and M9), beyond the CORE-0 list; the criterion tests them.
12. **BOM.** The import paths lose a byte-order mark because `TextDecoder` is used without `ignoreBOM` (found by REQ-ANALYST); criterion 1 of REQ-102 covers it and the design must fix it.
13. **P-code R0.1 = REQ-102** (mapped in `PROGRESS.md`). Stale descriptions of REQ-009, REQ-010, REQ-015 and REQ-091 that mention masked result files are fixed by DOC-UPDATER in the release step of this run (criterion sentences were amended, descriptions were out of the scope of the analyst).

## Addition 2 (ORCH, 2026-10-28, after the gate FAIL `handoffs/ISS-0093-20261028-01/step-02b-req-validator.json`, finding F1)

14. **The refused set may not be narrower than what the old rules protected, except M7 and M10.** The gate reproduced on a clone of the tag that the old `maskSecrets` hid in result files, besides the CORE-0 list: values after `API_KEY=`, `secret=`, `token=`, `passwd=`, `authorization=` (rule M9), any `Authorization:` header value such as Basic (rule M2), and a literal after `Bearer` outside a header (rule M8); my own run of `maskSecrets` on samples confirmed it. Therefore the refusal set of REQ-102 covers every form of the rules M1-M6, M8 and M9 that hides a secret in the old code, for a **literal** value; each form has a refuse sample and a keep sample (a name followed by an expression, not a literal, such as `{ token: data.token, user: x }`, `token = process.env.TOKEN`, stays stored). Only M7 (three dotted parts, the cause of ISS-0093) and M10 (long unprefixed strings) are not carried over, as items 10 and 8 say; the residual risk of M10 stays named. The claim "protection is not weaker" in the requirement is rewritten to say exactly this. Placeholders (items of the plan's list and obvious ones such as `changeme`, `example`) are named in a closed list; an ordinary output such as `postgres:postgres@host` is decided by the analyst with a refuse or keep sample and the reason.

## Addition 5 (ORCH, 2026-10-28, after the rework `step-02e-req-analyst.json`; answers its issues under item 19)

21. **An expression is not a secret literal.** Quality bar Q7 asks for secrets *by reference*. A value that is a call (`getSecret()`), a command substitution (`$(…)`), a block opener or a plain identifier names a place where the secret is read from; it is the form Q7 wants. Items 14 and 18 refuse a **literal** value and keep «a name followed by an expression» (their keep samples). REQ-102 therefore keeps these four classes stored, as written, beside the two classes the plan seeds demand (a path such as `data.token`, a template such as `${token}`). This is not an exception from the bar. The residual risk — a real secret typed in exactly such a form is stored — is named in the requirement, the README and the release report.
22. **Closed questions for the owner, not decided by ORCH** (asked in the M0 report; the default applies until he answers): (а) keep the four expression classes (recommended) or tighten to path plus template only — refusing them adds 1 refused file of 1072 in a dependency tree and 35 of 1164 in a large TypeScript client tree; (б) whether the closed placeholder list may get test words such as `tok` or `pw` (without them, test fixtures like `token: 'tok'` are refused: 150 of 1164 files in that client tree, 118 of them by one form) — default: no, the list stays closed; (в) the plan-seed exceptions of item 18 are the owner's own plan (AC0.3); the three-part token without the `eyJ` start, the 40-character identifier and a path or template value are stored by that plan, and the residual risk is told to him in plain words.
