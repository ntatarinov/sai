# 0039 — Команда `npm run handoff` (REQ-039): жёсткая ссылка для `new`, подмена двух значений в тексте для `close`

Статус: **принято** (ORCH, 2026-10-11T19:25:26Z, после PASS CODE-DESIGN-VALIDATOR step-01b-r2; предложено CODE-DESIGNER, прогон `REQ039-20261011-01`, шаг 01; владелец может отменить). Опирается на `0002` (Node 22, без зависимостей), `0004` (запись: временный файл, переименование, жёсткие ссылки), `0031` (метка базы), `0037`, `0038`. Проект — `docs/design/REQ-039-handoff-command.md`.

## Вопрос

Как `npm run handoff -- new` фиксирует файл так, чтобы занятое имя давало отказ, а не замену, и как `npm run handoff -- close` меняет два значения уже существующего файла, не трогая остальное и не оставляя мусора?

## Варианты

Для `new` (требование оставляет выбор CODE-DESIGNER):

1. **Жёсткая ссылка** временного файла на имя handoff-а: `linkSync` на занятое имя даёт `EEXIST`; затем временный файл удаляется.
2. **Замок** с исключительным созданием на время записи (пара «замок и запись»).
3. **Исключительное создание самого файла** (`wx`) и запись в него.
4. **Переименование** временного файла — требованием запрещено (заменяет существующий файл; проверено запуском: `renameSync` заменил содержимое, второй `linkSync` дал `EEXIST`).

Для `close`:

5. Перезапись всего документа `JSON.stringify` — переформатирует чужой файл.
6. Подмена двух значений **в тексте** файла (остальные байты прежние) и запись общим писателем `writeAllOrNothing` (`0004`).

## Решение

- `new` — вариант 1. `close` — вариант 6.
- После создания ссылки `new` ещё раз ищет тот же `handoff_id` в других файлах и при находке удаляет свою ссылку (оба одновременно запущенных `new` с одним `handoff_id` и разными ролями не могут остаться оба).
- Остаточные риски приняты и названы: потерянное обновление при одновременной правке файла `close` другим писателем (окно — миллисекунды, ORCH и получатель одновременно один файл не пишут по `handoffs.md`); остаток `.<имя>.sai-tmp` после убийства процесса (виден в `git status`, следующий `new` того же имени откажет, а не заменит); файловая система без жёстких ссылок — отказ кодом 2, запасного пути нет.

## Почему

- Вариант 1: имя появляется уже с полным содержимым (читатель — `handoffs-check`, параллельный агент — не видит половину файла); один системный вызов решает «занято или нет»; временный файл рядом с целью, как в `0004`; жёсткие ссылки на этом проекте уже используются (`0004`) и работают (проверено запуском).
- Вариант 2 отклонён: замок — второй файл, который нужно убирать; прерванный процесс оставляет замок и блокирует имя; файл при записи виден полупустым.
- Вариант 3 отклонён: файл виден полупустым, при сбое записи остаётся обрезанный handoff с занятым именем.
- Вариант 5 отклонён: изменил бы поля, которые закрытие не трогает (требование: «меняются только значения status и completed_at»); живые handoff-ы набраны по-разному (форма массивов, отступы).
- Вариант 6: байты вне двух токенов прежние; сбой — откат общего писателя; самопроверка (глубокое сравнение разобранного нового текста со старым документом, где изменены только два поля) в той же операции не даёт ошибке сканера стать испорченным файлом.

## Дополнения r1 (замечания ворот F1–F10, ответы ORCH)

- Сообщения об ошибке записи `close` — целиком по-русски: английские тексты `writeAllOrNothing` не печатаются; команда берёт из них только код ОС и строит русский текст, состояние файла определяет сама перечитыванием (ограничение «рамка русская, хвост английский» снято). `writeAllOrNothing` не меняется.
- `close` перед записью перечитывает файл и сравнивает байты с прочитанными ранее (окно «потерянного обновления» сужено; полностью не закрыто — риск остаётся принятым).
- `base_tag` пишется при любой найденной метке `base/<RUN-ID>`; отказ без метки только у WF-02.
- `write_set` — список; пример в `handoffs.md` не правится.
- Если после создания ссылки не удалился временный файл: файл создан, stdout пуст, выход 2, одна строка stderr с путём и `handoff_id` (ответ ORCH).
- Файлы учёта прогона допустимы сверх таблицы состава, как в REQ-038 (проект, п. 2.1).
- При сбое повторного поиска `handoff_id` после создания ссылки файл не остаётся.
