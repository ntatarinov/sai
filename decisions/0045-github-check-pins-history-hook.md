# 0045 — Проверка на GitHub: версии действий по SHA, полная история, без кэша, правила хука

Статус: **принято** (ORCH, 2026-10-13, после PASS CODE-DESIGN-VALIDATOR `step-01b-r4`; предложено CODE-DESIGNER, прогон `REQ030-20261012-01`; владелец может отменить). Проект — `docs/design/REQ-030-github-check.md`, п. 10.

## Вопрос

Как закрепить версии официальных действий в `.github/workflows/check.yml`; сколько истории получать при получении кода; нужен ли кэш npm; когда хук `pre-push` пропускает проверку.

## Варианты

1. Закрепление версий: по тегу (`@v7`) или по полному SHA коммита.
2. История: один коммит или полная (`fetch-depth: 0`).
3. Кэш: встроенный кэш npm или без кэша.
4. Хук: проверяет каждую отправку или пропускает отправку, в которой только удаления веток и меток.

## Решение

- Действия закрепляются по полному SHA коммита, в конце строки — комментарий с версией (тег — подвижная ссылка, SHA — нет; теги и коммиты проверены чтением GitHub, факты Ф12–Ф14 проекта).
- Получение кода — с полной историей (`fetch-depth: 0`): без неё `npm run check` на GitHub красный на шаге `handoffs-check` (в неполной истории нет коммита базы, `E_HC_BASE_COMMIT`, факт Ф9; шаг не убирается, история целая — это не обход Q6).
- Кэш не используется (безопасность кэша не доказана).
- Хук пропускает только отправки, где есть одни удаления: иначе ветку с красной проверкой нельзя удалить (факт Ф11).

## Почему

Защита от подмены действий и воспроизводимость важнее удобства; проверка не ослабляется ни в одном из выборов.

## Граница

Решение не включает защиту ветки `main` (`0023`, D1; включение — отдельным решением по слову владельца), не разрешает обход хука (`--no-verify` в самом хуке не используется), не меняет `npm run check` и не касается видимости репозитория и настроек Actions.
