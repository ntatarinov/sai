# 0004 — Запись файлов в служебном коде конвейера: временный файл, переименование, откат жёсткими ссылками (ISS-0002)

Статус: принято (2026-10-01). Подготовил ORCH по проекту `docs/design/REQ-002-idea-verdict.md`
(версия 4, раунд 3), который прошёл CODE-DESIGN-VALIDATOR
(`handoffs/ISS-0002-20260930-01/step-03-code-design-validator-r2.json`, PASS). Владелец может
отменить это решение одной фразой — тогда исправление ISS-0002 останавливается до нового
решения.

## Основание

- ISS-0002 (`docs/issues/ISS-0002-apply-verdict-partial-write.md`, HIGH): `apply-verdict` пишет
  STATE.md, `proposed-actions.json` и `apply-report.json` на месте, одну за другой; `prepare-run`
  тоже. Диагноз ISSUE-FIXER (`handoffs/ISS-0002-20260930-01/step-01-issue-fixer.json`, запуск на
  копиях проекта): M1 — сбой на втором или третьем файле оставляет уже записанные; M2 — запись на
  месте, прерванная сбоем (EFBIG при ограничении размера, ENOSPC на диске HFS+), оставляет саму
  цель обрезанной, в том числе STATE.md, который восстановить не из чего: папка `sai/` не под
  git.
- Критерий 11 REQ-002 (`docs/requirements.yaml`) — проверенное требование для этой работы.

## Вопрос

Как писать выходные файлы `apply-verdict` и `prepare-run`, чтобы сбой записи не оставлял
наполовину применённое состояние и не обрезал STATE.md?

## Варианты

По дизайну, §11 (варианты 1–3 — почти дословно; вариант 4 расписан здесь подробнее, чем в дизайне):

1. **Запись на месте с проверками до неё** — отклонено: M2 остаётся, а ENOSPC, EFBIG и EIO
   проверкой заранее не поймать.
2. **Временный файл и переименование без отката, STATE.md последней**, в сообщении — что уже
   заменено — отклонено: при сбое фиксации список файлов меняется, обещание дизайна §5 «ни одной
   записи» нарушено.
3. **То же, но откат из копий старых байтов** — отклонено: откат требует ещё одной записи, которая
   сама может сломаться, и возвращает другой файл (новое время изменения, новый inode).
4. **Временный файл рядом с целью, переименование по порядку, STATE.md последней (точка фиксации),
   откат из жёстких ссылок на старые файлы** — выбрано: откат без записи, возвращается тот же
   файл.

Отдельно рассмотрено и отклонено (дизайн §5.1): перехват исключения, который только убрал бы
трассировку, — симптомное исправление (Q6), M1 и M2 остались бы.

## Решение

Вариант 4. Подробности — дизайн §5.1–§5.7:

- новые байты — только во временный файл `.<имя>.sai-tmp` рядом с целью, создаваемый
  эксклюзивно и сбрасываемый на диск; старая версия цели — жёсткая ссылка `.<имя>.sai-old`;
  у `prepare-run` вся папка прогона собирается во временной папке и фиксируется одним
  переименованием;
- переименования по порядку, STATE.md — последней; сбой переименования k — откат целей 1..k-1 из
  жёстких ссылок;
- любой обработанный сбой — код 1, только строки `E_WRITE`, без трассировки, строгий список
  `<root>` тот же; остаток прерванного запуска команда сама не удаляет и отказывает по имени
  файла;
- в `E_WRITE` превращаются только ошибки ОС; ошибка программы по-прежнему идёт с трассировкой.

## Что меняется для владельца и пользователя (дизайн §5.4)

- **Новый отказ:** папка только для чтения, в которой цель нужно изменить. Раньше запись на месте
  там проходила; теперь отказ, потому что иначе вернулась бы M2.
- **Новый отказ:** цель — символьная ссылка или папка на пути к цели — ссылка. Раньше запись шла
  по ссылке, в том числе за пределы `<root>`.
- Цель только для чтения, которую нужно изменить, как и раньше отказ, но без частичной записи.
- Заменённый файл — новый файл: inode, владелец, ACL и расширенные атрибуты не сохраняются; права
  переносятся. Для проекта одного пользователя это ничего не ломает.
- Файловая система без жёстких ссылок (FAT): замена существующей цели — отказ без изменений.
  Проект лежит на APFS.
- Только POSIX (macOS, Linux), как и прежде.

## Принятое чтение по ссылке на папку прогона

`validate` и фаза чтения `apply-verdict` переходят по ссылке `runs/<RUN-ID>` (или `runs`) на папку
вне `<root>`: `resolveRunDir` (`tools/src/cli.js`) сравнивает пути, а существование проверяет
`statSync`, который идёт по ссылкам. Они только читают; запись за пределы `<root>` закрыта (дизайн
§5.4, W13, W13b), поэтому `cli.js` и `validate.js` не меняются. Принято ORCH 2026-10-01 как
сознательное решение (AP-014: место того же класса оставлено намеренно и записано там, где его
будет искать следующий читатель). Чтобы запретить такое чтение, нужны отдельное решение, правка
`resolveRunDir` и тест на `E_USAGE`, код 2.

## Граница

- Решение касается только служебного кода конвейера в `tools/` (`apply.js`, `prepare.js`,
  `util.js`) и по `decisions/0002` не выбирает стек продукта.
- Запись файла снимка (`cli.js:145`) и остальные места без защиты — ISS-0003; она использует этот
  же код `E_WRITE`.
- `tools/src/snapshot.js` не меняется: он защищён на время прогона REQ-006, и дизайн этого не
  требует.
