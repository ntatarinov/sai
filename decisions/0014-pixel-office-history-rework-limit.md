# 0014 — Прогон «Просмотр истории» (REQ-008): лимит доработок превышен по слову владельца «не возвращайся пока не решишь все»; решения ORCH внутри прогона

Статус: принято (2026-10-06, ORCH). Владелец может отменить.

## Вопрос

`WF-01` и `WF-02` разрешают две доработки после FAIL ворот; после второй с FAIL работа останавливается и вопрос уходит
владельцу. В прогоне `PO-20261005-02` ворота возвращали работу больше двух раз. Нужна ли была остановка, и какие решения
ORCH принял внутри прогона сам?

## Варианты

1. Остановиться после второго FAIL подряд и вернуться к владельцу.
2. Продолжить до PASS, записав превышение открыто, пока действует прямое слово владельца не возвращаться до полного
   решения.

## Решение

Вариант 2. Что и сколько раз возвращали (файлы — в `handoffs/PO-20261005-02/`):

- проверка требования (REQ-VALIDATOR): FAIL три раза (первый запуск, r1, r3), PASS с r2 и r4;
- ворота проекта (CODE-DESIGN-VALIDATOR): `step-01b-…` и `step-01b-…-r1` — FAIL, PASS с r2 и r3;
- безопасность (SECURITY-REVIEWER), часть (а): FAIL — настоящая дыра в маскировании секретов в кавычках и в форме
  `ИМЯ=значение` (F1, F2), после правки проекта и кода — PASS (`step-03-security-reviewer-r1.json`); часть (б) — PASS;
- ревью (REVIEWER), часть (б): FAIL (`step-04-reviewer-b.json`), после правки `step-04f-code-fixer.json`; отдельного нового
  запуска REVIEWER по части (б) в файлах нет — правка проверена DESIGN-QA-VALIDATOR и RELEASE-VALIDATOR;
- проверка тестов (TEST-DESIGN-VALIDATOR), часть (а): FAIL, затем PASS с r1; часть (б): PASS.

Каждая доработка закрывала настоящее замечание по существу (дыру в маскировании, противоречие внутри проекта, недостающий
тест), а не обходила проверку. Итог: TEST-RUNNER — `cd tools && npm run check`, 483 из 483 дважды и на чистой копии
(`step-06b-test-runner.json`); DESIGN-QA-VALIDATOR — PASS по снимкам; RELEASE-VALIDATOR — PASS по критериям 1–19
(`step-09-release-validator.json`); все пять проверок — их собственными запусками.

Решения ORCH внутри прогона (кратко):

1. `/api/events` отвечает `204` (как в REQ-001), `/api/note` — `200`.
2. У команды записи «как понял» параметр `--session` необязателен, ORCH его не передаёт; сервер привязывает запись к
   последнему сообщению владельца в журнале (`request_time_auto`). Риск чужой сессии принят и назван в `tools/README.md`.
3. JWT маскируется по букве критерия 7 — со следствием, названным в `decisions/0013`.
4. Остаточный риск маскирования назван прямо (`decisions/0013`, `tools/README.md`), а не закрыт обещанием.
5. Окно «Просмотр истории» открывается из журнала и из карточек панели «Задачи», не из карточки агента.
6. Если карточка агента открыта, при открытии окна она закрывается.
7. Мета окна без `Stop` показывает только слово статуса («в работе · начат …»), без повтора.

## Почему

Владелец поручил довести работу до конца без возврата к нему. Остановка на второй доработке остановила бы всю работу над
просмотром истории, которой он добивался. Превышение записано открыто, чтобы не выдавать его за соблюдённое правило
(Q14); качество не пострадало: ни одна проверка не была ослаблена, каждый PASS — независимый запуск проверяющего.

## Граница

Решение касается только прогона `PO-20261005-02`. Лимит доработок `WF-01` и `WF-02` не меняется. Это не разрешение на
будущее: следующий прогон снова останавливается на второй доработке, пока владелец не скажет иное. Решения ORCH 1–7
относятся к REQ-008 и могут быть отменены владельцем по одному.

## Основание

Слова владельца (2026-10-05): «не возвращайся пока не решишь все» — в той же форме поручение записано в
`decisions/0010` («Продолжи свою работу и не вохвращайся ко мне пока что не решишь все.»); оно действует на этот прогон. Источники превышения — файлы
`handoffs/PO-20261005-02/step-00b-…`, `step-01b-…`, `step-03-…`, `step-04-…`, `step-05b-…` и
`step-09-release-validator.json`. Подробности по правилам маскирования — `decisions/0013-pixel-office-mask-rules.md`.
