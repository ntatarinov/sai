# Планка качества

**Нижняя граница — [образец].** Его сделал ментор владельца, и это эталон. Ниже него
опускаться нельзя. Выше — можно, маленькими шагами, по правилу храповика (§4): что
однажды поднято, обратно не опускается.

Этот файл обязателен для **каждой** роли перед **любым** действием. Он сильнее
формулировки конкретной задачи.

---

## 1. Главное правило

1. **Ни один агент не имеет права понизить планку.** Ни ради скорости, ни «для MVP»,
   ни «временно», ни потому, что так написано в задаче.
2. Если задачу нельзя выполнить, не понизив планку, агент **останавливается** и пишет в
   handoff (`result.issues`): какой пункт §2, почему он не выполним, что агент
   предлагает. Работу дальше не продолжает.
3. Исключение может дать **только владелец**, письменно, отдельной записью в
   `decisions/NNNN-*.md` с причиной и сроком. Устное «ну можно» — не исключение.
4. Понижением планки считаются, в том числе, такие фразы: «тесты допишем потом»,
   «для MVP можно без проверки», «временно захардкодим ключ», «пропустим ревью, там
   мелочь», «отметим done, проверим завтра».

## 2. Пункты планки — минимум для каждого изменения

| # | Пункт | Как проверить | Откуда в [образец] |
|---|---|---|---|
| Q1 | **Сначала требование, потом код.** Каждое изменение привязано к REQ в `docs/requirements.yaml`; у REQ есть `acceptance_criteria`, каждый из которых проверяется командой или наличием конкретного содержимого в файле | У изменения есть REQ-id; у каждого критерия указано, чем он проверяется | `docs/requirements.yaml`, WF-01 |
| Q2 | **Кто делает — тот не проверяет.** У каждой производящей роли есть проверяющая. Проверяющая сама перепроверяет: запускает команду, читает файл. Пересказ отчёта производителя — не проверка | В handoff проверяющей есть её собственный запуск и вывод | core-directives: «Every producing step has a validating step» |
| Q3 | **Без домыслов.** «Работает» пишется только после реального запуска, с приложенным выводом. Запрещено: «должно работать», «скорее всего», «вероятно». Нет инструмента для проверки — статус остаётся `in_progress` | В отчёте есть вывод команды, а не обещание | core-directives: «No Speculation» |
| Q4 | **Одна команда проверки.** Форматирование + сборка с предупреждениями как ошибками + все тесты, остановка на первой ошибке. Определяется решением о стеке (`decisions/0001`). Пока её нет, продуктовый код не может быть `done` | Команда описана в README и проходит на чистой копии | `mix [образец].check` |
| Q5 | **Тест на каждый критерий.** Каждый `acceptance_criteria` закрыт запускаемым тестом. Тест на отказ проверяет ещё и то, что состояние **не изменилось**. Тесты не зависят друг от друга | Сопоставление критерий → тест в дизайне и в отчёте TEST-DESIGNER | TEST-DESIGNER / TEST-DESIGN-VALIDATOR |
| Q6 | **Проверку не обманывают.** Если проверка красная — чинят причину. Нельзя удалять, пропускать или помечать `skip` тест, маскировать код выхода, отключать линтер, переименовывать то, что ищет проверка | В диффе нет `skip`, отключённых правил, `|| true` у команд проверки | core-directives: «Never Satisfy a Gate by Editing What It Measures» |
| Q7 | **Секреты только по ссылке.** Ни одного ключа, токена или пароля в коде, в конфиге в git, в клиентском бандле, в документации. Пример, как нельзя: токен Telegram в клиентском коде Advisor | Поиск по репозиторию и собранному бандлу не находит секретов | security-invariants: INV-4 |
| Q8 | **Данные магазинов не смешиваются.** Каждый доступ к данным ограничен магазином-владельцем. Идентификатор магазина не берётся из запроса клиента. Чужой объект отвечает «не найден», а не «запрещено» | Тест: магазин A не видит и не меняет данные магазина B; ответ неотличим от несуществующего объекта | INV-1, INV-5, INV-6 |
| Q9 | **Никакой склейки SQL из строк.** Только параметры | Поиск по коду | INV-7 |
| Q10 | **Реалистичные сбои не роняют систему.** Недоступен сервис примерки, WhatsApp, сеть, пришёл кривой ввод — пользователь видит понятное сообщение, процесс не падает | Тест на каждый внешний вызов с имитацией сбоя | INV-8 |
| Q11 | **Внешние адреса проверяются.** Любой URL, который задаёт магазин или покупатель и по которому ходит сервер, проверяется | Тест с внутренним адресом (localhost, 169.254…) отклоняется | INV-9 |
| Q12 | **Решения записываются.** Выбор между вариантами фиксируется в `decisions/NNNN-*.md`: вопрос, варианты, выбор, причина. Код не расходится с записанным решением молча | У нетривиального выбора есть запись | `docs/migration/decisions/` |
| Q13 | **Ошибки процесса записываются.** Если агенты споткнулись о то, на чём можно споткнуться снова, это попадает в `docs/anti-patterns.md` | Запись есть в той же работе, где ошибка найдена | `docs/anti-patterns.md` |
| Q14 | **Учёт не откладывается.** Статус требования, `STATE.md` и handoff обновляются в той же работе, а не «потом» | ORCH сверяет конкретные поля до записи DONE | core-directives: «Bookkeeping Is Not Optional» |

## 3. Где планка уже поднята выше [образец]

Это тоже пол: убрать нельзя.

| # | Пункт | Почему |
|---|---|---|
| R1 | **Мерж подтверждает человек.** Безлюдный мерж [образец] (его решение 0004) здесь не действует | Решение 0004 держится на том, что в [образец] нет реальных пользователей. Здесь будут реальные магазины и их покупатели |
| R2 | **Pixel Office показывает только правду.** Каждое событие работы агентов попадает в журнал из реального источника — хуков Claude Code — с реальным временем. Выдуманные, дописанные задним числом или «сжатые в один день» события запрещены. Режим симуляции существует только отдельно и помечен | В [образец] журнал был написан вручную в коде, с искусственным временем. Здесь это исправляется (REQ-001) |
| R3 | **Фото покупателей — персональные данные.** Фото не хранится дольше, чем нужно для примерки, без явного согласия покупателя; не попадает в логи и отчёты | Продукт работает с фотографиями людей |

## 4. Как поднимать планку (храповик)

1. Любой агент может предложить улучшение: раздел «Предложение поднять планку» в
   handoff — что именно, зачем, как это проверять.
2. ORCH оформляет предложение как запись в `decisions/`.
3. Владелец принимает или отклоняет.
4. Принятое вносится в §3 и с этого момента становится полом.
5. Шаги маленькие: **одно улучшение за раз**, и у него есть проверка. Улучшение без
   способа проверки не принимается.

---

## 5. Масштаб

Планка — про **дисциплину, а не про объём**. В [образец] 91 тысяча строк; MVP здесь
может быть в десятки раз меньше, но каждый его кусок сделан по §2 и §3.

Если процесс начинает весить больше самой работы — это повод предложить упрощение
**через решение владельца**, при котором каждый пункт §2 остаётся проверяемым. Молча
пропустить шаг нельзя.
